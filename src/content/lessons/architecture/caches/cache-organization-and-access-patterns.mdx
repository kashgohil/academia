A **cache** is a small, fast memory near the core. It keeps copies of data that the program used recently. A load that finds its data in the L1 cache is a **hit**, and it takes about 1 ns. A load that must go to DRAM is a **miss**, and it takes about 80 ns. Two things decide which one you get: how the cache places addresses, and the order in which your code touches memory.

The simulator below models a real cache. It is written in Rust and compiled to WebAssembly, and it simulates every access that you see.

## Anatomy of an address

A cache stores data in **lines**, which are blocks of $B$ bytes, usually 64. It puts its lines into groups called **sets**. Each set has $W$ places for lines, called **ways**. $W$ is the **associativity** of the cache. A cache of $S$ bytes has $S/(B \cdot W)$ sets.

The cache splits every address into three fields:

| tag | set index | offset |
|---|---|---|
| all other bits | $\log_2(\text{sets})$ bits | $\log_2 B$ bits |

The offset selects a byte in the line. The set index selects the one set where the line can go. The cache stores the tag with the line, so that it can tell which line is in a way. A **direct-mapped** cache has $W = 1$. A **fully associative** cache has one set that holds every line.

The cache has space for a full column of 64 lines. The mapping lets the column use only 16 of them.

## The three C's

Mark Hill sorts every miss by its cause. The first simulator labels each access in this way. It compares the real cache with a fully associative LRU cache of the same size.

- **Compulsory**: the first access to a line. No cache can prevent it, but prefetching can hide it. Larger lines decrease these misses, because more bytes arrive with each miss.
- **Capacity**: the working set (the data that the loop uses again) does not fit. A fully associative cache of the same size also misses. To fix it, make the cache larger or the working set smaller, for example with tiling or more compact data.
- **Conflict**: the cache removed the line only because too many lines map to its set. A fully associative cache of the same size would hit. To fix it, add ways, or change the addresses with padding or a different layout.

In the first demo, select **Two arrays, 8 KiB apart** with 4 KiB and 1 way. Every access is a conflict miss, because `a[i]` and `b[i]` have the same index bits. With 2 ways, or with a 16 KiB cache, the hit rate is 93.8%. Strides and array sizes that are powers of two often cause conflict misses in real code. The usual fix is to add one cache line of padding between the arrays.

## Replacement policy

When a set is full, the cache must remove a line to make space. The **replacement policy** selects that line. **LRU** (least recently used) removes the line that the program used longest ago. **FIFO** (first in, first out) removes the oldest line. **Random** removes any line. Hardware uses cheap versions of LRU, such as tree pseudo-LRU and RRIP.

## The cost model

The **average memory access time** (AMAT) combines the hit time, the miss rate and the **miss penalty**, which is the extra time of a miss:

$$
\text{AMAT} = t_\text{hit} + \text{miss rate} \times \text{miss penalty}
$$

Use a 1 ns hit and an 80 ns penalty. A hit rate of 93.8% gives 6 ns per access, and a hit rate of 0% gives 81 ns. So the column walk is 13.5 times slower, for the same bytes in a different order. Real hierarchies make this gap smaller, and hardware prefetchers detect constant strides. But the principle is the same at every level.

A typical core today has an L1 of 32 to 48 KiB with 8 to 12 ways. It also has an L2 of 1 to 2 MiB and a shared L3. All levels use 64-byte lines.

Associativity has a cost. On each access, the cache compares the tags in all ways of the set at the same time. More ways use more energy and add time to each hit. For this reason, L1 caches stay small, with a moderate number of ways.

## What to do in your code

- **Walk memory in layout order.** In C, C++, Rust, Zig and Go, the last index changes fastest (row-major). Put it in the innermost loop.
- **Tile (block) your loops**, so that the working set fits in the cache. This is the key optimization for matrix multiply, convolutions and stencils.
- **Use a struct of arrays** when a hot loop reads only some fields. Then the cache lines do not carry cold data (Performance → Data-oriented design).
- **Avoid strides that are powers of two** between hot arrays, or add padding.
- **Measure.** `perf stat -e cache-misses,L1-dcache-load-misses` shows which case you have.
