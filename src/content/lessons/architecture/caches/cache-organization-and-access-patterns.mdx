A load that hits in L1 cache takes about 1 ns. A load that goes to DRAM takes about 80 ns. Whether your loop runs at memory speed or cache speed depends on two things: **how the cache maps addresses** and **the order in which you touch memory**. ## Anatomy of an address

A cache of size $S$ with $B$-byte lines and associativity $W$ (ways per set) has $S/(B \cdot W)$ sets. Every address splits into three fields:

| tag | set index | offset |
|---|---|---|
| everything else | $\log_2(\text{sets})$ bits | $\log_2 B$ bits |

The default setup (4 KiB, 64 B lines, direct-mapped) has 64 sets: 6 offset bits, 6 index bits, and the remaining 20 bits of a 32-bit address as tag. A line can live **only** in the set its index bits select. Within that set it can occupy any of the $W$ ways. Direct-mapped means $W = 1$; fully associative means a single set containing every line.

Back to the column walk. A row of the matrix is 256 B = 4 lines, so row $i$ starts at line $4i$, which maps to set $4i \bmod 64$. **Only 16 of the 64 sets are ever used**, and 64 rows compete for them. The cache has room for the whole column. It just can't *place* it.

## The three C's

Mark Hill's classification splits every miss by its cause. The simulator labels each access this way, using a shadow fully-associative LRU cache of the same size:

- **Compulsory**: first touch of a line. No cache avoids it, apart from prefetching. Larger lines reduce it, because more bytes arrive per miss.
- **Capacity**: the working set doesn't fit; even a fully associative cache would miss. Fix it by making the cache bigger or the working set smaller (tiling, compact data).
- **Conflict**: the line was evicted only because too many lines mapped to its set. Fix it with associativity, or by changing the address pattern (padding, a different layout).

Try **Two arrays, 8 KiB apart** at 4 KiB direct-mapped: every access is a conflict miss, because `a[i]` and `b[i]` have the same index bits. Switching to 2-way, or growing the cache to 16 KiB, takes it to 93.8%. Power-of-two strides and sizes are a classic cause of conflict misses in real code; the usual fix is to pad arrays by one cache line.

## Replacement policy and a counter-intuitive case

When a set is full, something must be evicted. **LRU** (least recently used) is the textbook answer, and hardware approximates it (tree pseudo-LRU, RRIP).

## The cost model

$$
\text{AMAT} = t_\text{hit} + \text{miss rate} \times \text{miss penalty}
$$

With a 1 ns hit and an 80 ns penalty, a 93.8% hit rate gives about 6 ns per access, and 0% gives 81 ns. That is a **13× slowdown** for touching the same bytes in a different order. Real hierarchies (L1 ≈ 32–48 KiB, 8–12-way; L2 ≈ 1–2 MiB; L3 shared; all with 64-byte lines) soften this, and hardware prefetchers detect constant strides. The principle still holds at every level.

Associativity isn't free: every way in the set must be compared in parallel on each access, which costs energy and hit latency. That is why L1 caches stay small and modestly associative.

## What to do in your code

- **Traverse memory in layout order.** In C, C++, Rust, Zig and Go, the last index varies fastest (row-major), so put it in the innermost loop.
- **Tile (block) loops** so the working set fits in cache. This is the key optimization in matrix multiplication, convolutions and stencils.
- **Prefer struct-of-arrays** when a hot loop reads only some fields, so lines aren't wasted on cold data (Performance → Data-oriented design).
- **Avoid power-of-two strides** between hot arrays, or pad them.
- **Measure.** `perf stat -e cache-misses,L1-dcache-load-misses` tells you which case you are in.
