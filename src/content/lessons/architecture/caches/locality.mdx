Caches work because programs are predictable in two ways:

- **Temporal locality**: a program often uses the same data again soon.
- **Spatial locality**: a program often uses data near the data that it uses now. Caches move whole lines, usually 64 bytes, so the neighbors arrive at no extra cost.

One number for each access measures both: the **reuse distance**. It is the number of *different* lines that the program touches between two accesses to the same line. The first access to a line has an infinite distance.

## Reuse distance, step by step

Keep the lines in a stack, ordered by recency. The most recently used line is at the top. The depth of a line in the stack is its reuse distance. After the access, the line moves to the top.

<ReuseStackDemo />

1. Keep **Loop over 3 lines** and a cache of 3 lines. After the first pass, every access has distance 2, so every access hits.
2. Set the cache size to 2 lines. Now every access misses. A loop has a cliff, not a slope.
3. Select **One hot line**. A has distance 1 every time, so a cache of 2 lines keeps it.
4. Read the bars under the trace. One pass over the trace gives the hits for every cache size.

## The stack property

<Steps>
<div>Keep the lines in a stack ordered by recency. An access to a line at depth $d$ has reuse distance $d$. Move the line to the top.</div>
<div>A fully associative LRU cache of $C$ lines holds exactly the top $C$ lines of the stack.</div>
<div>So an access hits if and only if its distance is less than $C$. This is the <b>inclusion property</b> of LRU (Mattson and others, 1970). A larger LRU cache always holds everything that a smaller one holds.</div>
<div>So one pass over a trace gives the hit rate of <i>every</i> cache size: it is the cumulative histogram of the distances. Real set-associative caches add conflict misses (see the Cache organization lesson).</div>
</Steps>

The **working set** of a program phase is the set of lines that the phase uses again. If the working set fits in the cache, the only misses are compulsory. If it does not fit, an LRU-like cache can miss on every access.

## Spatial locality and stride

A **stride** is the distance between two accesses that follow each other. A loop that reads every int has a stride of 1. A loop that reads one field of each struct has a stride of one struct.

<StrideLinesDemo />

1. Keep stride 1 and 64 B lines. The loop uses every byte of each line, so it misses once in 16 accesses.
2. Set the stride to 2, 4 and 8. Each line brings fewer useful ints, and the misses per access double each time.
3. Set the stride to 16. Each access now needs its own line. The cache moves 64 bytes to use 4 bytes, so only 6.25% of the moved bytes are useful.
4. Change the line size. Larger lines help a sequential scan. When the stride is larger than a line, larger lines only move more unused bytes.

## Loop order changes everything

Matrix multiply does $n^3$ multiply-adds in every loop order. Only the order of the memory accesses changes. With row-major storage, the innermost loop should walk along rows.

The demo below shows why. Each matrix row of 8 doubles is one 64-byte line.

<LoopOrderDemo />

1. Select **ijk**. The inner loop walks along a row of A, but down a column of B. Each step down B needs a new line.
2. Select **jki**. The inner loop walks down the columns of A and C. Each iteration needs 2 new lines.
3. Select **ikj**. The inner loop walks along rows of B and C. 8 iterations share each line.

| Order | The inner loop touches | Misses per inner iteration (64 B lines, large N) |
|---|---|---|
| ijk | A along a row, B **down a column** | ≈ 1/8 + 1 |
| jki | A and C **down a column** | ≈ 2 |
| ikj | B and C along a row | ≈ 1/8 + 1/8 |

The simulator gets about 1.04, 2.02 and 0.13. The order ikj does even better than the table. One row of C (512 bytes) stays in the cache for the whole k loop. This analysis comes from Bryant and O'Hallaron, *Computer Systems: A Programmer's Perspective*. On real hardware the gap has the same order of magnitude.

## Tiling

**Tiling** goes further. It splits the matrices into $T \times T$ blocks, called tiles. One tile each of A, B and C fits in the cache at the same time. The loop then uses every loaded element $T$ times before the cache removes it. With an 8 KiB cache, 8×8 tiles (3 × 512 B) cut the misses to about 0.035 per iteration, 30 times fewer than ijk.

With 16×16 tiles, the three tiles need 6 KiB. With the conflict misses, they no longer fit in an 8 KiB 8-way cache, and the benefit disappears. So the best tile size depends on the cache, and BLAS libraries select it for each CPU. The Performance → Cache-friendly code lesson shows a tiled loop in 3D.

## Designing for locality

- **Walk memory in layout order.** Use row-major order in C, C++, Rust, Zig, Go and Odin. Use column-major order in Fortran, MATLAB and Julia.
- **Keep hot data dense.** Move fields that the program uses rarely out of hot structs. Use arrays in place of linked structures.
- **Use a struct of arrays** when loops touch a few fields of many objects (Performance → Data-oriented design).
- **Tile** every nested loop that uses data again across an outer loop: matrix kernels, stencils, convolutions and image filters.
- **Measure** with `perf stat -e cache-misses,L1-dcache-load-misses`, or with `perf c2c` for sharing problems.
