Caches work because programs are predictable in two ways:

- **Temporal locality**: data used now is likely to be used again soon.
- **Spatial locality**: data *near* what's used now is likely to be used soon. Caches move whole lines (usually 64 bytes), so neighbors arrive for free.

Both can be measured precisely with one number per access: the **reuse distance**.

4. **Random over 64 KiB**: a smooth curve. With no locality, the hit rate is roughly cache size ÷ footprint.

## Reuse distance and the stack property

The reuse distance of an access is the number of *distinct* lines touched since the last access to the same line. First touches have infinite distance.

<Steps>
<div>Keep lines in a stack ordered by recency: most recently used on top. An access to a line at depth $d$ has reuse distance $d$; move it to the top.</div>
<div>A fully associative LRU cache of $C$ lines holds exactly the top $C$ lines of that stack.</div>
<div>So an access hits if and only if its distance is less than $C$. This is the <b>inclusion property</b> of LRU (Mattson et al., 1970): a bigger LRU cache always contains what a smaller one does.</div>
<div>One pass over a trace therefore gives the hit rate of <i>every</i> cache size: the cumulative histogram of distances. Real set-associative caches add conflict misses on top (Cache organization lesson).</div>
</Steps>

The **working set** is the set of lines a program phase reuses. If it fits, misses are only compulsory; if it doesn't, an LRU-like cache can thrash completely.

## Loop order changes everything

Matrix multiply does $n^3$ multiply-adds whatever the loop order. Only the *access pattern* changes. With row-major storage, the innermost loop should walk along rows.

| Order | Inner loop touches | Misses per inner iteration (64 B lines, large N) |
|---|---|---|
| ijk | A row-wise, B **column-wise** | ≈ 1/8 + 1 |
| jki | A and C **column-wise** | ≈ 2 |
| ikj | B and C row-wise | ≈ 1/8 + 1/8 |

The demo gets about 1.04, 2.02 and 0.13. ikj does even better than the table, because one row of C (512 bytes) stays in cache across all of the k loop. This is the analysis from Bryant and O'Hallaron's *Computer Systems: A Programmer's Perspective*, and on real hardware the gap is the same order of magnitude.

**Tiling** goes further. It splits the matrices into $T \times T$ blocks so that one block each of A, B and C fits in cache together, and every element loaded is reused $T$ times before eviction. With an 8 KiB cache, 8×8 tiles (3 × 512 B) cut misses to about 0.035 per iteration, 30× fewer than ijk. Choose 16×16 and the three tiles (6 KiB), plus conflict misses, no longer fit an 8 KiB 8-way cache, and the benefit disappears. Tile size is tuned to the cache, which is why BLAS libraries pick it per CPU.

## Designing for locality

- **Walk memory in layout order.** Row-major in C, C++, Rust, Zig, Go and Odin; column-major in Fortran, MATLAB and Julia.
- **Keep hot data dense.** Split rarely used fields out of hot structs, and prefer arrays to linked structures.
- **Struct of arrays** when loops touch a few fields of many objects (Performance → Data-oriented design).
- **Tile** any nested loop that reuses data across an outer loop: matrix kernels, stencils, convolutions, image filters.
- **Measure**: `perf stat -e cache-misses,L1-dcache-load-misses`, or `perf c2c` for sharing problems.
