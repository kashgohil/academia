A miss to DRAM costs a few hundred cycles. If the hardware predicts the address early enough, it can fetch the line in the background, and the program does not wait. This is **prefetching**. Every modern core has several prefetchers that watch the stream of misses. Your loop runs at cache speed only if one of them understands your access pattern.

## Early enough

A prefetch must start before the program needs the data. The **prefetch distance** is how many lines ahead of the program the prefetcher fetches.

<PrefetchTimelineDemo />

1. Set the distance to 0, which means no prefetch. Each line costs 200 cycles of waiting plus 20 cycles of work: 220 cycles.
2. Set the distance to 1. The wait for each line overlaps with one iteration of work, and the cost decreases to 110 cycles per line.
3. Set the distance to 10. Each line arrives before the loop needs it. The cost is the work alone, 20 cycles per line, which is 11 times faster.
4. Set the work to 50 cycles. Now a distance of 4 is sufficient. The distance must cover the latency: distance ≥ latency ÷ work.

This model lets any number of misses be in flight at the same time. A real L1 cache can track only about 10 to 20 misses at the same time. This limits how much latency prefetching can hide.

Things to try:

1. Select **Sequential scan** with **Next-line**. Almost every miss disappears. This is the easy case, and every CPU handles it.
2. Select **Stride of 3 lines** with **Next-line** at degree 2. The coverage is 0%, because the prefetcher fetches the next 2 lines and the loop skips them.
3. Set the degree to 4. The coverage is now 100%, but the accuracy is only 33%. Two of every three prefetched lines are never used, and they remove useful data. Select **Stride** to get 100% accuracy.
4. Select **Two interleaved streams**. The global stride prefetcher covers 0%, and the stride prefetcher per PC covers 100%.
5. Select **Linked list (pointer chase)**. Nothing helps, because the next address is *inside* the data that the load brings.
6. Select **Indirect gather**. The stride prefetcher per PC covers the `idx[]` stream, but the random `a[idx[i]]` accesses still miss.

## Measuring a prefetcher

- **Coverage**: the share of the misses that a prefetch turned into hits.
- **Accuracy**: the share of the prefetches that the program used before the cache removed them. Useless prefetches waste memory bandwidth and remove useful lines. This is called **pollution**.
- **Timeliness**: a correct prefetch that arrives late still makes the program wait. The first demo shows this. Real prefetchers set a **distance** and a **degree**, which is the number of lines to fetch for each trigger. They tune both, so that the data arrives just before the program needs it.

## The classic designs

<Steps>
<div><b>Next-line and stream buffers</b> (Jouppi, 1990): on a miss, fetch the next few lines. The prefetcher tags each prefetched line. The first use of a tagged line triggers the next prefetch, so a sequential stream stays ahead.</div>
<div><b>Stride, with a reference prediction table</b> (Chen and Baer, 1995): for each load instruction, remember the last address and the last stride. When the same stride occurs again, prefetch <code>addr + k·stride</code>. The index by PC separates interleaved streams.</div>
<div><b>Spatial and region prefetchers</b>: learn which lines of a page the program touches together. This pattern is a footprint. These prefetchers help with structs and objects.</div>
<div><b>Limits</b>: hardware prefetchers usually stop at 4 KiB page boundaries, because the next physical page is unknown without a translation. They also slow down when the memory bandwidth is full.</div>
</Steps>

## When the hardware cannot help

Pointer chasing is the hard case. Linked lists, trees and hash chains with pointers all do it. The address of node $i+1$ is known only when node $i$ has arrived. The options, from most to least effective:

- **Change the layout**: store the nodes in an array, in traversal order. Pool allocators help. Use B-trees in place of binary trees, and open addressing in place of chained hashing.
- **Software prefetch**: use `__builtin_prefetch(p)` in C and C++, `@prefetch` in Zig, or `_mm_prefetch` from `std::arch` in Rust. Issue it several iterations ahead when the address is known early, for example `a[idx[i + 8]]`.
- **Overlap independent chains**: walk several lists at the same time, so that their misses are in flight together. This is called memory-level parallelism.
