Loads only fetch data. Stores raise two separate questions, and each combination of answers produces very different memory traffic:

- **On a write hit**: update memory now (**write-through**), or mark the line *dirty* and write it back when it's evicted (**write-back**)?
- **On a write miss**: fetch the line into the cache first (**write-allocate**), or send the store straight to memory (**no-write-allocate**)?

Things to try:

1. **memset**: write-allocate pays 16 KiB of pointless reads; no-allocate writes exactly the data.
2. **a[i] += 1, 20 passes**: write-back writes each line *once*, whatever the number of passes. Write-through sends all 5,120 stores (20 KiB) to memory.
3. **Transpose 64×64 ints**: writes jump 256 bytes apart. With write-allocate in a 4 KiB cache, each written line is fetched, dirtied once and evicted: about 270 KiB read and 256 KiB written, for 16 KiB of data. No-allocate moves just 16 KiB in each direction.
4. **Scattered counters**: count *transactions*, not bytes. Write-through moves fewer bytes, but DRAM transfers whole 64-byte bursts, so a 4-byte write isn't 16× cheaper in practice.

## The usual pairings

| | On hit | On miss | Where |
|---|---|---|---|
| Write-back + write-allocate | dirty bit, write on eviction | fetch line, then write | L1/L2/L3 data caches on nearly all CPUs |
| Write-through + no-allocate | write memory every time | bypass cache | simple caches, some GPUs' L1, write buffers |

Write-back exploits locality in *stores*: many writes to a line cost one memory write. Its costs are a dirty bit per line, a write-back on eviction (which can delay the fill that caused it), and memory that is temporarily stale. That is harmless for a single core; multi-core systems need coherence (Multicore → MESI).

## Why memset reads: read-for-ownership

On a coherent multi-core CPU, a core must *own* a line before modifying it. On a store miss it issues a **read for ownership (RFO)**, which fetches the line and invalidates other copies. That's write-allocate plus coherence. For a full-line overwrite the read is wasted, so CPUs provide escape hatches:

- **Non-temporal (streaming) stores**: x86 `MOVNTI` / `MOVNTDQ` (`_mm_stream_si128`), ARM `STNP`. They go through write-combining buffers straight to memory with no RFO, and don't pollute the cache. Use them for large outputs you won't read back soon.
- **Fast string instructions**: `rep stosb` / `rep movsb` (ERMSB) can avoid RFOs for large aligned regions. Good `memset`/`memcpy` implementations switch strategies by size.
- **Full-line write detection**: some cores skip the fetch when a store sequence covers an entire line.

<Callout kind="warn" title="Dirty data is owed traffic">
The demo counts dirty lines still in the cache as writes "owed". They will be written eventually, on eviction or an explicit flush. For durable storage on persistent memory, that flush (`CLWB` plus a fence) is the program's responsibility.
</Callout>
