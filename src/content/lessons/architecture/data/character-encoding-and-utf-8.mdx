A CPU has no instructions for text. Text is a sequence of numbers, and an **encoding** says which numbers mean which characters, and how the numbers become bytes. If the writer and the reader use different encodings, the reader gets wrong characters, or it rejects the input.

**ASCII** (1963) gives 128 characters the numbers 0 to 127: English letters, digits, punctuation and control codes such as newline (10). It needs 7 bits, so it fits in a byte with one bit to spare. For decades, many incompatible "code pages" used the values 128 to 255 for other alphabets. A file did not say which code page it used.

**Unicode** gives one number to every character of every script. This number is a **code point**, written `U+` and at least four hex digits: `U+0041` is A, and `U+20AC` is the euro sign €. The code space is U+0000 to U+10FFFF, which is 1,114,112 code points in 17 planes of 65,536. The first plane, U+0000 to U+FFFF, is the **Basic Multilingual Plane** (BMP). Most emoji and many historic scripts are above it.

Unicode defines numbers, not bytes. An **encoding form** turns each code point into one or more **code units** of a fixed size. UTF-32 uses one 32-bit unit for each code point. UTF-16 uses one or two 16-bit units. UTF-8 uses one to four 8-bit units.

## The bit packing of UTF-8

UTF-8 keeps ASCII as it is: a code point below 128 is one byte. Larger code points use a lead byte and one to three continuation bytes. The lead byte starts with as many 1 bits as the sequence has bytes. Each continuation byte starts with `10` and carries 6 bits of the code point.

| Code points | Bytes | Bit pattern | Payload bits |
|---|---|---|---|
| U+0000 to U+007F | 1 | `0xxxxxxx` | 7 |
| U+0080 to U+07FF | 2 | `110xxxxx 10xxxxxx` | 11 |
| U+0800 to U+FFFF | 3 | `1110xxxx 10xxxxxx 10xxxxxx` | 16 |
| U+10000 to U+10FFFF | 4 | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` | 21 |

Ken Thompson and Rob Pike designed UTF-8 in September 1992, on a placemat in a New Jersey diner, by Pike's account. Plan 9 used it within a week. The design has four properties that made it win:

- **ASCII compatibility.** Every ASCII file is already valid UTF-8. No byte of a multi-byte sequence is below 0x80. So a search for `/` or for a NUL byte never matches inside a character. C string functions and Unix tools kept working.
- **Self-synchronization.** A byte shows its role with no context: ASCII, lead or continuation. A reader that starts in the middle skips at most 3 continuation bytes to find the next character.
- **Sort order.** Byte-by-byte comparison of UTF-8 gives code point order. So `memcmp` sorts UTF-8 strings by code point.
- **No byte order.** The code unit is a byte, so UTF-8 needs no byte order mark. UTF-16 and UTF-32 come in big-endian and little-endian forms.

The original design allowed up to 6 bytes and 31 bits. RFC 3629 (2003) limited UTF-8 to U+10FFFF, the range that UTF-16 can reach, so 4 bytes is the maximum.

## Invalid sequences

Not every byte sequence is valid UTF-8. A decoder must reject or replace these cases:

- **Overlong forms.** `C0 AF` decodes to the bits of `/` (U+002F), but in 2 bytes when 1 byte is enough. The Unicode standard forbids it, so there is exactly one encoding for each code point. The bytes C0, C1 and F5 to FF never appear in valid UTF-8.
- **Surrogates.** `ED A0 80` would encode U+D800, which is not a character.
- **Values above U+10FFFF.** `F4 90 80 80` would be U+110000.
- **Truncated sequences**, and **stray continuation bytes** with no lead byte.

The decoder in the demo follows the WHATWG Encoding Standard, which browsers and the JavaScript `TextDecoder` use. It replaces each **maximal subpart** of an invalid sequence with one U+FFFD (the replacement character �). The Unicode standard describes this practice but does not require it. A strict decoder rejects the whole input: Rust `str::from_utf8` returns an error, and a Rust `&str` is always valid UTF-8. Validate at the boundary where bytes enter the program, and keep a type that says "already valid" after that.

## UTF-16 and surrogate pairs

Unicode began in 1991 as a 16-bit code. Windows NT, Java and JavaScript adopted 16-bit characters at that time. When Unicode grew beyond 65,536 code points, UTF-16 kept the BMP as one unit and added **surrogate pairs** for the rest. A code point above U+FFFF becomes $v = c - \text{0x10000}$, a 20-bit value. The high 10 bits go into a unit from D800 to DBFF, and the low 10 bits into a unit from DC00 to DFFF. That is why these 2,048 code points can never be characters.

UTF-16 lost the sort property: U+FF61 sorts after U+1F600 in UTF-16, because the high surrogate D83D is less than FF61. In UTF-8 and in code point order it sorts before. Java `compareTo` and JavaScript `<` compare UTF-16 units, so they can disagree with a sort in Rust, Go or a database.

A **grapheme cluster** is what a reader sees as one character. Unicode Standard Annex #29 defines the rules, and they change as new emoji appear. Swift counts these by default. Other languages need a library, such as `Intl.Segmenter` in JavaScript or the `unicode-segmentation` crate in Rust. A text editor must move the cursor by grapheme clusters, or it can split an emoji in half.

**Normalization** fixes a related problem. "é" can be one code point (U+00E9) or two (e plus U+0301). The two forms look the same but compare as different. NFC composes characters where it can, and NFD decomposes them.

The old macOS file system HFS+ stored names in a decomposed form. Most other file systems do not normalize, and most text input produces NFC. Normalize before you compare or hash user text.

What this means for code: index a UTF-8 string by byte offsets that you got from a search, never by a character count. In Rust, slicing a `&str` in the middle of a character panics. In Go, `len(s)` counts bytes, and `for range s` decodes runes, which are code points, with U+FFFD for each invalid byte. Python 3 counts code points. It stores each string with 1, 2 or 4 bytes per code point, chosen by the largest code point in the string (PEP 393).

## Validation at memory speed

A byte-at-a-time decoder needs several branches for each byte. Validation is on the hot path of every JSON parser and web server.

John Keiser and Daniel Lemire showed how to validate with SIMD instructions in "Validating UTF-8 In Less Than One Instruction Per Byte" (2021). Their method looks up 3 nibbles of each pair of adjacent bytes in small tables, and ANDs the results to find every error class. It checks 32 or 64 bytes per step with no branches. The paper reports that it is more than 10 times faster than the validators of many common libraries. The simdutf library and simdjson use this method.
