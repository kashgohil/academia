The [previous lesson](/architecture/data/binary-and-hexadecimal) read a word as an unsigned number. A machine also needs negative numbers. Early computers tried two other methods. **Sign-magnitude** uses the top bit as a sign. **Ones' complement** negates a number by inverting every bit. Both have two zeros (+0 and −0), and both need extra adder logic for mixed signs.

**Two's complement** gives the top bit a negative weight. In a $w$-bit word, bit $w - 1$ counts $-2^{w-1}$, not $+2^{w-1}$:

$$
x = -b_{w-1} \cdot 2^{w-1} + \sum_{i=0}^{w-2} b_i \cdot 2^i
$$

So an 8-bit word holds −128 to 127, and the pattern `1111 1111` is −1. There is one zero. Every current CPU uses two's complement. C23 and C++20 require it, after decades in which the standards also allowed the two older methods.

## One adder for both

Put the $2^w$ bit patterns around a circle. Adding 1 moves one step clockwise. The unsigned reading and the signed reading are two sets of labels on the same circle. They differ only on the lower half, where the signed labels are the unsigned labels minus $2^w$.

4. Select 8 bits. The same seams sit between 255 and 0, and between 127 and −128.

The adder does not know if its inputs are signed. It computes the sum modulo $2^w$, and the bits are right for both readings when the true result fits. The flags report the two ways that it can fail.

- **CF** (carry flag) is the carry out of the top bit. It is set when the unsigned result is wrong.
- **OF** (overflow flag) is set when both inputs have the same sign and the result has the other sign. It is set when the signed result is wrong.
- **SF** copies the top bit, and **ZF** is set when the result is 0.

The x86 `ADD` instruction sets all of them, plus AF and PF. The code that follows chooses the flag. Unsigned branches (`jb`, `ja`) read CF, and `ja` also reads ZF. Signed branches (`jl`, `jg`) compare SF with OF, and `jg` also reads ZF. In C, the type of the variable decides which branch the compiler emits.

## Negation and its one failure

To negate in two's complement, invert every bit and add 1. The sum of $x$ and its inverse is all ones, which is −1, so $\lnot x + 1 = -x$.

One value has no negative. In 8 bits, −128 is `1000 0000`. Its inverse is `0111 1111`, and adding 1 gives `1000 0000` again. The range is not symmetric: there is one more negative value than positive values.

So `abs(INT_MIN)` and `-INT_MIN` overflow. In C they are undefined behavior. In Rust, `i32::MIN.abs()` panics in a debug build and returns `i32::MIN` in an optimized build.

## Sign extension and zero extension

A load of one byte into a 32-bit or 64-bit register must fill the upper bits. **Zero extension** fills them with 0 and keeps the unsigned value. **Sign extension** copies the top bit of the byte and keeps the signed value. Each ISA has both kinds of load.

<ArchDataExtendDemo />

1. Keep the byte 0xF6. Sign extension gives 0xFFFFFFF6, which is −10. Zero extension gives 0x000000F6, which is 246.
2. Move the slider below 0x80. Bit 7 is 0, and both loads give the same register.

| Load | RISC-V | x86-64 | AArch64 |
|---|---|---|---|
| byte, sign-extend | `lb` | `movsx` | `ldrsb` |
| byte, zero-extend | `lbu` | `movzx` | `ldrb` |

RV64 adds a twist. The 32-bit operations such as `addw` sign-extend their 32-bit result into the 64-bit register. On x86-64, a write to a 32-bit register such as `eax` zero-extends into `rax`. A wrong choice here is a classic bug. C code that reads a `char` from a buffer can get a negative number for a byte above 0x7F. This occurs where `char` is signed, as on x86-64 Linux.

## Right shifts round toward minus infinity

A **logical right shift** fills the top with zeros. An **arithmetic right shift** fills it with copies of the sign bit, so a negative number stays negative. RISC-V names them `srl` and `sra`, and x86 names them `shr` and `sar`.

1. Keep x = −7 and k = 1. The shift gives −4, and the division gives −3.
2. Set x = −8. Now both give −4, because nothing is rounded.
3. Set x to a positive value. The two always agree for $x \geq 0$.
4. Read the last value. The compiler adds $2^k - 1$ to a negative x before the shift, and gets the division result.

The Intel SDM entry for `SAR` says the same. The quotient of `IDIV` is rounded toward zero, and the "quotient" of `SAR` is rounded toward negative infinity. This is why `x / 2` on a signed `int` costs two or three instructions more than on an `unsigned`. If you know that x is not negative, use an unsigned type or a shift. In C11, a right shift of a negative signed value is implementation-defined. GCC and Clang define it as an arithmetic shift.

## Overflow in the ISA and in the language

RISC-V has no flags at all. Its base ISA has no carry flag and no overflow flag, and no integer instruction traps on overflow. The spec shows how to check in software. For unsigned addition, one branch after the add is enough:

```riscv
    add  t0, t1, t2
    bltu t0, t1, overflow   # the sum is smaller than an input: it wrapped
```

For general signed addition, three instructions follow the add. The sum is less than `t1` exactly when `t2` is negative, unless the add overflowed:

```riscv
    add  t0, t1, t2
    slti t3, t2, 0          # t3 = (t2 < 0)
    slt  t4, t0, t1         # t4 = (sum < t1)
    bne  t3, t4, overflow
```

The tests for this lesson check this sequence against the x86 OF rule for all 65,536 pairs of 8-bit inputs. They agree on every pair.

Division has two edge cases: division by zero, and MIN / −1, where the true quotient $2^{w-1}$ does not fit. The ISAs and the languages disagree on both.

<ArchDataOverflowDemo />

1. Click **MAX + 1**. The bits wrap to MIN everywhere. Only the languages differ in what they call it: undefined behavior, a panic, `None` or a defined wrap.
2. Select **a / b** and click **MIN / −1**. x86 raises a divide error, so the process gets SIGFPE on Linux. RISC-V and AArch64 return MIN with no trap.
3. Click **7 / 0**. RISC-V returns all ones as the quotient, and AArch64 returns 0. Both continue.
4. Change the width to 8. The edge values change, but the behavior does not.

| | Signed `+` overflow | MIN / −1 |
|---|---|---|
| C, C++ | undefined behavior | undefined behavior |
| Rust | panic in debug builds, wraps in release builds by default | panic in every build |
| Go | wraps, defined by the spec | the result is MIN, defined by the spec |
| Zig | illegal behavior: a panic in Debug and ReleaseSafe | `a / b` does not compile for signed values; `@divTrunc(MIN, -1)` is illegal behavior |
| Java | wraps, defined by the JLS | the result is MIN |

C undefined behavior is not "wraps". The optimizer assumes that signed overflow never happens. So it can delete a check such as `if (x + 1 < x)`, because that condition is always false without overflow. Write the check before the operation, or use `__builtin_add_overflow`, or C23 `ckd_add`.

In Rust, say what you mean: `wrapping_add`, `checked_add` (returns an `Option`), `overflowing_add` (returns the value and a flag) or `saturating_add`. In Zig, use `+%` to wrap, `+|` to saturate, and `@addWithOverflow` to get the result and an overflow bit. The Systems track covers the C rules in depth.
