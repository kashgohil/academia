The ISA has no idea of a function. It has a jump that saves a return address (`jal`), an indirect jump (`jalr`), and registers. Functions that were compiled separately can still call each other, because they all follow one more contract: the **calling convention**. For RISC-V, the RISC-V **psABI** document defines it. On x86-64 Linux it is the System V AMD64 ABI, and on Windows it is the Microsoft x64 convention. On 64-bit Arm it is the AAPCS64.

A calling convention answers four questions. Where are the arguments and the return value? Which registers must a function keep for its caller? How is the stack laid out and aligned? Who removes what from the stack?

## RISC-V roles

| Registers | Role | Kept across a call? |
|---|---|---|
| `a0`–`a7` | Arguments; `a0` and `a1` also return values | No |
| `ra` | Return address, written by `jal` and `jalr` | No |
| `sp` | Stack pointer, 16-byte aligned | Yes |
| `s0`–`s11` | Saved registers; `s0` can be the frame pointer | Yes |
| `t0`–`t6` | Temporaries | No |
| `gp`, `tp` | Global pointer and thread pointer | Not allocated |

A **caller-saved** register (also called volatile) can change in any call. If the caller needs its value after the call, the caller must save it first. A **callee-saved** register (nonvolatile) must have the same value after the call. If the callee wants to use it, the callee saves it on entry and restores it before it returns.

The psABI requires that `sp` is aligned to 128 bits, 16 bytes, at every procedure entry, and that it stays aligned in the standard ABI. Data below `sp` is not safe: the psABI says that procedures must not rely on it.

The demo shows why calls in a debugger form a **call stack**. A debugger walks the saved return addresses to show it. With frame pointers, each frame also stores the caller's `s0`, so the walk is a linked list. Without them, the debugger needs unwind tables (DWARF CFI) that describe each prologue.

## Leaf functions

A **leaf function** calls nothing. It does not need to save `ra`, and it can often use only `a` and `t` registers. Then it needs no frame at all. Most small functions compile to leaves after inlining.

On x86-64 System V, a leaf can also use the **red zone**. This is 128 bytes below `rsp` that "shall not be modified by signal or interrupt handlers". The function can use this space without moving `rsp`.

The Linux kernel builds x86-64 code with `-mno-red-zone`. In kernel mode, an interrupt arrives on the current kernel stack. The CPU pushes its interrupt frame right below `rsp`, so it would overwrite any data in a red zone. The RISC-V psABI defines no red zone.

## Why both kinds of register

If every register were caller-saved, a function that keeps values across many calls would save them around every call. If every register were callee-saved, every small leaf function would save the registers that it uses as scratch. Real programs have both kinds of function, so conventions split the registers.

## The conventions side by side

| | RISC-V psABI | System V AMD64 | Microsoft x64 | AAPCS64 |
|---|---|---|---|---|
| Integer arguments | `a0`–`a7` | `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9` | `rcx`, `rdx`, `r8`, `r9` | `x0`–`x7` |
| Return | `a0`, `a1` | `rax`, `rdx` | `rax` | `x0`, `x1` |
| Return address | `ra` register | on the stack (`call`) | on the stack (`call`) | `x30` (LR) |
| Callee-saved | `sp`, `s0`–`s11`; `fs0`–`fs11` in the hard-float ABI | `rbx`, `rbp`, `r12`–`r15`, `rsp` | `rbx`, `rbp`, `rdi`, `rsi`, `r12`–`r15`, `rsp`, `xmm6`–`xmm15` | `x19`–`x29`, `sp`; the low 64 bits of `v8`–`v15` |
| Stack alignment | 16 B | 16 B at the `call` | 16 B | 16 B |
| Special | | 128-byte red zone | 32-byte shadow space | `x8` indirect result, `x16`, `x17` linker scratch, `x18` platform |

The Microsoft convention requires the caller to reserve stack space for the four register arguments, even when the callee takes fewer. This is the 32-byte **shadow space** (home space). The callee can store its register arguments there, which helps varargs and debuggers.

Here is one small function in each convention. The x86-64 and AArch64 code is clang -O2 output. The RISC-V code is hand-written in the same style.

```c
int h(int);
int keep(int x) { return h(x) + x; }   // x must survive the call
```

```asm
; x86-64 System V                     ; x86-64 Microsoft
push rbx          ; save callee-saved   push rsi           ; rsi is callee-saved here
mov  ebx, edi     ; x lives in rbx      sub  rsp, 0x20     ; 32-byte shadow space
call h                                  mov  esi, ecx      ; x arrives in ecx
add  eax, ebx                           call h
pop  rbx                                add  eax, esi
ret                                     add  rsp, 0x20
                                        pop  rsi
                                        ret
```

```asm
// AArch64 (AAPCS64)
stp  x29, x30, [sp, #-0x20]!   // save fp and lr, open a 32-byte frame
str  x19, [sp, #0x10]          // save callee-saved x19
mov  x29, sp
mov  w19, w0                   // x lives in x19
bl   h
add  w0, w0, w19
ldr  x19, [sp, #0x10]
ldp  x29, x30, [sp], #0x20
ret
```

```riscv
keep:   addi sp, sp, -16    # open a 16-byte frame
        sw   ra, 12(sp)     # call overwrites ra
        sw   s0, 8(sp)      # save callee-saved s0
        mv   s0, a0         # x lives in s0
        call h
        add  a0, a0, s0
        lw   s0, 8(sp)
        lw   ra, 12(sp)
        addi sp, sp, 16
        ret
```

On System V, `call` pushes 8 bytes, so `rsp` is 8 bytes off 16 at entry. The `push rbx` aligns it again before the next `call`. The Microsoft version also pushes one register, and the 32-byte shadow space keeps the alignment.

## Structs and varargs, briefly

The RISC-V psABI passes an aggregate of up to XLEN bits in one register, and of up to 2×XLEN bits in a pair. A larger aggregate is passed by reference: the caller makes a copy and passes its address. Variadic arguments use the integer registers in the same way as named arguments, with one exception for aligned register pairs. On System V AMD64, a variadic call also sets `al` to the number of vector registers that hold arguments.

## What this means for your code

- **Small functions that call nothing are almost free.** They need no frame and no saves. Keep hot helpers small enough to be leaves, or to be inlined.
- **A value that lives across a call costs a callee-saved register,** and that costs a save and a restore in the function. Long chains of calls in hot loops pay this many times.
- **Pass small structs by value.** Up to two machine words, they travel in registers on RISC-V, System V and AAPCS64. Larger structs go through memory anyway.
- **Keep frame pointers on** (`-fno-omit-frame-pointer`) if you profile in production. The stack walk is then a cheap list walk.
- **Hand-written assembly must follow the convention exactly**: save what you use from the callee-saved set, and keep `sp` 16-byte aligned at every call.
