Most code that you run executes on one of two ISAs. x86-64 runs PCs and most servers. AArch64 runs phones, Apple Macs and a growing share of servers. They came from opposite traditions. x86-64 extends the 1978 Intel 8086, through the 32-bit 80386 and AMD's 64-bit extension. AArch64 is the 64-bit ISA that Arm introduced with Armv8-A as a clean design. RISC-V is the third column in this lesson, because its choices are the simplest to read.

This lesson compares the encodings, the way to branch, the operand forms, memory access and the memory model. Each section uses real compiler output.

Things to try:

1. Read **sum of an array**. Count the byte lengths of the x86-64 rows: 1, 2 and 3 bytes. Every AArch64 and RISC-V row is 4 bytes.
2. Select **p->c += v**. x86-64 needs 1 instruction plus `ret`, because `add dword ptr [rdi + 0x8], esi` reads memory, adds and writes back. AArch64 and RISC-V need a load, an add and a store.
3. Select **max(a, b)**. x86-64 uses `cmovg` and AArch64 uses `csel`, so neither branches. The RISC-V base ISA has no conditional move, so it branches.
4. Select **strlen: a byte loop**. Each loop body has 3 instructions on every ISA. AArch64 uses `cbnz`, which tests a register and branches with no flags.
5. Read the colors of the x86 bytes. A REX prefix (`48`) marks a 64-bit operation. A ModRM byte follows most opcodes and names the operands.

## Encoding: 1 to 15 bytes against 4

An x86-64 instruction starts with optional legacy prefixes and an optional REX prefix. Then comes an opcode of 1 to 3 bytes and an optional ModRM and SIB byte. Last come a displacement of 0, 1 or 4 bytes and an immediate of 0 to 8 bytes. The Intel SDM limits an instruction to 15 bytes. In the four functions of the demos, x86 instructions are 1 to 7 bytes long.

AArch64 instructions are always 32 bits, aligned to 4 bytes. RISC-V base instructions are also 32 bits. The C extension adds 16-bit forms, but bits 1 and 0 of the first parcel still give the length at once.

The cost of variable length is in decode. A wide core wants to decode several instructions per cycle. With fixed length, instruction n starts at byte 4n, and every decoder slot can start at once. With x86, the start of an instruction is known only when the lengths of all earlier instructions are known.

1. Keep start byte 1. The decoder reads `test` with a length of 2, and is back in step at byte 3.
2. Move the start to 14. The decoder reads one 4-byte instruction that the compiler never wrote, a valid `ror`, and is back in step at byte 18.

The length decoder in this demo implements the one-byte opcode map and the common two-byte and three-byte maps of the Intel SDM, Vol. 2. The test file compares its lengths with the LLVM disassembler on compiled code, from several start bytes.

Real x86 cores attack this problem with hardware. They find the instruction boundaries in a separate predecode step, and some designs store these marks with the cache lines. They also keep a cache of already decoded micro-ops, so hot loops skip the length decode. Both cost area and power. A fixed-length ISA does not need them for this reason.

## Flags against compare-and-branch

x86-64 and AArch64 use **condition flags**. An ALU instruction or a compare sets the flags, and a later conditional jump reads them. RISC-V has no flags: `blt`, `bge`, `bltu` and `bgeu` compare two registers inside the branch.

<IsaFlagsDemo />

1. Keep a = 100 and b = -100. The true difference is 200, which does not fit in 8 signed bits. So OF (overflow) is 1, and SF (sign) alone would give the wrong answer. This is why `jl` tests SF ≠ OF.
2. Set a = 5 and b = 10. As unsigned numbers, a is smaller, so x86 sets CF = 1. AArch64 sets C = 0 for the same compare. Its carry flag after a subtraction is the opposite of a borrow, so `b.lo` tests C = 0.
3. Read the RISC-V column. There is no `bgt` instruction: the assembler writes `blt b, a`, with the operands swapped.

Each design has a cost. Flags are extra architectural state that many instructions write. An out-of-order core must rename them like registers. Flags also link instructions: a compare and its branch must stay in order with nothing that writes flags between them. RISC-V avoids this state, but some operations need more instructions.

The RISC-V manual shows that an overflow check for signed addition needs three extra instructions after the `add`. An unsigned check needs one extra branch, for example `add t0, t1, t2` then `bltu t0, t1, overflow`.

AArch64 reduces the coupling. Most ALU instructions do not set flags. Only compares and the forms with an `s` suffix, such as `adds` and `subs`, write them. It also has `cbz`, `cbnz`, `tbz` and `tbnz`, which test a register and branch without flags.

## Operand forms

| | x86-64 | AArch64 | RISC-V |
|---|---|---|---|
| ALU form | two-operand: `add eax, ebx` overwrites `eax` | three-operand: `add w0, w1, w2` | three-operand: `add a0, a1, a2` |
| Memory in ALU ops | yes: `add [rdi + 8], esi` | no: load/store | no: load/store |
| General registers | 16 (APX adds 16 more) | 31, plus a zero register or `sp` in register 31 | 31, plus `x0` = 0 |
| Conditional select | `cmovcc` | `csel`, `csinc`, `csneg` | none in the base ISA (Zicond adds `czero.eqz`, `czero.nez`) |
| Load pairs | no | `ldp`, `stp` | no (RV32 Zilsd loads an even–odd register pair) |

A two-operand form destroys one source. When the compiler needs both inputs later, it adds a `mov` first, as in the `max2` code: `mov eax, esi` before `cmovg`. Large x86 cores can often execute such a `mov` at rename, with no execution unit. This is **move elimination**. The AVX encodings (VEX and EVEX) brought three-operand forms to the vector instructions of x86.

## Memory model

The ISA also defines the order in which other cores see loads and stores. x86-64 uses a strong model close to **TSO** (total store order). A core can see its own store before other cores do, but stores become visible in program order. AArch64 and RISC-V (RVWMO) use weak models. The hardware can reorder independent loads and stores unless the code uses acquire, release or fence instructions.

The [memory consistency models](/architecture/multicore/memory-consistency-models) lesson covers this in depth. Here only one consequence matters: code that is correct only because of TSO can fail on AArch64. Emulators that run x86 code on Arm must insert fences, or use hardware help.

RISC-V defines an optional Ztso extension for this. The manual says that Ztso "is meant to facilitate the porting of code originally written for the x86 or SPARC architectures". Reverse-engineering reports say that Apple M-series cores have a TSO mode for Rosetta 2. Apple does not document it, so do not rely on it.

## What this means for your code

- **Compare code size on the binary, not on instruction counts.** x86-64 often needs more instructions but fewer bytes than AArch64. RISC-V with the C extension is usually close to both.
- **Branchless code is portable.** `cmov`, `csel` and Zicond all turn a simple `?:` into a select. The compiler picks it when the branch is unpredictable (see [branch prediction and branchless code](/performance/cpu/branch-prediction-and-branchless-code)).
- **Do not depend on x86 ordering** in lock-free code. Use the atomics and orderings of your language. An acquire load and a release store compile to plain moves on x86-64, and to `ldar` and `stlr` on AArch64.
- **Read the length of x86 instructions** when you align hot loops or patch code. A jump into the middle of an instruction decodes as something else, with no error.
