Each core has its own L1 and L2 caches. Two cores can keep copies of the same **cache line**, the 64-byte block that caches move. If one core writes its copy, the other copy becomes **stale**: it holds an old value. A **coherence protocol** makes sure that no program can see a stale copy. It keeps two rules, called **invariants** (Sorin, Hill and Wood, *A Primer on Memory Consistency and Cache Coherence*):

- **Single writer, multiple readers (SWMR)**: at any time, one core can write a line, or any number of cores can read it. These two cases never occur together.
- **Data value**: a read gets the value of the last write to that line.

Each line in each cache has a **state**. In the simplest design, all caches share a **bus**: one set of wires on which each request goes to every cache, in the same order. Each cache **snoops**: it watches the bus and looks up each request in its own cache.

Things to try:

1. Select **Read, then write (one core)**. Compare MSI and MESI: 2 bus transactions against 1.
2. Select **Producer → consumer ×2**, and compare MESI and MOESI. MESI writes the dirty line back to memory each time the consumer reads it. MOESI keeps the dirty line in the producer as **Owned** and sends it directly to the other cache.
3. Look at the memory row. "Stale" means that memory holds an old value. This is permitted while a cache owns the line.
4. Select **Everyone reads, one writes**. The write invalidates all the other copies at the same time.
5. Select **Ping-pong writes**. Each write by a different core moves the line and invalidates the other copy. A contended atomic or a shared counter has this cost.

## The states

Look at one line in one cache. Its state changes when this core reads or writes the line. It also changes when another core reads or writes the line.

<MesiStateMachineDemo />

1. Click **This core reads**, then **This core writes**. Under MESI, the line goes from I to E to M with one bus transaction. Under MSI, it goes from I to S to M with two.
2. Click **Other core reads**. Under MESI, M changes to S, and the dirty data goes back to memory. Under MOESI, M changes to O, and memory stays stale.
3. Click **Other core writes**. The copy in this core becomes I, from any state.
4. Select **MOESI** and get the line into O. Then click **This core writes**. The core must invalidate the other copy with a BusUpgr before it can write.

| State | Meaning | Can read | Can write | Memory up to date |
|---|---|---|---|---|
| **M**odified | only copy, dirty | yes | yes | no |
| **O**wned (MOESI) | dirty, but others may hold S copies; this cache answers requests | yes | no | no |
| **E**xclusive (MESI) | only copy, clean | yes | yes, silently → M | yes |
| **S**hared | one of possibly many clean copies | yes | needs upgrade | yes (or an O holds it) |
| **I**nvalid | not present | no | no | — |

A line is **dirty** when the cache has changed it and memory has the old value. A line is **clean** when memory has the same value. The bus transactions are:

- **BusRd**: a read miss. The cache gets a shared copy.
- **BusRdX**: a write miss. The cache gets the line and invalidates all other copies.
- **BusUpgr**: a write hit in S. The cache invalidates the other copies. It does not need the data.
- **Writeback**: a dirty line goes back to memory.

Real CPUs add variants. In Intel **MESIF**, one sharer is the **Forwarder** (F), which answers the requests for the line. AMD uses MOESI, so it can share dirty data without a writeback to memory.

## False sharing

Coherence works on whole lines, not on variables. Two threads can write *different* variables that are in the same line. Then the line moves between the two cores, as if they shared one variable. This is **false sharing**. Typical causes are per-thread counters in an array, a lock next to the data that it protects, and struct fields that different threads write.

1. Start at **8 bytes**. Almost every access is a red bus transaction. The line moves to the other core at each increment.
2. Move the distance to **56 bytes**. The counters are still in the same line, so nothing changes.
3. Move the distance to **64 bytes**. Counter B is now in line 1. After the first miss of each core, every access is a hit.
4. Compare the cycles: 1,154 against 320. False sharing makes the same work about 3.6 times slower.

The fix is to give each variable its own line, with padding or alignment. Many libraries use 128 bytes. On x86-64, the adjacent-line prefetcher fetches lines in pairs, so two neighbor lines can also interfere.

```rust
#[repr(align(128))]   // crossbeam's CachePadded uses 128 on x86-64: adjacent-line prefetch pairs lines
struct PerThread { count: AtomicU64 }
```

```zig
const PerThread = struct { count: std.atomic.Value(u64) align(std.atomic.cache_line) };
```

C++17 has `std::hardware_destructive_interference_size` for this. On Linux, `perf c2c` finds false sharing. It reports the cache lines with much cross-core "HITM" traffic: loads that hit a line in the Modified state in another core.
