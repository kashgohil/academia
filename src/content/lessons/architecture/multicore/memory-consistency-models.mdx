Coherence (the previous lesson) makes all cores agree on the order of the writes to **one** address. It says nothing about accesses to **different** addresses. The **memory consistency model** covers these. It is the contract of the hardware: it tells which reorderings other cores can see.

Lamport defined **sequential consistency** (SC) in 1979. Under SC, the result is the same as if all operations ran in one interleaving, and each core kept its program order. No mainstream CPU uses SC, because SC forbids the most important optimization: the **store buffer**. A store buffer is a small queue in each core. It holds the stores that the core has run but that have not reached the cache yet.

5. Select **Store buffering with seq_cst fences**. The fence blocks until the buffer is empty. This is the x86 `MFENCE`, and it is why `MFENCE` costs tens of cycles.

## See it on a timeline

A store buffer delays the time when a store becomes visible to other cores. The demo shows one schedule of the same program. Core 0 runs `x = 1`, then `r0 = y`. Core 1 runs `y = 1`, then `r1 = x`.

<StoreBufferTimelineDemo />

1. Start with the default values. Each store needs 8 cycles to reach memory, and core 1 starts 2 cycles later. Both loads read 0.
2. Move the store time down to 3 cycles. The store of core 0 now reaches memory in time for the load of core 1, so r1 = 1.
3. Move the store time to 0. This is a machine without a store buffer. No start delay gives r0 = r1 = 0.
4. Set the store time back to 8 and turn on the fence. Each load now waits until the store of its own core reaches memory. The result r0 = r1 = 0 disappears, but each load waits 7 cycles.

In this model, both loads read 0 when a store needs more cycles to reach memory than the start delay plus 1.

## Count every schedule

A **litmus test** is a small program that shows if a reordering can occur. The machine can take its steps in many orders. A step runs the next instruction of a core, or writes a permitted store from a buffer to memory. The demo counts all the schedules and groups them by result.

<ScheduleCountDemo />

1. Select **Store buffering, relaxed** with **None (SC)**. There are 6 schedules, and none of them gives r0=0 r1=0.
2. Select **FIFO (TSO)**. There are now 80 schedules, and 18 of them give r0=0 r1=0. Click that result to see one of the schedules.
3. Select **Message passing, relaxed** with TSO. No schedule gives r0=1 r1=0. Select **PSO**: 1 schedule of 45 gives it.
4. Select **Store buffering with seq_cst fences** with TSO. None of the 70 schedules gives r0=0 r1=0.

A count of schedules is not a probability. But it shows that a weak result often needs one specific timing. So a weak result can be rare in tests and still occur in production.

## Why hardware reorders

- **Store buffers**: a store that misses the cache would stop the core for hundreds of cycles. The buffer hides this delay, because later loads can go first. This gives store → load reordering.
- **Out-of-order loads**: a load runs as soon as its address is known. x86 keeps the loads *apparently* in order. If a line is invalidated between two loads, the core discards the later load and runs it again. Weaker architectures do not do this.
- **Stores that drain out of order, and invalidation queues**: stores to different lines can complete out of order. A cache can also acknowledge an invalidation before it applies it. These give store → store and load → load reordering.
- **Shared store buffers, or writes that do not reach all cores at the same time**: different cores can see two writes in different orders. The litmus test for this is IRIW (independent reads of independent writes).

## The major models

| Model | Allows | Used by |
|---|---|---|
| Sequential consistency | nothing | none at full speed (the ideal) |
| **TSO** | store → load reordering, reading your own buffered stores early | x86, SPARC TSO, RISC-V with Ztso, Apple M-series in Rosetta mode |
| **PSO** | also store → store | SPARC PSO |
| **ARMv8 / RVWMO** | all four reorderings unless ordered by dependencies or barriers; multi-copy atomic | ARMv8+, RISC-V default |
| **POWER** | all of the above, and not multi-copy atomic (IRIW observable) | IBM POWER |

A model is **multi-copy atomic** when a write becomes visible to all other cores at the same time. A **barrier** (or fence) is an instruction that stops the reorderings across it. The barriers are:

- x86: `MFENCE`, or any instruction with a `LOCK` prefix.
- ARM: `DMB ISH`, and `LDAR` and `STLR` for acquire and release.
- RISC-V: `fence rw,rw`.

Compilers map C++ and Rust atomics to these instructions (see Atomics → Memory orderings). The demo below runs litmus tests under SC, x86-TSO and the C++ model.

## The contract you program against

Portable code does not target a hardware model directly. Each language defines its own model, for example C++, Rust, Java and Go. The compiler inserts the barriers that each architecture needs. The main promise is **SC for data-race-free programs**. Synchronize correctly, with locks or with atomics and correct orderings. Then you can think as if the hardware were SC.

The hardware models are important when you write synchronization primitives or read compiler output. They are also important when you debug a race that occurs "only on ARM".
