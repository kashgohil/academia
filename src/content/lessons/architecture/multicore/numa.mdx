A multi-socket server has two or more processor packages, called **sockets**. Each socket has its own memory controllers and its own memory. Every core can access all the memory. But **local** memory, on the socket of the core, is faster than **remote** memory, on another socket. A remote access must cross the link between the sockets. This is **NUMA**: non-uniform memory access.

Remote latency is usually 1.5 to 2 times local latency. The memory of each socket also has a fixed bandwidth, which all its readers share. A socket (or a part of a large socket) together with its memory is a **NUMA node**.

The operating system decides which node holds each page. The Linux default is **first touch**: a page goes to the node of the core that first *writes* it. This is not always the core that called `malloc`.

1. With **2 sockets** and **16 threads**, initialization by one thread stops at 60 GB/s. Parallel initialization and interleaving reach 120 GB/s.
2. Compare the latency cards. Parallel first touch is 100% local (90 ns). Interleaving is 50% remote (120 ns). It gets the bandwidth, but each access is slower on average.

4. Lower the thread count. With 6 threads or fewer, the cores are the limit, and the placement does not change the bandwidth. It still changes the latency.

## Where the pages go

<PageMapDemo />

1. Select **One thread initializes**. Every page goes to node 0. With 2 sockets, the threads on socket 1 find all their pages remote: 50% of all pages.
2. Select **Each thread initializes its part**. Each page goes to the node of the thread that uses it. No page is remote.
3. Select **Interleave pages**. The pages go to the nodes in turn. Each thread finds 50% of its pages remote with 2 sockets, and 75% with 4 sockets.
4. Change the thread count with 2 sockets. The remote fraction of each placement stays the same: 50%, 0% and 50%.

4. Select **Each thread initializes its part**. No dot crosses a link, and both memories share the work.
5. Select **4 sockets** and **Interleave pages**. Dots of all four colors go to every socket. With 16 threads, each link carries 10 GB/s of its 40 GB/s.

## Rules that follow

<Steps>
<div><b>Initialize data with the same threads, and the same partitioning, that will use it.</b> A parallel loop that fills the part of each thread puts the pages in the correct place at no cost.</div>
<div><b>Pin threads to cores.</b> If you do not, the scheduler can move a thread away from its data. Use <code>taskset</code>, <code>pthread_setaffinity_np</code>, or <code>OMP_PROC_BIND=close</code> with <code>OMP_PLACES=cores</code>.</div>
<div><b>Interleave data that all threads read</b>, such as shared tables and hash maps. <code>numactl --interleave=all</code> puts the pages on the nodes in turn. The bandwidth is balanced, but the average latency is higher.</div>
<div><b>Keep shared data that is written often on one socket.</b> Coherence traffic between sockets costs much more than inside a socket. So false sharing across sockets is the worst case.</div>
</Steps>

## Tools

- `numactl --hardware` shows the nodes, their memory, and the **distance** matrix. A distance of 10 means local. Remote distances from 20 to 32 are typical.
- `numactl --cpunodebind=0 --membind=0 ./app` runs a program on node 0 with the memory of node 0. Other options are `--interleave=all` and `--preferred=N`.
- `numastat -p <pid>` shows where the pages of a process are.
- `mbind`, `set_mempolicy` and `move_pages` (libnuma) control the placement of each region from code.
- **Automatic NUMA balancing** (`/proc/sys/kernel/numa_balancing`): the kernel samples accesses and moves pages toward the threads that use them. It helps processes that run for a long time, but it has overhead. Pinning and correct first touch are more predictable.
- One socket can also be NUMA. Intel **Sub-NUMA Clustering** and AMD **NPS** settings divide one socket into several nodes. Each node then has a lower local latency, but software must place its data with more care.
