In the [five-stage pipeline](/architecture/pipelining/five-stage-pipeline), an instruction reads its registers in ID and writes its result in WB, three stages later. The next instruction is already in ID when the first one is in EX. So if it needs that result, the value is not in the register file yet. This is a **data hazard**.

```riscv
add  t0, a0, a1     # writes t0 in WB, cycle 5
sub  t1, t0, a2     # reads t0 in ID, cycle 3: too early
```

The hazard here is a **read after write (RAW)**: the younger instruction reads what the older one writes. It is a **true dependence**, because the value really flows from one instruction to the other. Two other orders exist in principle:

- **Write after read (WAR)**: a younger instruction writes a register before an older one has read it.
- **Write after write (WAW)**: two writes to one register finish in the wrong order.

Neither can happen in this pipe. Every instruction reads in ID and writes in WB, and instructions go through the stages strictly in order. So an older read always comes before a younger write, and writes happen in program order. WAW appears when instructions can finish out of order, for example behind a long divide. An in-order core then stalls the younger write.

WAR and WAW both appear when instructions issue out of order. Then the core uses register renaming (see [Register renaming](/architecture/ooo/register-renaming)).

## Stall, or forward

The simple fix is to **stall**: hold the younger instruction in ID until the older one has written back. The register file writes in the first half of a cycle and reads in the second half. So the user can read the value in the same cycle as the producer's WB. A distance of 1 instruction costs 2 stalls, a distance of 2 costs 1 stall, and a distance of 3 costs nothing.

But the value exists much earlier. An ALU result is ready at the end of EX, and it sits in the EX/MEM pipeline register for the next cycle. **Forwarding** (also called **bypassing**) adds multiplexers in front of the ALU. They take an operand from EX/MEM or MEM/WB in place of the stale value from ID/EX.

## The forwarding unit

The forwarding unit compares register numbers. It needs no values. For the first ALU operand, the conditions from Patterson and Hennessy are:

```verilog
// EX hazard: the instruction one ahead writes the register that we read.
wire fwd_a_exmem = exmem_regwrite && exmem_rd != 5'd0 && exmem_rd == idex_rs1;
// MEM hazard: the instruction two ahead writes it, and the one ahead does not.
wire fwd_a_memwb = memwb_regwrite && memwb_rd != 5'd0 && memwb_rd == idex_rs1 && !fwd_a_exmem;

always @(*) begin
  case ({fwd_a_exmem, fwd_a_memwb})
    2'b10:   alu_a = exmem_alu_result;   // the newest value wins
    2'b01:   alu_a = memwb_value;
    default: alu_a = idex_rs1_val;
  endcase
end
```

Three details matter:

- The test for `rd != 0` exists because `x0` is always 0. An instruction that writes `x0` must not forward its result.
- The newest value wins. In `add t0, ...; add t0, ...; sub t1, t0, ...`, the second add is the correct producer.
- The same logic repeats for the second operand. A real core also forwards into the store data path and into the branch comparator.

The **hazard detection unit** sits in ID and handles the case that forwarding cannot fix:

```verilog
// Load-use: the instruction in EX is a load, and we read its destination.
wire stall = idex_memread && idex_rd != 5'd0 && (idex_rd == ifid_rs1 || idex_rd == ifid_rs2);
// On stall: keep pc and IF/ID, and send a bubble into ID/EX.
```

## Forwarding on real programs

1. Keep **Linked-list walk**. With no forwarding, the 37 instructions take 90 cycles. Full forwarding cuts this to 71. The 16 stalls that remain are all load-use stalls: each loaded value is needed by the next instruction.
2. Select **memcpy, byte by byte**. Full forwarding gives 168 cycles in place of 222. The store `sb t1, 0(t0)` needs the byte that `lbu` loaded just before it. Select **Also MEM/WB → MEM**: 152 cycles, with no load-use stall at all.
3. Select **Dot product** and look at the arrows in the diagram. Most of the forwarding happens in a long chain: load, load, mul, add.
4. Compare the programs. The extra path to MEM helps only code where a store writes a value that was just loaded.

The cost of forwarding is in the wires and the multiplexers. Every ALU input needs a multiplexer with one input for each forwarding source. A wide superscalar core has many ALUs, and each one can be a source for every other one. So the bypass network grows much faster than the width. In fast cores, this network is often on the critical path, and some designs forward only between nearby units.

## When the load-use stall is the ISA's problem

The MIPS R2000 did not have a load-use interlock. Its manual says that the data from a load cannot be used in the following instruction. This is the **load delay slot**: the compiler had to put an independent instruction, or a `nop`, after each load. Later MIPS cores added the interlock, and RISC-V has always required the hardware to handle it. The cycle is still lost if nothing useful fills it. Only the responsibility moved.

<ArchPipeCompilerDemo />

1. Read the original order. It loads `b` and `e` and adds them at once: 1 stall. It loads `f` and adds it at once: 1 more stall. Total 16 cycles.
2. Select the line `lw t3, 16(a0)` and move it up, above `add t2, t0, t1`. Both stalls go away, and the block takes 14 cycles. This is the example from Patterson and Hennessy, chapter 4.
3. Now move `add t2, t0, t1` above `lw t1, 12(a0)`. The banner turns red: `t2` gets the wrong value, because `t1` is not loaded yet. The hart catches it.
4. Move a `sw` above the `add` that computes its value. The memory check fails, and the banner names the word that differs.

A compiler does this as **instruction scheduling**. It reorders instructions inside a block and never moves a user above its producer. GCC and LLVM use a model of the target pipeline for this. For example, `-mtune=sifive-7-series` gives GCC the latencies of SiFive's in-order cores. On an out-of-order core, the hardware reorders by itself, so the scheduling matters less. On an in-order core, it can matter a lot.

## What this means for your code

- On an in-order core, keep a loaded value away from its first use. Unrolling a loop gives the scheduler independent loads to put in the gap.
- Pointer chasing (`p = p->next`) is a chain of load-use hazards, and no compiler can break it. On any core, each step costs at least the full load latency, and much more on a cache miss.
- Forwarding makes a dependent ALU chain run at one instruction per cycle on a simple pipe. On a wide core, the same chain still runs at one per cycle, while the other units sit idle (see [Instruction-level parallelism](/performance/cpu/instruction-level-parallelism)).
