A [five-stage pipeline](/architecture/pipelining/five-stage-pipeline) finishes at most one instruction per cycle, so its CPI is at least 1. To go below 1, a core must start more than one instruction in a cycle. A **superscalar** core fetches, decodes and issues several instructions per cycle, through several copies of the pipeline. We then count **IPC**, instructions per cycle, the inverse of CPI. A core that issues up to $w$ instructions per cycle is **$w$-wide**.

The simplest form is **in-order dual issue**. The core fetches two consecutive instructions. If they can run together, both enter EX in the same cycle. If not, the older one goes alone, and the younger one waits for the next cycle. The order of the program never changes.

Real in-order dual-issue cores are common:

- The Intel Pentium (P5) had two integer pipes, U and V. The V pipe took only simple instructions, and Intel gave the pairing rules in section 3.6 of its optimization manual.
- The Arm Cortex-A53 is an in-order core with symmetric dual issue of most instructions (Cortex-A53 MPCore TRM).
- The SiFive U74, a 64-bit RISC-V core, has a dual-issue, in-order pipeline with a peak of two instructions per cycle (U74 Core Complex Manual).

## Pairing rules

Two instructions can issue together only if the hardware has room for both, and the second does not need the first. The shared model in these demos uses these rules:

- **Dependence**: the younger instruction must not read a register that the older one writes. Forwarding cannot help: in the same cycle, the value does not exist yet.
- **Ports**: one data memory port, so two loads or stores cannot pair. One multiplier, so two `mul` cannot pair.
- **Control**: a branch or jump ends the pair. The instruction after it may be on the wrong path.
- **Fetch**: both instructions come from the same fetch, so a taken branch also splits the stream.

The register file now needs 4 read ports and 2 write ports, and the forwarding network must feed both ALUs from both pipes.

## The limits of in-order width

Why not issue 4 or 8 instructions per cycle in order? Three limits get in the way:

- **Dependences**: real code has short chains. An in-order core can only pair neighbours, and neighbours often depend on each other.
- **Ports and fetch**: every extra slot needs register-file ports, bypass paths and decoders, and fetch must deliver a group of $w$ useful instructions. A taken branch ends the group.
- **Latency**: an in-order core can let a load miss and go on until an instruction needs the loaded value. It must then stop the whole pipe. Every younger instruction waits, even the independent ones.

The last limit is the important one. The model below runs RISC-V programs from the hart through an issue model that ignores pipeline stages. It compares an in-order core with an idealised out-of-order **window**: a core that can issue any instruction among the next $N$ whose operands are ready.

<ArchPipeWidthDemo />

1. Keep **y[i] = 3·x[i] + y[i]**, a 40-cycle miss and a window of 64. At width 4, the in-order core reaches an IPC of 0.96. The window reaches 1.92.
2. Move the miss latency down to 2 cycles: no real misses. The in-order core reaches 1.29 at width 4, and the window 2.98. Even without misses, in-order issue cannot find enough independent neighbours.
3. Move the miss latency to 200 cycles. The in-order IPC collapses. The window still overlaps the misses of several iterations, until the window itself is full.
4. Select **Linked list of 256 nodes**. Both cores sit at an IPC of about 0.1. Each load needs the address from the previous load, so no core can overlap the misses. Only a different data structure helps.
5. Make the window smaller, 16 instructions. It holds fewer iterations, so it overlaps fewer misses.

This is why fast general-purpose cores are out of order: they find independent work far beyond the next instruction. The [out-of-order module](/architecture/ooo/register-renaming) shows how. Renaming removes WAR and WAW hazards, and a reorder buffer keeps the program order for exceptions. A scheduler issues ready instructions from a large window. In-order cores stay where power and area matter more than single-thread speed: small cores in phones, microcontrollers and many RISC-V chips.

## VLIW: let the compiler issue

A third approach removes the pairing logic from the hardware. In a **VLIW** (very long instruction word) machine, the compiler packs independent operations into one wide instruction, one operation for each unit. The hardware issues the whole word without checks. Fisher's "Very Long Instruction Word Architectures and the ELI-512" (ISCA 1983) described the idea and the trace scheduling that feeds it.

Intel's Itanium (IA-64) used a related design called EPIC. Its instructions come in 128-bit **bundles** of three 41-bit slots and a 5-bit template (Itanium Architecture Software Developer's Manual, volume 1, section 3.3). The template tells the hardware which units the slots use, and where the groups of independent instructions end.

VLIW works well when the compiler knows the latencies, as in signal processing and many accelerators. It works badly for general code. The compiler cannot know which load will miss in the cache, so a static schedule stops on a miss, just like an in-order core. The binary also encodes one machine's latencies and widths. Itanium did not replace out-of-order x86 cores. VLIW lives on in DSPs and in parts of accelerators.

## What this means for your code

- On an in-order dual-issue core (Cortex-A53, SiFive U74), the instruction order the compiler picks matters. Build with the right `-mtune` or `-mcpu`.
- Independent work is the fuel for width. Several accumulators, unrolled loops and structure-of-arrays layouts give the core neighbours that can pair (see [Instruction-level parallelism](/performance/cpu/instruction-level-parallelism)).
- On any in-order core, a cache miss stops everything at the first use of the value. Prefetching (see [Prefetching](/architecture/caches/prefetching)) and data layouts that avoid pointer chasing matter more there than on an out-of-order core.
