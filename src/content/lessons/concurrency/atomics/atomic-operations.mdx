An atomic operation is one that no other thread can observe half-done. That single property removes a whole class of bugs, but it is narrower than it sounds. Atomicity is about *one* operation on *one* location. It says nothing about the order in which other memory becomes visible (that's the orderings lesson), and nothing about a sequence of operations taken together.

## What an atomic gives you

<Steps>
<div><b>No tearing.</b> A 64-bit atomic store is seen entirely or not at all, never as half old and half new bytes.</div>
<div><b>No data race.</b> Concurrent atomic accesses to the same location are defined behavior. Concurrent plain accesses where at least one writes are undefined behavior in C, C++, Rust and Zig.</div>
<div><b>One modification order per location.</b> All threads agree on the order of writes to a single atomic variable, and each thread's reads move forward through it (coherence).</div>
<div><b>Indivisible read-modify-write.</b> <code>fetch_add</code>, <code>exchange</code> and <code>compare_exchange</code> read and write as one step. No other write to that location can land in between.</div>
</Steps>

## How hardware does it

- **Plain loads and stores** of naturally aligned values up to the word size (8 bytes, sometimes 16) are already atomic on mainstream CPUs. An atomic load is often the same instruction as a normal load; what changes is what the *compiler* may do with it.
- **Read-modify-writes** need the cache line held exclusively for the duration. x86 uses `LOCK`-prefixed instructions (`lock xadd`, `lock cmpxchg`). ARM uses load-linked/store-conditional pairs (`ldxr`/`stxr`, which retry if another core touched the line) or, since ARMv8.1, single atomic instructions (`ldadd`, `cas`).
- **Contention is the cost.** Every RMW from a different core moves the line across the cache coherence fabric, tens of nanoseconds per transfer. One hot atomic counter updated by every core can be slower than a mutex-free per-thread counter by orders of magnitude. **False sharing** (two unrelated atomics on one 64-byte line) has the same cost without any real sharing.
- Types too large for hardware atomics fall back to a hidden lock. `std::atomic<T>::is_always_lock_free` tells you which you got.

## The same operation in your languages

| | Atomic increment, relaxed |
|---|---|
| C++ | `std::atomic<int> c; c.fetch_add(1, std::memory_order_relaxed);` |
| Rust | `static C: AtomicUsize = AtomicUsize::new(0); C.fetch_add(1, Ordering::Relaxed);` |
| Zig | `var c = std.atomic.Value(u32).init(0); _ = c.fetchAdd(1, .monotonic);` |
| Go | `var c atomic.Int64; c.Add(1)` (Go atomics are always sequentially consistent) |

Odin exposes the same operations and orderings through `intrinsics.atomic_*_explicit` and `core:sync`.
