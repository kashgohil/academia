An **atomic operation** is an operation that no other thread can see half-done. Other threads see the state before it or the state after it, never a state in the middle. This property removes a large class of bugs. But it is narrower than it sounds.

Atomicity applies to *one* operation on *one* memory location. It does not set the order in which other memory becomes visible to other threads. The lesson on memory orderings covers that. Atomicity also does not join a sequence of operations into one indivisible step.

Each thread loads `count` into a register, adds 1, and stores the result. You choose which thread runs its next step. The bars show the final result of every possible order of the steps.

1. On Thread 0, click **Run next step** three times. Then do the same on Thread 1. The result is `count = 2`, because one thread finished before the other started.
2. Click **Reset**. Run the load of Thread 0, then the load of Thread 1. Look at the dark bars: every order that remains now gives `count = 1`.
3. Look at the light bars. 18 of the 20 possible orders lose an update. Only the 2 orders where one thread finishes before the other starts give 2.
4. Select **3** threads. Only 6 of the 1680 orders give the correct value 3.
5. Select **one fetch_add**. Each thread now has one step, and every order gives the correct count.

The demo counts each order once. Real hardware does not pick all orders with equal probability. The time between the load and the store is usually short, so the bug can be rare. A rare bug is dangerous, because the tests pass and the program fails later in production.

## The same test in the litmus explorer

A **litmus test** is a small program that shows one behavior of a memory model. The explorer runs the program under every possible schedule. For the C++ column, it also tries every value that each load may legally return. Each row is a different final state.

<LitmusDemo presets={LESSON_PRESETS.atomics} />

1. **Counter: plain read + write** shows `count=1` and a **data race** banner. A data race is two accesses to one location from different threads, with no synchronization, where one writes and one is not atomic. With a plain `int` the program has undefined behavior, so even `count=1` is an optimistic result.
2. **Counter: atomic load, then atomic store** has no data race, but `count=1` is still possible.
3. **Counter: fetch_add** has one row, `count=2`, under all three models, even with `relaxed`.
4. **Coherence (CoRR)**: a relaxed load can read an old value, but the reads of one thread never go backwards. Add a third load to the test and check.

## Torn values

A value is **torn** when a reader sees part of an old value and part of a new value. Atomic accesses are never torn. A plain access can be torn when the CPU must split it into smaller accesses.

<TornValueDemo />

1. Run one writer step, then both reader steps. The reader gets `0x00000000_FFFFFFFF`. No thread ever wrote that value.
2. Look at the bars. The 6 possible orders give 4 different values, and 2 of those values are torn.
3. Select **one 64-bit atomic**. Each thread now has one step. Only the old value and the new value remain.

## What an atomic gives you

<Steps>
<div><b>No tearing.</b> A reader sees all of an atomic store or none of it. It never sees some old bytes and some new bytes.</div>
<div><b>No data race.</b> Concurrent atomic accesses to one location are defined behavior. Concurrent plain accesses, where at least one access writes, are undefined behavior in C, C++, Rust and Zig.</div>
<div><b>One modification order per location.</b> All threads agree on the order of the writes to one atomic variable. The reads of each thread move forward through that order. This property is called <b>coherence</b>.</div>
<div><b>Indivisible read-modify-write.</b> A <b>read-modify-write</b> (RMW) reads a value and writes a new value in one step. <code>fetch_add</code>, <code>exchange</code> and <code>compare_exchange</code> are RMWs. No other write to that location can occur between the read and the write.</div>
</Steps>

## How the hardware does it

- **Plain loads and stores** of naturally aligned values up to the word size (8 bytes, sometimes 16) are already atomic on mainstream CPUs. A value is **naturally aligned** when its address is a multiple of its size. An atomic load is often the same instruction as a normal load. The difference is what the *compiler* may do with it.
- **Read-modify-writes** must hold the cache line exclusively for the duration of the operation. x86 uses instructions with a `LOCK` prefix, such as `lock xadd` and `lock cmpxchg`.
- ARM uses **load-linked/store-conditional** (LL/SC) pairs, `ldxr` and `stxr`. The store-conditional fails if another core touched the line, and the loop tries again. Since ARMv8.1, ARM also has single atomic instructions, such as `ldadd` and `cas`.
- **Contention is the cost.** Contention means that many cores use the same location at the same time. Each RMW from a different core moves the cache line between cores, and each transfer takes tens of nanoseconds. One hot counter that every core updates can be orders of magnitude slower than one counter per thread.
- **False sharing** has the same cost without real sharing. It occurs when two unrelated atomics are on the same 64-byte cache line.
- A type that is too large for the hardware atomics falls back to a hidden lock. `std::atomic<T>::is_always_lock_free` tells you which one you got.

## The same operation in your languages

| | Atomic increment, relaxed |
|---|---|
| C++ | `std::atomic<int> c; c.fetch_add(1, std::memory_order_relaxed);` |
| Rust | `static C: AtomicUsize = AtomicUsize::new(0); C.fetch_add(1, Ordering::Relaxed);` |
| Zig | `var c = std.atomic.Value(u32).init(0); _ = c.fetchAdd(1, .monotonic);` |
| Go | `var c atomic.Int64; c.Add(1)` (Go atomics are always sequentially consistent) |

Odin gives the same operations and orderings through `intrinsics.atomic_*_explicit` and `core:sync`.
