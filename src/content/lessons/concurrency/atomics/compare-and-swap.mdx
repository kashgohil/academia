`compare_exchange(expected, desired)` is an atomic read-modify-write. If the value is still `expected`, it writes `desired` and reports success. If not, it writes nothing, reports failure and returns the current value. It does all of this in one indivisible step. The common name is **CAS** (compare-and-swap).

With CAS you can build any atomic update: a maximum, a push onto a linked list, or a change of state. Every lock-free data structure uses it. Herlihy proved that CAS is **universal**: it can implement any wait-free shared object for any number of threads. Plain loads and stores cannot do this.

## The retry loop

Every update with CAS has the same shape. Load the value and compute the new value from it. Then try the CAS. If the CAS fails, another thread changed the value first. The failed CAS gives you the current value, so you compute again and try again.

<CasLoopDemo />

1. Click **Run** once on each thread, so that all threads load `x = 1`. Then run Thread 0 again. Its CAS succeeds.
2. Run Thread 1. Its CAS fails, because `x` is not 1 now. The failed CAS also gives it the new value. Run it again, and it succeeds.
3. Look at **fewest / most attempts**. With 3 threads, the best order needs 3 attempts and the worst order needs 6. With 4 threads, the worst order needs 10.
4. Look at **final x**. It is the same for every order, because CAS never loses an update.
5. Select **x * 2**. C++ and Rust have no atomic multiply, and x86 and ARM have no instruction for it. A CAS loop can still do it.

Each failure means that another thread succeeded after your load. So with n threads, one thread can fail at most n − 1 times. In the worst order, the threads need n(n+1)/2 attempts in total. A `fetch_add` needs exactly n.

```rust
let mut cur = x.load(Ordering::Relaxed);
loop {
    let new = f(cur);
    match x.compare_exchange_weak(cur, new, Ordering::AcqRel, Ordering::Relaxed) {
        Ok(_) => break,
        Err(actual) => cur = actual, // another thread won; retry with the value it wrote
    }
}
```

```zig
var cur = x.load(.monotonic);
while (x.cmpxchgWeak(cur, f(cur), .acq_rel, .monotonic)) |actual| {
    cur = actual; // null means success; otherwise we get the current value back
}
```

- **Weak and strong.** `compare_exchange_weak` can fail **spuriously**, which means that it can fail when the value matched. On LL/SC machines such as ARM and RISC-V, the store-conditional fails if anything disturbed the cache line. Use weak inside a loop. Use strong for a single attempt.
- **Two orderings.** The first ordering applies on success, to the full read-modify-write. The second ordering applies on failure, which is only a load. The failure ordering cannot be `release`, because the CAS wrote nothing.

## The ABA problem

CAS compares values. It cannot see that a value changed from A to B and then back to A. In that case, the CAS succeeds when it should fail. This is the **ABA problem**. It breaks structures that hold pointers, when a node is freed and its memory is used again.

The demo shows a **Treiber stack**: a lock-free stack where `top` points to the first node. A pop reads `top` and `top.next`, then tries `CAS(top, old, next)`.

<AbaDemo />

1. Click **Set up the bad order**. Thread 0 read `old = A` and `next = B`. Then Thread 1 popped A, popped and freed B, and pushed A back.
2. Run Thread 0. Its CAS sees `top = A` and succeeds. Now `top` points to the freed node B.
3. Select **a pointer and a tag**. A **tag** is a counter stored next to the pointer, and every successful CAS adds 1 to it. Set up the bad order again, and run Thread 0 until it is done.
4. The CAS of Thread 0 fails, because the tag changed. Thread 0 reads fresh values and pops A correctly. Only C stays on the stack.
5. Click **Reset**. Run Thread 0 to the end before Thread 1 starts. There is no problem, because the operations do not overlap.

A tag is one common fix. It needs a double-width CAS, or spare bits in the pointer. The lock-free module also covers hazard pointers and epoch-based reclamation.

## Contention

<CasContentionDemo />

1. Move **Threads** from 1 to 16. The CAS attempts per increment grow.
2. Turn on **Exponential backoff**. After each failure, a thread waits a random time before it tries again, and the maximum wait doubles. The attempts drop.

Each failed CAS is wasted work. It is also one more transfer of the cache line between cores. In this simulation, the attempts per increment are 1.0 with one thread, about 2.7 with 8 threads and about 3.7 with 16 threads. With backoff, the numbers drop to about 2.0 and 2.4. On real hardware, each attempt also includes a transfer between cores, so the cost per increment grows faster still.

Practical rules:

- **Use a dedicated RMW** (`fetch_add`, `fetch_or`, `exchange`) when one exists. It cannot fail, and it is one instruction.
- **Test-and-test-and-set**: spin on a plain `load` until the lock looks free, and only *then* try the CAS. Many cores can share the cache line for loads, but every CAS needs it exclusively.
- **Back off** under contention. On x86, use a pause hint while you spin: `_mm_pause` in C, `std::hint::spin_loop()` in Rust, `std.atomic.spinLoopHint()` in Zig.
- **Shard** a hot counter: keep one counter per thread or per core, and add them together when you read.
