A **fence** is a memory-ordering instruction that is not attached to one atomic operation. In C++ it is `std::atomic_thread_fence`, and in Rust it is `std::sync::atomic::fence`. Zig removed `@fence` in version 0.14, so in Zig you put the ordering on the atomic operations. A fence makes the *relaxed* atomic operations around it stronger.

Fences are useful when one ordering point must cover many operations. They are also useful when you know only after a loop that you need acquire ordering.

## Where a fence must go

A fence orders the operations before it against the operations after it, in the same thread. So its position matters. In this demo, you put fences into the empty slots, and the memory-model explorer checks every outcome.

<FencePlacementDemo />

1. In **Message passing**, put `rel` between the two stores of the writer. The stale outcome is still possible in the C++ model.
2. Also put `acq` between the two loads of the reader. Now the outcome is forbidden, because the two fences pair up.
3. Move the fence of the writer below the flag store, or the fence of the reader above the flag load. The outcome comes back. A release fence must come before the store that carries it. An acquire fence must come after the load that carries it.
4. Look at the x86 result. x86 never shows this outcome, even with no fences. But the compiler can still reorder relaxed accesses, so you need the fences on every CPU.
5. Select **Store buffering**. Put `rel` and `acq` fences between the store and the load. The outcome stays possible. Only `sc` in both threads forbids it.

The text under each fence shows the instruction that GCC and Clang emit for it. On x86, acquire and release fences emit no instruction, because the hardware already gives that order.

## The rules

<Steps>
<div>Thread A does a <b>release fence F</b>, and then a relaxed store S. Thread B does a <b>relaxed load L</b> that reads the value of S, and then an <b>acquire fence G</b>. Then F synchronizes-with G. Everything that A did before F happens-before everything that B does after G.</div>
<div>Mixed pairs also work. A release fence can pair with an acquire load. A release store can pair with an acquire fence.</div>
<div>A <b>seq_cst fence</b> is both an acquire fence and a release fence. It also has a place in the single total order of all seq_cst operations. That extra part is what forbids store buffering.</div>
<div>A fence needs a relaxed atomic access to "carry" it to another thread. Without such an access, the fence does nothing across threads.</div>
</Steps>

## Why use a fence instead of stronger operations

- **Acquire once, after a loop.** Spin with relaxed loads, then pay for acquire ordering only once:

```rust
while !ready.load(Ordering::Relaxed) { std::hint::spin_loop(); }
fence(Ordering::Acquire); // synchronizes with the writer's release
```

- **Order many operations with one fence.** Publish several relaxed flags after one release fence.
- **Conditional synchronization.** The `Arc` type in Rust decrements its count with release ordering on every drop. Only the thread that sees the count reach zero does an acquire fence, and then it frees the object.
- **Dekker and hazard-pointer patterns** need the order "my store, then your load". That order needs a seq_cst fence on both sides.

## Hardware fences and compiler fences

- On x86, acquire and release fences cost nothing, because of TSO (total store order, the x86 memory model). A seq_cst fence is `mfence`, or a locked instruction.
- On ARMv8, a full fence is `dmb ish`. An acquire fence is `dmb ishld`, which orders loads before later loads and stores.
- A **compiler fence** stops the *compiler* from reordering, but it emits no instruction. Examples are `atomic_signal_fence` in C++, `compiler_fence` in Rust and `asm volatile("" ::: "memory")` in C.
- A compiler fence is correct only against a signal handler or an interrupt on the same core. It is never correct between threads.
- The Linux kernel uses other names for the same ideas: `smp_mb()`, `smp_wmb()`, `smp_rmb()`, `smp_store_release()` and `smp_load_acquire()`.
