All the ordering rules in this module build one relation: **happens-before**. If event A happens-before event B, then B sees the effects of A, or later effects. The relation decides two things. First, it decides which writes a read is allowed to see. Second, it decides if the program has a **data race**.

Two accesses **conflict** when they use the same location, at least one of them writes, and at least one of them is not atomic. A data race is two conflicting accesses that happens-before does not order. In C, C++, Rust and Zig, a data race is undefined behavior for the whole program. It is not only a wrong value.

Each box is one event. Grey arrows show program order inside a thread. A dashed arrow shows that a read took its value from a write. A green arrow is a **synchronizes-with** edge, which links two threads.

1. In **Two threads, one flag**, both flag operations are relaxed. The wait reads the value 1, but the arrow is dashed: it creates no edge. The plain accesses race.
2. Set the store to `release` and the wait to `acquire`. A green edge appears. Now a chain of edges leads from `data = 42` to `r0 = data`.
3. Set only one of the two to release or acquire. The green edge disappears. Release and acquire work only as a pair.
4. Select **Three threads, a chain**. Thread 2 never touches flag `a`. With all four orders set to release or acquire, it still reads `data` safely, because happens-before is transitive.
5. Compare **fetch_add in the middle** with **store in the middle**. A read-modify-write continues the **release sequence** of the first store, so the edge still goes from Thread 0 to Thread 2. An atomic store from another thread breaks it.
6. Click events to see their past. A **vector clock** is a list with one counter for each thread. A happens-before B exactly when the clock of B is at least the clock of A, in every position.

## How the relation is built

<Steps>
<div><b>Sequenced-before</b>: inside one thread, the program order.</div>
<div><b>Synchronizes-with</b>: a release operation (or fence) in thread A, and an acquire operation (or fence) in thread B. The acquire reads the value that A wrote, or a later value in its release sequence.</div>
<div><b>Release sequence</b>: the release write, followed by the read-modify-writes that read from it, one after another. An atomic store from another thread ends it. Before C++20, a store from the same thread also continued it.</div>
<div><b>Happens-before</b>: the transitive closure of the two edges. A happens-before B if a chain of sequenced-before and synchronizes-with edges leads from A to B.</div>
<div><b>Visibility</b>: a read sees the last write that happens-before it, or a write that is not ordered with it. The second case is legal only for atomics. This is where relaxed reads get their freedom.</div>
</Steps>

## The guarantee that makes this usable

**SC for DRF** means sequential consistency for data-race-free programs. If a program has no data races and uses only seq_cst atomics, every execution looks like a simple interleaving of the threads. You can then reason with the model of the "Seq. consistent" column. Weaker orders keep the "no race" part. They give up the "simple interleaving" part. That is the real trade when you write `relaxed`.

## Find races in practice

The explorer finds races in the same way as **ThreadSanitizer**. Each thread has a vector clock. A release/acquire pair merges the clock of the writer into the clock of the reader. An access races if the clock of the current thread does not cover the conflicting access.

- C and C++: `-fsanitize=thread`. Rust: `RUSTFLAGS="-Zsanitizer=thread"` on nightly. Go: `go test -race`. Zig: `-fsanitize-thread`.
- A sanitizer checks only the schedules that actually ran. A **model checker** explores *all* schedules, as the explorer here does. Examples are **loom** (Rust), **GenMC** and **CDSChecker** (C and C++), and TLA+ for designs.
- The Rust type system prevents data races on safe references at compile time, with `Send` and `Sync`. Ordering mistakes between atomics are still possible.
