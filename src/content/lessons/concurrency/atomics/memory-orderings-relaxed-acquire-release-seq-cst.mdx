Inside one thread, code appears to run in program order. Across threads, it does not. Compilers reorder memory operations that do not depend on each other. CPUs execute instructions out of order, and they let a load pass a store that waits in a buffer. On some architectures, different cores see writes in different orders.

A **memory order** on an atomic operation tells the compiler and the CPU which reorderings to prevent. So it also tells them which instructions to emit.

1. **Message passing, relaxed**: the C++ model lets the reader see the flag but old data. x86 never does this, because TSO keeps stores in order. ARM and POWER can do it, and so can the compiler.
2. **Message passing, release/acquire**: the stale outcome disappears. This pattern is the base of every lock, every queue and `Arc`.

4. **IRIW** (independent reads of independent writes): with acquire loads, two readers can disagree about which of two writes occurred first. With seq_cst, all threads agree on one global order again.
5. **Coherence**: no ordering lets the value of one location go backwards.

## See the store buffer

A **store buffer** is a small queue in each core. A store waits there before it goes to the cache, and the core continues without waiting. A later load on the same core can read memory before the store leaves the buffer. This is how both threads can read 0 in store buffering.

1. Click **Run** on Core 0, Core 1, Core 0 and Core 1. Both stores wait in the buffers, and both loads read 0 from memory. Then drain both buffers. The result `r0=0 r1=0` is not sequentially consistent.
2. Click **Reset**. This time, click **Drain** right after each store. The result is now one that an interleaving gives. On x86 this program has 4 possible outcomes, but under sequential consistency only 3.
3. Select **Store buffering, seq_cst**. The store becomes `xchg`, which drains the buffer first. The fourth outcome is gone.
4. Select **Message passing, relaxed**. Try to get `r0=1 r1=0`. You cannot, because the buffer drains the oldest store first. x86 keeps stores in order.

The model in this demo is **x86-TSO** (total store order), the memory model of x86. ARM and POWER allow more reorderings than TSO. The litmus explorer shows them in the C++ column.

## The four orders

| Order | Guarantees | Typical use |
|---|---|---|
| `relaxed` | atomicity and per-location coherence only | counters, statistics, flags that do not publish data |
| `release` (stores) | everything before it in this thread is visible to a thread that acquires this value | publishing data, unlocking |
| `acquire` (loads) | everything after it sees what the releasing thread wrote before its release | consuming data, locking |
| `acq_rel` (RMWs) | both, on one read-modify-write | lock-free updates that both consume and publish |
| `seq_cst` | acquire and release, plus one total order of all seq_cst operations that every thread agrees on | the default; Dekker-style "I write, then check yours" logic |

Release and acquire work as a **pair**: a release store, and an acquire load that reads the value it wrote. One of them alone orders nothing across threads.

## What it compiles to

| | x86-64 | ARMv8 |
|---|---|---|
| relaxed / acquire load | `mov` | `ldr` / `ldar` (or `ldapr`) |
| relaxed / release store | `mov` | `str` / `stlr` |
| seq_cst store | `xchg` (or `mov` + `mfence`) | `stlr` |
| RMW (any order) | `lock xadd`, `lock cmpxchg` | `ldadd`/`cas` variants, or LL/SC loops |

On x86, everything except seq_cst stores is free at the hardware level, because TSO already gives acquire and release. That is why relaxed-ordering bugs often hide on x86. They appear on ARM: phones, Apple silicon and AWS Graviton. The *compiler* can still reorder relaxed accesses on every architecture.

<Callout title="What this simulator shows and does not show">
The C++ column is an operational model. Each thread keeps a view of memory, a release write carries the view of its thread, and an acquire read merges that view. It reproduces the standard results for MP, SB, IRIW, coherence and fences. It does not produce "load buffering" outcomes, where both threads read the *later* writes of each other. The C++ standard allows them, but no mainstream hardware shows them. The model also puts relaxed writes in execution order. ARMv8 is "multi-copy atomic", so real ARM forbids the IRIW outcome that the C++ model allows, but POWER allows it.
</Callout>

## How to choose

1. **Start with seq_cst.** It is the default everywhere, and the only option in Go. It is correct for any reasoning about a data-race-free program as interleavings.
2. **Use release/acquire** for pairs that publish and consume data: flags, queues and reference counts that drop to zero. Use it only after you can name the pair.
3. **Use relaxed** only when no other memory depends on the value: statistics, counters for unique IDs, and the increment (not the decrement) of a reference count.
4. **Treat `consume` as acquire.** Every major compiler already does this.
