Hazard pointers protect single nodes. **Epoch-based reclamation** (EBR, Keir Fraser, 2004) protects *periods of time* instead. A global counter, the **epoch**, advances slowly. When a thread starts an operation, it **pins** itself: it announces "I am active in epoch e". When the operation ends, the thread unpins.

A thread that removes a node puts it on the **limbo list** of the current global epoch. A limbo list holds removed nodes that wait to be freed. The global epoch can move from e to e + 1 only when every pinned thread announced e. When the global epoch reaches e + 2, every pinned thread pinned after the removal. So no thread can hold a node from the list of epoch e, and the whole list is freed in one batch.

Three limbo lists are enough. Only the lists of the current and the previous epoch hold nodes. The third list was freed when the epoch last moved, and it becomes the list of the next epoch.

## Watch the epochs

<EpochRingDemo />

1. Watch the arrow in the center: it points to the global epoch. The epoch moves only when every pinned thread announced the current epoch. One thread in the previous sector holds it back.
2. Watch a sector when the epoch moves two steps past it. Its nodes are freed in one batch. With 4 threads, at most 9 nodes wait during this run.
3. Turn on **T0 stalls while pinned**. The global epoch reaches 1 and stops there. No node is ever freed, and after 300 steps, 99 nodes wait.
4. Change the number of threads. More threads must catch up before each move, so more nodes wait. With 2 threads, at most 5 nodes wait. With 6 threads, at most 16 nodes wait.

## Step through it

In this stepper, each thread keeps its own three bags. A bag is a limbo list that belongs to one thread.

<LockFreeStepper title="Treiber stack with epoch-based reclamation" scenario={EBR} scripts={EBR_SCRIPTS} scheme="epoch" />

1. Run **T0 pinned while T1 retires three nodes**. The first advance succeeds, because T0 announced the current epoch 0. The next attempt stops at `check T0's epoch`, because T0 is still in epoch 0. The global epoch stays at 1, and the three nodes of T1 stay in its bags.
2. Reset. Run the whole pop of T0 first, then the three pops of T1. No thread is pinned in an old epoch, so the advance attempts of T1 succeed, and the global epoch reaches 2. The bags are still not freed at the end. A thread frees its old bags only when it pins again in a later epoch.
3. Count the steps for each operation, and compare them with hazard pointers. There is a pin, an unpin and sometimes an attempt to advance. There is **no fence for each node** that the thread visits.

## Correctness and cost

<StressDemo configs={STRESS_EBR} />

| | Hazard pointers | Epoch-based |
|---|---|---|
| Cost for readers | a store and a fence for each protected pointer | one announcement for each *operation* |
| Long traversals | expensive | cheap: one pin covers any number of nodes |
| Memory that waits | bounded | unbounded if a thread stalls while pinned |
| Freeing | scans for each thread | in batches, by epoch |

This trade-off decides most real choices. EBR suits data structures with short operations, where threads do not block inside an operation. In Rust, the crossbeam-epoch crate is the base of crossbeam-deque, which Rayon uses, and of crossbeam-skiplist. Linux RCU uses the same idea with **quiescent states** instead of explicit epochs. A context switch is a quiescent state: after it, a CPU holds no pointers that RCU protects.

Hazard pointers suit long-lived readers and systems that must limit memory. Hybrid schemes, such as hazard eras and interval-based reclamation, try to get the speed of EBR with bounded memory.
