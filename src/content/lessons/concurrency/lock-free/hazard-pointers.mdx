The last two lessons showed the problem. A thread holds the address of a node, and another thread can free that node at any moment. **Hazard pointers** (Maged Michael, 2004) make this holding visible. Each thread owns a few shared slots, called **hazard slots**. Before a thread uses a node, it writes the address of the node into one of its slots. A thread that wants to free nodes first reads every slot, and it keeps each node that a slot names.

2. Select **Hazard pointers** and run the same script. The steps of T0 now include `hazard[0] = A` and the check. When T1 has retired two nodes, it scans. It finds A in the slot of T0, so it frees only B.
3. Watch the **retired** list of each thread. A retired node was removed from the stack but is not freed yet. It waits on the list until a scan proves that no slot names it.

## The scan

1. Watch one scan. T0 reads the slots of each thread in turn. A node that a slot names turns orange and stays on the list. T0 frees all the other nodes.
2. Select **Stall forever**. Each reader protects two nodes and then stops. Those nodes stay on the list for ever, but T0 frees every other node. With R = 12, the list never holds more than 12 nodes.
3. Move R down to 8. In the worst case, a scan now frees nothing, because 8 slots can protect all 8 nodes. The slot reads per freed node go up.
4. Move R up to 16. A scan still reads 8 slots, but it frees at least 8 nodes. That is at most 1 slot read for each freed node.

## The protocol

<Steps>
<div><b>Protect</b>: <code>p = head.load(); hazard[i].store(p, SeqCst); if head.load() != p, retry</code>. This store and the load after it form the store-buffering pattern from the memory-ordering lesson. Without seq_cst, the scan of the reclaimer and the check of the reader can both miss each other.</div>
<div><b>Use</b>: read <code>p</code> freely while it stays in the slot.</div>
<div><b>Retire</b>: after a thread removes a node, it puts the node on its own retired list. It does not free the node yet.</div>
<div><b>Scan</b>: when the list reaches a threshold R, read the hazard slots of every thread. Free each retired node that no slot names.</div>
</Steps>

## Costs and guarantees

<StressDemo configs={STRESS_HP} />

- **Correct**: the stress test finds no violations for the stack or the queue. Hazard pointers also solve ABA, because nobody can free and reuse a protected node.
- **Bounded memory**: at most $H \times T$ nodes are protected, with $H$ slots for each of $T$ threads. So the retired list of each thread stays below about $R + H \cdot T$, *even if another thread stalls forever*. This is the main advantage over epoch-based reclamation (next lesson).
- **Cost for each access**: each protected pointer needs a store, a full fence and a second load. This is acceptable for occasional accesses. It is expensive when a thread walks a long list node by node.
- **Scan cost**: if $R$ is proportional to $H \cdot T$, a scan costs $O(1)$ per retired node on average. For example, $R = 2 \cdot H \cdot T$ gives at most 1 slot read for each freed node. Real scans sort or hash the set of hazard pointers to look up nodes fast.

C++26 adds `std::hazard_pointer`, based on the Folly library of Meta. Rust has the `haphazard` crate.
