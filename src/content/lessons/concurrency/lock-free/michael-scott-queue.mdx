A queue has two ends, so a lock-free queue must keep two pointers consistent. But a CAS changes only one word at a time. Maged Michael and Michael Scott published a solution in 1996. Java's `ConcurrentLinkedQueue` and many other queues use it. The design has two ideas:

- **A dummy node.** `head` always points to a node whose value was already taken. The first real element is `head.next`. So enqueue and dequeue never change the same pointer, even when the queue holds one element.
- **A lagging tail, plus helping.** An enqueue needs *two* CAS operations. The first CAS links the new node after the last node. The second CAS moves `tail` to the new node. Another thread can run between them and find that `tail.next` is not null. That thread does not wait: it **helps**, which means that it moves `tail` forward itself and then continues.

2. Reset and step a dequeue yourself. The value comes from `head.next`, and the old dummy is retired. The node whose value was just taken becomes the new dummy.
3. Step a dequeue while `head == tail` and an enqueue is half done. The dequeuer first helps to move `tail`, and only then can it continue. So `head` never passes `tail`.

## Watch the tail lag

1. Keep **Enqueuer stalls**. T0 links C, but tail stays on B. The tail label turns red: tail is 1 node behind. T1 moves tail to C and then does its own enqueue. Later, the tail CAS of T0 fails, and the queue is still correct.
2. Select **Dequeuer helps**. The queue is empty, and T0 stalls after its link. T1 wants to dequeue, but head and tail both point to the dummy. T1 first moves tail and then takes 10, so head never passes tail.
3. Select **No stall**. Each enqueue does its two CAS operations one after the other. Tail is behind only between them, and no thread helps.
4. Watch the old dummy nodes. After each dequeue, the node that held the value becomes the new dummy. The old dummy leaves the queue and is retired.

## The invariants

<Steps>
<div>The list from <code>head</code> is never broken. Nodes are only added at the end, with a CAS on the last <code>next</code> from null. Nodes are only removed at the front, with a CAS on <code>head</code>.</div>
<div><code>tail</code> points to the last node or to the node before it. So it lags by at most one node, and any thread that sees the lag fixes it.</div>
<div><code>head</code> never passes <code>tail</code>. A dequeuer that sees <code>head == tail</code> and a <code>next</code> that is not null first helps to move <code>tail</code>.</div>
<div>Linearization points: a successful enqueue takes effect at its CAS on <code>last.next</code>. A successful dequeue takes effect at its CAS on <code>head</code>.</div>
</Steps>

The stepper checks the first three invariants after every step. At the end, it also checks that each value came out exactly once, in FIFO order.

## Memory reclamation, again

<StressDemo configs={STRESS_MSQ} />

The queue reads `head.next` and `tail.next` through pointers that other threads can retire. So it needs a reclamation scheme. With hazard pointers, a dequeue needs *two* slots: one for `head` and one for `head.next`. The second slot is valid only after a new check of `head`. Select hazard pointers in the stepper and look for `hazard[1]`.

## In practice

- **Contention on two hot pointers** limits how far the queue scales. Production queues often use arrays and ring buffers, such as the bounded MPMC queue of Vyukov or the LMAX Disruptor. Others link segments of arrays, such as the `SegQueue` of crossbeam. Both touch fewer cache lines for each operation.
- **Variants with a single producer or a single consumer** remove most atomic operations and are much faster. Use the most restricted variant that your design allows.
- **Helping** is a general technique. If an operation is visible in an intermediate state, design it so that any thread can finish it. This is how lock-free structures avoid waiting for stalled threads.
