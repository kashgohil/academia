A CAS asks one question: is the value still the value that I saw? The real question is different: did *anything* change since I looked? The two questions have different answers when a value goes **A → B → A**. With pointers, this happens easily. A thread pops a node and frees it, and the allocator gives the same address to a new node. For the CAS, head is "still A".

1. Run **Play the ABA schedule** without tags. Watch the free list: the node that was freed last is the next node that the allocator gives out. Real allocators do the same. The checks panel reports that values 1 and 8 are lost or returned twice.
2. Turn on **tagged pointers** and run the script again. Now `head` also holds a version number, and every successful CAS increments it. T0 saw `A·v0`, but head is `A·v4` at the CAS. So the CAS fails, T0 tries again, and it pops 8 correctly.
3. With tags, step through T0 slowly. T0 still **reads A.next after A was freed** before its CAS fails. This is a use-after-free: a read of memory that was already freed.

1. Move the slider from 0 to 4. Only position 4 breaks the stack. T0 returns 1, which T1 also returned, and 8 is lost.
2. At position 4, click the steps one by one. Watch the freed nodes and the next allocations. The allocator gives out the newest freed node first, so A comes back.

4. Turn on **tagged pointers**. Now no position breaks the stack, with either allocator.

## How common is it?

<StressDemo configs={STRESS_ABA} />

Under random schedules, immediate free causes a violation in most runs. Most violations are use-after-free reads. Some runs also lose or duplicate values, corrupt the list or free a node twice. Tags remove every *logical* failure, but the use-after-free reads stay. In this simulation, a freed node is still mapped memory, so the stale read does no harm.

A real program is different. The allocator can return the page to the operating system, and the read then causes a segmentation fault. Or the allocator can reuse the memory for a different type, and the thread reads garbage and acts on it.

## Where can the tag live?

A **tagged pointer** puts a version counter next to the pointer, and the CAS compares both. The counter needs bits, and there are three usual places for them.

<TagBitsDemo />

1. With **4 low bits**, click **Set to 2^4**. After 16 changes, the tag is 0 again. If the address is also A again, the CAS cannot see the change.
2. Select **16 high bits**. The tag repeats only after 65,536 changes. A thread that sleeps for a long time can still miss exactly that number of changes, but it is much less likely.
3. Select **Second word**. A 64-bit counter does not wrap in practice.

## Fixes and their limits

| Fix | How | Limit |
|---|---|---|
| **Tagged pointers** | CAS a (pointer, counter) pair: `cmpxchg16b` on x86-64, or put the counter in unused pointer bits (16 high bits with 48-bit addresses, or low bits from alignment) | does not stop reads of freed memory; a small counter can wrap |
| **LL/SC** | ARM `ldxr`/`stxr`: the store fails if any thread wrote the cache line, so the location itself has no ABA | not available in portable code; C++ and Rust give you CAS |
| **Type-stable memory** | never return nodes to the general allocator; reuse them only as nodes (for example, a pool) | still needs tags; the memory never goes back to the system |
| **Safe memory reclamation** | do not reuse a node while a thread can still hold its address: hazard pointers, epochs, RCU | extra work in each operation (next two lessons) |
| **Garbage collection** | the address cannot be reused while a reference exists | not available in C, C++, Rust or Zig without a library |

The robust answer is safe memory reclamation. If no thread frees a node while another thread can hold its address, the address cannot come back as "A". So reclamation fixes ABA and use-after-free together.
