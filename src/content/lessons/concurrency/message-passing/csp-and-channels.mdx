Threads can cooperate in two ways. They can share memory and protect it with [locks](/os/sync/locks-and-spinlocks). Or they can keep their data private and send messages to each other. This module is about the second way.

In 1978 Tony Hoare published "Communicating Sequential Processes" (CSP) in the Communications of the ACM. In CSP, a program is a set of sequential processes that share no variables. A process can do only two things with another process: send it a value (`P!x`) or receive a value from it (`P?y`). Both sides of a CSP communication wait for each other. This meeting is a **rendezvous**: the value moves only when the sender and the receiver are both ready.

Hoare's 1985 book turned CSP into a process algebra with a full theory of traces and refinement. The occam language on the Inmos transputer used CSP as its model. Rob Pike carried the ideas through Newsqueak and Limbo into Go. Effective Go states the result as a slogan: "Do not communicate by sharing memory; instead, share memory by communicating."

A **channel** is the object that carries the messages. Hoare's first paper named processes directly, but later CSP and Go use channels: anonymous, typed queues that any process with a reference can use. A channel has a **capacity** C. With C = 0 it is a rendezvous, as in Hoare's paper. With C > 0 it has a buffer: a send waits only when C values are already in it.

## What a buffer buys

A pipeline of two stages cannot be faster than its slower stage. If the consumer needs 30 µs per item, 24 items need at least 720 µs, whatever the channel. A buffer does not add capacity. It only lets the faster side run ahead by up to C items, and then that side blocks.

A buffer is useful in two cases. First, when both sides have the same mean speed but each item takes a random time, the buffer absorbs the differences. Without it, a slow item on one side makes the other side wait, and that time is lost. Second, a buffer reduces the number of times a thread must block and wake up. Each wake-up costs a context switch, which is a model input of a few µs for an OS thread.

A big buffer has a cost too. When the consumer is slower, the buffer is always full. Each item then waits behind C others, so its latency grows by C × 30 µs, and nothing gets faster. The lesson on [backpressure](/concurrency/message-passing/backpressure) shows this cost under overload.

## What a channel orders

A channel moves a value, and it also orders memory. The [Go memory model](/concurrency/atomics/happens-before) states four rules for channels:

| Rule | Edge |
|---|---|
| Send | A send is synchronized before the completion of the corresponding receive |
| Close | A close is synchronized before a receive that returns a zero value because the channel is closed |
| Unbuffered | A receive from an unbuffered channel is synchronized before the completion of the corresponding send |
| Capacity C | The kth receive is synchronized before the completion of the (k+C)th send |

The first rule makes message passing safe. Everything that the sender wrote before the send is visible to the receiver after the receive. The second rule lets a close act as a broadcast signal to every receiver.

The third and fourth rules go the other way, from the receiver to the sender. With C = 0, a completed send tells the sender that the receiver has the value. With C > 0, the sender learns less: when send k + C completes, receive k has happened. So a sender can be at most C values ahead of its receiver.

The capacity rule has a famous use: a buffered channel is a counting semaphore. A send takes a token, and a receive returns it. So at most C goroutines run the protected code at the same time.

```go
var sem = make(chan struct{}, 8) // at most 8 requests run at once

func handle(r *Request) {
    sem <- struct{}{}        // wait for a free slot
    defer func() { <-sem }() // give the slot back
    process(r)
}
```

## Ownership moves with the message

A channel orders the handoff, not later use. Suppose that a producer sends a pointer to a buffer, and then writes to that buffer again. The send happens before the receive, but the second write has no edge to the consumer's read. This is a data race, even though every access went through a channel.

So the rule of message passing is a rule of **ownership**. After a send, the sender must not touch the value again. The receiver owns it. Go cannot check this rule at compile time. The race detector (`go test -race`) finds a violation only when the racy code runs.

Rust checks it in the compiler. `Sender::send` takes the value by move, so the sender has no name for it after the call. A `Sender` can move to another thread only if the value type is `Send`, which means that it is safe to move to another thread. An `Rc` is not `Send`, so you cannot pass an `Rc` to another thread this way.

```rust
use std::sync::mpsc;
let (tx, rx) = mpsc::sync_channel::<Vec<u8>>(0); // capacity 0: a rendezvous
std::thread::spawn(move || {
    let mut buf = vec![1, 2, 3];
    tx.send(buf).unwrap();
    // buf.push(4); // error[E0382]: borrow of moved value: `buf`
});
let got = rx.recv().unwrap();
```

## Channels in other languages

| Language and library | Channel | Capacity 0 | Notes |
|---|---|---|---|
| Go | `chan T`, `make(chan T, n)` | yes, the default | Many senders and receivers. `select` waits on several channels |
| Rust std | `mpsc::channel`, `mpsc::sync_channel(n)` | `sync_channel(0)` | One receiver. Since Rust 1.67 its code comes from crossbeam-channel |
| Rust crossbeam | `bounded(n)`, `unbounded()` | `bounded(0)` | Many receivers, and a `select!` macro |
| Rust Tokio | `tokio::sync::mpsc::channel(n)` | no: 0 panics | `send` is async and waits for capacity |
| Odin | `core:sync/chan` | yes | Buffered and unbuffered channels, and a select |
| occam | `CHAN OF INT c:` | the only kind | Pure CSP: `c ! x` and `c ? y` |

Zig removed `std.event` and its channel in 0.12, after async functions stopped working in 0.11. Zig 0.16 added `std.Io.Queue`, a bounded queue that can be closed.

Channels are not free of the problems of locks. Two processes that each wait to receive from the other are in a [deadlock](/os/sync/deadlock). When every goroutine waits, the Go runtime reports "all goroutines are asleep". A channel also hides a queue, and a queue needs a policy for when it is full. The next lessons take these problems one at a time.
