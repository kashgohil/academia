A fork-join program makes tasks at run time, and nobody knows in advance how long each task takes. A scheduler must give these tasks to P workers (threads, one per core). It must keep every worker busy, and it must not make the workers wait for each other while it does that.

**Work stealing** solves this with one data structure per worker: a **deque**, a double-ended queue. A worker pushes the tasks that it creates at the **bottom** of its own deque and pops its next task from the bottom too. When its deque is empty, the worker becomes a **thief**. It picks another worker, the **victim**, and takes the task at the **top** of the victim's deque. Cilk, Rayon and Java's `ForkJoinPool` use this design. Go and Tokio use a variant with bounded FIFO queues, described below.

## Why the two ends matter

The owner works at the bottom, in **LIFO** order (last in, first out). So it runs the task that it created last: the smallest, most recent piece of its current subproblem. This is depth-first order. It has three effects:

- **Memory.** The deque holds at most one pending task per level of the split tree. In the next demo, 65,536 items with a grain of 256 need at most 8 levels. With LIFO, the longest deque is 7 tasks. With FIFO, the owner runs breadth-first and the longest deque is 23 tasks.
- **Locality.** The newest task works on data that the owner touched a moment ago. That data is still in its cache.
- **Few conflicts.** The owner and the thieves work at different ends. They compete only when one task is left.

Thieves work at the top, in FIFO order. The oldest task is the largest one, so a thief gets much work with one steal. Blumofe and Leiserson ("Scheduling Multithreaded Computations by Work Stealing", J. ACM 1999) prove that a randomized work-stealing scheduler runs a fully strict computation in expected time $T_1/P + O(T_\infty)$. That is Brent's bound from the [fork-join lesson](/concurrency/patterns/fork-join), up to a constant factor on the span. The expected number of steal attempts is $O(P \cdot T_\infty)$, which does not depend on the work.

## The deque itself

A work-stealing deque must let the owner push and pop without a lock, because the owner does that for every task. Thieves can pay more. Arora, Blumofe and Plaxton (SPAA 1998) gave the first non-blocking deque of this kind. Chase and Lev ("Dynamic Circular Work-Stealing Deque", SPAA 2005) made it a circular array that can grow. Lê, Pop, Cohen and Zappa Nardelli (PPoPP 2013) gave a portable C11 version with explicit memory orders. They proved an optimized version correct on the POWER and ARM memory models.

```cpp
// After Lê et al. 2013, simplified: grow() is not shown.
void push(Task* x) {                       // owner only
    long b = bottom.load(relaxed), t = top.load(acquire);
    if (b - t == N) grow();                // the real deque copies to a larger buffer
    buf[b % N].store(x, relaxed);
    atomic_thread_fence(release);
    bottom.store(b + 1, relaxed);
}
Task* pop() {                              // owner only
    long b = bottom.load(relaxed) - 1;
    bottom.store(b, relaxed);
    atomic_thread_fence(seq_cst);          // the store to bottom must be seen before top is read
    long t = top.load(relaxed);
    if (t > b) { bottom.store(b + 1, relaxed); return nullptr; }       // empty
    Task* x = buf[b % N].load(relaxed);
    if (t == b) {                          // the last task: race with thieves for it
        if (!top.compare_exchange_strong(t, t + 1, seq_cst, relaxed)) x = nullptr;
        bottom.store(b + 1, relaxed);
    }
    return x;
}
Task* steal() {                            // any thief
    long t = top.load(acquire);
    atomic_thread_fence(seq_cst);
    long b = bottom.load(acquire);
    if (t >= b) return nullptr;            // empty
    Task* x = buf[t % N].load(relaxed);
    if (!top.compare_exchange_strong(t, t + 1, seq_cst, relaxed)) return RETRY;
    return x;
}
```

The owner's fast path has no compare-and-swap (CAS). Only the last task needs a CAS, because the owner and a thief can both want it. Thieves always CAS on `top`, so two thieves cannot take the same task. The `seq_cst` fence in `pop` is the expensive part. Without it, the owner and a thief can each miss the other's update, and both take the last task. Rust's `crossbeam-deque` implements this deque, and its `Worker::new_lifo`, `Worker::new_fifo` and `Stealer::steal` match the two ends.

## Work-first and help-first

When a task spawns a child, a runtime can run the child at once and leave the **continuation** (the rest of the parent) for thieves. This is the work-first policy of Cilk. Or it can push the child and keep running the parent: the help-first policy. Rayon's `join(a, b)` is close to help-first: it pushes `b`, runs `a`, then pops `b` if no thief took it. Guo, Barik, Raman and Sarkar (IPDPS 2009) compare the two. Help-first works better when one parent spawns many children in a loop, because thieves then find the children at once.

A join that finds its child stolen must not block the worker. Rayon's worker runs other tasks while it waits for the thief. Java's `ForkJoinTask.join` also runs other tasks while it waits.

## Real schedulers

| Runtime | Local queue | Other sources of work | Steal |
|---|---|---|---|
| Go (`proc.go`, go1.25) | 256 goroutines per P, plus one `runnext` slot | global run queue, checked when `schedtick % 61 == 0`; a full local queue moves half of it there | half of the victim's queue; up to 4 passes over all Ps in random order |
| Tokio multi-thread (1.54) | 256 tasks, plus a LIFO slot for a task woken by the current one | an injection queue; the check interval tunes itself (since 1.29) | half of the victim's queue; the LIFO slot cannot be stolen |
| Rayon | a Chase-Lev deque per worker (`crossbeam-deque`) | a global injector queue for jobs from outside the pool | one job from the top |
| Java `ForkJoinPool` | a deque per worker; `asyncMode` makes it FIFO for tasks that are never joined | shared submission queues; the common pool has max(1, CPUs − 1) workers | from the top |

Go and Tokio do not use a Chase-Lev deque. Their local queues are bounded FIFO rings, and the owner and thieves both take from the head. Only the `runnext` slot or the LIFO slot gives LIFO order for the newest task.

The `runnext` slot and Tokio's LIFO slot solve one problem. A task that wakes another task, as in a channel send, should hand over the core at once. Go steals the `runnext` goroutine only on the last of its 4 passes, and only when the victim's queue is empty. If the victim is running, the thief first sleeps for about 3 µs. Then a quick send and receive can finish on the victim's P. On Windows, OpenBSD and NetBSD it yields instead.

The check of the global queue every 61 ticks stops the local queues from starving goroutines in the global queue.

## When work stealing breaks

- **Too few tasks.** With fewer tasks than workers, or a few huge ones, there is nothing to steal.
- **Blocking tasks.** A task that blocks in a system call or on a lock holds its worker. Go hands its P to another thread. Tokio has `spawn_blocking` for this.
- **Locality across sockets.** A random victim can sit on another NUMA node. Some runtimes try nearby victims first (see [NUMA](/architecture/multicore/numa)).
- **Idle spinning.** Thieves that find nothing burn CPU. Real runtimes park idle workers after a few failed rounds and wake them when new work arrives.
