A test of concurrent code runs one schedule, chosen by the operating system. A bug that needs a rare order of steps can pass a million runs and then fail in production. A **model checker** removes the luck. It explores every reachable state of a model of the program and checks a property in each one.

Edmund Clarke and Allen Emerson introduced model checking at Harvard in 1981, and Jean-Pierre Queille and Joseph Sifakis developed a similar method independently in 1982. Clarke, Emerson and Sifakis shared the 2007 ACM Turing Award for it. For a concurrent program, a **state** is the memory plus the program counter and registers of each thread. A **transition** is one atomic step of one thread. The explorer of the [critical sections lesson](/os/sync/critical-sections) is a small model checker of this kind.

A model checker can check two kinds of property. A **safety** property says that a bad state never occurs. Examples are a failed assertion, two threads in a critical section, or a deadlock. A counterexample is a finite schedule. A **liveness** property says that something good eventually occurs. Its counterexample is an infinite run, such as a loop in which a thread never gets the lock.

## Why it explodes

With n threads of k steps each, a schedule chooses positions for each thread's steps:

$$
\frac{(nk)!}{(k!)^n}
$$

For 3 threads of 4 steps this is 34,650, and for 4 threads of 6 steps it is 2,308,743,493,056. Real programs have loops, so the steps per thread are not even fixed. This growth is the **state explosion problem**, and every tool below is a way to fight it.

## Fight 1: remember states

Many schedules reach the same state. An **explicit-state** model checker keeps a hash table of visited states and does not explore a state twice. If each thread writes only its own variable, a state is just the n program counters, so there are $(k+1)^n$ states. That is 125 for 3 threads of 4 steps, against 34,650 schedules.

SPIN, by Gerard Holzmann at Bell Labs, works this way on models in its language Promela. It won the ACM Software System Award for 2001. TLC, the checker for TLA+, also stores states. The [next lesson](/concurrency/verification/tla-basics) shows its search step by step.

Storing states needs a model that can copy and hash its whole state. Real programs have heaps, kernels and stacks, so that is hard. **Stateless model checking**, introduced by Patrice Godefroid in VeriSoft (POPL 1997), runs the real program again from the start for each schedule. It stores no states, so it needs another way to avoid redundant work.

## Fight 2: skip equivalent orders

Two steps of different threads are **independent** if they touch different variables, or if both only read. Independent steps commute: both orders reach the same state. Two schedules are **equivalent** if one turns into the other by swapping adjacent independent steps. An equivalence class is a **Mazurkiewicz trace**. Every schedule in a trace gives the same result, so a checker needs to run only one.

**Partial order reduction** (POR) explores one schedule per trace, or close to it. Godefroid's 1996 book, "Partial-Order Methods for the Verification of Concurrent Systems" (LNCS 1032), presents two classic tools. A **persistent set** is a subset of the threads that is enough to explore from a state. A **sleep set** holds threads whose next step was already explored from an earlier branch and is independent of everything since.

```text
explore(state, sleep):
  for each thread t that can run, and is not in sleep:
    a = next step of t
    explore(state after a, { u in sleep : next step of u is independent of a })
    sleep = sleep + { t }       // later siblings need not start with a
```

Sleep sets alone run each trace once, but they can still start runs that end in a dead end. That is the "dead ends" count in the demos. Flanagan and Godefroid made the method practical for real code with **dynamic POR** (DPOR, POPL 2005). DPOR finds conflicts while it runs, instead of from a static analysis, and adds backtracking points only where a conflict appeared. **Optimal DPOR** (Abdulla, Aronis, Jonsson and Sagonas, POPL 2014) "always explores exactly one interleaving per Mazurkiewicz trace, and never initiates any sleep set-blocked exploration".

## Fight 3: search less, but where bugs are

Even one run per trace can be too many. Two ideas trade completeness for reach.

**Preemption bounding.** A **preemption** is a switch away from a thread that could still run. Musuvathi and Qadeer built this into CHESS ("Iterative Context Bounding for Systematic Testing of Multithreaded Programs", PLDI 2007). For n threads of k steps with no blocking, the number of executions with c preemptions is at most about $(n^2 k)^c \, n!$. That is polynomial in k and exponential only in c. They found 9 unknown bugs, "each of which was exposed by an execution with at most 2 preempting context switches".

**Randomized search.** A random walk picks a random thread at each step. It is cheap, but a bug that needs one thread to run a long stretch alone becomes very unlikely. **PCT** (Burckhardt, Kothari, Musuvathi and Nagarakatte, ASPLOS 2010) gives random priorities to the threads and lowers the running thread's priority at $d-1$ random steps. Define the **depth** d of a bug as the smallest number of ordering constraints that make it happen. For n threads and k steps in total, PCT finds such a bug in one run with probability at least $1/(n k^{d-1})$.

The racy ticket is a small example, so a full search is cheap here. The point is the shape of the numbers. Exhaustive search grows with the state space. Bounded search grows polynomially in the length and finds shallow bugs. Random walks lose against long, narrow windows, and PCT keeps a guarantee for them.

## Tools for real code

| Tool | For | Method |
|---|---|---|
| SPIN | Promela models | explicit states, hashing, POR; a bitstate mode saves memory |
| TLC | TLA+ specs | explicit states, breadth-first |
| CBMC | C and C++ | bounded model checking with a SAT solver (Clarke, Kroening and Lerda, TACAS 2004) |
| GenMC | C and C++, and Rust as an experimental option, as LLVM IR | stateless, optimal DPOR, with the SC, TSO, RA, RC11 and IMM memory models |
| loom | Rust | exhaustive under the C11 memory model, after CDSChecker; optional preemption bound |
| Shuttle | Rust | mainly randomized, including PCT, plus a DFS mode for small tests; not sound in random mode, but scales to large tests |
| Lincheck | JVM | stress testing or bounded model checking of data structures |

In Rust, **loom** replaces `std::sync` and `std::thread` in a test, and `loom::model` runs the closure many times, once for each execution that it explores.

```rust
use loom::sync::atomic::{AtomicUsize, Ordering::SeqCst};
use loom::sync::Arc;
use loom::thread;

#[test]
fn tickets_are_unique() {
    loom::model(|| {
        let next = Arc::new(AtomicUsize::new(0));
        let hs: Vec<_> = (0..2).map(|_| {
            let next = next.clone();
            thread::spawn(move || {
                let t = next.load(SeqCst);  // the bug: use fetch_add(1, SeqCst)
                next.store(t + 1, SeqCst);
                t
            })
        }).collect();
        let t: Vec<usize> = hs.into_iter().map(|h| h.join().unwrap()).collect();
        assert_ne!(t[0], t[1]); // loom finds the schedule that breaks this
    });
}
```

By default loom explores without a bound. Its documentation says that "setting the thread pre-emption bound to 2 or 3 is enough to catch most bugs", with `LOOM_MAX_PREEMPTIONS=3`. It also lists its limits. It treats `SeqCst` accesses as `AcqRel`, which can give false alarms. It does not explore some load-buffering executions, so it can miss bugs.

The two tools are often used together. The Amazon S3 team checked ShardStore (Bornholt et al., SOSP 2021) with both. They used loom for "small, correctness-critical code". They used **Shuttle** "to randomly check interleavings of larger test harnesses". They wrote Shuttle for that work. Its README states the trade: Shuttle "is not sound", but it "scales to much larger test cases than Loom".
