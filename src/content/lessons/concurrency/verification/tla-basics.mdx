The model checkers of the [previous lesson](/concurrency/verification/model-checking) explore real code. That is precise, but a bug in the *design* is often found too late, after the code exists. **TLA+** lets you check a design first. You describe the system as a state machine in plain mathematics, and a model checker explores every state.

Leslie Lamport defined the logic in "The Temporal Logic of Actions" (ACM TOPLAS, 1994). His book "Specifying Systems" (Addison-Wesley, 2002) is free on his web site. **TLC**, the model checker, is by Yuan Yu, Panagiotis Manolios and Lamport (CHARME 1999).

## A spec is Init and Next

A TLA+ spec has three parts. The **variables** hold the state. **Init** is a formula that says which states are initial. **Next** is a formula that relates a state to the following state. In Next, a plain name such as `big` is the value now, and a **primed** name such as `big'` is the value after the step.

This is the DieHard spec from the tlaplus Examples repository. In the film, the heroes must measure exactly 4 gallons with a 3-gallon jug, a 5-gallon jug and a faucet.

```text
------------------------------ MODULE DieHard ------------------------------
EXTENDS Naturals
VARIABLES big, small

TypeOK == /\ small \in 0..3
          /\ big   \in 0..5

Init == /\ big = 0
        /\ small = 0

FillSmallJug  == /\ small' = 3
                 /\ big' = big
FillBigJug    == /\ big' = 5
                 /\ small' = small
EmptySmallJug == /\ small' = 0
                 /\ big' = big
EmptyBigJug   == /\ big' = 0
                 /\ small' = small

Min(m,n) == IF m < n THEN m ELSE n

SmallToBig == /\ big'   = Min(big + small, 5)
              /\ small' = small - (big' - big)
BigToSmall == /\ small' = Min(big + small, 3)
              /\ big'   = big - (small' - small)

Next ==  \/ FillSmallJug  \/ FillBigJug
         \/ EmptySmallJug \/ EmptyBigJug
         \/ SmallToBig    \/ BigToSmall

Spec == Init /\ [][Next]_<<big, small>>

NotSolved == big # 4
=============================================================================
```

Each action, such as `FillSmallJug`, is a formula that is true or false of a *pair* of states. Read `/\` as "and" and `\/` as "or". An action must say what happens to every variable. That is why `FillSmallJug` states `big' = big`: without it, `big` could take any value.

## Behaviors and stuttering

A **behavior** is an infinite sequence of states. `Spec` is a temporal formula that is true of a behavior or false of it. `Init /\ [][Next]_vars` means: the first state satisfies Init, and every step satisfies `[Next]_vars`. The box `[]` means "always". `[Next]_vars` is `Next \/ UNCHANGED vars`, so a **stuttering** step, which changes none of the variables, is always allowed.

Stuttering has a purpose. A spec of a clock with only an hour variable must allow the steps where only the minutes change. With stuttering, a finer spec can **implement** a coarser one: its extra steps are stutters of the coarse variables. The price is that `Spec` alone allows a system to stop and stutter forever. The section on fairness below deals with that.

An **invariant** is a formula over one state that must hold in every reachable state. `TypeOK` says that each variable has the expected type. `NotSolved` is a trick: we claim that the puzzle cannot be solved, and the counterexample is the solution.

## How TLC searches

TLC computes every initial state and then applies Next to each state that it has found. It keeps a set of the states that it has seen. By default it searches **breadth-first**. So when it finds a state that breaks an invariant, it prints "a minimal-length behavior" that reaches it. With more than one worker thread, TLC can rarely print a trace that is not the shortest.

TLC also checks for **deadlock** by default: a reachable state from which Next allows no step. You turn that check off with `-deadlock`, or with `CHECK_DEADLOCK FALSE` in the configuration file.

```text
\* DieHard.cfg
SPECIFICATION Spec
INVARIANT TypeOK
INVARIANT NotSolved
```

## A spec of a concurrent program

A design with threads is a state machine too. The steps of different threads interleave, and Next is a disjunction with one action for each thread. This spec models a Java bounded buffer with one monitor, `wait` and `notify`. It follows Markus Kuppe's BlockingQueue tutorial, "Weeks of debugging can save you hours of TLA+", which studies legacy Java code of this form. Only the length of the buffer matters for deadlock, so the spec keeps no data.

```text
---------------------------- MODULE BlockingQueue ----------------------------
EXTENDS Naturals
CONSTANTS Producers, Consumers, BufCapacity
VARIABLES len, waitSet
vars == <<len, waitSet>>

RunningThreads == (Producers \cup Consumers) \ waitSet

Notify == IF waitSet # {}
          THEN \E t \in waitSet : waitSet' = waitSet \ {t}   \* any waiting thread
          ELSE UNCHANGED waitSet

Wait(t) == /\ waitSet' = waitSet \cup {t}
           /\ UNCHANGED len

Put(t) == IF len < BufCapacity THEN /\ len' = len + 1
                                    /\ Notify
                               ELSE Wait(t)

Get(t) == IF len > 0 THEN /\ len' = len - 1
                          /\ Notify
                     ELSE Wait(t)

Init == len = 0 /\ waitSet = {}
Next == \/ \E p \in Producers \cap RunningThreads : Put(p)
        \/ \E c \in Consumers \cap RunningThreads : Get(c)
Spec == Init /\ [][Next]_vars
=============================================================================
```

In Java, `notify()` wakes one waiting thread, and the program cannot choose which one. The spec says this with `\E t \in waitSet`. TLC then explores every choice, including the bad ones.

A test of the Java code could run for weeks without this schedule. The whole state graph of this model has only 14 states. There are two fixes. `notifyAll()` is simple, but it wakes every thread on every change. Two condition variables, one for "not full" and one for "not empty", wake only a thread that can proceed. Java's `ArrayBlockingQueue` uses one `ReentrantLock` with two `Condition` objects, and Go code does the same with two `sync.Cond` values.

## Fairness and liveness

Deadlock freedom is a safety property: a bad state never occurs. "Every value that is put is eventually taken" is a **liveness** property, written with `<>` ("eventually"). Because `Spec` allows stuttering forever, a liveness property fails unless the spec also says that steps must happen.

**Weak fairness** `WF_vars(A)` says: if A stays enabled forever, then an A step eventually occurs. **Strong fairness** `SF_vars(A)` says: if A is enabled infinitely often, then infinitely many A steps occur. A typical spec is `Init /\ [][Next]_vars /\ WF_vars(Next)`. TLC checks such properties, given with `PROPERTY` in the configuration file, by searching the state graph for a bad cycle.

## PlusCal and the wider toolbox

Many engineers write **PlusCal**, Lamport's algorithm language (ICTAC 2009), which looks like pseudocode and translates to TLA+. Each label is one atomic step. This is the racy ticket from the previous lesson:

```text
(* --algorithm tickets
variables next = 0;
process worker \in 1..3
variable t = 0;
begin
  Load:  t := next;
  Store: next := t + 1;
end process;
end algorithm; *)
```

Amazon Web Services reported its use of TLA+ in "How Amazon Web Services Uses Formal Methods" (Newcombe et al., CACM, April 2015). Teams wrote specs for parts of S3, DynamoDB, EBS and an internal lock manager. In DynamoDB, TLC found 3 bugs. For one of them, "the shortest error trace exhibiting the bug contained 35 high level steps".

TLC is not the only tool. **Apalache** is a symbolic model checker that translates TLA+ for SMT solvers such as Z3. **TLAPS**, the TLA+ Proof System, checks proofs for all sizes of a model, where TLC checks one finite instance.
