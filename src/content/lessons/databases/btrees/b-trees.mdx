A database reads storage in **pages**: fixed blocks of 4 to 16 KiB. One page read from storage takes much longer than thousands of key comparisons in memory. So an index must find a key with as few page reads as possible. A binary search tree is a bad fit, because each node holds one key and each step down the tree can be a new page.

A **B-tree** puts hundreds of keys in each node and makes each node one page. The number of children of a node is its **fanout**. With a fanout of 500, each level divides the search space by 500, not by 2. Rudolf Bayer and Edward McCreight described B-trees in 1970, and almost every relational database still uses them for indexes.

## B-tree and B+ tree

The original B-tree stores keys and their values in all nodes. The **B+ tree** is the variant that engines actually use:

- **Internal nodes** hold only **separator keys** and child pointers. A separator tells the search which child to follow. It is a copy of a key, not the data.
- **Leaves** hold all the keys and their values (a row, or a pointer to a row).
- Each leaf has a pointer to the next leaf. So a **range scan** finds the first key once and then reads leaves in order.

Internal nodes without values are small, so their fanout is higher, and the tree is shorter. InnoDB stores each table as a B+ tree on the primary key, with the rows in the leaves. SQLite stores tables as B+ trees on the rowid, but its index B-trees keep keys in internal nodes too. PostgreSQL keeps rows in a heap file and uses B+ trees for indexes.

## The rules

A B+ tree of **order** m has at most m children in each internal node, so a node holds at most m − 1 keys. (Some books count order in keys, not children. Check the definition.) Every node except the root must stay at least half full. Every leaf is at the same depth. These rules make the height a function of the number of keys only, not of the insert order.

**Search.** Start at the root. In each internal node, find the first separator that is greater than the key, and follow the pointer to its left. At the leaf, do a binary search. Separators obey one rule: child i holds every key k with keys[i−1] ≤ k < keys[i].

**Insert.** Search for the leaf and put the key in sorted position. If the leaf now has m keys, **split** it. The left half stays, and the right half goes to a new leaf. The first key of the new leaf is copied up into the parent.

If the parent overflows, it splits too. In an internal split, the middle key moves up and does not stay in either half. When the root splits, a new root grows above it.

**Delete.** Remove the key from its leaf. If the leaf is now below half full, look at a sibling with the same parent. If the sibling has a spare key, **borrow** it and update the separator. If not, **merge** the two nodes and remove their separator from the parent.

A merge can make the parent too empty, so the repair can go up to the root. When the root has one child left, that child becomes the new root.

```rust
// Search in one internal node: the number of separators <= key is the child index.
fn child_index(seps: &[u64], key: u64) -> usize {
    seps.partition_point(|&s| s <= key)
}

fn lookup(tree: &Tree, key: u64) -> Option<u64> {
    let mut page = tree.root;
    loop {
        match tree.read(page) {                      // one page read per level
            Node::Inner { seps, kids } => page = kids[child_index(seps, key)],
            Node::Leaf { keys, vals, .. } => {
                return keys.binary_search(&key).ok().map(|i| vals[i]);
            }
        }
    }
}
```

Each split and merge changes a few pages and takes $O(m)$ time. A search reads one page per level, so the cost of every operation is $O(\log N)$ page reads. Real engines do not always follow the delete rules. PostgreSQL never merges half-empty index pages: it removes a page only when the page is completely empty. InnoDB merges a page with a neighbor when the page drops below 50% full. The next lesson shows how this threshold is set.

1. Keep the defaults: 8-byte keys, 1 G keys and 16 KiB pages. The fanout is 903, and the tree has 4 levels with 1, 2, 1,227 and 1,107,420 nodes.
2. Read the size of all levels above the leaves: 19.2 MiB. With a 64 MiB buffer pool, those levels stay in memory, and a lookup needs only 1 storage read.
3. Set **Average page fill** to 69%. The fanout drops to 623, but the tree still has 4 levels.
4. Select **4 KiB** pages and move **Key size** to 64 B. The fanout falls to 53, and the tree needs 6 levels. Long keys cost levels.
5. Move **Buffer pool** down to 1 MiB. Now the cache holds fewer levels, and each lookup needs more storage reads.

The height of a B+ tree is about $\log_F N$ for fanout $F$. Because $\log_{903} 10^9 \approx 3$, the tree needs three internal levels plus the leaves. Each step of fanout counts only through a logarithm, so the height changes slowly. But the levels near the root are tiny. Almost all pages are leaves, so the buffer pool can keep every internal page in memory. A real lookup then costs one leaf read.

|---|---|---|
| InnoDB (MySQL) | 16 KiB | `innodb_page_size`; table rows live in the leaves of the primary-key tree |
| PostgreSQL | 8 KiB | fixed when the server is compiled; indexes point to rows in a heap file |
| SQLite | 4 KiB | `PRAGMA page_size`; tables are B+ trees on the rowid |
| LMDB | 4 KiB | the operating system page size; copy-on-write B+ tree |

## In memory: cache lines, not pages

When the whole index is in RAM, the unit of cost is the 64-byte **cache line**, not the page. A binary search tree with a billion keys has 30 levels. Each node is a separate allocation, so each level can be a cache miss.

<CacheLinesDemo />

1. Read the 64 B row. A node of one cache line has fanout 4, so the tree has 15 levels and one lookup touches 15 lines. That is half of the 30 lines of the binary tree.
2. Read the 4 KiB row. The tree has only 4 levels, but the binary search inside each node touches about 6 lines. The total is 24 lines.
3. Change the key size to 32 B. Only one key fits in a 64-byte node, and every node size now touches 30 lines or more. Long keys remove the advantage.

So in-memory B-trees use small nodes of a few cache lines. Lines inside one node are close together, so the hardware prefetcher and the TLB help too. Disk-based engines keep large pages, because there the cost of a page read is much larger than the cost of a cache miss.

## Shorter keys: prefix and suffix truncation

Fanout depends on key size, so engines shrink the keys in internal nodes.

- **Suffix truncation**: a separator must be greater than the last key on its left, and not greater than the first key on its right. Between "database" and "datum", the separator "datu" is enough. PostgreSQL 12 and later truncate separators this way.
- **Prefix compression**: keys on one page often share a prefix, such as "user:1001", "user:1002" and "user:1093". The page stores the prefix "user:10" once. WiredTiger can store keys like this, and MongoDB turns it on for indexes.

```go
// Shortest separator s with left < s <= right (suffix truncation).
func shortestSeparator(left, right string) string {
	for n := 1; n <= len(right); n++ {
		if right[:n] > left {
			return right[:n]
		}
	}
	return right
}
```

## When it breaks

- **Random keys** such as UUIDv4 send each insert to a random leaf. The working set is the whole leaf level, so the buffer pool misses often. Keys that grow with time, such as UUIDv7 or a sequence, keep inserts in a few hot leaves.
- **Long keys** cut the fanout and add levels. An index on a 200-byte text column is taller than one on a 64-bit integer.
- **Concurrent writers** must protect the pages that a split changes. The lesson on [latch crabbing and B-link trees](/databases/btrees/latch-crabbing-and-b-link-trees) covers this.
