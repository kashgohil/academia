A B+ tree in a buffer pool is a shared data structure, and many threads use it at the same time. A split changes three pages: the old page, the new page and the parent. The change cannot be atomic. So between the steps of a split, another thread can see a tree that is only half changed.

## Latches are not locks

Databases use two separate words. A **latch** protects a data structure in memory, such as one page in the buffer pool. A **lock** protects logical data, such as a row or a key range, for a transaction.

| | Latch | Lock |
|---|---|---|
| Protects | a page or other in-memory structure | rows, keys, tables |
| Held by | a thread | a transaction |
| Held for | the time of one operation on the page (microseconds) | until commit or abort |
| Deadlocks | prevented by a fixed order of acquisition | detected by the lock manager |
| Example | a reader-writer latch on each buffer frame | `SELECT ... FOR UPDATE` |

This lesson is about latches. A latch has two modes: **shared (S)** for readers and **exclusive (X)** for writers. Many threads can hold S together, but X excludes every other holder. Transaction locks are a separate topic: [two-phase locking and deadlocks](/databases/transactions/two-phase-locking-and-deadlocks).

## Latch crabbing

**Latch crabbing**, or latch coupling, moves down the tree like a crab. It holds the parent, takes the child, and only then lets go of the parent. So no writer can change the pointer between the read of the parent and the latch on the child.

- **Search**: S-latch the root. For each level, S-latch the child, then release the parent.
- **Insert or delete**: X-latch the root. For each level, X-latch the child. If the child is **safe**, release all latches above it. A node is safe for an insert when it is not full. For a delete, it is safe when it is more than half full.

A safe node cannot split or merge, so no change can go above it. So the writer keeps latched exactly the part of the path that a split or merge could change. Latches are always taken from parent to child, so two descents cannot wait for each other in a circle. A scan that moves left along the leaf chain breaks this order, so it must use a try-latch and restart when the latch is busy.

```cpp
// Pessimistic insert with latch crabbing (C++20).
Page* p = pool.fix(root);  p->latch.lock();            // X on the root
std::vector<Page*> held{p};
while (!p->is_leaf()) {
    Page* c = pool.fix(p->child_for(key));
    c->latch.lock();                                    // X on the child
    if (!c->full()) {                                   // safe: no split can reach above c
        for (Page* a : held) a->latch.unlock();
        held.clear();
    }
    held.push_back(c);
    p = c;
}
insert_and_split(held, key, val);                       // changes only latched pages
for (Page* a : held) a->latch.unlock();
```

The problem is the root. Every writer takes an X latch on it, even when the insert changes only a leaf. So writers run one at a time through the top of the tree.

## Optimistic descent

Most inserts do not split. In the sim below, with order 64, only 119 of 4,984 inserts find a full leaf. Rudolf Bayer and Mario Schkolnick proposed an **optimistic** writer in 1977. It descends like a reader, with S latches, and it takes X only on the leaf. If the leaf is not safe, the writer releases everything and starts again with the pessimistic crabbing above.

## B-link trees: move right

Philip Lehman and S. Bing Yao described the **B-link tree** in 1981. Each node gets two more fields:

- a **right link**: a pointer to the next node on the same level, also for internal nodes;
- a **high key**: an upper bound for all keys in the node and its subtree.

A split now happens in two separate steps. First comes the **half split**. Make the new right node, and copy the high key and right link of the old node into it. Then give the old node the new high key and a link to the new node. After this step, the new node is already reachable through the link. Second, insert the separator into the parent, as a separate change with its own short latch.

A reader that arrives at a node after a half split checks the high key. If its key is not below the high key, the key moved right, so the reader follows the right link. So a reader needs only one latch at a time, and a writer holds the leaf latch only for the half split. PostgreSQL B-tree indexes use this design. Each page has a high key and a right link, and a search "moves right" when it finds that the page split under it.

```go
// B-link search: one short latch at a time; move right past concurrent splits.
func (t *Tree) Search(key uint64) (uint64, bool) {
	n := t.root.Load()
	for {
		n.mu.RLock()
		for key >= n.high && n.right != nil { // the node split after we chose it
			next := n.right
			n.mu.RUnlock()
			n = next
			n.mu.RLock()
		}
		if n.leaf {
			v, ok := n.find(key)
			n.mu.RUnlock()
			return v, ok
		}
		child := n.childFor(key)
		n.mu.RUnlock()
		n = child
	}
}
```

Deletes are harder. A merge removes a node that a reader may still be about to visit. Engines often skip merges or mark pages dead and remove them later, when no reader can hold a pointer to them. PostgreSQL deletes only empty pages, and it keeps a deleted page until no running transaction can still reach it.

## Optimistic lock coupling

On a many-core machine, even S latches hurt. A shared latch is a counter, and every reader must write it. So the cache line of the root latch moves from core to core on every operation. **Optimistic lock coupling (OLC)** removes these writes. It comes from the research engines HyPer and LeanStore, and Umbra uses it too.

Each node has a 64-bit **version**. The lowest bit means locked, and the other bits count changes.

- A **reader** reads the version, reads the node, and reads the version again. If the version changed, or was odd, it restarts. The reader writes nothing to shared memory.
- A **writer** locks with a compare-and-swap from an even version to the next odd one, changes the node, and unlocks by adding one more.
- **Coupling**: after the reader reads the version of a child, it checks the version of the parent again. If the parent changed, the child pointer may be stale, so the reader restarts.

```rust
use std::sync::atomic::{AtomicU64, Ordering::*};

struct Version(AtomicU64);
impl Version {
    fn read_lock(&self) -> Result<u64, Restart> {
        let v = self.0.load(Acquire);
        if v & 1 == 1 { Err(Restart) } else { Ok(v) }     // locked by a writer
    }
    fn validate(&self, v: u64) -> Result<(), Restart> {
        std::sync::atomic::fence(Acquire);
        if self.0.load(Relaxed) == v { Ok(()) } else { Err(Restart) }
    }
    fn write_lock(&self, v: u64) -> Result<(), Restart> {
        self.0.compare_exchange(v, v + 1, Acquire, Relaxed).map(|_| ()).map_err(|_| Restart)
    }
    fn write_unlock(&self) { self.0.fetch_add(1, Release); }
}
```

OLC has costs. A reader can read a node while a writer changes it. So it can see garbage, such as an offset out of range or a wrong key count. The code must check bounds before it uses such values, and it must validate before it acts on them.

A writer can also free a node that a reader still reads. So OLC needs safe memory reclamation, such as [epoch-based reclamation](/concurrency/lock-free/epoch-based-reclamation). Under heavy write contention, readers can restart many times.

## Which one?

| Protocol | Readers write shared memory | Root X latches | Latches held by a writer |
|---|---|---|---|
| Latch crabbing | yes, S latches | every write | up to the full path |
| Optimistic descent | yes, S latches | only after a full leaf | up to the full path, after a restart |
| B-link (Lehman–Yao) | yes, one short S latch per node | only when the root changes | about 2 |
| Optimistic lock coupling | no | only when the root changes | the nodes it changes |

Disk-based engines spend most time on I/O, so B-link trees with short latches are enough. In-memory engines spend most time on cache misses, so OLC wins there.
