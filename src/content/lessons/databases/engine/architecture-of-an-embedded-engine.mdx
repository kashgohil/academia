The earlier modules built the parts of a database one at a time: [pages](/databases/storage/pages-and-slotted-records), a [buffer pool](/databases/storage/buffer-pools), [B+ trees](/databases/btrees/b-trees), [LSM trees](/databases/lsm/memtables-and-sstables), [MVCC](/databases/transactions/mvcc) and [ARIES](/databases/recovery/aries). A **storage engine** is these parts joined into one program that stores keys and values and keeps them safe. This module joins them. This lesson shows the layers and the choices. The next lesson builds a working engine, and the third lesson tries to break it.

An **embedded engine** is a library that runs inside the process of the application. SQLite, LMDB, RocksDB and LevelDB are embedded. A call to `put()` is a function call, and the data files belong to the application. A **client/server** database such as PostgreSQL or MySQL runs as its own process. Clients send queries over a socket.

## The layers

Every engine in this track has the same seven layers, from top to bottom:

| Layer | Job | In this track |
|---|---|---|
| API | `begin`, `get`, `put`, `delete`, `commit`, `abort` | [ACID](/databases/transactions/acid) |
| Transaction manager | snapshots, visibility, write conflicts, commit order | [MVCC](/databases/transactions/mvcc), [SSI](/databases/transactions/serializable-snapshot-isolation) |
| Access method | find the key in a B+ tree, an LSM tree or a hash table | [B+ trees](/databases/btrees/b-trees), [compaction](/databases/lsm/compaction-leveled-vs-tiered) |
| Buffer pool | cache pages in frames, pin them, write back dirty pages | [buffer pools](/databases/storage/buffer-pools) |
| Page and file layer | page numbers to file offsets, checksums | [slotted pages](/databases/storage/pages-and-slotted-records), [checksums](/databases/storage/durability-fsync-torn-writes-and-checksums) |
| Write-ahead log | log records, LSNs, the WAL rule, group commit | [WAL](/databases/recovery/write-ahead-logging), [group commit](/databases/recovery/group-commit) |
| OS and device | `pread`, `write`, `fsync` | [disks vs SSDs](/databases/storage/disks-vs-ssds) |

Each layer talks only to the layer below it, with one exception. The buffer pool must ask the log before it writes a page, because of the WAL rule.

## The life of a put()

A `put(k, v)` inside a transaction goes down the layers like this:

1. **API.** The engine checks that the transaction is open.
2. **Transaction manager.** It looks at the newest version of `k`. If another open transaction wrote it, or a transaction committed it after our snapshot, this is a write conflict.
3. **Access method.** It descends from the root to the leaf. Each page comes from the buffer pool and stays pinned while it is in use. A full leaf splits first.
4. **Write-ahead log.** It appends a record with the old and the new value. The record gets the next LSN. The page header gets that LSN as its pageLSN.
5. **Buffer pool.** The leaf is now dirty. Its recLSN, the first LSN that dirtied it, goes into the dirty page table.

Nothing has touched the device yet. At commit, the log layer appends a commit record and calls `write()` and `fsync()`. Only then does the client hear "committed". The page goes to disk much later. Before that write, the buffer pool forces the log up to the pageLSN.

## The life of a get()

A `get(k)` stops much higher. The transaction manager gives it a snapshot. The access method descends to the leaf through the buffer pool, and the transaction manager picks the newest version that the snapshot can see. A get writes nothing, with one exception: a cache miss can evict a dirty page. Then the read pays for a page write and a log flush, as step 6 shows.

## Embedded vs client/server

| | Embedded (SQLite, LMDB, RocksDB) | Client/server (PostgreSQL, MySQL) |
|---|---|---|
| A call costs | a function call | a round trip over a socket, and a context switch |
| Concurrency | threads of one process; LMDB and SQLite also share files between processes with locks | many connections, one server process per connection (PostgreSQL) or a thread pool |
| Who owns the files | the application | the server |
| Crash of the application | can be a crash of the engine | the server keeps running |
| Typical use | phones, browsers, devices, the storage layer of a larger system | shared databases for many applications |

Many servers use an embedded engine inside. MySQL runs InnoDB, MongoDB runs WiredTiger, and CockroachDB runs Pebble, an LSM engine in Go that follows the design of RocksDB.

## Five choices

An engine is mostly the sum of five choices. Each choice moves cost from one place to another.

<DesignExplorerDemo />

1. Read the default: B+ tree, in place, undo + redo log, many writers, own buffer pool. This is InnoDB. A 100-byte update writes about 42 bytes for each byte: one log record and one 4 KiB page.
2. Select **Copy-on-write** and **Shadow paging**. Write amplification grows to about 246, because each update copies the whole path from leaf to root. In exchange, recovery has no work to do.
3. Select **LSM tree**. The page writes are gone, and write amplification falls to 24. A point read now costs 1.03 I/O and a range of 100 records costs 7 I/Os instead of 4.
4. Select **Hash + log**. Writes cost about 5 bytes for each byte, but a range of 100 records costs 100 I/Os. The hash keeps no key order.
5. Select **B+ tree**, **In place**, and **OS page cache / mmap**. The explorer refuses. With a writable memory map, the OS can write a page before its log record is durable.

### B+ tree or LSM tree

A B+ tree keeps one copy of each key in a sorted page. Reads and ranges are cheap, but each update rewrites a page. An LSM tree buffers writes in memory and writes sorted runs. It writes fewer bytes, but a read may probe several runs, and compaction uses bandwidth in the background. The [tuning lesson](/databases/lsm/tuning-an-lsm-tree) finds the crossover for one workload.

### In place, copy-on-write or log-structured

An **in-place** engine overwrites a page at its own address. It needs a log for crash safety, and it needs protection against torn pages. A **copy-on-write** engine writes changed pages to new addresses and then switches one root pointer. Old pages stay valid, so readers need no locks. A **log-structured** engine never changes a file after it writes it. Space comes back only when compaction or cleaning rewrites live data.

### Undo, redo or shadow paging

The log design follows from the buffer pool policy, as the [WAL lesson](/databases/recovery/write-ahead-logging) explains. STEAL needs undo information, and NO-FORCE needs redo information. ARIES logs both. PostgreSQL logs only redo, because MVCC keeps old row versions in the table. SQLite in rollback mode logs only undo: it copies the original pages to a journal and forces the new pages at commit. Shadow paging logs nothing, because the old tree is still on disk.

### One writer or many

LMDB and SQLite allow one write transaction at a time. There are no write-write conflicts, no deadlocks and no latches between writers. The cost is write throughput. Each commit waits for its own fsync, and nothing can share it. InnoDB, PostgreSQL and RocksDB allow many writers. They need locks or optimistic checks, latch crabbing in the tree, and group commit to share log flushes.

### Own buffer pool or mmap

With `mmap`, the OS page cache is the buffer pool. The code is small, and reads cost no copy. But the OS chooses the victims and the time of each write-back, and an I/O error arrives as a `SIGBUS` signal. Crotty, Leis and Pavlo measured these problems in a CIDR 2022 paper: "Are You Sure You Want to Use MMAP in Your Database Management System?". LMDB maps its file read-only and writes with `pwrite`, so copy-on-write keeps it safe. Engines that update in place keep their own pool and often use `O_DIRECT`.

| Choice | Option A | Option B | Engines |
|---|---|---|---|
| Access method | B+ tree: cheap reads and ranges | LSM: cheap writes, more read probes | SQLite, InnoDB vs RocksDB, Cassandra |
| Updates | in place: small files, needs a log | copy-on-write: lock-free readers, path copies | InnoDB vs LMDB, WiredTiger |
| Crash safety | log (ARIES, redo-only) | shadow paging: no recovery work | PostgreSQL vs LMDB |
| Writers | one: simple, fsync-bound | many: locks, latches, group commit | SQLite, LMDB vs InnoDB, RocksDB |
| Caching | own pool: control | mmap: small code, little control | InnoDB vs LMDB |
