A B+ tree finds a key in about $\log_F N$ page reads. A **hash index** tries to do better: it computes a hash of the key and goes to one page. That page is a **bucket**: a page that holds all keys whose hash maps to it. For an equality lookup such as `WHERE id = 42`, one bucket read is enough.

The hard part is growth. A hash table in memory doubles its array and moves every key. A disk-based index cannot stop and rewrite gigabytes. This lesson shows three ways to grow: overflow chains, a directory that doubles, and a split pointer that moves one bucket at a time.

## Static hashing

**Static hashing** fixes the number of buckets $B$ when the index is built. Key $k$ goes to bucket $h(k) \bmod B$. When a bucket page is full, the engine links an **overflow page** behind it. A lookup reads the bucket page and then each overflow page in the chain.

The **load factor** $\alpha$ is the number of keys divided by the number of key slots in the primary pages. Below about 80%, most lookups read one page. When the table grows past its planned size, the chains grow, and every lookup gets slower. The only fix is a full rebuild with a larger $B$.

## Extendible hashing

**Extendible hashing** (Fagin, Nievergelt, Pippenger and Strong, 1979) adds a **directory**: an array of $2^g$ pointers to buckets. The number $g$ is the **global depth**. The low $g$ bits of the hash select a directory slot, and the slot points to a bucket.

Each bucket has a **local depth** $d \le g$. All keys in the bucket agree on their low $d$ bits, and $2^{g-d}$ slots point to it. When a bucket is full:

- If $d < g$, split only the bucket. Keys with a 1 in bit $d$ move to a new bucket, and half of the slots move to it.
- If $d = g$, double the directory first. Each new slot copies the pointer of its partner slot. Then split the bucket.

A lookup reads one directory slot and one bucket page. The directory is small, so engines keep it in memory, and a lookup costs one page read. A split rewrites only two pages and part of the directory.

The weak point is the directory. Keys whose hashes share many low bits force many doublings. In the demo at the end, 6,000 random keys with 4 keys per bucket need 2,175 buckets but 16,384 directory slots. With 16 keys per bucket, the same keys need 544 buckets and 1,024 slots. Bigger buckets keep the directory small.

## Linear hashing

**Linear hashing** (Witold Litwin, 1980) has no directory. It keeps a **split pointer** `next` and a round number $L$. With $N_0$ starting buckets, a round has $M = N_0 \cdot 2^L$ buckets. The address of a key with hash $h$ is:

$$
a = h \bmod M, \quad \text{and if } a < \text{next}: \quad a = h \bmod 2M.
$$

Buckets before `next` have already split in this round, so they use the finer function. When the load factor passes a limit, the bucket at `next` splits, and `next` moves one step. The split bucket is usually not the bucket that overflowed. That bucket keeps its overflow page until the pointer reaches it. When `next` reaches $M$, the round ends, $L$ grows by one, and `next` goes back to 0.

```go
// Address of a key in linear hashing: no directory, two hash functions.
func (t *LinearHash) addr(h uint32) uint32 {
	m := t.n0 << t.level // buckets in this round
	a := h % m
	if a < t.next { // this bucket has already split in this round
		a = h % (2 * m)
	}
	return a
}
```

Linear hashing grows by one bucket at a time, so growth is smooth. The bucket array can be one file that grows at its end. The cost is overflow pages on buckets that the pointer has not yet reached.

4. Read the extendible dot. Its buckets are 69.0% full on average, close to $\ln 2 = 69.3\%$, the fill of random splits.
5. Select **in memory**. At 80%, a linear probing miss checks 11.78 slots, but a Robin Hood miss checks 3.19. Select **key absent** and **key present** to compare.

For hash tables in memory, the cost is slot probes and cache misses, not pages. **Linear probing** puts a key in the next free slot. Its misses get slow near a full table: Knuth's estimate is $\frac{1}{2}(1 + 1/(1-\alpha)^2)$. **Robin Hood hashing** (Celis, 1986) lets a key that is far from home take the slot of a key that is closer to its home. The mean hit cost does not change, but the longest probe at 80% falls from 93 slots to 10. A miss can stop early.

**Cuckoo hashing** (Pagh and Rodler, 2001) gives each key two possible slots, so a lookup checks at most two. An insert kicks the old key to its other slot. With one key per slot, the first insert fails at a load of 53.4% in the demo. Real cuckoo tables use buckets of 4 or 8 slots to fill much more. The algorithms track covers [Robin Hood hashing](/algorithms/hashing/robin-hood-hashing) and [cuckoo hashing](/algorithms/hashing/cuckoo-hashing) in depth.

## Why a hash index cannot scan a range

A good hash function scatters keys. Keys 41, 42 and 43 go to three unrelated buckets. So a query such as `WHERE id BETWEEN 40 AND 50` cannot use a hash index: it must read every bucket. The same is true for `ORDER BY`, `MIN`, `MAX` and prefix matches such as `LIKE 'abc%'`. A hash index answers only equality. A B+ tree answers equality with a few more page reads, and it also answers all of these.

## Hash indexes in real engines

**PostgreSQL** has `CREATE INDEX ... USING hash`. Before version 10, hash indexes were not WAL-logged. A crash could corrupt them, and replicas did not get them. The documentation told users not to use them. Since version 10, they are WAL-logged and crash-safe.

A PostgreSQL hash index stores only the 4-byte hash code of each key, not the key. So a long text key costs the same 4 bytes, but every match must be checked against the row. The index supports only the `=` operator, only one column, and no `UNIQUE` constraint. Its buckets split one at a time, in the style of linear hashing.

**InnoDB** has no hash index on disk. Its **adaptive hash index** is an in-memory hash table that InnoDB builds on top of B+ tree pages that queries read often. It maps a search key straight to a record in a buffer pool page, so a lookup skips the tree descent. Under heavy write load it can become a point of contention. MySQL 8.4 turns it off by default (`innodb_adaptive_hash_index=OFF`).

**Bitcask**, the storage engine that Riak used by default, puts the hash table in memory and the data in a log. Every write appends the key and value to the active data file. An in-memory table, the **keydir**, maps each key to its file, offset and value size. A read is one hash lookup and one disk read. A background **merge** rewrites old files without the dead values, much like LSM compaction.

The price is memory: the keydir must hold every key. In our model each entry holds the key plus 20 bytes of fields. With 100 million keys of 16 bytes, that is 3.35 GiB before hash table overhead. Bitcask also writes **hint files** next to merged data files, so a restart can rebuild the keydir without a full scan of the data.

## When it breaks

- **Skewed or duplicate keys**: many rows with one key all go to one bucket, and no split can separate them.
- **Range queries and sorting**: a hash index cannot help. Use a B+ tree.
- **A directory that explodes**: extendible hashing with small buckets and unlucky hashes can double the directory many times for one insert.
- **Memory-only maps**: Bitcask and the InnoDB adaptive hash index need RAM for every key or page.
