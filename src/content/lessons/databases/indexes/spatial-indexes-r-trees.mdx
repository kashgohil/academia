A query such as "all shops inside this map window" has two range conditions: one on x and one on y. A B+ tree on x can find the rows in the x range quickly. But those rows have every y value, so the tree must read the whole strip and filter it. A composite index on (x, y) has the same problem, because the range on x stops the leftmost-prefix walk (see [secondary and covering indexes](/databases/indexes/secondary-and-covering-indexes)).

A one-dimensional order cannot keep all points that are near in 2D near in the order. **Spatial indexes** solve this in two ways. Some index the shapes in 2D directly: R-trees, quadtrees and k-d trees. Others map 2D to 1D with a space-filling curve and use an ordinary B-tree.

## The R-tree

The **R-tree** (Antonin Guttman, 1984) is a balanced tree like a B+ tree, but its keys are rectangles. Each entry holds a **minimum bounding rectangle** (MBR): the smallest axis-aligned rectangle that contains a shape, or all shapes below a child. A leaf entry is the MBR of one object and a pointer to it. An inner entry is the MBR of a child node and a pointer to that node.

Each node holds between $m$ and $M$ entries, and all leaves are at the same depth. Unlike B-tree key ranges, the MBRs of sibling nodes can overlap. That is the main difference, and the source of most of the cost.

**Search** for a query box $Q$: start at the root. For each entry whose MBR intersects $Q$, go down into that child. At a leaf, report each object whose MBR intersects $Q$, then check its exact shape. Because MBRs overlap, a search can follow several paths.

```rust
fn search(node: &Node, q: &Rect, out: &mut Vec<u64>) {
    for e in &node.entries {
        if !e.mbr.intersects(q) { continue; }          // prune this whole subtree
        match &e.child {
            Child::Node(n) => search(n, q, out),       // overlapping MBRs: maybe several paths
            Child::Object(id) => out.push(*id),        // candidate: check the exact shape later
        }
    }
}
```

## Insert and split

**Insert** goes down from the root to a leaf. At each level, **ChooseSubtree** picks the child whose MBR needs the **least enlargement** to include the new rectangle. Ties go to the child with the smaller area. The idea is to keep MBRs small, so that later searches enter fewer nodes.

If the leaf now has $M + 1$ entries, it **splits** into two nodes. The split goes up like a B-tree split, and a root split adds a level. Each MBR on the path then grows to include the new entry.

The split decides the quality of the tree. Guttman's **quadratic split**:

<Steps>
<div>**PickSeeds**: for every pair of entries, compute the area of their joint MBR minus their own areas. The pair that wastes the most area starts the two groups.</div>
<div>**PickNext**: for each remaining entry, compute how much each group's MBR must grow to take it. Choose the entry with the biggest difference between the two groups.</div>
<div>Put that entry in the group that grows less. Ties go to the smaller area, then to the group with fewer entries.</div>
<div>If one group needs all remaining entries to reach $m$ entries, give them all to it. Repeat until no entry is left.</div>
</Steps>

PickSeeds costs $O(M^2)$, so the method is called quadratic. Guttman also gave a linear split, which is faster but makes worse trees.

**The R\*-tree** (Beckmann, Kriegel, Schneider and Seeger, 1990) changes three things. At the leaf level, ChooseSubtree minimizes the growth of **overlap** with siblings, not only of area. The split chooses an axis by the sum of the group perimeters, then the split position by the least overlap. And before it splits a full node, it removes about 30% of the entries and **reinserts** them from the top. This moves entries to better nodes as the tree grows. Most modern R-tree code, such as the SQLite R\*Tree module, follows the R\*-tree.

## Bigger nodes on disk

On disk, a node is a page with dozens or hundreds of entries. The sim also measured a bigger tree: 2,000 random points, with square queries of 5% of the map side that find 6.2 points on average.

| Max entries M | Height | Nodes | Nodes visited per query |
|---|---|---|---|
| 4 | 7 | 1,008 | 15.7 |
| 16 | 3 | 193 | 6.7 |
| 50 | 3 | 62 | 4.1 |

A wider node means fewer levels and fewer page reads, as in a B-tree. The cost is more entry tests per node, which is cheap in memory.

## Nearest neighbors

A **k-nearest-neighbor** (kNN) query asks for the k objects closest to a point. The R-tree answers it with **best-first search** (Hjaltason and Samet, 1999). A priority queue holds nodes and objects, ordered by **MINDIST**: the smallest possible distance from the query point to an MBR.

Pop the closest item. If it is an object, report it. If it is a node, push its entries. No unvisited node can hold anything closer than its MINDIST, so the first k objects popped are the answer. The search opens only the nodes whose MBRs come closer than the k-th result.

## Other structures

- A **quadtree** (Finkel and Bentley, 1974) splits a square into four equal quarters, again and again, until each cell holds few points. Its cells do not overlap, but its shape depends on the data.
- A **k-d tree** (Bentley, 1975) is a binary tree that splits on x, then y, then x again, at a point of the data. It is good in memory, but it is hard to keep balanced on disk.
- PostgreSQL **SP-GiST** supports these space-partitioning trees, and PostGIS can use it.

## Space-filling curves on a B-tree

A **space-filling curve** visits every cell of a $2^k \times 2^k$ grid once. Its position along the curve is a single integer key, so an ordinary B-tree can index it. A box query becomes a set of key ranges.

- **Z-order** (Morton order) interleaves the bits of x and y: bit $i$ of x goes to bit $2i$ of the key, bit $i$ of y to bit $2i + 1$. It is cheap to compute, but the curve jumps across the grid at each power-of-two boundary.
- The **Hilbert curve** turns so that consecutive cells are always neighbors. It needs more work to compute, but it keeps 2D neighborhoods together better.
- A **geohash** is Z-order over longitude and latitude bits, written in base 32. The point (57.64911, 10.40744) has the geohash u4pruydqqvj. Keys that share a prefix lie in the same cell, so a prefix query on a B-tree finds a cell.

Each range costs one B-tree seek, and each false positive costs a wasted row. So engines cap the number of ranges and filter the false positives with the exact test. Google's S2 library numbers cells on a sphere along a Hilbert curve, and MongoDB's `2dsphere` index uses S2 cells. Delta Lake's `OPTIMIZE ... ZORDER BY` sorts the data files by a Z-order key, so data skipping works for filters on several columns.

## Spatial indexes in real engines

**PostGIS** indexes geometries with a **GiST** index. GiST (generalized search tree) is a PostgreSQL framework for balanced trees with custom keys, and PostGIS uses it as an R-tree of bounding boxes. The `&&` operator tests bounding box overlap with the index. Functions such as `ST_Intersects` use the index first and then run the exact test. The `<->` distance operator in `ORDER BY` gives index-assisted kNN.

```sql
CREATE INDEX shops_geom ON shops USING gist (geom);
-- The 5 shops nearest to a point, using the index:
SELECT id FROM shops ORDER BY geom <-> ST_SetSRID(ST_MakePoint(10.4, 57.6), 4326) LIMIT 5;
```

**InnoDB** builds an R-tree for a `SPATIAL INDEX`. **SQLite** has the R\*Tree virtual table module.

## When it breaks

- **Large or long objects**: a road across a country has a huge MBR that overlaps everything. Split long shapes into pieces, or use a grid index.
- **Heavy overlap**: random insert order and poor splits make MBRs overlap, and searches visit many paths. Bulk loading, for example by sorting on a Hilbert key, builds much better trees.
- **Many dimensions**: above about 10 dimensions, MBRs of most nodes intersect most queries, and a scan is as fast. Vector search uses other methods.
