A B+ tree compares whole keys. Each comparison of two 16-byte keys reads both keys, and a lookup does about $\log_2 N$ of them. A **trie** never compares whole keys. It uses each byte of the key to choose a child, one level per byte. A lookup costs one step per key byte, so the height depends on the key length, not on the number of keys.

In memory, this is fast. The cost of an index in memory is cache misses and branch mispredictions, not page reads. This lesson builds up to the **adaptive radix tree** (ART) of Leis, Kemper and Neumann (ICDE 2013), the index of the HyPer and DuckDB databases.

## Tries and radix trees

A trie node for byte keys has 256 child pointers, one for each byte value. This is a **radix tree** with a span of 8 bits. To find a 4-byte key, read the first byte and follow that pointer, then the second byte, and so on. A 4-byte key needs 4 steps for any number of keys.

The problem is memory. A node of 256 pointers takes 2 KiB, and most of the pointers are empty in the lower levels. Two old ideas reduce the waste:

- **Path compression**: a chain of nodes with one child each becomes one node that stores the shared bytes as a **prefix**. Morrison's PATRICIA tree (1968) does this.
- **Lazy expansion**: if only one key is below a point, store a leaf there. Do not build the nodes for the remaining bytes.

## Adaptive nodes

ART also changes the node layout with the number of children. Each inner node has a 16-byte header (type, child count, prefix) and one of four layouts:

| Node | Children | Layout | Bytes (8-byte pointers) |
|---|---|---|---|
| Node4 | 1–4 | 4 sorted key bytes, 4 pointers | 52 |
| Node16 | 5–16 | 16 sorted key bytes, 16 pointers | 160 |
| Node48 | 17–48 | 256-byte index from byte to slot, 48 pointers | 656 |
| Node256 | 49–256 | 256 pointers, indexed by the byte | 2,064 |

When a node is full, it grows to the next type. When it loses children, it shrinks. A leaf is a **tagged pointer**: a pointer with one low bit set that points to the row. The tree stores no separate leaf objects, and a lookup checks the full key against the row at the end.

## Search inside a node

Node4 and Node16 keep their key bytes sorted. A Node4 search compares up to 4 bytes. A Node16 search uses one SIMD instruction to compare the search byte with all 16 key bytes at once:

```cpp
#include <emmintrin.h>
// Find the child for byte b in a Node16 (keys[] sorted, count <= 16).
Node* findChild16(const Node16* n, uint8_t b) {
    __m128i key = _mm_set1_epi8(static_cast<char>(b));             // b in all 16 lanes
    __m128i cmp = _mm_cmpeq_epi8(key, _mm_loadu_si128((const __m128i*)n->keys));
    unsigned mask = _mm_movemask_epi8(cmp) & ((1u << n->count) - 1); // one bit per lane
    return mask ? n->child[__builtin_ctz(mask)] : nullptr;
}
```

A Node48 reads one byte of its index to find the slot. A Node256 reads the pointer directly. No layout has a loop with unpredictable branches, so a lookup is a few cache misses per level.

## Binary-comparable keys

A radix tree compares bytes from left to right, like `memcmp`. So the bytes of a key must sort in the same order as the values. Many key types do not do this in their memory layout. The same rule holds for any engine that compares raw bytes: RocksDB with its default comparator, FoundationDB, and the "memcomparable" key format of MyRocks.

| Type | Encoding | Why |
|---|---|---|
| unsigned integer | big-endian | the most significant byte must come first |
| signed integer | flip the sign bit, then big-endian | $-2^{31}$ becomes 00 00 00 00, −1 becomes 7F FF FF FF, 0 becomes 80 00 00 00 |
| IEEE 754 float | positive: flip the sign bit; negative: flip all bits; big-endian | negative floats have the sign bit set and a reversed magnitude order |
| string | UTF-8, escape 00 as 00 FF, end with 00 00 | the terminator makes keys prefix-free; byte order is code point order, not a collation |
| composite | concatenate the encoded parts | each part must be self-delimiting, or the next part leaks into the comparison |

The tree also needs keys to be **prefix-free**: no key may be a prefix of another key. With "ab" and "abc", the search for "ab" ends inside the path of "abc". Fixed-length integers are prefix-free, and the string terminator makes strings prefix-free.

5. Select **(string, int32)** and **no terminator**. The int bytes after "ab" compare with the "c" of "abc", and the rows go out of order. The terminated encoding fixes it.

```rust
// Binary-comparable encodings (big-endian bytes).
fn enc_i32(v: i32) -> [u8; 4] { ((v as u32) ^ 0x8000_0000).to_be_bytes() }
fn enc_f64(v: f64) -> [u8; 8] {
    let b = v.to_bits();
    let b = if b >> 63 == 1 { !b } else { b | (1 << 63) }; // negative: flip all; positive: flip sign
    b.to_be_bytes()
}
```

ART adapts to the data. Dense keys cost almost nothing beyond one pointer each. Sparse keys cost more, but the paper proves a worst case of 52 bytes per key. A B+ tree in memory stores a copy of each key, so long keys cost more there. ART stores a key byte only once for all keys that share it.

## What ART gives you

- **Ordered scans**: an in-order walk returns keys in byte order. So ART answers range queries and prefix queries, which a hash table cannot.
- **Fast point lookups**: a few nodes per lookup, each with a fixed search cost. The paper measured lookups faster than a B+ tree and close to a hash table.
- **No rebalancing**: the shape depends only on the set of keys, not on the insert order.

It also has limits. Long keys with long shared prefixes make deep trees. In this lesson's sim, the full prefix is stored in the node. The paper stores only up to 8 bytes and skips the rest, then checks the whole key at the leaf. Concurrent writers need a protocol, such as the optimistic lock coupling of Leis and others (2016).

## Where it is used

**HyPer** uses ART as its main index. **DuckDB** uses ART for primary keys, unique constraints and `CREATE INDEX`. Radix trees also appear outside databases. The Linux page cache finds pages with a radix tree (the XArray), and Redis keeps streams in one.
