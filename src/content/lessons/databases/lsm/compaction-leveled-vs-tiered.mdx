Each flush adds one more sorted run to the tree. If nothing merges the runs, three problems grow without limit:

- **Reads get slower.** A lookup may have to check every run.
- **Space grows.** Old versions and tombstones stay on disk for ever.
- **Deletes never finish.** A tombstone hides data, but the data still uses space.

**Compaction** is the background job that fixes this. It reads some sorted runs, merges them like the merge step of merge sort, and drops versions that no reader can see. Then it writes the result as new files and deletes the inputs. The input files never change, so readers can use them until the new files are ready.

Three numbers describe the cost of a design:

- **Write amplification (WA)**: bytes written to disk per byte that the user writes.
- **Read amplification**: sorted runs, or block reads, per lookup.
- **Space amplification (SA)**: bytes on disk per byte of live data.

No design makes all three small at the same time. This is the RUM conjecture (Athanassoulis and others, EDBT 2016). The [amplification lesson](/databases/storage/read-write-and-space-amplification) shows it for all storage engines.

## Two shapes

**Leveled compaction** is the default in LevelDB and RocksDB. L0 holds the flush output, and its files can overlap. Each deeper level Li is one sorted run, cut into files of `target_file_size_base` (64 MiB in RocksDB).

Each level has a byte budget. In RocksDB, L1 gets `max_bytes_for_level_base` (256 MiB), and each next level gets $T$ times more. $T$ is the **size ratio** (`max_bytes_for_level_multiplier`, default 10). When a level is over its budget, the engine picks one file. It merges the file with the files of the next level that overlap its key range.

**Tiered compaction** lets each level collect up to $T$ runs of about the same size. When a level has $T$ runs, all of them merge into one run in the next level. Cassandra's size-tiered strategy (by default, 4 similar runs merge) and RocksDB's universal compaction work like this.

## Write amplification

<Steps>
<div>**Tiered.** A merge writes each byte once into the next level. A byte moves through about $L = \log_T(D/W)$ levels, where $D$ is the data size and $W$ the memtable size. So $\text{WA} \approx L$.</div>
<div>**Leveled, one level.** A byte that moves from Li to Li+1 merges with the overlapping part of Li+1. When Li+1 is full, that part is $T$ times bigger, so the merge writes $T + 1$ bytes per byte moved.</div>
<div>While Li+1 fills from empty to full, the overlap grows from 0 to $T$. On average, a byte that moves down costs about $T/2$.</div>
<div>Add the flush (1 byte) and the L0 → L1 merge ($1 + B/(F_0 W)$, with $B$ the L1 budget and $F_0$ the L0 trigger). So $\text{WA} \approx 2 + B/(F_0 W) + (T/2) \log_T(D/B)$.</div>
<div>Example: RocksDB defaults and 100 GiB of data. $\log_{10}(400) = 2.6$ levels below L1 give 13.0, so the total is 16.0. Every user byte becomes 16 bytes of disk writes.</div>
</Steps>

## The trade-off

| | Leveled | Tiered |
|---|---|---|
| Write amp | about $T/2$ per level, up to $T + 1$ | about 1 per level |
| Sorted runs | L0 files plus 1 per level | up to $T - 1$ per level |
| Space amp, worst case | $T/(T-1)$: 1.11 for $T = 10$ | up to $T$ copies of hot keys |
| Good for | reads, scans, space | heavy writes, write-once data |

Leveled space amplification is small for a reason. With $T = 10$, the last level holds about 90% of the data. Even if all upper levels hold only old versions, they add at most 11%. RocksDB's `level_compaction_dynamic_level_bytes` (the default since version 8.4) sets the level budgets from the real size of the last level. It keeps this bound true when the data size changes.

Tiered compaction has a worse problem. A full merge of the last level needs free space for a full copy of the data while it runs. RocksDB's universal compaction limits the space with `max_size_amplification_percent` (default 200). Above that limit, it merges all runs.

## Which compaction runs next

The engine computes a **score** for each level. For L0, it is the number of files divided by `level0_file_num_compaction_trigger` (default 4). For a deeper level, it is the level size divided by its budget. The level with the highest score of at least 1 goes first.

In that level, the engine must choose a file. LevelDB walks the key space round-robin. Newer RocksDB versions prefer the file with the smallest overlap ratio below it (`kMinOverlappingRatio`), so they write less.

If a file overlaps nothing in the next level, the engine only changes the metadata. This is a **trivial move**, and it costs no I/O. With keys that only grow, such as time stamps, every compaction is a trivial move. The write amp then stays at 1.

```cpp
// RocksDB: leveled compaction with dynamic level sizes and the default priority.
options.compaction_style = rocksdb::kCompactionStyleLevel;
options.level_compaction_dynamic_level_bytes = true;
options.compaction_pri = rocksdb::kMinOverlappingRatio;
options.max_background_jobs = 8;   // flushes and compactions run in parallel
options.max_subcompactions = 4;    // split one big L0 -> L1 job into parallel ranges
```

## Tombstones

Compaction can drop a tombstone only when two conditions are true. First, no lower level can hold an older version of the key. In practice, the tombstone must reach the bottom of the data for its key range. Second, no live snapshot must need the old version. Until then, the tombstone uses space, and every scan must read and skip it.

This hurts queues and other delete-heavy patterns. A scan from the head of a queue can read thousands of tombstones before the first live key. RocksDB has tools for this. `DeleteRange` writes one range tombstone in place of many point tombstones. `NewCompactOnDeletionCollectorFactory` marks a file for compaction when it holds many tombstones. `SingleDelete` removes a key that was written only once, and it can drop both entries early.

## L0 and write stalls

L0 files overlap, so a lookup must check all of them. If flushes add L0 files faster than compaction removes them, reads slow down.

RocksDB then protects itself in two steps. At `level0_slowdown_writes_trigger` (20 files), it limits writes to `delayed_write_rate`. At `level0_stop_writes_trigger` (36 files), it stops writes. LevelDB uses 8 and 12 files. RocksDB also stalls when the bytes that wait for compaction pass 64 GiB (soft limit) or 256 GiB (hard limit).

Things to try:

1. Keep 20 MiB/s of writes. L0 never passes the trigger by much, and no write waits. Compaction below L1 already needs 520 MiB/s of the 1000 MiB/s.
2. Move the writes to 40 MiB/s. The deep levels now take almost all the bandwidth. L0 grows to the slowdown limit, and the engine spends 16% of the time slowed down. The average falls to 36.1 MiB/s.
3. Move **Compaction bandwidth** up until the stalls stop. A write rate needs about $2 \times \text{WA}$ times that rate in disk bandwidth.
4. Select a 256 MiB write buffer. L0 gets fewer, larger files, but each L0 → L1 job takes longer.

A stall is a symptom. The cause is that compaction cannot keep up with the write rate times the write amplification. More compaction threads, faster disks, a lower WA or a lower write rate fix it. A higher stall trigger only delays it.

## FIFO compaction

Some data only expires: logs, metrics, cache entries. For these, RocksDB has `kCompactionStyleFIFO`. All files stay in L0, and the engine never merges them. When the total size passes `compaction_options_fifo.max_table_files_size`, it deletes the oldest file. A time-to-live option can delete files by age. The write amp is 1, but a lookup must check every file, so filters are important.
