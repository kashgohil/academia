A column holds values of one type, often with few distinct values or in sorted order. So a column compresses much better than a row, which mixes types. Compression in an analytical engine has two goals. It reduces the bytes that the disk and memory must move. It also lets the engine do less work per value, because some operators can run on the compressed form.

There are two kinds of compression. A **lightweight encoding** uses the meaning of the values: runs, small ranges, repeated strings. It is fast to decode, and often the engine can skip the decode. A **general-purpose codec** such as LZ4 or Zstd sees only bytes. It finds repeated byte sequences in any data, but the engine must decompress a whole block before it can read one value.

## The lightweight encodings

- **Run-length encoding (RLE)** stores each run of equal values once, with its length. It needs long runs, so it works on sorted or clustered columns.
- **Dictionary encoding** stores each distinct value once, in a dictionary. The column then holds small integer **codes**. It works when the column has few distinct values.
- **Frame of reference (FOR)** stores, for each block, the minimum value. Each value is then stored as its small offset from that minimum.
- **Delta encoding** stores the difference between each value and the previous value. Sorted IDs and timestamps have small, nearly equal differences.
- **Bit-packing** stores each integer in exactly as many bits as the largest value needs, not in 32 or 64 bits. FOR, delta and dictionary codes all end in bit-packing.

The bit width for values in $0 \ldots m$ is $\lceil \log_2(m + 1) \rceil$. So 8 distinct strings need 3-bit codes, and offsets up to 400 need 9 bits.

## Why sorted data compresses better

RLE and delta depend on the order of the rows. A sort brings equal values together, so runs get long and deltas get small. In a table, only one sort order exists. So the choice of the sort key decides which columns compress well.

Things to try:

1. Keep **unsorted**. The status column has only 3 values, but it still has 1,363 runs in 4,096 rows. RLE makes the table only 6% smaller.
2. Select **region, country**. Region falls to 4 runs and country to 17. Country is sorted inside each region, and each country is in one region.
3. Select **status, region, country, day**. The first keys have few distinct values, so each later key still gets long runs. The table under RLE is now 24% of its plain size.
4. Select **customer, status**. Customer has 1,000 values, so its runs are short, and they break every column after it. The sort hardly helps.

The rule is: sort by the low-cardinality columns first. C-Store and Vertica chose a sort order for each **projection** for this reason. ClickHouse sorts each part by the `ORDER BY` key, and its documentation also suggests low-cardinality columns first.

## Running queries on compressed data

An engine that decodes everything before it starts gets only the I/O saving. Abadi, Madden and Ferreira (2006) showed that operators can work on the compressed form directly:

- **SUM over RLE** adds `value × length` once per run, not once per value.
- **A predicate on a dictionary column** looks up the constant once in the dictionary. Then it compares integer codes, never strings. An order-preserving dictionary also turns `<` and `>` into code ranges.
- **A predicate on FOR data** subtracts the block minimum from the constant once. Then it compares the small offsets.

The integer compares are also easy to vectorize. A SIMD instruction can compare many 8-bit or 16-bit codes in one step, and some engines compare bit-packed codes without unpacking them.

## General-purpose codecs

LZ4 replaces a byte sequence that occurred before with a short back-reference: an offset and a length. Its block format is simple, and the lab above runs a real LZ4 encoder. Zstd adds entropy coding (Huffman and FSE) on top of the same kind of matching, so it compresses more but runs slower. Snappy and LZ4 favor speed, and Zstd and gzip favor ratio.

```cpp
// Decode one LZ4 sequence: token, literals, then a back-reference into the output so far.
auto read_len = [&](size_t len) {             // 15 means: more length bytes follow
  if (len == 15) { uint8_t b; do { b = *ip++; len += b; } while (b == 255); }
  return len;
};
uint8_t token = *ip++;
size_t lit = read_len(token >> 4);
std::memcpy(op, ip, lit); ip += lit; op += lit;
if (ip == end) return op;                     // the last sequence has only literals
uint16_t offset = ip[0] | (ip[1] << 8); ip += 2;
size_t len = read_len(token & 15) + 4;        // the minimum match is 4 bytes
for (size_t i = 0; i < len; i++, op++) *op = *(op - offset); // the copy may overlap
```

Engines often use both kinds of compression. Parquet first encodes a page (for example with a dictionary), then compresses it with a codec. Spark writes Snappy by default. ClickHouse compresses each column block with LZ4 by default, and a column can name a chain such as `CODEC(Delta, ZSTD)`. DuckDB relies on lightweight encodings in its own storage format, so a scan usually needs no general-purpose decompress step.

**Strings** need special care, because each value has a different length. Dictionary encoding works for few distinct strings. **FSST** (fast static symbol table, Boncz, Neumann and Leis, 2020) handles the rest. It learns a table of up to 255 frequent substrings of 1 to 8 bytes, and replaces each one with a 1-byte code. Code 255 escapes a literal byte.

Each string still decodes on its own, so a single value can be read without its neighbors. DuckDB uses FSST for string columns.

**Floats** are hard, as the lab shows. Gorilla (Facebook, 2015) stores the XOR of each value with the previous one, which works for slowly changing metrics. ALP, which DuckDB uses, finds decimals that were stored as doubles and turns them back into integers.

## Choosing per column

No encoding wins for every column, so engines pick one per column and per block:

- **Parquet** encodings are `PLAIN`, `RLE_DICTIONARY`, `RLE` (for booleans and levels), `DELTA_BINARY_PACKED`, `DELTA_LENGTH_BYTE_ARRAY`, `DELTA_BYTE_ARRAY` and `BYTE_STREAM_SPLIT`. Writers try a dictionary first and fall back to plain when the dictionary page gets too large.
- **DuckDB** analyzes each column segment at checkpoint time. Every method (constant, RLE, dictionary, bit-packing with FOR and delta, FSST, ALP and others) estimates its size, and the smallest one wins.

The lab marks the same choice: the smallest lightweight encoding.

```ts
function chooseEncoding(type: ColType, values: Value[]): EncodingResult {
  return encodeAll(type, values)
    .filter((r) => r.encoding !== "lz4")              // lightweight only, as in DuckDB storage
    .reduce((a, b) => (b.bytes < a.bytes ? b : a));   // smallest estimate wins
}
```

Compression has costs too. Encoded blocks cannot change in place, which is one reason for the delta stores in the [column stores lesson](/databases/olap/column-stores). A codec with a high ratio can make a fast disk wait for the CPU. And a block-level codec forces a full block decode even to read one row.
