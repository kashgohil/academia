A column store keeps each column apart, but a query returns rows. So at some point the engine must **materialize** tuples: copy the values of one row from several columns into one row-shaped record. The question is when. Abadi, Myers, DeWitt and Madden studied it in "Materialization Strategies in a Column-Oriented DBMS" (ICDE 2007).

- **Early materialization** builds row tuples as soon as it reads the columns. After that, the plan works like a row store.
- **Late materialization** keeps the columns apart for as long as possible. Operators pass **positions**, the row numbers that are still alive, not values. The engine reads the output columns only at the end, and only at the surviving positions.

## Positions, bitmaps and selection vectors

A **position list** is a sorted array of row numbers. A filter on a column writes the positions where the predicate is true. The next operator reads its column only at those positions. Two position lists combine with a merge, which gives their intersection.

A **bitmap** has one bit per row. Two predicates can scan their columns in parallel, and an AND of the bitmaps combines them, one machine word at a time. A dense result is smaller as a bitmap than as a list of 32-bit positions. A sparse result is smaller as a list.

A **selection vector** is the form that vectorized engines use (see [vectorized execution](/databases/query/vectorized-execution)). DuckDB processes vectors of 2,048 values, and Velox uses the same idea. A filter does not copy the surviving values. It writes a short array of the indexes that are still active, and later operators read only those indexes.

```go
// A filter that writes a selection vector. It copies no values, only indexes.
func filterGreater(vec []int32, sel []uint16, limit int32, out []uint16) []uint16 {
	out = out[:0]
	for _, i := range sel {
		if vec[i] > limit {
			out = append(out, i)
		}
	}
	return out
}
```

## Why late wins, and when it loses

Late materialization saves work in three ways:

- **It reads less.** Columns after the first filter are read only at surviving positions. With a selective predicate, most values are never touched.
- **It copies less.** Tuples are built only for output rows. Early materialization copies every value of every row, then throws most tuples away.
- **It keeps the data compressed for longer.** A predicate on an RLE or dictionary column runs on the compressed form (see [compression](/databases/olap/compression)). Early materialization must decode every value to put it into a tuple.

It also has costs. Each position list must be written and read. A fetch by position is a **gather**: it reads scattered values, not a sequential stream, so the hardware prefetcher helps less. If the output also needs a predicate column, the late plan reads that column a second time. This is the **re-access** problem.

The cost model is simple, but it follows the shape of the real result. Early materialization pays for every input row. Late materialization pays for every surviving row, at a higher price per row:

<Steps>
<div>Early: scan $k$ columns, copy $k$ values per row, check the predicate per row. The cost per input row is a constant, $C_E$.</div>
<div>Late: scan the predicate column, write $s$ positions, gather $s$ values from each of $m$ output columns, copy $s \cdot m$ values. The cost is $C_P + s \cdot (1 + m \cdot (g + 1))$ plus cache misses.</div>
<div>The gather price $g$ is larger than a sequential read. At $s = 1$ the late plan does all of the early work, plus the positions and the gathers.</div>
<div>So late wins below some selectivity and loses above it. More output columns and re-access move the crossover down.</div>
</Steps>

Abadi and others measured the same pattern in C-Store. Late materialization won by a large factor for selective predicates, most of all on compressed columns. Early materialization won when most rows passed and the query output many columns. In practice, engines decide per operator. DuckDB evaluates scan filters with selection vectors, and it skips the other columns of a vector when no row in it passes. The Rust Parquet reader (arrow-rs) can take a row filter: it decodes the filter columns first, then the other columns only for the selected rows.

## Joins

Joins make late materialization harder. A hash join produces pairs of positions, one from each side, and these positions are not in order. A late fetch from the probe side is then a random gather over the whole column. Many engines materialize the join keys early for this reason, and keep the wide payload columns late.

The **invisible join** (Abadi, Madden and Hachem, 2008) handles the common star-schema case. A fact table holds foreign keys into small dimension tables:

1. Apply each dimension predicate to its dimension table, and build a hash set of the keys that pass.
2. Scan each foreign-key column of the fact table, probe its set, and write a position list.
3. AND the position lists. Only the fact rows that pass every dimension remain.
4. For the output, read the dimension values. Dimension keys are often dense integers, so the key itself is the position in the dimension column.

```rust
// Step 4 of the invisible join: a dense dimension key is an array index, not a hash probe.
fn dim_values<'a>(fk: &[u32], positions: &[u32], dim_col: &'a [&'a str]) -> Vec<&'a str> {
    positions.iter().map(|&p| dim_col[(fk[p as usize] - 1) as usize]).collect()
}
```

If the passing dimension keys form a contiguous range, step 2 becomes a range check on the foreign key. Abadi called this **between-predicate rewriting**. No hash table is needed at all.
