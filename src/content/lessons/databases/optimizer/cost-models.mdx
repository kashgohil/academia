A SQL query says what rows you want, not how to get them. The **optimizer** (also called the planner) chooses how. It lists the possible **plans**: trees of operators such as scans, joins and sorts. It gives each plan a **cost**, which is an estimate of the work it does. Then it runs the cheapest plan.

The cost is not a time. It is a sum of three kinds of work:

- **I/O**: pages read from disk or from the OS page cache, in order or at random positions.
- **CPU**: tuples (rows) passed through an operator, and operators (comparisons, hashes) evaluated on them.
- **Memory**: a sort or a hash table that does not fit in `work_mem` writes temporary files, which adds I/O.

The optimizer cannot measure these before it runs the query. It estimates them from **statistics**: the number of rows and pages of each table, and the distribution of values in each column. The next lesson, [cardinality estimation](/databases/optimizer/cardinality-estimation), is about those statistics. This lesson takes the row counts as given and asks how they become a cost.

## PostgreSQL's cost units

PostgreSQL measures cost in units of one sequential page read. Five settings give the price of everything else:

| Setting | Default | The price of |
|---|---|---|
| `seq_page_cost` | 1.0 | one 8 KiB page read as part of a sequential scan |
| `random_page_cost` | 4.0 | one page read at a random position |
| `cpu_tuple_cost` | 0.01 | passing one row through a plan node |
| `cpu_index_tuple_cost` | 0.005 | processing one index entry |
| `cpu_operator_cost` | 0.0025 | evaluating one operator or function call |

The PostgreSQL documentation explains the 4.0: random access is about 40 times slower than sequential access, but about 90% of random reads hit a cache. So $40 \times 0.1 = 4$. The CPU constants are small because one page holds many rows.

## Three ways to read one table

The PostgreSQL documentation uses a table `tenk1` with 10,000 rows of 244 bytes in 345 pages: 29 rows per page. It has a B-tree index `tenk1_unique1` with 30 pages. Here are the three access paths for `WHERE unique1 < 100`.

A **sequential scan** reads every page in order and checks every row:

$$\text{cost} = \text{pages} \times \texttt{seq\_page\_cost} + \text{rows} \times (\texttt{cpu\_tuple\_cost} + n_\text{quals} \times \texttt{cpu\_operator\_cost})$$

With no filter, that is $345 + 10{,}000 \times 0.01 = 445.00$. With one filter it is 470.00. These are the numbers that `EXPLAIN` prints in the documentation, and our model gives them exactly.

An **index scan** descends the B-tree, reads the matching index entries in key order, and fetches each row from the heap. The heap fetches are random reads unless the table is stored in index order. A **bitmap scan** first reads all matching index entries into a bitmap of row positions. Then it reads the marked heap pages in physical order, so it reads each page only once.

### The heap part of each formula

For an index scan, PostgreSQL computes two extremes. If the index order is random, each fetched row costs one random page read. The number of distinct pages comes from the **Mackert–Lohman** formula, which models an LRU cache of the table's share of `effective_cache_size`. If the index order matches the heap order, the scan reads $\lceil s \cdot \text{pages} \rceil$ pages, mostly in sequence. The cost interpolates between the two with the square of the column's **correlation**, a statistic between −1 and 1.

For a bitmap scan, the pages are read in order, but with gaps. The price per page falls from `random_page_cost` towards `seq_page_cost` as the fraction of pages read grows:

```rust
/// cost_bitmap_heap_scan(), the heap part (loop_count = 1).
fn bitmap_heap_cost(t: &Table, sel: f64, p: &CostParams) -> f64 {
    let tuples = (sel * t.rows).round().max(1.0);
    let pages_total = t.pages;
    let mut pages = 2.0 * pages_total * tuples / (2.0 * pages_total + tuples);
    pages = if pages >= pages_total { pages_total } else { pages.ceil() };
    let per_page = if pages >= 2.0 {
        p.random_page_cost - (p.random_page_cost - p.seq_page_cost) * (pages / pages_total).sqrt()
    } else {
        p.random_page_cost
    };
    pages * per_page + tuples * (p.cpu_tuple_cost + p.cpu_operator_cost) // recheck the qual
}
```

For `unique1 < 100` this gives 88 pages at 2.48 each. The index scan pays 4.0 for most of the same pages.

## Startup cost and total cost

`EXPLAIN` prints two costs for each node: `cost=startup..total`. The **startup cost** is the work before the node can return its first row. The **total cost** is the work to return all rows. A seq scan has startup 0. A sort, a hash table build and a bitmap must read all of their input first, so their startup cost is high.

The two numbers matter when the query does not need all rows. For `LIMIT k`, PostgreSQL charges $\text{startup} + (\text{total} - \text{startup}) \times k / \text{rows}$. That is why a `LIMIT` often turns a hash join into a nested loop, or a sort into an index scan in key order.

## When the plan flips

The planner compares straight lines and curves. Where two cost curves cross, the plan changes at once. A small change in a statistic or a setting can move a query to the other side of a crossing.

### Why SSD setups lower random_page_cost

The default 4.0 dates from spinning disks. On an SSD, a random 8 KiB read costs only a little more than a sequential one, and a large cache absorbs many reads. Many guides suggest 1.1 to 1.5 for SSDs. Set it with `ALTER TABLESPACE ... SET (random_page_cost = 1.1)` or for the whole server. Measure first: a lower value makes the planner choose index scans more often, and an index scan on a cold, large table can be slow.

### effective_cache_size

`effective_cache_size` (default 4 GB) does not allocate memory. It tells the planner how much of the database the OS cache and `shared_buffers` can hold together. Only the Mackert–Lohman part uses it. If the table is larger than its share of the cache, repeated reads of the same page count as new reads. A 1% index scan of `events` costs 3.99 M at 128 MB, 3.06 M at 4 GB and 2.94 M at 64 GB. The bitmap scan costs 1.33 M at every setting, so it wins in all three.

## Join costs

The same constants price joins. A **nested loop** runs its inner side once for each outer row. Each candidate pair costs `cpu_tuple_cost` plus the join condition. If the inner side is an index scan, each run is a short B-tree lookup. A **hash join** reads the inner side once, builds a hash table, then probes it once for each outer row. Its startup cost includes the whole build.

## What the model leaves out

The formulas are cheap, which matters: the planner may cost thousands of paths for one query. But they make strong assumptions. Every page read of one kind costs the same. CPU costs do not depend on the data type. Concurrent queries, parallel workers and the real cache state do not exist. The largest error is usually not in the formulas but in the row counts that go into them.
