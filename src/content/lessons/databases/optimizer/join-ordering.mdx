A query that joins $n$ tables gives the same result in any join order. The cost does not stay the same. One order keeps every intermediate result small. Another order first joins two large tables that share no predicate, and builds a result of billions of rows that a later join throws away. Join ordering is the part of optimization where the difference between plans is largest.

## The query graph and the cost model

Draw each table as a node and each join predicate as an edge. This is the **query graph**. Its shape decides how hard the problem is:

- **Chain**: A–B–C–D, as in a path through foreign keys.
- **Star**: one fact table joined to many dimension tables, as in a data warehouse.
- **Cycle** and **clique**: extra predicates that close loops. A clique has an edge between every pair.

A join of two tables with no edge between them is a **cross product**. Its size is the product of the input sizes.

To compare orders we need a cost. We use $\boldsymbol{C}_{\textbf{out}}$: the sum of the sizes of all intermediate results. It ignores the join algorithm, but it follows the real work closely. Leis et al. found that simple cost models like it give good plans when the cardinalities are right. The size of a set of tables is the product of their row counts and of the selectivities of the edges inside the set. That is the independence assumption from [cardinality estimation](/databases/optimizer/cardinality-estimation).

## How large is the search space?

A **left-deep** tree joins one new base table at each step: $((A \bowtie B) \bowtie C) \bowtie D$. There are $n!$ of them, one for each order of the tables. A **bushy** tree may join two intermediate results. The number of binary tree shapes with $n$ leaves is the Catalan number $C_{n-1}$, and each shape can hold the tables in $n!$ orders:

$$
\text{bushy}(n) = C_{n-1} \cdot n! = \frac{(2n-2)!}{(n-1)!}
$$

| Tables | Left-deep ($n!$) | Bushy ($C_{n-1} \cdot n!$) |
|---|---|---|
| 4 | 24 | 120 |
| 6 | 720 | 30,240 |
| 10 | 3,628,800 | 17,643,225,600 |
| 12 | 479,001,600 | $2.8 \times 10^{13}$ |

## Selinger's dynamic programming

Selinger et al. described the System R optimizer in 1979. The key idea is the **principle of optimality**. The best plan for a set of tables contains the best plans for the two parts it joins. So the optimizer solves each subset once, from the smallest to the largest, and stores the best plan in a table:

```rust
/// DPsub: the best C_out for every connected subset, by increasing subset value.
/// A proper subset of s has a smaller value than s, so it is solved before s.
fn dp_sub(n: usize, card: &[f64], connected: impl Fn(u32) -> bool, linked: impl Fn(u32, u32) -> bool) -> f64 {
    let full = (1u32 << n) - 1;
    let mut best = vec![f64::INFINITY; 1 << n];
    for i in 0..n { best[1 << i] = 0.0; }                  // a base table costs nothing
    for s in 1..=full {
        if s.count_ones() < 2 || !connected(s) { continue; }
        let mut l = (s - 1) & s;                           // every non-empty proper subset of s
        while l > 0 {
            let r = s ^ l;
            if l > r && linked(l, r) && best[l as usize].is_finite() && best[r as usize].is_finite() {
                let c = best[l as usize] + best[r as usize] + card[s as usize];
                best[s as usize] = best[s as usize].min(c);
            }
            l = (l - 1) & s;
        }
    }
    best[full as usize]
}
```

### Interesting orders and other dimensions

System R kept more than one plan per subset. A plan whose output is sorted on a join column or an `ORDER BY` column can save a sort later. Such a sort order is an **interesting order**. The DP keeps the cheapest plan for each subset and each interesting order. PostgreSQL does the same with **pathkeys**. Its `add_path()` keeps a path if no other path is better in every dimension: total cost, startup cost, sort order and parameterization.

### Avoiding cross products

The DP above skips any split without an edge between its parts. That cuts the search space a lot: a chain of 10 tables has 165 splits to consider, a clique 28,501. System R and PostgreSQL both postpone cross products. PostgreSQL considers a clauseless join only when no join with a predicate is possible.

DPsub, as written above, still enumerates every subset and every split, and then rejects most of them. **DPccp** (Moerkotte and Neumann, 2006) enumerates only the pairs of a connected subgraph and a connected complement. Its work is exactly the number of such pairs: $(n^3 - n)/6$ for a chain, $(n-1)\,2^{n-2}$ for a star and $(3^n - 2^{n+1} + 1)/2$ for a clique. **DPhyp** extends it to complex predicates that touch more than two tables. DuckDB and MySQL's newer hypergraph optimizer use DPhyp.

## Left-deep or bushy?

A left-deep plan has practical advantages. Each join reads one base table, so it can be an index nested loop on that table. With hash joins, the intermediate result streams through a pipeline of probes. MySQL's classic optimizer builds only left-deep plans. It uses a greedy search whose depth `optimizer_search_depth` limits.

Bushy plans can be much cheaper, as the fixed example shows: 48.1 times in $C_{\text{out}}$. They also allow two independent subtrees to run in parallel. PostgreSQL's DP considers bushy plans, and so do most modern optimizers.

## Many tables: greedy and genetic search

Exhaustive DP grows like $3^n$ on a clique. For large queries, optimizers fall back to heuristics:

- **Greedy Operator Ordering** (GOO, Fegaras 1998) starts with one tree per table. At each step it joins the two trees whose result is smallest. It is fast and often good, but one early choice can lock in a bad plan.
- **Randomized search** (iterative improvement, simulated annealing) starts from random plans and changes them step by step.
- **PostgreSQL GEQO** treats a join order as a permutation, as in the travelling salesman problem. It runs a genetic algorithm with edge recombination crossover over a pool of orders. GEQO starts when a query has `geqo_threshold` (12) or more FROM items.

PostgreSQL has two more limits. `join_collapse_limit` (8) stops the planner from reordering explicit `JOIN` clauses past eight items, and `from_collapse_limit` (8) stops it from merging subqueries into the parent's search. Above these limits the written order constrains the plan. Raise them for a large query whose order you do not want to fix by hand.
