`EXPLAIN` prints the plan that the optimizer chose, with its estimates. `EXPLAIN ANALYZE` also runs the query and prints what really happened. The difference between the two is where most performance problems show. The `BUFFERS` option adds the pages that each node touched.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT c.country, sum(o.total) FROM orders o JOIN customers c ON c.id = o.customer_id
WHERE o.created_at >= DATE '2026-10-01' GROUP BY c.country ORDER BY 2 DESC LIMIT 10;
```

`EXPLAIN ANALYZE` executes the statement. For an `UPDATE` or a `DELETE`, put it inside `BEGIN; ... ROLLBACK;`. In PostgreSQL 18, `ANALYZE` includes `BUFFERS` by default, and the actual row counts have two decimals.

## The anatomy of a plan line

A plan is a tree. Each node pulls rows from its children, so data flows from the most indented lines up to the top line. Read a plan from the inside out. Each node line has two groups of numbers:

```text
->  Hash Join  (cost=3606.97..6543.63 rows=42466 width=13) (actual time=9.524..25.182 rows=44164 loops=1)
                ^ startup ^ total     ^ estimate  ^ bytes                ^ first  ^ last   ^ real     ^ runs
```

- `cost=startup..total` is the estimate in planner units, as in [cost models](/databases/optimizer/cost-models). A node's cost includes its children.
- `rows` is the estimated number of rows that the node returns, and `width` the average row size in bytes.
- `actual time=first..last` is in milliseconds: the time to the first row and to the last row. It includes the children.
- `rows` in the actual part and `loops` say how many rows the node returned and how many times it ran.

The trap is `loops`. Some nodes run more than once, such as the inner side of a nested loop. For them, the time and the rows are **averages per loop**. The real total is the per-loop value times `loops`. A line with `actual time=0.064..0.763 rows=10 loops=8000` spent about 6.1 seconds in total, not 0.76 ms.

`Buffers: shared hit=5682 read=5682` counts 8 KiB pages. A **hit** page was in `shared_buffers`. A **read** page came from the operating system, which is either its page cache or the disk. `temp read` and `temp written` count pages of temporary files from sorts and hashes that did not fit in `work_mem`. Buffers, like time, include the children.

## The common node types

| Node | Reads | Look for |
|---|---|---|
| Seq Scan | every page of the table | `Rows Removed by Filter` much larger than `rows` |
| Index Scan | the index, then each matching heap row | many `loops`; random heap reads |
| Index Only Scan | only the index, if pages are all-visible | `Heap Fetches` near the row count: run `VACUUM` |
| Bitmap Index / Heap Scan | the index into a bitmap, then pages in order | `Heap Blocks: lossy` when `work_mem` is small |
| Nested Loop | the inner side once per outer row | a large outer side; a large `Rows Removed by Join Filter` |
| Hash Join + Hash | builds on the inner side, probes with the outer | `Batches` above 1: the hash spilled |
| Merge Join | two inputs sorted on the join key | an extra Sort below it |
| Sort | all of its input before the first row | `Sort Method: external merge  Disk: …` |
| HashAggregate | all input into a hash table of groups | `Batches` above 1, `Disk Usage` |
| Limit | stops early | a slow child with a high startup cost |

## Finding the problem

Work through a slow plan in this order:

1. **Find where the time goes.** Look for the node with the largest self time. Remember to multiply by `loops`.
2. **Compare estimated and actual rows**, from the bottom up. The lowest node where they differ by 10 times or more is usually the cause. Every node above it was planned for the wrong input.
3. **Look at the work per row.** A scan that removes almost all of its rows needs an index. A join that removes almost all of its pairs uses the wrong algorithm.
4. **Look for disk use.** `temp read` and `temp written`, `external merge`, and `Batches` above 1 mean that a sort or a hash did not fit in memory.

The fixes follow from the cause:

- **Bad estimates.** Run `ANALYZE` if the statistics are stale. Raise the statistics target of a skewed column. Add `CREATE STATISTICS` for related columns. Avoid predicates the planner cannot estimate, such as functions on a column, or give them an expression index.
- **Missing index.** Add an index on the filter or join column. A partial index or a covering index (`INCLUDE`) can make it smaller or allow an index-only scan.
- **Spills.** Raise `work_mem` for the session or the query, not for the whole server: every sort and hash node in every connection may use that much. Hash nodes may use `work_mem × hash_mem_multiplier` (2.0).
- **Wrong join algorithm.** Rewrite conditions that a hash or merge join cannot use, such as an `OR` across columns or a range. Fix the estimate that made a nested loop look cheap.

Do not leave `enable_nestloop = off` or similar switches in production. They do not forbid a node type; they add a very large cost to it. They hide the cause and can hurt other queries. Use them only to test what the planner would do without that node.

## MySQL

MySQL 8.0.16 and later print a similar tree with `EXPLAIN FORMAT=TREE`. MySQL 8.0.18 added `EXPLAIN ANALYZE`, which prints `(actual time=first..last rows=N loops=N)` like PostgreSQL. The tree reads the same way, with a few differences:

- The names differ: `Table scan on t`, `Index lookup on t using idx`, `Index range scan`, `Inner hash join`, `Nested loop inner join`, `Filter: (...)` as a separate node.
- Costs use MySQL's own units, so do not compare them with PostgreSQL costs.
- The classic MySQL optimizer builds left-deep plans only, so the tree has a simple shape.

The **MySQL FORMAT=TREE** view in the first demo shows our plan in this form.

## Plans in production

You cannot run `EXPLAIN ANALYZE` on every slow query by hand. The `auto_explain` module logs the plan of any statement slower than `auto_explain.log_min_duration`, and it can include `ANALYZE` numbers. `pg_stat_statements` shows which normalized queries use the most total time, so you know which plans to read first. Note that `ANALYZE` timing adds overhead for each row. `EXPLAIN (ANALYZE, TIMING OFF)` keeps the row counts and drops the per-node clock reads.
