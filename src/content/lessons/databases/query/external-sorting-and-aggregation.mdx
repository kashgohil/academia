Many operators need sorted data or groups: `ORDER BY`, `GROUP BY`, `DISTINCT`, the [sort-merge join](/databases/query/join-algorithms) and `CREATE INDEX`. In memory, a sort is easy. But a database must also sort a table of 100 GB with 64 MB of memory, and it must do so with few I/Os. The standard answer is **external merge sort**. It is also the base for one of the two ways to aggregate.

## External merge sort

The algorithm has two phases. Again, the data has N pages, and the sort has B buffer frames.

- **Run generation** (pass 0). Read B pages into memory, sort them, and write them back as a **run**: a sorted file of B pages. Repeat until all input is read. The result is $\lceil N/B \rceil$ runs.
- **Merge passes.** Keep one input frame for each of B − 1 runs and one output frame. Repeatedly move the smallest head key of the input frames to the output frame. Write the output frame when it is full, and read the next page of a run when its frame is empty. One merge makes one run from B − 1 runs.

Each merge pass divides the number of runs by B − 1. Each pass, including pass 0, reads and writes every page once.

<Steps>
<div>After pass 0 there are $\lceil N/B \rceil$ runs.</div>
<div>After merge pass $j$ there are $\lceil N/B \rceil / (B-1)^j$ runs, rounded up. The sort ends when one run is left.</div>
<div>So the number of merge passes is $\lceil \log_{B-1} \lceil N/B \rceil \rceil$, and the total is $\text{passes} = 1 + \lceil \log_{B-1} \lceil N/B \rceil \rceil$.</div>
<div>Each pass reads N pages and writes N pages, so the cost is $2N \cdot \text{passes}$ I/Os.</div>
</Steps>

## How memory changes the passes

The logarithm has base B − 1, so memory has a strong effect. With two passes, the sort can handle $B(B - 1)$ pages: B pages per run, and B − 1 runs in one merge. So a two-pass sort needs only about $\sqrt{N}$ frames of memory.

Real engines add three improvements:

- **A heap for the merge.** Picking the smallest of k heads by a linear scan costs k − 1 comparisons per row. A binary heap costs work in proportion to $\log_2 k$. With k = 511, the heap has only 9 levels.
- **Double buffering.** Two frames per run let the engine read the next page while it merges the current one. The fan-in drops to about B/2, but the CPU never waits for the disk.
- **Larger I/Os.** Each run is read in blocks of many pages, so the disk sees long sequential reads. This matters most on a hard disk, where each seek costs milliseconds.

```rust
// k-way merge of sorted runs with a binary heap: log2(k) comparisons per row.
use std::{cmp::Reverse, collections::BinaryHeap};

fn merge(mut runs: Vec<impl Iterator<Item = u64>>, out: &mut Vec<u64>) {
    let mut heap = BinaryHeap::new();
    for (i, r) in runs.iter_mut().enumerate() {
        if let Some(k) = r.next() { heap.push(Reverse((k, i))); }
    }
    while let Some(Reverse((k, i))) = heap.pop() {
        out.push(k);
        if let Some(next) = runs[i].next() { heap.push(Reverse((next, i))); } // refill from the same run
    }
}
```

In PostgreSQL, `EXPLAIN ANALYZE` names the method: `quicksort` when the input fits in `work_mem`, and `external merge` with the disk space used when it does not. PostgreSQL 15 replaced its old polyphase merge with a balanced k-way merge. DuckDB converts the sort keys into **normalized keys**: binary strings that compare correctly with `memcmp`.

## Replacement selection

Pass 0 does not have to make runs of exactly B pages. **Replacement selection** keeps a heap of M records. It writes the smallest key to the current run and reads the next input record. If the new key is at least as large as the last key written, it can still join the current run. If not, it is marked for the next run. A run ends when every record in the heap is marked.

On random input, the runs are about 2M records long. Knuth explains this with a snowplow on a circular road in constant snowfall. In the steady state, one lap clears twice the snow that lies on the road at any moment. Longer runs mean fewer runs, and sometimes one merge pass less.

Replacement selection has a cost: a heap operation for every record, with cache misses in a large heap. A quicksort of a full memory load is much more cache-friendly. PostgreSQL used replacement selection for its first run in version 9.6, and version 11 removed it. On modern hardware, the faster run generation was worth more than the longer runs.

## Sort against hash aggregation

`GROUP BY` and `DISTINCT` need all rows of a group together. There are two ways to do this:

- **Sort aggregation** sorts the input on the group key, then reads it in order. Each group is a range of adjacent rows. The last merge pass can feed the aggregate directly, so it never writes the sorted output.
- **Hash aggregation** keeps a hash table with one entry per group. Each row updates its entry. Memory depends on the number of groups G, not on the number of rows.

If the groups fit in memory, hash aggregation reads the input once, with no sort at all. If they do not fit, it must **spill**. PostgreSQL 13 added spilling to its `HashAggregate`.

Once the table is full, it still updates the groups that it holds. Rows of new groups go to partition files on disk. Each partition is then aggregated in the same way. DuckDB partitions its hash tables by the hash value before it spills.

Sort aggregation still has uses. Its output is sorted, which can save a later `ORDER BY`. It also streams if the input is already sorted, for example from an index. A planner compares both, and PostgreSQL shows the choice as `GroupAggregate` or `HashAggregate`.

## Top-N with a heap

`ORDER BY price LIMIT 10` does not need a full sort. A **max-heap** of the 10 smallest keys seen so far is enough. Each new key is compared with the largest key in the heap, and only a smaller key enters. Memory is 10 rows, and almost every row costs one comparison.

```cpp
// The k smallest keys: one comparison per row, plus log2(k) for the rare row that enters.
std::vector<int64_t> top_n(std::span<const int64_t> keys, size_t k) {
    std::priority_queue<int64_t> heap; // max-heap: top() is the largest of the k smallest
    for (int64_t x : keys) {
        if (heap.size() < k) heap.push(x);
        else if (x < heap.top()) { heap.pop(); heap.push(x); }
    }
    std::vector<int64_t> out;
    for (; !heap.empty(); heap.pop()) out.push_back(heap.top());
    return {out.rbegin(), out.rend()};
}
```

For 100,000 random keys and k = 10, the sim counts 100,411 comparisons. A full merge sort of the same keys needs 1,536,789. PostgreSQL uses this method when the limit is known at sort time, and EXPLAIN shows it as `top-N heapsort`.
