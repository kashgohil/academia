SQL says what result you want. It does not say how to compute it. Before a database can run a query, it translates the SQL text into a tree of **operators**. Each operator takes one or two tables as input and makes one new table. This set of operators is the **relational algebra**, which Edgar Codd defined in 1970.

The algebra matters for two reasons. First, it gives each SQL query an exact meaning. Second, it has **equivalence rules**: two different trees can always give the same result. A query optimizer uses these rules to replace a slow tree with a fast one. The rest of this module is about how engines run the operators. This lesson is about what the operators are and how the tree can change.

## Relations, sets and bags

A **relation** is a table: a **schema** (a list of named columns) and a collection of **tuples** (rows). In Codd's model, a relation is a set, so it has no duplicate rows and no row order. SQL tables are **bags** (multisets): the same row can occur many times. SQL keeps duplicates unless you ask for `DISTINCT`, because removing them costs a sort or a hash table.

No relation has an order either. `ORDER BY` is not part of the algebra. It is a request about the final output only. So a subquery with an `ORDER BY` but no `LIMIT` gives the engine no promise, and PostgreSQL can ignore that order.

## The operators

| Operator | Symbol | SQL | Result |
|---|---|---|---|
| Selection | $\sigma_p(R)$ | `WHERE p` | the rows of R where p is true |
| Projection | $\pi_{a,b}(R)$ | `SELECT a, b` | only the columns a and b |
| Cross product | $R \times S$ | `FROM R, S` | every pair of a row of R and a row of S |
| Theta join | $R \bowtie_p S$ | `JOIN ... ON p` | $\sigma_p(R \times S)$, computed without the full product |
| Natural join | $R \bowtie S$ | `NATURAL JOIN` | an equi-join on all columns with the same name |
| Union, difference, intersection | $\cup$, $-$, $\cap$ | `UNION`, `EXCEPT`, `INTERSECT` | set operations on tables with the same columns |
| Rename | $\rho_e(R)$ | `FROM emp e` | the same table with a new name |
| Grouping | $\gamma_{k;\,f}(R)$ | `GROUP BY k` with aggregates f | one row per group |
| Duplicate removal | $\delta(R)$ | `DISTINCT` | each row once |

A **theta join** has any predicate. An **equi-join** has only equality predicates, such as `e.did = d.did`. Most joins in real queries are equi-joins, and the fast join algorithms in [the join lesson](/databases/query/join-algorithms) need them. Grouping is an extension of Codd's algebra: it has no set-theory meaning, but every engine needs it.

Each operator takes relations and returns a relation, so operators compose. This property is **closure**. It is the reason a query is a tree: the output of one operator is the input of the next.

## From SQL to a tree

A parser and a binder turn the SQL text into a tree. The direct translation of a `SELECT-FROM-WHERE` block is the **canonical form**. Take the cross product of the FROM tables, apply one selection with the whole WHERE clause, and put a projection on top.

$$
\pi_{e.name,\,p.pname}\big(\sigma_{e.did = d.did \,\wedge\, p.did = d.did \,\wedge\, d.city = \text{Berlin} \,\wedge\, p.budget > 100}((E \times D) \times P)\big)
$$

`GROUP BY` adds a γ above the selection, and `HAVING` adds a σ above the γ. `DISTINCT` adds a δ at the top. A correlated subquery becomes a **semi-join** (for `EXISTS` or `IN`) or an **anti-join** (for `NOT EXISTS`), when the engine can unnest it.

The canonical form is correct, but it is a terrible plan. With 100 employees, 8 departments and 30 projects, the cross product alone has 24,000 rows.

## Equivalence rules

These rules hold for bags as well as for sets. Each one replaces a subtree with another subtree that gives the same rows.

| Rule | Equivalence | Condition |
|---|---|---|
| Cascade | $\sigma_{p \wedge q}(R) \equiv \sigma_p(\sigma_q(R))$ | none |
| Commute selections | $\sigma_p(\sigma_q(R)) \equiv \sigma_q(\sigma_p(R))$ | none |
| Push selection | $\sigma_p(R \times S) \equiv \sigma_p(R) \times S$ | p uses only columns of R |
| Form a join | $\sigma_p(R \times S) \equiv R \bowtie_p S$ | none |
| Commute joins | $R \bowtie S \equiv S \bowtie R$ | column order is fixed by a projection |
| Associate joins | $(R \bowtie S) \bowtie T \equiv R \bowtie (S \bowtie T)$ | each predicate moves to a join that has its columns |
| Push projection | $\pi_a(R \bowtie_p S) \equiv \pi_a(\pi_{a_R}(R) \bowtie_p \pi_{a_S}(S))$ | $a_R$ and $a_S$ keep the columns of a and of p |

A heuristic optimizer applies them in a fixed order. Split each selection into its conjuncts. Push each conjunct down to the lowest node that has all its columns. Turn a selection over a product into a join. Then choose a join order and prune columns.

## How an optimizer uses the rules

The rules define a **search space**: all the trees that are equivalent to the query. Selection pushdown almost always helps, so engines apply it as a heuristic, with no cost estimate. PostgreSQL attaches each WHERE condition to the lowest relation or join that has its columns. DuckDB has a separate filter pushdown pass in its optimizer.

Join order is different. The best order depends on table sizes and on how selective each predicate is, so the optimizer needs a **cost model**. At 50 employees, the rewritten join order of the demo is better. With other data, it can be worse. PostgreSQL searches join orders with dynamic programming up to 12 tables (`geqo_threshold`), and uses a genetic algorithm above that. The [join ordering lesson](/databases/optimizer/join-ordering) covers this search.

```rust
// Selection pushdown over a plan tree: put a predicate at the lowest node that has its columns.
fn push(pred: Pred, plan: Plan) -> Plan {
    match plan {
        Plan::Join { left, right, cond } if covers(&left, &pred) =>
            Plan::Join { left: Box::new(push(pred, *left)), right, cond },
        Plan::Join { left, right, cond } if covers(&right, &pred) =>
            Plan::Join { left, right: Box::new(push(pred, *right)), cond },
        Plan::Select { pred: p, input } => Plan::Select { pred: p, input: Box::new(push(pred, *input)) },
        other => Plan::Select { pred, input: Box::new(other) },
    }
}
```

The rules break in some places:

- **Outer joins.** In `R LEFT JOIN S ON ...`, a WHERE filter on S cannot move into S while the join stays an outer join. The join makes NULL-padded rows for R rows without a match, and the filter must see them. If the filter rejects NULLs, the optimizer first turns the outer join into an inner join, and PostgreSQL does this. A filter on S in the ON clause is different: it can move into S.
- **Volatile functions.** A predicate with `random()` or a side effect cannot move, because the number of calls changes.
- **Projection with DISTINCT.** π and δ do not commute: removing duplicates before or after dropping a column gives different counts.

## NULLs and three-valued logic

SQL uses **three-valued logic**: a comparison is TRUE, FALSE or UNKNOWN. Any comparison with NULL is UNKNOWN, even `NULL = NULL`. AND, OR and NOT follow these tables:

| p | q | p AND q | p OR q | NOT p |
|---|---|---|---|---|
| TRUE | UNKNOWN | UNKNOWN | TRUE | FALSE |
| FALSE | UNKNOWN | FALSE | UNKNOWN | TRUE |
| UNKNOWN | UNKNOWN | UNKNOWN | UNKNOWN | UNKNOWN |

WHERE keeps a row only when the predicate is TRUE. So rows with UNKNOWN disappear, and this causes real bugs:

- `did = 10` keeps 3 employees and `did <> 10` keeps 4. Together they keep 7 of 8, because Flo matches neither.
- `NOT IN` with a NULL in the list returns no rows at all. `40 NOT IN (10, 20, NULL)` is UNKNOWN, because `40 = NULL` is UNKNOWN. In the demo data, "departments not in the list of employee departments" returns 0 rows with NOT IN. `NOT EXISTS` and `EXCEPT` both return department 40.
- Set operations, `DISTINCT` and `GROUP BY` treat two NULLs as the same value. Comparisons do not. SQL calls this "not distinct", and `IS NOT DISTINCT FROM` is the comparison with that meaning.
- `COUNT(*)` counts rows, so it gives 8. `COUNT(salary)` skips NULLs and gives 7. `SUM` and `AVG` of no values are NULL, not 0.

The rewrite rules stay correct under three-valued logic, because σ treats UNKNOWN like FALSE everywhere. But a rewrite that turns `NOT IN` into an anti-join must handle NULLs on purpose. PostgreSQL does not make this change for `NOT IN` when NULLs are possible. That is one reason why `NOT EXISTS` is often much faster in PostgreSQL.
