The [relational algebra](/databases/query/relational-algebra) says what each operator computes. An engine also needs a way to connect the operators so that rows move from the tables to the client. The classic answer is the **iterator model**, which Goetz Graefe described for the Volcano system in 1994. Most row-oriented databases still use it, PostgreSQL among them.

## One interface for every operator

In the iterator model, every **physical operator** (an operator together with its algorithm, such as a hash join) has the same three functions:

- `open()` prepares the operator and calls `open()` on its inputs.
- `next()` returns the next output row, or a special end value (EOF) when there are no more rows.
- `close()` releases memory and calls `close()` on its inputs.

A parent gets rows by calling `next()` on its child. The child calls `next()` on its own child when it needs input. So rows are **pulled** from the root. The client calls `next()` on the root until it gets EOF.

```rust
trait Operator {
    fn open(&mut self);
    fn next(&mut self) -> Option<Row>; // None is EOF
    fn close(&mut self);
}

struct Filter { input: Box<dyn Operator>, pred: Box<dyn Fn(&Row) -> bool> }

impl Operator for Filter {
    fn open(&mut self) { self.input.open() }
    fn next(&mut self) -> Option<Row> {
        while let Some(row) = self.input.next() { // pull until a row passes
            if (self.pred)(&row) { return Some(row); }
        }
        None
    }
    fn close(&mut self) { self.input.close() }
}
```

The design is simple and general. An operator does not know which operators are above or below it. Any tree of operators works, and a new operator needs only these three functions. In PostgreSQL, the function `ExecProcNode` plays the role of `next()`. Each call returns one tuple slot. MySQL 8.0 rewrote its executor into iterators of this kind.

## Pipelines and pipeline breakers

In the first plan, a row goes from the scan to the client with no stop. It is never stored. A chain of operators like this is a **pipeline**. Pipelining keeps memory low and gives the first result row early.

Some operators cannot return a row before they have read a whole input. They are **pipeline breakers** (blocking operators):

- **Sort** must see every row, because the last input row can be the first output row.
- **Hash aggregation** must see every row of a group before the group is final. It holds one entry per group.
- **Hash join** must build its hash table from the whole build input. But it blocks only on that side: probe rows then stream through it.
- **Materialization**: a nested-loop join that must rescan its inner input, or a common subexpression used twice, stores rows.

A breaker cuts the plan into pipelines. The input pipeline must finish before the output pipeline can start. The breaker holds the data in between, so it needs memory. When the data is larger than memory, it spills to disk: see [external sorting and aggregation](/databases/query/external-sorting-and-aggregation).

## The cost of one call per row

The iterator model is elegant, but it is slow on a modern CPU. Each `next()` is an indirect call through a function pointer or a virtual table. Each operator checks its state, and each expression is interpreted node by node for each row. The plan for TPC-H query 1 does a few additions per row. In an iterator engine, the calls and the bookkeeping cost far more than the additions.

The number of calls is not the main problem. In the demo, a push model needs the same 19 calls as the pull model. The problem is the work per call: it is large, it is not inlined, and it is repeated for every row.

| Cost per row and operator | Why |
|---|---|
| An indirect call | the CPU cannot inline it; it may mispredict the target |
| A state check | each operator must know if it is in its build phase, at EOF, and so on |
| Interpreted expressions | `salary > 55` is a small tree of nodes, evaluated for each row |
| Poor locality | the code of all operators runs for each row, so the instruction cache works hard |

Two designs remove this overhead. **Vectorization** keeps the iterator interface but passes about a thousand rows per call, so the overhead is paid once per batch: see [vectorized execution](/databases/query/vectorized-execution). **Compilation** generates a tight loop for each pipeline, so no calls remain between operators: see [query compilation](/databases/query/query-compilation).

## Push instead of pull

In a **push-based** model, control goes the other way. The source of a pipeline (a scan or the output of a breaker) runs a loop. For each row, it calls `consume(row)` on its parent, which processes the row and calls `consume` on its own parent. A breaker ends a pipeline: its `consume` stores the row.

```go
// A push pipeline: the scan drives the loop; each operator pushes to its parent.
type Sink interface{ Consume(r Row) }

type Filter struct{ Pred func(Row) bool; Parent Sink }
func (f *Filter) Consume(r Row) { if f.Pred(r) { f.Parent.Consume(r) } }

func RunPipeline(rows []Row, first Sink) {
	for _, r := range rows { first.Consume(r) } // the loop lives in the source
}
```

HyPer used push-based pipelines for its compiled code in 2011. DuckDB moved from pull to push in 2021. Push has three advantages:

- **Tight loops.** The loop over the rows is in the source, so a compiler can fuse a whole pipeline into one loop.
- **Scheduling.** The pipeline is a natural unit of work. In **morsel-driven parallelism** (Leis et al., SIGMOD 2014), worker threads take small chunks of a pipeline's input, called morsels. In HyPer, a morsel was about 100,000 rows.
- **Shared results.** One operator can push its rows to two parents, so a plan can be a graph, not only a tree.

Pull is better at one thing: stopping early. A `LIMIT` in a pull plan simply stops calling `next()`. A push plan must send a signal back to the source to stop it.

| Engine | Model | Unit per call |
|---|---|---|
| PostgreSQL | pull (Volcano) | one tuple |
| MySQL 8.0 | pull (iterators) | one row |
| SQLite | bytecode program with nested loops | one row |
| DuckDB | push, morsel-driven | a vector of 2,048 values |
| HyPer, Umbra | push, compiled to machine code | one row inside a fused loop |
