**ARIES** (Algorithms for Recovery and Isolation Exploiting Semantics) is the recovery method that C. Mohan and his colleagues at IBM published in 1992. Db2 and SQL Server use it, and InnoDB follows the same plan. It works with the most flexible buffer pool, STEAL + NO-FORCE, from the [write-ahead logging](/databases/recovery/write-ahead-logging) lesson. After a crash, the disk can hold uncommitted changes, and it can miss committed changes. ARIES fixes both in three passes over the log.

The demo uses four pages, A to D, with one value each. Four transactions run, a fuzzy checkpoint happens in the middle, the buffer pool writes some pages, and T2 aborts. Then the power fails.

## The three passes

| Pass | Reads the log | Builds or does |
|---|---|---|
| Analysis | forward, from the last checkpoint to the end | the transaction table (ATT) and dirty page table (DPT) at the crash |
| Redo | forward, from the smallest recLSN in the DPT | every page as it was at the crash |
| Undo | backward, following the chains of the losers | rolls back the losers and writes CLRs |

### Analysis

A known place on disk holds the **master record**: the LSN of the last complete checkpoint. In PostgreSQL this is the `pg_control` file. Analysis loads the **ATT** (active transaction table) and **DPT** (dirty page table) from that checkpoint, and then reads forward:

- A record of a transaction that is not in the ATT adds it. Every record updates its lastLSN.
- A commit record marks the transaction committed. An abort record marks it aborting. An end record removes it.
- An update or CLR for a page that is not in the DPT adds the page, with recLSN = this LSN.

At the end, the ATT holds the **losers** (running or aborting) and the committed transactions that have no end record yet. The DPT holds every page that *may* be dirty. It can list too many pages, but never too few. Redo starts at the smallest recLSN in the DPT.

### Redo

Redo reads forward and looks at each update and CLR. It skips a record in three cases:

1. The page is not in the DPT. The change reached disk before the checkpoint.
2. The record's LSN is smaller than the page's recLSN. The page was written after this change and dirtied again later.
3. The page's pageLSN is greater than or equal to the record's LSN. The page already has the change. Only this check reads the page from disk.

Otherwise redo applies the record and sets pageLSN to its LSN. Redo is **physiological** and idempotent, as the lesson on [logging forms](/databases/recovery/physical-logical-and-physiological-logging) shows. It repeats history for losers too, because undo is logical and needs the pages in their real state at the crash.

### Undo

Undo rolls back all losers in one backward pass. It keeps the set ToUndo, which holds the next LSN to undo for each loser. It always takes the largest LSN, so the log is read backward only once:

```ts
// The undo pass of ARIES (src/sims/db/recovery/aries.ts, simplified).
const toUndo = new Set(losers.map((t) => att.get(t)!.lastLSN));
while (toUndo.size > 0) {
  const lsn = Math.max(...toUndo);
  toUndo.delete(lsn);
  const r = log.record(lsn);
  let next: Lsn;
  if (r.kind === "update") {
    // Undo the change and log the undo as a redo-only CLR.
    log.append({ kind: "clr", txn: r.txn, prevLSN: att.get(r.txn)!.lastLSN,
                 page: r.page, slot: r.slot, after: r.before, undoNextLSN: r.prevLSN });
    next = r.prevLSN;
  } else if (r.kind === "clr") {
    next = r.undoNextLSN;      // skip work that an earlier undo already did
  } else {
    next = r.prevLSN;          // abort record: keep walking the chain
  }
  if (next === 0) log.append({ kind: "end", txn: r.txn });
  else toUndo.add(next);
}
```

A **compensation log record (CLR)** describes one undo action. It is redo-only: recovery can repeat it, but never reverses it. Its **undoNextLSN** is the prevLSN of the record that it undid. So it points to the next record of the transaction that still needs undo.

## Why CLRs make recovery safe to repeat

Recovery can crash too. Redo is idempotent, so repeating it is harmless. Undo is the hard part: some undo actions reached the disk or the log, and others did not.

The argument has three steps:

<Steps>
<div>Redo replays CLRs like any update, so after redo, every durable undo action is in the pages again.</div>
<div>Undo never undoes a CLR. When it meets one, it jumps to the CLR's undoNextLSN, past the work that is already undone.</div>
<div>So each update of a loser is undone exactly once over all attempts. The log grows by at most one CLR for each update, and recovery always ends.</div>
</Steps>

The same mechanism serves normal rollback. A transaction that aborts writes CLRs as it goes. If the system crashes during the rollback, recovery continues it from the last CLR. ARIES also uses CLRs for **partial rollback** to a savepoint: undo back to the savepoint's LSN and stop.

## What the passes cost

Analysis and redo read the log from the checkpoint, or from the oldest recLSN if that is earlier. The cost of these passes depends on the checkpoint interval, which the [checkpoints](/databases/recovery/checkpoints) lesson explores. Undo depends on the work of the losers. One transaction that ran for an hour without a commit can mean an hour of log to undo.

Engines reduce that cost in different ways:

- **InnoDB** does redo first and then opens the database. Background threads roll back the incomplete transactions, and their row locks protect the rows meanwhile.
- **SQL Server** follows ARIES. Since SQL Server 2019, **accelerated database recovery** keeps row versions in a persistent version store. Undo then only marks the loser aborted, so it takes constant time.
- **PostgreSQL** has no undo pass at all. Redo replays the WAL from the redo point of the last checkpoint. MVCC makes the rows of losers invisible, because the commit log never says that the losers committed.
