Without checkpoints, the log grows forever, and recovery must read it from the very start. A **checkpoint** gives recovery a later starting point. It also tells the engine which old log it can delete or reuse. The price is I/O: dirty pages must reach the disk before the log that describes them can go.

## What a checkpoint must achieve

Recovery needs the log from two points:

- **Redo** needs it from the oldest change that may not be on disk: the smallest recLSN of a dirty page.
- **Undo** needs it from the first record of the oldest transaction that is still running.

The log before both points is garbage. A checkpoint records where recovery can start, and pushes that point forward. The log size and the recovery time both follow from the distance between the end of the log and that point.

## Sharp and fuzzy checkpoints

A **sharp** (consistent) checkpoint stops new updates, writes every dirty page, writes a checkpoint record, and lets work continue. Recovery starts at that record, and redo has nothing older to do. But the stop lasts as long as the page writes, which can be seconds or minutes with a large buffer pool.

A **fuzzy** checkpoint, as in ARIES, writes no pages at all:

1. Write a begin_checkpoint record.
2. Copy the active transaction table and the dirty page table. Work continues during and after the copy.
3. Write an end_checkpoint record with the copies, and flush the log.
4. Only then, store the LSN of begin_checkpoint in the master record.

```zig
pub fn checkpoint(self: *Engine) !void {
    // begin: note the position and copy the tables; workers keep running
    const begin = try self.log.append(.begin_checkpoint);
    var att = try self.att.clone(self.alloc);
    defer att.deinit();
    var dpt = try self.dpt.clone(self.alloc);
    defer dpt.deinit();
    // end: write the snapshot and make it durable
    const end = try self.log.append(.{ .end_checkpoint = .{ .begin = begin, .att = att, .dpt = dpt } });
    try self.log.flushTo(end);
    // a crash before this line simply uses the previous checkpoint
    try self.master.write(begin);
}
```

A fuzzy checkpoint costs almost nothing, but it moves the redo start only as far as the oldest dirty page allows. So engines also write old dirty pages in the background, to keep the oldest recLSN recent.

## PostgreSQL

A PostgreSQL checkpoint is between the two kinds. It notes the current WAL position as the **redo point**. Then the checkpointer process writes every buffer that was dirty at that moment, while transactions continue. It calls `fsync` on the data files, writes a checkpoint record, and updates `pg_control`. Recovery replays the WAL from the redo point of the last complete checkpoint.

A checkpoint starts for one of these reasons:

- `checkpoint_timeout` passed since the last one (default 5 min).
- The WAL since the last one reached about `max_wal_size / (1 + checkpoint_completion_target)`. With the defaults, 1 GiB and 0.9, that is 539 MiB.
- A `CHECKPOINT` command, a shutdown, or the end of a recovery.

`checkpoint_completion_target` spreads the writes over that part of the interval. Its default changed from 0.5 to 0.9 in PostgreSQL 14. If checkpoints come more often than `checkpoint_warning` (30 s), the server logs a warning to raise `max_wal_size`. The background writer also writes some dirty buffers ahead of time.

## InnoDB

InnoDB never stops for a checkpoint. Page cleaner threads write dirty pages from the **flush list**, which orders the dirty pages by the LSN of their oldest change. The checkpoint LSN is that oldest LSN. The **checkpoint age** is the current LSN minus the checkpoint LSN.

The checkpoint age must stay below the redo log capacity, because the redo log is reused in a circle. Adaptive flushing raises the write rate as the age grows. If the age comes too near the capacity, InnoDB must write the oldest pages before it can reuse their part of the log. The MySQL manual calls this a **sharp checkpoint**. User writes stall until it ends, so a small `innodb_redo_log_capacity` causes periodic stalls under heavy writes.

## The trade-off

| checkpoint_timeout | Checkpoints in 1 hour | Worst recovery | Data pages written | WAL written |
|---|---|---|---|---|
| 60 s | 59, by time | 3.3 s | 6.2 GiB | 6.5 GiB |
| 300 s | 11, by time | 12.7 s | 4.4 GiB | 5.0 GiB |
| 900 s | 4, by WAL size | 29 s | 3.1 GiB | 4.1 GiB |
| 1,800 s | 2, by WAL size | 48 s | 1.9 GiB | 3.5 GiB |

All rows use a target of 0.9 and a `max_wal_size` of 1 GiB. The pattern is general:

- **Recovery time** grows with the WAL since the redo point: about one interval, plus the time to complete the checkpoint.
- **Page writes** fall with longer intervals, because a hot page that changes many times is written once for each checkpoint.
- **WAL volume** falls with longer intervals, because each page needs a full image only once for each checkpoint.
- **I/O smoothness** comes from spreading. A spread checkpoint completes later, so the redo point moves later.

Most production systems choose long intervals, a large `max_wal_size`, and spread writes. They accept a recovery time of minutes, because a failover to a replica is faster than any recovery. SQL Server takes a different route. Its **indirect checkpoints** set a target recovery time, 60 s by default for new databases, and write pages to meet it.
