A log record must say what changed, so that recovery can do it again or reverse it. There are three styles:

- **Physical** logging records bytes: "at offset 59 of page 7, write `7`". A **full page image** is the extreme case: the record holds the whole page.
- **Logical** logging records an operation on a table: "UPDATE t SET qty = qty + 2 WHERE name = 'bob'". The record names no page.
- **Physiological** logging is "physical to a page, logical within a page". The record names one page and an operation inside it: "page 7, slot 1: set qty to 7".

The demos use one tiny 64-byte slotted page. The page has a 4-byte header: pageLSN, slot count, start of the record area, and checksum. A slot directory follows, and 4-byte records grow from the end. Real pages work the same way: see [pages and slotted records](/databases/storage/pages-and-slotted-records).

## Replay twice

Recovery cannot know how much of the work reached disk. The buffer pool may have written the page before the crash, after operation 4, or after operation 5. So redo must give the same result whether the page already has a change or not. A redo operation with this property is **idempotent**: doing it twice has the same effect as doing it once.

## Three forms compared

| Form | Example record | Size | Twice | Torn page | Used by |
|---|---|---|---|---|---|
| Physical: byte diff | offset 59: `7` | small for small changes, large when a page is reorganized | idempotent | repaired if the log reaches back to the last whole copy | rarely alone |
| Physical: full page image | all 8 KiB | very large | idempotent | repaired | PostgreSQL after each checkpoint, SQLite WAL frames |
| Physiological | page 7, slot 1: qty = 7 | small | idempotent with the pageLSN check | needs a valid page | ARIES redo, InnoDB redo, PostgreSQL redo |
| Logical | UPDATE ... qty + 2 | smallest | not idempotent | needs valid pages and indexes | ARIES undo, replication logs |

A byte diff is small for a one-byte update. But some page operations move every byte, for example compacting the free space or splitting a B-tree node. A physiological record for "compact page 7" is a few bytes, and redo runs the same compaction code again.

The sizes at real scale, under the assumptions in the sim, are about 146 bytes for a physiological update of a 100-byte row. A full image of an 8 KiB page costs 8,236 bytes, 56 times more.

## The pageLSN check makes redo idempotent

<Steps>
<div>Each page stores the LSN of the last record applied to it, and the page write stores it together with the data.</div>
<div>Records for one page are applied in LSN order, so the page contains exactly the records up to its pageLSN.</div>
<div>So a record with LSN ≤ pageLSN is already in the page, and a record with LSN > pageLSN is not.</div>
<div>Skip the first kind and apply the second. Any number of replays gives the same page.</div>
</Steps>

```cpp
// Physiological redo of one record. Safe to run any number of times.
void redo(const LogRecord& r, BufferPool& pool) {
    if (r.type == RecType::FullPageImage) {      // needs no old page at all
        pool.install(r.page_id, r.payload, r.lsn);
        return;
    }
    Page& p = pool.fetch(r.page_id);             // fails if the checksum is wrong
    if (p.page_lsn() >= r.lsn) return;           // the page already has this change
    switch (r.type) {
        case RecType::Insert:   p.insert(r.slot, r.payload); break;
        case RecType::SetField: p.record(r.slot).write(r.offset, r.payload); break;
        case RecType::Delete:   p.delete_slot(r.slot); break;
        default: break;
    }
    p.set_page_lsn(r.lsn);
    pool.mark_dirty(p, r.lsn);
}
```

The check works only if the pageLSN is true. A torn page breaks that assumption.

## Torn pages and full-page writes

A device writes one sector atomically, 512 bytes or 4 KiB. A database page is larger: an 8 KiB PostgreSQL page spans 16 sectors of 512 bytes. If power fails during the page write, some sectors are new and some are old. This is a **torn page**. A checksum detects it, but detection does not repair it.

Physiological redo must read the page to act on it, so it cannot start from a torn page. Engines use one of these fixes:

- **Full-page writes (PostgreSQL)**: the first change to a page after a checkpoint logs an image of the whole page. Recovery starts at the checkpoint, so the image comes before any other record for that page. Replay copies the image in and never reads the torn bytes. PostgreSQL leaves out the free "hole" in the middle of the page, and `wal_compression` can shrink the image more.
- **Doublewrite buffer (InnoDB)**: InnoDB first writes each batch of 16 KiB pages to a doublewrite area and flushes it. Then it writes the pages to their real places. After a crash, a torn page is restored from its good copy in the doublewrite area.
- **Atomic storage**: a copy-on-write file system such as ZFS never overwrites a page in place. Some setups turn off `full_page_writes` there.

Full-page writes make the WAL much larger just after each checkpoint. The [checkpoints](/databases/recovery/checkpoints) lesson measures this.

## Physiological redo, logical undo

ARIES combines the forms on purpose:

- **Redo is physiological.** Redo repeats history page by page, in LSN order, with the pageLSN check. The records are small, and the page can reorganize itself freely.
- **Undo is logical.** After T1 inserts key 42 into a B-tree leaf, T2 can split that leaf, and key 42 moves to another page. The undo of T1 must be "delete key 42 from the index", and it must find the key where it is now.

Logical undo is not idempotent. ARIES makes sure that each undo runs exactly once: it logs each undo action in a compensation log record, which the [ARIES](/databases/recovery/aries) lesson explains.

Logical logs are also the base of replication and change data capture. The MySQL binary log holds statements or row images. PostgreSQL with `wal_level = logical` decodes its physiological WAL into row changes. These logs describe the data, not the pages, so a replica with a different page layout can apply them.
