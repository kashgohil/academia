Every storage engine pays three kinds of overhead. Each one is a ratio, so engines of different designs can be compared:

- **Read amplification (RA)**: the I/Os (or bytes) that one lookup reads, compared with what it returns. Here: I/Os per point lookup, and I/Os for a range of 100 records.
- **Write amplification (WA)**: the bytes written to storage for each byte the user changes. The WAL counts.
- **Space amplification (SA)**: the bytes kept on disk and in memory indexes for each byte of live data.

An ideal engine has 1 for all three. The **RUM conjecture** (Athanassoulis and others, EDBT 2016) says that no engine can. If a design bounds two of the read, update and memory overheads, it must pay more on the third.

## Computing the numbers

All four models use 100-byte records, 4 KiB pages, 100 GB of data, a 64 MiB memtable and Bloom filters with 10 bits per key. The workload updates random keys over a fixed key set.

<Steps>
<div>**B+ tree, in place.** A lookup reads one leaf; the inner nodes are in memory. An update writes the WAL record and then the whole page: $WA = 1 + P/(r \cdot a)$, where $a$ is the number of updates that one page write carries. With $a = 1$, WA = 42. Random inserts leave pages 69% full on average ($\ln 2$, Yao 1978), so SA = 1.45.</div>
<div>**LSM tree, leveled, size ratio T = 10.** The data needs $L = \lceil \log_{10}(100\text{ GB} / 64\text{ MiB}) \rceil = 4$ levels below the memtable. Each byte is written to the WAL, flushed once, and then rewritten about $(T+1)/2$ times per level: $WA = 2 + 4 \cdot 5.5 = 24$. The upper levels are at most 1/9 of the last level, so SA = 1.12 with the filters.</div>
<div>**LSM tree, tiered, T = 10.** Each level collects up to T − 1 runs and merges them once into the next level, so each byte is written once per level: WA = 2 + 4 = 6. With updates over a fixed key set, the last level holds about T / 2 runs that each cover all keys, so SA ≈ 5.</div>
<div>**Log with a hash index (Bitcask).** Every write is appended to a log, and a hash table in memory maps each key to its offset. A segment is cleaned when only a fraction *u* of it is live: to free 1 − *u*, the cleaner copies *u*. So WA = 1/(1 − *u*) = 5 at 80%. The hash table costs about 32 bytes per key, so SA = 1.43.</div>
</Steps>

| Design | Point lookup I/Os | Range of 100 records, I/Os | WA | SA |
|---|---|---|---|---|
| B+ tree, 1 update per page write | 1 | 4 | 42 | 1.45 |
| LSM, leveled, T = 10 | 1.03 | 7 | 24 | 1.12 |
| LSM, tiered, T = 10 | 1.29 | 39 | 6 | 5.01 |
| Log + hash, clean at 80% live | 1 | 100 | 5 | 1.43 |
| Sorted file, no index | 25 | 28 | 500,000,000 | 1 |
| Log, no index, clean at 50% live | 16,276,042 | 32,552,083 | 2 | 1.33 |

The LSM point lookups cost a little more than 1 I/O. A Bloom filter with 10 bits per key gives a false positive 0.82% of the time, and each level adds that chance of one useless read. The last two rows are the extremes: one is nearly ideal on writes and space, the other on space and reads. Each is useless on the third axis.

The leveled formula in code:

```ts
/** Write amplification of a leveled LSM tree with size ratio T. */
function leveledWa(T: number, dataBytes: number, memtableBytes: number): number {
  const levels = Math.max(1, Math.ceil(Math.log(dataBytes / memtableBytes) / Math.log(T)));
  return 1 /* WAL */ + 1 /* flush */ + levels * (T + 1) / 2;
}
leveledWa(10, 100e9, 64 * 2 ** 20); // 24
```

These are first-order models. Real engines add compression, which divides SA. They add partial merges and caches, which change RA. The point is the shape: you can move a design along a curve, but not toward all three corners at once.

## Write amplification multiplies

The engine's WA is not the end. The file system can add its own (a journal, metadata updates), and the SSD adds device WA from garbage collection, as the [disks lesson](/databases/storage/disks-vs-ssds) showed. The factors multiply:

$$
\text{NAND bytes} = \text{user bytes} \times WA_{engine} \times WA_{fs} \times WA_{device}
$$

The device factor depends on the *pattern* of the engine's writes. A B+ tree writes 4 KiB pages at random addresses, so each erase block holds a mix of live and dead pages. An LSM tree writes large files and deletes whole files. With TRIM, whole erase blocks become invalid together, and the device WA stays near 1.

1. Keep the defaults. The SSD writes 28 TB of NAND per day for 86 GB of user data per day.
2. Select **28%** spare space. The device WA falls from 7.02 to 2.40, and the life grows to 0.86 years. Enterprise drives reserve this space for a reason.
3. Select **LSM, leveled**. The engine WA is 24, but the device WA is 1.00, so the total is 26.4 and the SSD lasts 3.6 years.
4. Select **LSM, tiered**. The total falls to 6.6 and the life to 14.4 years. The price is the space and the range reads of step 3 above.
5. Move the user writes to 10 MB/s. Every line moves down by a factor of 10: the life is inversely proportional to the write rate.

New interfaces attack the device factor directly. Zoned namespaces (ZNS) and flexible data placement (FDP) let the host tell the SSD which data dies together. An LSM tree that puts each file in its own zone gets a device WA close to 1 without spare space.

## Measuring it on a real system

Each factor has a counter, so you can measure the chain instead of guessing it:

- **Engine.** RocksDB prints a compaction table with a `W-Amp` column for each level (`rocksdb.stats`). PostgreSQL 14 and later report `wal_bytes` and `wal_fpi` (the full-page images) in the `pg_stat_wal` view.
- **File system and block layer.** `iostat` and `/proc/diskstats` count the bytes that the host sends to the device. Divide them by the engine's own write counter.
- **Device.** The NVMe SMART log reports "Data Units Written", in units of 512,000 bytes. That counts host writes only. NAND writes, and so the device WA, are in vendor-specific logs.

Measure over at least an hour of steady load. Compaction, checkpoints and garbage collection run in bursts, so short samples mislead.

## Choosing a design

| If your workload… | Prefer | Because |
|---|---|---|
| reads far more than it writes | B+ tree | 1 I/O per lookup, cheap ranges |
| writes a lot, reads recent keys | leveled LSM | WA in the tens, SA near 1.1, device WA near 1 |
| ingests a stream, rarely reads | tiered LSM | lowest WA; pays with space and range reads |
| has keys that fit in memory and no ranges | log + hash | 1 I/O per lookup, low WA |
