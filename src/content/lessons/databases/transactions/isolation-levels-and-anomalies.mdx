Serializability is expensive, so most engines give a weaker **isolation level** by default. A weaker level allows some **anomalies**: results that no serial order can give. To choose a level, you must know which anomalies it allows. The names of the levels do not tell you this reliably.

The demo runs a small engine with eight modes. Four use locks: none, read uncommitted (RU), read committed (RC) and repeatable read (RR). One is full two-phase locking with predicate locks (2PL). Three use **snapshots**, which are frozen views of the committed data. These are read committed with a snapshot per statement (RC-s), snapshot isolation (SI) and serializable SI (SSI).

## The anomalies

Berenson et al. (1995) gave each anomaly a short code and a pattern. Here `r1[P]` is a read of all rows that match a predicate P, and `c1` is a commit.

| Code | Name | Pattern | What goes wrong |
|---|---|---|---|
| P0 | dirty write | `w1[x] w2[x]` before T1 ends | an abort of T1 can erase the write of T2; rows can mix two transactions |
| A1 | dirty read | `w1[x] r2[x] a1` | T2 used a value that never existed |
| A2 | non-repeatable (fuzzy) read | `r1[x] w2[x] c2 r1[x]` | the same read gives two values |
| A3 | phantom | `r1[P] w2[y in P] c2 r1[P]` | the same query returns a new row |
| P4 | lost update | `r1[x] w2[x] w1[x] c1` | one increment disappears |
| A5A | read skew | `r1[x] w2[x] w2[y] c2 r1[y]` | T1 sees half of a transfer |
| A5B | write skew | `r1[x] r2[y] w1[y] w2[x]` | each transaction keeps the invariant, together they break it |

Write skew is the subtle one. Each transaction reads a set of rows, checks a condition, and writes a different row. No row gets two writes, so no write-write check can see the problem. Sometimes the read set is empty, as in a booking that checks that no other booking exists. Then the problem is a phantom and a write skew at the same time.

## Why the ANSI definitions are ambiguous

SQL-92 defines four levels by the phenomena that each one must prevent: dirty read, non-repeatable read and phantom. Berenson, Bernstein, Gray, Melton, O'Neil and O'Neil showed three problems in "A Critique of ANSI SQL Isolation Levels" (1995).

1. The English text allows two readings. The **strict** reading forbids only the anomaly itself, for example a dirty read followed by an abort. The **broad** reading forbids the dangerous pattern, for example any read of uncommitted data. Only the broad reading makes the top level serializable.
2. The list misses anomalies. Dirty write (P0) is not in it, but every real level must forbid it, or rollback cannot work. Lost update and the two skews are also missing.
3. Snapshot isolation fits nowhere. It prevents all three ANSI phenomena in the strict reading, so it looks serializable. It still allows write skew.

So a level name is a promise about a few patterns, not a guarantee. The real behavior depends on the mechanism, locks or snapshots, and each engine maps the names differently.

## What engines give at each name

| Engine | READ UNCOMMITTED | READ COMMITTED | REPEATABLE READ | SERIALIZABLE | default |
|---|---|---|---|---|---|
| PostgreSQL | same as RC | snapshot per statement | snapshot isolation | SSI (since 9.1) | RC |
| MySQL InnoDB | reads the newest row, even uncommitted | snapshot per statement, few gap locks | snapshot for plain reads; locking reads and UPDATE use the newest row and next-key locks | RR where plain SELECTs take shared locks | RR |
| SQL Server | no shared locks | short shared locks, or a snapshot per statement with `READ_COMMITTED_SNAPSHOT` | shared locks held to the end | key-range locks (2PL) | RC with locks |
| Oracle | not available | snapshot per statement | not available | snapshot isolation | RC |
| SQLite | (shared cache only) | not available | not available | one writer at a time, always serializable | serializable |

Three entries need care. PostgreSQL REPEATABLE READ is snapshot isolation, so it allows write skew. It aborts a lost update with "could not serialize access due to concurrent update". Oracle SERIALIZABLE is also snapshot isolation, so it also allows write skew (error ORA-08177 is its write conflict).

InnoDB REPEATABLE READ is not snapshot isolation. A plain SELECT reads the snapshot, but an UPDATE reads the newest committed row and does not abort. So a read-modify-write in two statements loses updates under the MySQL default. SQL Server also has a SNAPSHOT level, which is SI, and it reports a write conflict as error 3960.

## Living with weak levels

The practical rules follow from the matrix. Under any snapshot level, protect a read-modify-write with `SELECT ... FOR UPDATE`, or do the change in one statement, such as `UPDATE t SET x = x + 1`. A check across rows ("at least one doctor on call") needs SERIALIZABLE, or a lock on a row that stands for the whole check. And at SERIALIZABLE, every transaction must be ready to retry:

```go
// Retry a transaction that fails with SQLSTATE 40001 (serialization failure)
// or 40P01 (deadlock detected). The work must be safe to run again.
func WithRetry(ctx context.Context, db *sql.DB, work func(*sql.Tx) error) error {
	for attempt := 0; ; attempt++ {
		tx, err := db.BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelSerializable})
		if err != nil {
			return err
		}
		if err = work(tx); err == nil {
			err = tx.Commit()
		} else {
			tx.Rollback()
		}
		var pgErr *pgconn.PgError
		if errors.As(err, &pgErr) && (pgErr.Code == "40001" || pgErr.Code == "40P01") && attempt < 10 {
			time.Sleep(time.Duration(1<<attempt) * time.Millisecond) // back off, then try again
			continue
		}
		return err
	}
}
```
