MVCC keeps an old version for every reader that might still need it. Each update and each delete leaves one version behind. When no snapshot can see a version any more, it is **dead**, and its space can be used again. Finding and removing dead versions is **garbage collection**. If it falls behind, the table **bloats**: it grows, scans read dead data, and caches hold less useful data.

A version that died at time d can go only when every running snapshot started after d. So the engine computes a **horizon**: the start of the oldest snapshot that is still running. Everything that died before the horizon is removable. One old snapshot holds back the horizon for the whole database.

## What holds the horizon back

In PostgreSQL, the horizon is the oldest xmin among several sources. Each one can cause bloat:

- a long query or transaction, also a read-only one at REPEATABLE READ;
- a session that is **idle in transaction**: the application opened a transaction and forgot it (`idle_in_transaction_session_timeout` can end it);
- a **replication slot** whose consumer is slow or gone;
- a standby with `hot_standby_feedback = on` that runs a long query;
- a **prepared transaction** of two-phase commit that nobody finished.

The `backend_xmin` column of `pg_stat_activity` and the `xmin` columns of `pg_replication_slots` and `pg_prepared_xacts` show the culprits. The root cause is almost always a long-running transaction. Tuning VACUUM cannot fix it.

## PostgreSQL VACUUM

A plain `VACUUM` runs beside normal traffic. It works in phases:

1. Scan the heap and collect the ids of dead tuples. Skip pages that the **visibility map** marks all-visible. The map has 2 bits per heap page: all-visible and all-frozen.
2. Remove the dead entries from every index.
3. Free the dead tuples in the heap, record the space in the **free space map**, and set visibility map bits again.

VACUUM truncates only empty pages at the end of the file. `VACUUM FULL` rewrites the whole table into a new file, but it holds an ACCESS EXCLUSIVE lock for the whole time.

**Autovacuum** wakes every `autovacuum_naptime` (1 minute by default). It vacuums a table when its dead tuples exceed `autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × reltuples`. The defaults are 50 and 0.2. So a table of 1,000 rows needs 250 dead tuples, and a table of 1,000,000 rows needs 200,050. For a large table, 20% dead is a lot of bloat, so busy large tables often get a smaller scale factor.

Many dead tuples go away even without VACUUM. When a query reads a page that is nearly full, PostgreSQL **prunes** it. It removes dead tuples of HOT chains inside the page and leaves a redirect line pointer for the index. Pruning needs no index work, because a HOT chain has only one index entry.

## InnoDB purge

InnoDB keeps the newest version in the table, so its table does not fill with dead rows. The old versions are in the **undo log**. When a transaction commits, its update undo records go to the **history list**. **Purge threads** (`innodb_purge_threads`, 4 by default) remove the records that no read view can need. They also remove index entries that were delete-marked.

`SHOW ENGINE INNODB STATUS` reports the **history list length**: the number of committed transactions whose undo is not yet purged. A long transaction holds an old read view, so purge stops and the history list grows. Then the undo tablespace grows, and every query that reads an old version must walk a longer undo chain. The symptom is different from PostgreSQL, but the root cause is the same.

## Transaction id wraparound

PostgreSQL stores xmin and xmax as 32-bit numbers. There are $2^{32} = 4{,}294{,}967{,}296$ transaction ids, and the counter wraps around. So "older" cannot mean "smaller". PostgreSQL compares two normal ids on a ring. Id a is older than id b when the 32-bit difference a − b is negative as a signed integer. Each id sees $2^{31} = 2{,}147{,}483{,}648$ ids in its past and the same number in its future.

```rust
/// TransactionIdPrecedes for normal XIDs (3 and above): compare on a ring of 2^32.
fn xid_precedes(a: u32, b: u32) -> bool {
    (a.wrapping_sub(b) as i32) < 0
}
```

4. Set 10,000 per second. The ring is half used in 2.5 days. A busy database depends on freezing to keep running.

Freezing has three settings. `vacuum_freeze_min_age` (50 million) says how old a tuple must be before a normal VACUUM freezes it. `vacuum_freeze_table_age` (150 million) makes VACUUM scan every page that is not all-frozen. `autovacuum_freeze_max_age` (200 million) starts an anti-wraparound autovacuum on a table even if autovacuum is off. The oldest unfrozen id of each table is `relfrozenxid`, and `age(datfrozenxid)` shows it for each database.

If freezing cannot keep up, PostgreSQL warns when fewer than 40 million ids remain. Close to the limit, it refuses to assign new ids, so the database accepts only reads until an administrator runs VACUUM. What stops freezing? The same things that stop garbage collection: a long transaction, a forgotten replication slot or an old prepared transaction. A frozen tuple must be visible to everyone, so VACUUM cannot freeze past the horizon.
