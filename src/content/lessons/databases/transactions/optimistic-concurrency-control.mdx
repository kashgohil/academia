Locking assumes that conflicts are common, so it makes every transaction ask first. **Optimistic concurrency control** (OCC) assumes that conflicts are rare. A transaction runs without locks, keeps its writes private, and checks for conflicts only at the end. If the check fails, the transaction aborts and runs again.

Kung and Robinson described the method in 1981. Each transaction has three phases:

1. **Read phase**: read committed data, and record each item in the **read set**. Put each write in a private buffer, the **write set**.
2. **Validation phase**: check that no conflicting transaction makes this one non-serializable.
3. **Write phase**: copy the write set into the database, and take the next **transaction number** (tn) from a global counter.

The tn order is the serial order. Validation and write run as one short critical section, so two transactions never validate at the same time.

## Backward and forward validation

**Backward validation** looks into the past. Transaction Tj records the counter value when it starts. At validation, it checks every Ti that committed with a larger tn. If the write set of Ti overlaps the read set of Tj, Tj may have read an old value, and Tj aborts. The committed write sets must be kept until no active transaction started before them.

**Forward validation** looks at the transactions that are still running. Tj checks its own write set against the read sets of the active transactions. On a conflict, the engine can abort Tj or the readers. Forward validation has two advantages. It can abort a doomed reader early, and a read-only transaction always passes, because its write set is empty. Its cost: the read sets of active transactions must be visible to the validator while they still change.

Backward validation does not record when each read happened. So it also aborts Tj when Tj read the new value, after Ti committed. That schedule is serializable, but the set check cannot tell. This is the price of a simple check.

## Silo: OCC without a central counter

A global counter and a validation lock serialize every commit, which limits a multi-core machine. **Silo** (Tu et al., SOSP 2013) removed both. Each record has a 64-bit **TID word** that holds a lock bit and the transaction id of the last writer. A read copies the value and the TID word, then checks that the word did not change during the copy.

The commit protocol has three steps:

1. Lock every record in the write set, in a fixed order (so that two committers cannot deadlock). Then read the current **epoch**, a global number that a background thread advances every 40 ms.
2. Validate the read set: each TID word must be unchanged, and no other transaction may hold its lock.
3. Choose a new TID that is larger than every TID seen, inside the current epoch. Write the values, and store the new TID while it releases the lock.

Reads never write shared memory, so readers do not move cache lines between cores. Durability and the serial order work per epoch, not per transaction. The TID word is the same idea as a seqlock and a tagged pointer from the [compare-and-swap lesson](/concurrency/atomics/compare-and-swap).

```rust
use std::sync::atomic::{AtomicU64, Ordering::*};

const LOCK: u64 = 1 << 63;

struct Record { tid: AtomicU64, value: AtomicU64 }

/// Silo-style read: retry until the TID word is stable and unlocked.
fn read(r: &Record) -> (u64, u64) {
    loop {
        let t1 = r.tid.load(Acquire);
        if t1 & LOCK != 0 { std::hint::spin_loop(); continue; }
        let v = r.value.load(Acquire);
        if r.tid.load(Acquire) == t1 { return (v, t1); }
    }
}

/// Phase 2 of commit: the read set is valid if no TID changed and no other committer holds a lock.
fn validate(reads: &[(&Record, u64)], my_writes: &[&Record]) -> bool {
    reads.iter().all(|(r, seen)| {
        let now = r.tid.load(Acquire);
        let locked_by_other = now & LOCK != 0 && !my_writes.iter().any(|w| std::ptr::eq(*w, *r));
        now & !LOCK == *seen && !locked_by_other
    })
}
```

## OCC in your application

The same idea works on top of any database. Give each row a **version column**. Read the row and its version, compute, and then write only if the version did not change:

```go
// Optimistic update with a version column. Zero rows changed means that someone else won.
func Rename(ctx context.Context, db *sql.DB, id int64, name string) error {
	for {
		var version int64
		if err := db.QueryRowContext(ctx, `SELECT version FROM item WHERE id = $1`, id).Scan(&version); err != nil {
			return err
		}
		res, err := db.ExecContext(ctx,
			`UPDATE item SET name = $1, version = version + 1 WHERE id = $2 AND version = $3`,
			name, id, version)
		if err != nil {
			return err
		}
		if n, _ := res.RowsAffected(); n == 1 {
			return nil
		}
		// Lost the race: read again and retry.
	}
}
```

JPA uses this with `@Version`, and Rails with a `lock_version` column. HTTP has the same pattern with `ETag` and `If-Match`. It holds no lock while a user edits a form for minutes, which a database lock could not do.

## When optimism wins and when it loses

1. Read θ = 0, which is uniform access. 2PL gives 0.43 commits per tick and OCC 0.39. OCC already aborts 12% of attempts, but a real lock manager also costs CPU, which this model does not count.
2. Read θ = 0.8, where the hottest item gets 6.5% of accesses. 2PL throws away 11% of its work and OCC 47%. For OCC, the abort rate and the wasted work are the same line, because every abort happens at the end.
3. Turn off **CPU limit**. Wasted work now costs nothing, and at θ = 1.4 OCC gives 0.29 commits per tick against 0.10 for 2PL. With free resources, restarting beats waiting in a long queue.
4. Move **Concurrent transactions** down to 4. Conflicts become rare, and the two methods give almost the same throughput.

So OCC wins with short transactions, low contention, many reads and cheap restarts. It avoids a lock table and its latches, and it can never deadlock. It loses on **hot spots**, such as a counter or the newest rows of a queue. It also loses with long transactions, which have a long window for conflicts. SQL Server In-Memory OLTP (Hekaton) uses OCC and validates at commit. FoundationDB checks read and write sets at commit and limits each transaction to 5 seconds.
