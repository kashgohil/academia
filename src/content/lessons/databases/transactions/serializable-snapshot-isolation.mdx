Snapshot isolation (SI) gives each transaction a frozen view and stops lost updates. It prevents every anomaly in the ANSI list. One anomaly remains: **write skew**. The classic example is a hospital rule: at least one doctor must be on call. Alice and Bob are both on call, and both feel ill at the same moment.

Each transaction counts the doctors on call. Each one sees 2, so each decides that it is safe to leave, and each updates its own row. The two writes touch different rows, so first-updater-wins sees no conflict. Both commit, and nobody is on call.

## Dependencies between transactions

Adya (1999) describes a history with three kinds of edges between committed transactions. Each edge says "this one must come first in any equivalent serial order":

- **wr** (read dependency): T1 writes a version, and T2 reads it.
- **ww** (write dependency): T1 writes a version, and T2 writes the next version of the same row.
- **rw** (anti-dependency): T1 reads a version, and T2 writes the next version. T1 did not see the write of T2, so T1 must come first.

The history is serializable if this graph has no cycle. Under SI, two concurrent transactions cannot have a ww edge, because first-updater-wins aborts one. They cannot have a wr edge either, because neither sees the other. So between concurrent transactions, only rw edges can exist.

Fekete, Liarokapis, O'Neil, O'Neil and Shasha proved in 2005 that every cycle under SI has a special shape. It contains two rw edges in a row, T_in → T_pivot → T_out, between concurrent transactions. This shape is a **dangerous structure**, and T_pivot is the **pivot**. T_in and T_out can be the same transaction, as in the doctors example. In addition, T_out is the first transaction in the cycle to commit.

## SSI: abort the pivot

Cahill, Röhm and Fekete (SIGMOD 2008) turned the theorem into an algorithm: **serializable snapshot isolation** (SSI). Run SI as usual, track the rw edges, and abort a transaction when a dangerous structure appears. Not every dangerous structure is part of a cycle, so SSI has **false positives**. It never needs to block a reader.

To find rw edges, the engine must remember what each transaction read. It cannot use a normal lock, because reads must not block. So it uses a **SIREAD lock**, which only records the read and blocks nothing. An rw edge appears in two ways:

1. A reader finds a version that it cannot see, written by a concurrent transaction. This gives reader → writer.
2. A writer creates a new version of a row (or of a predicate) on which a concurrent transaction holds a SIREAD lock. This gives reader → writer as well.

SIREAD locks must outlive the commit. A committed reader can still be T_in of a structure that a later write completes. PostgreSQL keeps them until every overlapping transaction has finished.

## What PostgreSQL adds

PostgreSQL has used SSI for SERIALIZABLE since version 9.1. Ports and Grittner described the design (VLDB 2012). It adds several rules to reduce false positives:

- **Commit order**: abort only if T_out commits first, before T_pivot and T_in. This is the extra fact from the theorem. In the demo, it is the difference between the two SSI rows.
- **Read-only transactions**: if T_in is read-only, the structure is dangerous only if T_out committed before T_in took its snapshot.
- **Safe retry**: when possible, abort a transaction that will not hit the same conflict at once on retry. The pivot that has not committed is usually the right choice.
- **Safe snapshots**: a read-only transaction whose snapshot can never be part of a dangerous structure needs no tracking. `SERIALIZABLE READ ONLY DEFERRABLE` waits until such a snapshot exists, then runs with no SSI cost and no risk of abort.

SIREAD locks live in shared memory at three levels: tuple, page and relation. When a transaction holds too many, PostgreSQL promotes them to a coarser level. A page lock covers rows that the transaction never read, so promotion adds false positives. The limit is `max_pred_locks_per_transaction` (64 by default). A sequential scan takes a relation lock at once, so good indexes reduce aborts under SSI. The error is SQLSTATE 40001: "could not serialize access due to read/write dependencies among transactions".

## Alternatives

SSI is not the only way to stop write skew.

| Method | How | Cost |
|---|---|---|
| Strict 2PL with predicate locks | lock what you read, hold it to the end | readers block writers; deadlocks |
| `SELECT ... FOR UPDATE` | lock the rows that the check reads | does not help when the check finds no rows (the booking case) |
| Materialize the conflict | add a row that stands for the rule (for example one row per shift), and update it in every transaction | a hot row; you must remember it in every code path |
| A constraint | `UNIQUE` or a PostgreSQL exclusion constraint on time ranges | only for rules that a constraint can express |
| SSI | track rw edges, abort the pivot | false positives; every transaction must be able to retry |

For the doctors, the materialized conflict looks like this:

```sql
-- Both transactions update the same shift row, so first-updater-wins
-- makes the second one wait and then abort under REPEATABLE READ.
BEGIN ISOLATION LEVEL REPEATABLE READ;
UPDATE shift SET version = version + 1 WHERE shift_id = 1234;
SELECT count(*) FROM doctors WHERE on_call AND shift_id = 1234;
UPDATE doctors SET on_call = false WHERE name = 'alice' AND shift_id = 1234;
COMMIT;
```
