[Single-decree Paxos](/distributed/consensus/paxos) chooses one value. A replicated state machine needs a log: a sequence of slots, each with one chosen command. The obvious design runs one full Paxos instance per slot. That costs two round trips and two fsyncs on a majority for every command. **Multi-Paxos** removes most of that cost.

## One phase 1 for all slots

Phase 1 does two things. It makes the acceptors promise to refuse older ballots, and it reports what they accepted. Neither needs a separate run for each slot.

So a new leader sends one `prepare(b)` that covers every slot. Each acceptor promises b for all slots, and it replies with all the proposals it has accepted. After that, the leader runs only phase 2 for each new command: `accept(b, slot, v)` and `accepted(b, slot)`. A command now costs one round trip to a majority.

Paxos Made Live (Chandra, Griesemer and Redstone, PODC 2007) describes this for Chubby's log. Phase 1 messages may be omitted while the coordinator stays the same. The ballot works as a leader epoch, much like a term in Raft.

## Leader change

A new leader must finish the work of the old one before it adds commands. After its phase 1, it knows, for each slot, the accepted proposal with the highest ballot in its quorum. Then:

- If a slot has an accepted value, the leader proposes that value again with its own ballot. It may have been chosen, so it must survive.
- If a slot has no accepted value in the quorum, but a higher slot has one, the slot is a **gap**. No value can have been chosen in it, because a chosen value would appear in every majority. The leader fills it with a **no-op**.

The state machine applies the log in slot order. A gap would block every later slot forever, so the no-op is required.

## Leases for reads

A leader can answer reads from its own state only if it is sure that no newer leader exists. Otherwise, as [the consensus problem](/distributed/consensus/the-consensus-problem) showed, it can return old data. One safe option sends each read through the log. A cheaper option checks leadership with one round of heartbeats to a majority.

The cheapest option is a **lease**. While a majority grants the leader a lease, they promise not to support another leader. The leader then serves reads locally until the lease expires. This depends on bounded clock drift, as in [physical clocks and drift](/distributed/time/physical-clocks-and-drift).

| System | Consensus | Detail |
|---|---|---|
| Chubby (OSDI 2006) | Paxos | five replicas typical; the master holds a lease of a few seconds |
| Spanner (OSDI 2012) | Paxos, one group per tablet | leader leases of 10 seconds by default; the Paxos implementation is pipelined |
| Megastore (CIDR 2011) | Paxos | replicates every write across datacenters |
| etcd, CockroachDB, TiKV | Raft | a Raft group per cluster (etcd), per range (CockroachDB) or per region (TiKV) |
| ZooKeeper | Zab | an atomic broadcast protocol, not Paxos |

1. At n = 5, basic Paxos sends 16 messages per command, and Multi-Paxos sends 8. The rule is $4(n - 1)$ and $2(n - 1)$.
2. Move the phase-2 quorum to 2 for the green line. A thrifty leader sends `accept` to only 1 other node, so 2 messages per command.
3. Read the cost. With $q_2 = 2$ out of 5, a leader change needs $q_1 = 4$ promises, so it survives only 1 crash.
4. Move **Nodes n** to 15. Multi-Paxos needs 28 messages, but the green line stays at 2.

Flexible Paxos (Howard, Malkhi and Spiegelman, 2016) showed that majorities are not necessary. Only a phase-1 quorum and a phase-2 quorum must intersect:

$$
q_1 + q_2 > n
$$

Phase-2 quorums need not intersect each other. Commands are frequent and leader changes are rare, so a small $q_2$ often pays. The price is that a leader change needs a large $q_1$. A thrifty leader also has no spare replies: one slow node in its small quorum stalls every command.

## Beyond one leader

**EPaxos** (Moraru, Andersen and Kaminsky, SOSP 2013) has no fixed leader. Any replica leads its own commands. Commands that do not interfere commit in one round trip, with a fast quorum of $F + \lfloor (F + 1)/2 \rfloor$ replicas out of $N = 2F + 1$. Commands that conflict need a second round. The design removes the leader bottleneck, at the cost of a much harder recovery protocol.

## Compared with Raft

[Raft log replication](/distributed/consensus/raft-log-replication) is a Multi-Paxos design with stronger rules on the log.

| Question | Multi-Paxos | Raft |
|---|---|---|
| Leader epoch | ballot number | term |
| Who can become leader | any node; phase 1 brings in the missing values | only a node whose log is at least as up to date as that of each voter in a majority |
| Holes in the log | possible; filled with no-ops after a leader change | impossible; a follower accepts entry i only if it matches entry i − 1 |
| Old entries after a leader change | re-proposed with the new ballot | kept with their old term; a new leader commits a no-op of its own term first |
| Specification | a family of variants, with many details left to the implementer | one precise algorithm |

Raft's election rule means that a new leader already holds every committed entry, so it needs no phase 1 to learn values. The cost is less flexibility, for example in which node may lead.

```go
// The heart of a Multi-Paxos leader change: one value per slot, no-ops for gaps.
func (l *Leader) recover(promises []Promise) {
	best := map[uint64]Accepted{}
	top := uint64(0)
	for _, p := range promises {
		for slot, a := range p.Accepted {
			if cur, ok := best[slot]; !ok || a.Ballot > cur.Ballot {
				best[slot] = a
			}
			top = max(top, slot)
		}
	}
	for slot := l.commitIndex + 1; slot <= top; slot++ {
		v := NoOp
		if a, ok := best[slot]; ok {
			v = a.Value // may have been chosen: it must survive
		}
		l.sendAccept(l.ballot, slot, v)
	}
	l.nextSlot = top + 1
}
```
