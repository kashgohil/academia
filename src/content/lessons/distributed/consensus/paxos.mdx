Paxos chooses one value among many proposals. It never chooses two values, whatever the order of messages, and whatever the losses, duplicates and crashes. It decides as soon as one proposer can talk to a majority without interference. Leslie Lamport first described it in "The Part-Time Parliament" (ACM TOCS, 1998). This lesson follows his short version, "Paxos Made Simple" (ACM SIGACT News, December 2001).

## Roles and ballots

- A **proposer** suggests a value. It drives the protocol.
- An **acceptor** votes. The acceptors are the memory of the protocol: a value is **chosen** when a majority of acceptors accept the same proposal.
- A **learner** finds out which value was chosen.

One server usually plays all three roles. Each proposal has a **ballot number** (Lamport calls it the proposal number). Ballots must be unique and totally ordered. A common encoding is a pair (round, proposer id), compared by round first. In the demos, ballot 2.1 means round 2 of proposer P1.

## The two phases

<Steps>

**Phase 1a: prepare.** The proposer picks a ballot b, higher than any it has seen. It sends `prepare(b)` to the acceptors.

**Phase 1b: promise.** An acceptor that has not promised a higher ballot records the promise "I will not accept any ballot below b". It replies `promise(b)` with the highest-numbered proposal that it has accepted, if any.

**Phase 2a: accept.** With promises from a majority, the proposer chooses the value. If any promise reports an accepted proposal, the value is the one with the highest ballot. Only if none does may the proposer use its own value. It sends `accept(b, v)`.

**Phase 2b: accepted.** An acceptor accepts `(b, v)` unless it has promised a ballot higher than b. It tells the proposer and the learners. When a majority accepts ballot b, v is chosen.

</Steps>

An acceptor must store its promise and its accepted proposal on disk before it replies. Paxos Made Simple says that an acceptor must remember this information even if it fails and restarts. So each phase costs an fsync on a majority, as in [group commit](/databases/recovery/group-commit).

## Why it is safe

The proof rests on one invariant. Suppose a majority Q accepted ballot m with value v, so v is chosen. Then every proposal with a ballot $n > m$ carries v.

Use induction on n. The proposer of ballot n got promises from a majority Q′. Q and Q′ share at least one acceptor, a. Acceptor a accepted ballot m before it promised n, because after the promise it would refuse m. So a's promise reports some accepted ballot $k \ge m$.

The proposer takes the highest reported ballot, which is some $k$ with $m \le k < n$. By induction, the proposal of ballot k carries v. So the proposer also proposes v.

The proof uses three facts, and each demo bug breaks one of them:

| Fact | What breaks it |
|---|---|
| Any two majorities share an acceptor | a quorum smaller than a majority |
| An acceptor never forgets a promise or an acceptance | no fsync, or a disk that loses writes |
| A proposer adopts the highest accepted value | the "ignore old values" bug |

The unit tests check safety in two ways. An exhaustive search with 2 proposers and 3 acceptors tries every order, loss and delay. With one ballot per proposer it visits 3,417 states, and with two ballots per proposer 414,605 states. It finds no state with two chosen values. The same search finds a bad schedule at once for each bug. Random runs on the network then add loss, duplicates and acceptor crashes, for 500 seeds.

```rust
// An acceptor. `persist` must reach the disk before any reply is sent.
struct Acceptor { promised: Ballot, accepted: Option<(Ballot, Value)> }

impl Acceptor {
    fn on_prepare(&mut self, b: Ballot) -> Reply {
        if b < self.promised { return Reply::Nack(self.promised); }
        self.promised = b;
        persist(&self);                        // fsync
        Reply::Promise(b, self.accepted.clone())
    }
    fn on_accept(&mut self, b: Ballot, v: Value) -> Reply {
        if b < self.promised { return Reply::Nack(self.promised); }
        self.promised = b;
        self.accepted = Some((b, v));
        persist(&self);                        // fsync
        Reply::Accepted(b)
    }
}
```

The `Nack` reply is an optimization from the paper. The acceptor tells the proposer to give up, so that the proposer does not wait for a timeout.

## Liveness and duelling proposers

Safety never depends on timing, but liveness does.

Two proposers can preempt each other forever. P1 finishes phase 1 with ballot 1. P2 finishes phase 1 with ballot 2, so the acceptors refuse P1's accept. P1 retries with ballot 3, so they refuse P2's accept, and so on. Paxos Made Simple describes this case and gives the fix: choose a **distinguished proposer**, which is the only one that tries to propose.

1. With **Fixed timer** at 30 ms, the proposers start 27 ballots in 400 ms, and no value is chosen. Safety still holds: nothing wrong is chosen either.
2. Raise **Retry timer** to 40 ms or more. One ballot now completes, and a value is chosen at 45 ms.
3. Select **Random backoff**. A random extra wait breaks the symmetry. A value is chosen at 45 ms after 4 ballots.
4. Read the curves. Over 200 runs with varied start times, the fixed timer chooses a value within 400 ms in only 154 runs. Random backoff chooses in all 200 runs by 69 ms. One leader chooses in all runs by 32 ms.

Real systems combine both fixes. They elect a leader, and they use random timeouts for the election itself. Raft does exactly this, as [Raft leader election](/distributed/consensus/raft-leader-election) shows. A leader election needs a failure detector, and FLP says that it can be wrong. When two nodes both think that they lead, Paxos stays safe and only slows down.

## Paxos in real systems

- **Chubby** (Burrows, OSDI 2006), Google's lock service, runs a cell of typically five replicas. They use Paxos to elect a master, which holds a master lease of a few seconds.
- **Paxos Made Live** (Chandra, Griesemer and Redstone, PODC 2007) describes the Paxos log under Chubby. Its list of the gaps between the paper and production includes disk corruption, master leases, group membership and snapshots. A replica with a corrupted disk rejoins as a non-voting member. It votes again only after it sees one complete Paxos instance that started after it began to rebuild. A voter that forgot its votes would be the fsync bug above.
- **Megastore** (Baker et al., CIDR 2011) uses Paxos to replicate user data across datacenters on every write.
- **Cassandra** uses Paxos for lightweight transactions such as `INSERT ... IF NOT EXISTS`. The original protocol needs four round trips for a write: prepare, read, propose and commit. Since Cassandra 4.1, the optional `paxos_variant: v2` needs only two round trips for a write.

Single-decree Paxos chooses one value. A log needs a value for each slot, and two round trips per slot are expensive. [Multi-Paxos](/distributed/consensus/multi-paxos) runs phase 1 once for many slots.
