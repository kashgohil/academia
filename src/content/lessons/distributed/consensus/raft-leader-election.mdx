[Multi-Paxos](/distributed/consensus/multi-paxos) works best with one stable proposer, but the papers say little about how to choose it. **Raft** makes that choice the center of the design. Diego Ongaro and John Ousterhout published it as "In Search of an Understandable Consensus Algorithm" (USENIX ATC 2014). Ongaro's dissertation, "Consensus: Bridging Theory and Practice" (Stanford, 2014), adds the extensions that real systems use.

Raft splits [consensus](/distributed/consensus/the-consensus-problem) into three parts: leader election, log replication and safety. This lesson is about the first part. A **leader** is the one server that accepts client commands and sends them to the others. All decisions flow from the leader to the followers, so the rest of the protocol stays simple.

## Terms and roles

Raft divides time into **terms**, numbered 1, 2, 3 and so on. Each term starts with an election, and each term has at most one leader. A term number works as a logical clock: every message carries the sender's term. A server that sees a higher term adopts it at once and becomes a follower. A server rejects any request that carries a lower term.

A server is in one of three roles:

- A **follower** answers requests and does nothing else. It keeps an **election timer**. A message from the current leader resets the timer.
- A **candidate** is a follower whose timer expired. It increments its term, votes for itself and sends `RequestVote` to every other server.
- A **leader** is a candidate that got votes from a majority. It sends `AppendEntries` at a fixed interval, even with no new entries. These empty messages are **heartbeats**, and they keep the followers' timers from expiring.

Each server stores three values on disk before it answers any message: `currentTerm`, `votedFor` and the log. A server that forgets its vote after a crash could vote twice in one term. Then two candidates could each collect a majority.

## RequestVote and the vote rules

A candidate sends `RequestVote(term, candidateId, lastLogIndex, lastLogTerm)`. The reply is `(term, voteGranted)`. A server grants its vote only if all three rules hold:

| Rule | Why |
|---|---|
| The request's term is not lower than the voter's term | A stale candidate cannot win a term that has moved on |
| The voter has not voted in this term, or voted for this candidate | One vote per term, so two majorities cannot form |
| The candidate's log is at least as up to date as the voter's | A new leader holds every committed entry |

"Up to date" compares the last entries. The log whose last term is higher is newer. If the last terms are equal, the longer log is newer. This is the **election restriction**.

Why does it work? A committed entry is on a majority, and any winning candidate needs votes from a majority. These two sets overlap in at least one server, which refuses a candidate that lacks the entry. The [next lesson](/distributed/consensus/raft-log-replication) shows why this matters.

```go
func (r *Raft) handleRequestVote(m RequestVote) RequestVoteReply {
	if m.Term > r.currentTerm {
		r.currentTerm, r.votedFor = m.Term, None // a new term: step down, forget the old vote
		r.becomeFollower()
	}
	upToDate := m.LastLogTerm > r.lastTerm() ||
		(m.LastLogTerm == r.lastTerm() && m.LastLogIndex >= r.lastIndex())
	grant := m.Term == r.currentTerm && (r.votedFor == None || r.votedFor == m.CandidateID) && upToDate
	if grant {
		r.votedFor = m.CandidateID
		r.persist()            // write term and vote to disk before the reply leaves
		r.resetElectionTimer() // a server that just voted gives the candidate time to win
	}
	return RequestVoteReply{Term: r.currentTerm, VoteGranted: grant}
}
```

A candidate wins when it has votes from a majority. It loses when an `AppendEntries` from a leader of the same or a higher term arrives. If its timer runs out first, nobody won: it starts a new term and asks again.

## Why the timeouts are random

Two candidates in one term can split the votes, so that neither reaches a majority. Raft does not resolve a split. It avoids one: each server draws its timeout at random from a range, such as 150 to 300 ms in the paper. Usually one server times out alone and collects its votes before the next timer runs out.

A short model shows how much spread is enough. Take $n$ timers drawn uniformly from a window of $S$ ms. The expected gap between the first and the second is

$$
\mathbb{E}[\text{gap}] = \frac{S}{n+1}
$$

With 4 followers and $S = 150$ ms, the gap is 30 ms. A vote round trip, with its disk write, takes about 0.5 to 20 ms by the paper's estimate, so the first candidate usually wins. With $S = 5$ ms, the gap is 1 ms, and a second candidate often starts before the first one's requests arrive.

The paper measured the same shape on real servers (section 9.3). With no randomness, an election took longer than 10 seconds. With 5 ms of randomness, the median downtime was 287 ms. With timeouts of 12 to 24 ms, a leader was elected in 35 ms on average. The exact values in the demo differ, because its network and heartbeats are model inputs, but the cliff is the same.

The paper states the timing requirement as broadcastTime ≪ electionTimeout ≪ MTBF. The **broadcast time** is the time to send RPCs to every server and get the replies, including their disk writes. The paper puts it at 0.5 to 20 ms. The election timeout should be an order of magnitude longer, or followers start elections while the leader is healthy. It must also be much shorter than the mean time between failures (months), or the cluster spends too much time without a leader.

## What real systems use

| System | Heartbeat | Election timeout | Notes |
|---|---|---|---|
| etcd | `--heartbeat-interval` 100 ms | `--election-timeout` 1000 ms | the library draws from 1 to 2 times the timeout, in ticks |
| hashicorp/raft (Consul, Nomad, Vault) | every 100 to 200 ms (`HeartbeatTimeout` / 10) | `HeartbeatTimeout` 1000 ms, for a follower | `ElectionTimeout` 1000 ms, for a candidate; `LeaderLeaseTimeout` 500 ms |
| Kafka KRaft | none: followers fetch from the leader | `controller.quorum.fetch.timeout.ms` 2000 ms, for a follower | `controller.quorum.election.timeout.ms` 1000 ms, for a candidate |

The etcd tuning guide gives the rules of thumb. Set the heartbeat near the round-trip time between members. Set the election timeout to at least 10 times the round-trip time. etcd rejects an election timeout above 50,000 ms. In the etcd raft library, `ElectionTick` and `HeartbeatTick` count logical ticks, and each election timeout is drawn from `[ElectionTick, 2 × ElectionTick)`.

## Disruptive servers: pre-vote and check-quorum

Step 4 of the first demo shows a weakness. A server cut off from the others times out again and again, and each time it increments its term. When the network heals, its high term reaches the leader, and the leader steps down. The cluster loses its leader for a full election, although nothing was wrong with it.

**Pre-vote** (dissertation section 9.6) fixes this. Before it increments its term, a server asks the others whether they would vote for it in term $t+1$. A server answers yes only if the candidate's log is up to date and it has not heard from a leader within an election timeout. The pre-vote changes no state. A cut-off server never gets a majority of pre-votes, so its term never grows. When it returns, the others still hear the leader, so they refuse it.

**Check-quorum** handles the opposite case. A leader steps down if it has not heard from a majority within an election timeout. So a leader in a minority cannot keep its clients. With check-quorum on, a follower also follows the rule of dissertation section 4.2.3. If it heard from a leader within the minimum election timeout, it ignores a `RequestVote` or pre-vote with a higher term.

etcd calls this rule `inLease`. The etcd pre-vote checks only the log, so etcd needs `inLease` for the leader check.

The etcd server always sets `CheckQuorum: true`. It added the `--pre-vote` flag in version 3.4 with the default false. Pre-vote has been on by default since version 3.5. hashicorp/raft added pre-vote in version 1.7.0 (2024), on by default.

## Leadership transfer

Sometimes an operator wants to move the leader, for example before a server restarts for an upgrade. The dissertation (section 3.10) gives a short protocol.

The leader stops accepting new commands and brings the target's log up to date. Then it sends `TimeoutNow`. The target starts an election at once, without waiting for its timer. Its `RequestVote` carries a flag that lets it pass the lease rule above. In etcd this is `MsgTransferLeader`, and the flag is the `campaignTransfer` context.
