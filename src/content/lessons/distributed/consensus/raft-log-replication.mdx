A [leader election](/distributed/consensus/raft-leader-election) gives a term one leader. Now the leader must turn client commands into a **log**: a numbered list of entries that every server applies in the same order. Each entry holds a command and the term in which the leader received it. If every server applies the same log to the same deterministic state machine, every server reaches the same state. This is **state machine replication**, the same goal as [Multi-Paxos](/distributed/consensus/multi-paxos).

## AppendEntries

The leader appends a command to its own log and sends `AppendEntries` to every follower. Figure 2 of the Raft paper lists the fields:

| Field | Meaning |
|---|---|
| `term` | the leader's term |
| `leaderId` | so that followers can redirect clients |
| `prevLogIndex`, `prevLogTerm` | the index and term of the entry just before the new ones |
| `entries[]` | the new entries (empty for a heartbeat) |
| `leaderCommit` | the leader's commit index |

The reply is `(term, success)`. The leader keeps two numbers for each follower. `nextIndex` is the next entry to send. `matchIndex` is the highest entry known to be on that follower.

The follower accepts the request only if its log has an entry at `prevLogIndex` with term `prevLogTerm`. This is the **consistency check**. If the check passes, the follower deletes any entry that conflicts with a new one (same index, different term) and everything after it. Then it appends the new entries that it does not have yet. If the check fails, it replies false, and the leader lowers `nextIndex` and tries again.

The check gives the **Log Matching** property by induction. Suppose two logs have an entry with the same index and term. The leader created that entry once, so the two entries are equal. Each log also passed the check for the entry before it. That entry equals the one in the leader's log, and so on down to index 1. So the two logs are equal up to that index.

## Finding the point of agreement

After an election, the leader sets every `nextIndex` to the end of its own log. A follower with a different suffix rejects the first `AppendEntries`, and the leader lowers `nextIndex` by one each time. This can take one round trip per entry. The paper (section 5.3) gives an optimization: the follower returns the term of the conflicting entry and the first index it holds for that term. Then the leader skips a whole term at a time. The authors add that they doubt it is needed in practice, since failures are rare. etcd sends a similar hint in its reject messages.

## When an entry is committed

An entry is **committed** when the leader knows it is safe to apply. For entries of its own term, the leader uses a simple rule: an entry is committed once a majority has it. It sets `commitIndex` to the highest such index. Followers apply up to `min(leaderCommit, index of their last new entry)`. A follower's entries after that index may still be old and wrong, so it must not apply them.

A committed entry is never lost, because of the election restriction. The entry is on a majority. A winning candidate needs votes from a majority, and the two sets share at least one server. That server votes only for a candidate whose log is at least as up to date as its own.

But this argument fails for an entry of an **older** term. A majority can hold such an entry while a server with a newer last term still wins an election. Figure 8 of the paper shows how.

So Raft has a second rule: a leader commits by counting replicas **only** entries of its current term. Older entries commit indirectly. When an entry of the current term commits, every entry before it commits too, by Log Matching.

<Steps>
<div>Take an entry E of term T committed by leader L. A majority holds E.</div>
<div>Suppose a later leader U, of term U greater than T, is the first leader that lacks E. Some voter V of U also holds E, because the two majorities overlap.</div>
<div>V voted for U, so U's log was at least as up to date as V's. If U's last term equals V's last term, U's log is at least as long, and by Log Matching it contains E.</div>
<div>Otherwise U's last term is higher than V's. The leader of that newer term held E, because U is the first leader without it. U got that entry from that leader, and by Log Matching U holds E too. Both cases contradict the assumption.</div>
<div>This argument needs E to be from term T of leader L, the leader that counted the majority. The current-term rule makes that true. This is the Leader Completeness proof of section 5.4.3, in short.</div>
</Steps>

There is a cost: a new leader cannot commit anything from earlier terms until a client sends a command. So a leader appends a **no-op** entry at the start of its term (dissertation section 6.4). The no-op commits within one round trip, and with it every older entry. It also tells the leader which entries are committed, which it needs before it can answer reads.

## Applying, and what clients see

Each server keeps `lastApplied` and applies entries from `lastApplied + 1` to `commitIndex` in order. The state machine must be deterministic. A command that reads the clock or a random number gives different results on different servers. Real systems put such values into the command itself.

The leader replies to the client after it applies the entry. If the leader crashes before it replies, the client cannot know whether the command committed. So the client retries, often at a different server. For a command such as "add 1", a retry can apply it twice.

<ConsensusRaftSessionDemo />

1. Step through with the session turned off. The reply is lost, the client retries, and x ends at 2.
2. Turn the session on and step again. The retry finds sequence number 1 in the leader's session table, and x stays at 1.

The dissertation (section 6.3) gives the fix. Each client registers a **session** and numbers its commands. The state machine records, per client, the last sequence number it applied and its result. A duplicate gets the saved result and changes nothing. The session table is part of the replicated state, so every server has it and every snapshot contains it. Sessions must expire in the same way on every server, for example by log time, not by local clocks.

```rust
struct Session { last_seq: u64, last_result: Value }

fn apply(&mut self, client: ClientId, seq: u64, cmd: Command) -> Value {
    if let Some(s) = self.sessions.get(&client) {
        if seq <= s.last_seq {
            return s.last_result.clone(); // a retry: do not run it again
        }
    }
    let result = self.state.execute(cmd);
    self.sessions.insert(client, Session { last_seq: seq, last_result: result.clone() });
    result
}
```

## Throughput: batching and pipelining

Each commit needs at least one round trip to a majority and one disk write on each of them. A leader that sends one entry and waits for the reply commits one entry per round trip. Two optimizations remove most of that limit (dissertation section 10.2.2).

- **Batching** puts many entries into one `AppendEntries` and one disk write. It raises the throughput ceiling.
- **Pipelining** sends the next `AppendEntries` before the previous reply arrives. The leader advances `nextIndex` optimistically. After a rejection, it goes back to probing one message at a time.

The leader can also write to its own disk in parallel with the followers (section 10.2.1). It counts itself in the majority only after its own write finishes.
