Several servers must hold the same data, and any of them can crash at any time. To stay the same, they must apply the same commands in the same order. So, for each position in the order, the servers must agree on one command. That agreement is the **consensus problem**. etcd, ZooKeeper, Spanner, CockroachDB and TiKV all solve it many times per second.

## The problem

Each process starts with an input value. Each process may **decide** one value, once. A protocol solves consensus if every run has these properties:

- **Agreement**: no two processes decide different values.
- **Validity**: a decided value is the input of some process. A protocol that always decides 0 is not useful.
- **Termination**: every process that does not crash decides, after a finite time.

Most real systems need **uniform agreement**: a process that decides and then crashes also counts. A crashed leader may have told a client "done" before it died. If the survivors decide differently, that client saw a value that the system later contradicts.

Agreement and validity are **safety** properties: a bad thing never happens. Termination is a **liveness** property: a good thing happens in the end. It is easy to get one kind alone. The difficulty is to get both when processes crash and messages are late.

## Why replication needs it

Fred Schneider's tutorial "Implementing Fault-Tolerant Services Using the State Machine Approach" (ACM Computing Surveys, 1990) states the idea. Make the service a deterministic state machine. Give every replica the same sequence of commands. Then every replica goes through the same states and gives the same outputs.

The hard part is the sequence. A replicated log is a list of slots, and each slot is one consensus instance. Its question is "which command is number 17?". The [leader-follower](/distributed/replication/leader-follower) design moves the problem to a different place. The leader orders the commands, but when the leader fails, the replicas must agree on a new leader and on the last command that counts.

**Atomic broadcast** delivers the same messages, in the same order, to every correct process. Chandra and Toueg (JACM, 1996) proved that consensus and atomic broadcast are reducible to each other in asynchronous systems with crash failures. A log is atomic broadcast, so a replicated log and repeated consensus are the same problem.

## Why a majority

A protocol must make progress while some processes are down. So it cannot wait for all n replies. It waits for a **quorum**: a set of replies that it trusts. The quorums must have one property: any two of them share at least one process. That process carries the knowledge of the first quorum into the second.

Two sets of sizes a and b, taken from n nodes, share at least $a + b - n$ nodes. For two majorities $q = \lfloor n/2 \rfloor + 1$, this is $2q - n \ge 1$. A majority quorum must not need the crashed nodes, so f crashes require $n - f \ge q$. That gives the rule:

$$
n \ge 2f + 1
$$

| Nodes n | Majority | Crashes survived f | Common choice |
|---|---|---|---|
| 3 | 2 | 1 | small etcd or ZooKeeper cluster |
| 4 | 3 | 1 | no gain over 3, one more node to wait for |
| 5 | 3 | 2 | Chubby cells are typically five replicas |
| 7 | 4 | 3 | rare: each write waits for 4 nodes |

An even n adds a node but no tolerance. A majority is not the only safe choice. [Flexible Paxos](/distributed/consensus/multi-paxos) shows that only the quorums of different phases must meet.

## A protocol that breaks

The simplest idea: one fixed leader decides its own input and tells the others. Agreement then holds, because only one process decides on its own. But if the leader crashes, nobody else can ever decide. So we add **failover**: a node that hears nothing for a while takes over.

1. With **Cut off leader** and failover on, N1 decides A. N2 and N3 time out, and the other side decides B. Agreement is broken.
2. Turn failover off. Agreement holds, but N2 and N3 wait forever. Termination is broken.
3. Select **Leader crashes**. N1 decided A and then crashed. With failover, the survivors decide B. Only uniform agreement catches this case.
4. Select **One slow message**. No node fails, but N3 decides C. Raise the timeout step to 70 ms. Now the message arrives first, and the run is correct. Another delay would break it again.

Each fix trades one property for the other. The timeout is the problem: it guesses that a node is dead. The [failure detectors](/distributed/foundations/failure-detectors) lesson shows that no timeout is right in every run. A correct protocol must stay safe when the guess is wrong. Paxos and Raft do this: a guess can only cost time, never agreement.

## What consensus does not give you

- **Linearizable reads.** Consensus orders the writes in the log, but a read served from one replica's state can still be old. A leader that a partition cut off may not know that a new leader exists. The Raft paper (Ongaro and Ousterhout, 2014) says that a leader must check that it is still the leader before it answers. It can do this with a heartbeat round to a majority, or rely on a lease, which depends on bounded clock skew. See [linearizability](/distributed/consistency/linearizability).
- **Exactly-once effects.** A client that retries a command after a timeout can get it into the log twice. The state machine must remove duplicates, as in [timeouts, retries and idempotency](/distributed/foundations/timeouts-retries-and-idempotency).
- **Progress during a partition.** The minority side stops. This is the C in [CAP](/distributed/consistency/cap-and-pacelc).
- **Speed.** Each decision costs at least one round trip to a majority, and each acceptor writes to disk before it replies.

```go
// A replicated state machine: the log decides the order, the machine only applies it.
type Replica struct {
	log     ConsensusLog // Raft, Multi-Paxos or Zab
	applied uint64
	kv      map[string]string
}

func (r *Replica) Run() {
	for entry := range r.log.Committed() { // in slot order, each slot once
		if entry.Index != r.applied+1 {
			panic("gap: a log must deliver slots in order")
		}
		r.kv[entry.Key] = entry.Value // deterministic, so every replica agrees
		r.applied = entry.Index
	}
}
```

## Connect

- [FLP impossibility](/distributed/consensus/flp-impossibility) proves that no deterministic protocol can guarantee termination in an asynchronous system with even one crash.
- [Paxos](/distributed/consensus/paxos) and [Raft leader election](/distributed/consensus/raft-leader-election) are the two protocols that most systems use.
- [Two-phase commit](/distributed/transactions/two-phase-commit) is an agreement protocol that blocks when its coordinator fails.
- [Write-ahead logging](/databases/recovery/write-ahead-logging) is the single-node version of the same idea: a log makes the state recoverable.
