Eric Brewer stated a conjecture in his keynote at PODC 2000, "Towards Robust Distributed Systems". A shared-data system can have at most two of three properties: consistency, availability and tolerance to network partitions. Seth Gilbert and Nancy Lynch turned it into a theorem in "Brewer's Conjecture and the Feasibility of Consistent, Available, Partition-Tolerant Web Services" (SIGACT News, 2002). The theorem is now called **CAP**. It is often quoted and often misread, so we start from the exact words of the proof.

Gilbert and Lynch define the three properties precisely.

- **Consistency** means atomic, or linearizable, consistency. There is a total order of all operations, and each operation looks as if it completed at a single instant. This is [linearizability](/distributed/consistency/linearizability).
- **Availability** means that "every request received by a non-failing node in the system must result in a response". No time limit is given, but a node may not wait forever.
- **Partition tolerance** means that the network may lose any number of messages between nodes.

## The proof

The proof of Gilbert and Lynch needs only two groups of nodes and one write. The demo uses one node per group.

<Steps>
<div>Split the nodes into two non-empty groups, G1 and G2. Every message between G1 and G2 is lost. Partition tolerance says that the system must handle this case.</div>
<div>A client writes a new value at a node in G1. Availability says that this node must answer. It cannot reach G2, so G2 learns nothing.</div>
<div>Later, a client reads at a node in G2. Availability says that this node must answer. It has never heard of the write, so it answers the old value.</div>
<div>The write returned before the read began, but the read missed it. No linearization exists. So no algorithm can be both available and consistent in this network.</div>
</Steps>

The proof is short because the definitions are strong. Consistency means linearizability, and availability means that every live node answers. Weaker versions of each one escape the theorem.

## Why "pick two of three" misleads

Brewer himself wrote about this in "CAP Twelve Years Later: How the 'Rules' Have Changed" (IEEE Computer, 2012). He says that "the '2 of 3' formulation was always misleading because it tended to oversimplify the tensions among properties."

1. **Partitions are not optional.** A system that runs on more than one machine cannot choose to have no partitions. So "CA" is not a real third option. The real choice is what to do while a partition lasts.
2. **The choice is only during a partition.** When the network works, a system can be both consistent and available. CAP says nothing about this normal case.
3. **C and A are extreme.** A Raft cluster such as etcd is not "available" in this sense. The minority side cannot serve linearizable requests. But the majority side keeps working, which is good enough for most users.
4. **Many systems give neither.** A store that reads from followers is neither linearizable nor waits for anything. CAP does not put it in any box, and it is not consistent even without a partition.
5. **The choice can be per operation.** Consul and etcd let each read pick a mode. Cassandra lets each request pick a consistency level.

So "CP" and "AP" are short names for what a system does in a partition. They do not describe a system completely.

## PACELC: the choice without a partition

Partitions are rare. A cost that a system pays on every request is more important in practice. Daniel Abadi wrote this down in "Consistency Tradeoffs in Modern Distributed Database System Design" (IEEE Computer, 2012). He called it **PACELC**: if there is a Partition, choose Availability or Consistency; Else, choose Latency or Consistency.

The "else" half comes from replication. A consistent read must hear from enough replicas to know about the latest write. If some of those replicas are far away, every read pays for the distance, with or without a partition.

## Systems by their choices

Abadi classified the default settings of several systems in 2012.

| Class | Systems (Abadi 2012) | In a partition | Normal case |
|---|---|---|---|
| PA/EL | Dynamo, Cassandra, Riak | stay available | low latency, weaker reads |
| PC/EC | VoltDB/H-Store, Megastore, BigTable, HBase | refuse some requests | pay latency for consistency |
| PA/EC | MongoDB (with caveats in the paper) | stay available | consistent reads from the primary |
| PC/EL | PNUTS | give up availability | low latency, weaker reads |

Two warnings apply. First, the table describes defaults. Cassandra with `QUORUM` reads and writes behaves more like EC. Second, the systems have changed since 2012, and Abadi notes himself that MongoDB is not available in the strict CAP sense.

The useful habit is to ask two questions of any store. What does a read do when it cannot reach a quorum? And how many round trips, to which sites, does a read pay when everything works?
