A consistency model is a claim about histories. So you can test a system against it from the outside: run clients, record what they saw, and check the record. Kyle Kingsbury built **Jepsen** around this idea, starting in 2013. Jepsen has found consistency bugs in a long list of databases, often in systems whose documentation promised the opposite.

A Jepsen test has four parts.

1. A **generator** produces operations, for example reads, writes and compare-and-set on a few keys. Several client **processes** run them at the same time.
2. A **nemesis** injects faults: network partitions, crashes, pauses, clock jumps.
3. Every operation is recorded twice: when it is invoked, and when it completes. The result is a **history**.
4. A **checker** decides if the history is allowed by the model, for example a linearizable register.

## Recording a history

Each completed operation has one of three outcomes. The outcome **ok** means that it happened, with this result. The outcome **fail** means that it certainly did not happen, for example a write that the leader rejected. The outcome **info** means that nobody knows, for example after a timeout. Only info needs care.

A write that timed out may still take effect at any later time, or never. So the checker treats it as **pending**: its interval never ends. The client that issued it cannot know when it will finish, so it can no longer act as a sequential process. Jepsen gives the client a new process number and continues. The demo does the same: a timed-out client continues as a new process.

```ts
// One Jepsen-style client step. The history records the invocation before the request is sent.
async function step(proc: Process, op: Op, history: HistoryOp[]) {
  const h: HistoryOp = { process: proc.id, op, call: now(), ret: Infinity };
  history.push(h);
  try {
    const result = await withTimeout(proc.client.run(op), 1000);
    Object.assign(h, { ret: now(), result, type: "ok" });
  } catch (e) {
    if (isDefiniteFailure(e)) Object.assign(h, { ret: now(), type: "fail" }); // did not happen
    else { h.type = "info"; proc.id += proc.concurrency; } // unknown: pending forever, new process
  }
}
```

## The checker

The linearizability checker is the search from [the first lesson of this module](/distributed/consistency/linearizability). Wing and Gong described it in "Testing and Verifying Concurrent Objects" (Journal of Parallel and Distributed Computing, 1993). Checkers call this search **WGL**, with the improvement by Lowe that the last step describes.

<Steps>
<div>Keep a set of placed operations and the state of the model, starting with nothing placed and x = 0.</div>
<div>A **candidate** is an operation that is not placed and that was invoked before every unplaced operation returned. Any other operation would break real time.</div>
<div>Try each candidate in the model. If it is legal, place it, update the state and go deeper. If no candidate is legal, undo the last placement and try its next sibling.</div>
<div>When every completed operation is placed, the order is a linearization. When the search has undone everything, there is none.</div>
<div>Lowe ("Testing for Linearizability", 2017) added a cache. The pair (set of placed operations, model state) fully decides the rest of the search. If the search meets a pair that already failed, it can skip it.</div>
</Steps>

Knossos, the checker in Jepsen, is written in Clojure and offers this search as its `wgl` algorithm. Porcupine, by Anish Athalye, is a checker in Go. It uses the algorithm of Lowe with **P-compositionality** from Horn and Kroening ("Faster Linearizability Checking via P-Compositionality", FORTE 2015). For a key-value store, that means: split the history by key, and check each key alone. This is correct because linearizability is local.

The hard histories here are valid except for one stale read at the very end. A checker can accept a valid history as soon as it finds one order. It can reject an invalid one only after it has ruled out every order, so invalid histories are the expensive case.

In general, checking linearizability is NP-complete: Gibbons and Korach proved this in "Testing Shared Memories" (SIAM Journal on Computing, 1997). So no known checker is fast on every history. For one register and a fixed number of clients, the problem is polynomial.

In practice, three things keep it usable. Tests use a few clients and short runs. The cache removes repeated work. And the history is split by key, which bounds the concurrency in each part. A checker with a budget must report "unknown" when the budget runs out, never "valid". The checker in this module returns null in that case.

## What Jepsen found

Every finding below comes from the published analysis on jepsen.io or on Kingsbury's blog.

| Year | System | Finding |
|---|---|---|
| 2014 | etcd 0.4.1 and Consul | "consistent" reads did not go through the Raft log, so a leader that had been replaced could serve stale reads. Consul later added a mode that confirms leadership with a quorum; it is now called `consistent`. |
| 2015 | MongoDB 2.6.7 | even with majority write concern and reads from the primary, reads could see old versions of documents, and dirty reads also appeared |
| 2020 | etcd 3.4.3 | key-value operations appeared strict serializable, but etcd locks were unsafe: a test that updated a set under a lock lost acknowledged updates. The analysis also found a bug in lease validity. |
| 2020 | Redis-Raft (development build) | 21 issues, including stale reads in a healthy cluster with no faults, split-brain with lost updates, and data loss on failover |

The 2014 bug is the bug in the demo, in its real form. A Raft leader that answers reads alone is safe only while it is still the leader. The fix is the ReadIndex round, or a log entry per read, or a lease with a bound on clock drift.

For transactions, the same idea needs a different checker. Elle, by Kingsbury and Alvaro (PVLDB, 2020), infers a dependency graph between transactions from the history and searches it for cycles. That finds isolation anomalies without trying every order.

## Testing your own system

You do not need the Jepsen framework to use the method. Record invocation and completion times on the client side. Make write values unique, so that each read names its write. Mark timeouts as unknown, never as failures. Inject faults that your system will meet: partitions, crashes and pauses. Then check the history with Porcupine, Knossos or the checker in this module, which `src/sims/dist/consistency` exports for the later modules.
