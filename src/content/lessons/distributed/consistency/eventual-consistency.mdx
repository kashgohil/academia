Werner Vogels gave the common definition in "Eventually Consistent" (ACM Queue, 2008). The store guarantees that "if no new updates are made to the object, eventually all accesses will return the last updated value". Dynamo, Cassandra and Riak were built around this promise. It lets every replica accept reads and writes alone, even when the network is cut.

Read the definition carefully, and note what it leaves out. It gives no **bound**: "eventually" can be one millisecond or one week. It gives no **safety**: while writes continue, it says nothing about what a read returns. And writes never stop in a busy system.

So eventual consistency is a **liveness** property. Strictly, no finite history can break it. Real stores, and the checker in this module, also forbid a value that nobody wrote.

## What convergence needs

Two things make replicas converge, and a store needs both.

1. **Every replica gets every write.** Direct sends are fast, but they can be lost. A background **anti-entropy** process compares replicas and copies what is missing. Cassandra has three layers: **hinted handoff** on the write path, **read repair** on the read path, and full anti-entropy **repair** that compares Merkle trees.
2. **Replicas with the same writes hold the same value.** The merge must not depend on the order of delivery. The demo uses **last-writer-wins** (LWW): each value has a timestamp, and the larger timestamp wins. LWW converges, but it silently drops one of two concurrent writes.

The second point has a name. Shapiro, Preguiça, Baquero and Zawirski defined **strong eventual consistency** (SSS 2011). Correct replicas that have delivered the same updates have equivalent state. This convergence condition is a safety property: it holds at every moment, not only "eventually". Conflict-free replicated data types (CRDTs) give it by construction.

Many CRDTs, such as counters and add-wins sets, keep the effect of every concurrent update. An LWW register is also a CRDT, but it drops one of two concurrent writes.

How fast does a write spread? With pure gossip, a new value doubles its reach in each period, roughly. So the time grows with the logarithm of the number of replicas. The sim measures one write that only anti-entropy spreads, with no loss and a 50 ms period (mean of 40 runs):

| replicas | push | pull | push-pull |
|---|---|---|---|
| 4 | 121 ms | 118 ms | 66 ms |
| 16 | 335 ms | 242 ms | 159 ms |
| 64 | 473 ms | 368 ms | 226 ms |

Sixteen times more replicas costs about 3.4 times more time with push-pull. Push is slow at the end, when most replicas already have the value and push to each other. Pull is slow at the start, when few replicas have something to give. Push-pull does well in both phases.

## Measuring staleness: PBS

"Eventually" has no bound in the definition, but a real system has a distribution. Bailis, Venkataraman, Franklin, Hellerstein and Stoica measured it in "Probabilistically Bounded Staleness for Practical Partial Quorums" (PVLDB, 2012).

The setting is a Dynamo-style store with N replicas. A write goes to all N, and it returns after W replicas acknowledge it. A read asks all N, and it returns after R replicas answer. If R + W is larger than N, every read quorum meets every write quorum, so every read sees the latest write. If R + W is at most N, the store is a **partial quorum**, and reads can be stale.

4. Raise the mean delay to 20 ms. The curve stretches to the right. The staleness window scales with the network delay, so a store in one rack and a store across regions behave very differently.
5. Select N = 5 with R = W = 1. More replicas make each single read less likely to hit a fresh replica.

The model behind the demo is **WARS**, after its four delays. W carries the write from the coordinator to a replica, and A carries the acknowledgement back. R carries the read request, and S carries the read response. PBS defines two measures. The **t-visibility** is the probability that a read that starts t ms after a write commits sees that write. The **k-staleness** is the probability that a read returns one of the last k versions.

The delays in the demo are model inputs: exponential with the mean that you choose. The paper fit its model to production latency traces. For N = 3 and R = W = 1, it reports that 99.9% of reads were consistent 1.85 ms after the write with the LinkedIn SSD trace. With the Yammer trace, the same took 1364 ms. Same algorithm, same settings, very different staleness. You must measure your own system.

## Eventual consistency in real systems

In Cassandra, each request picks a **consistency level**. The `cqlsh` shell defaults to `ONE`, which is R = 1 for reads and W = 1 for writes. `QUORUM` on both sides gives R + W larger than N. Strict quorums alone still do not give linearizability. A read can see a write that has not finished, and a later read can miss it. The ABD algorithm fixes this: a reader writes the value back to a quorum before it returns.

A common pattern is to pay for the strong level only where it matters:

```go
// Strong reads only where a stale value would do harm.
q := session.Query(`SELECT balance FROM accounts WHERE id = ?`, id)
if needFresh {
	q = q.Consistency(gocql.Quorum) // with QUORUM writes: R + W > N
} else {
	q = q.Consistency(gocql.One) // fast, possibly stale
}
```
