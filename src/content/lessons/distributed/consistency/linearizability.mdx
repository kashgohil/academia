A replicated register keeps one value on several machines. Clients only see the requests that they send and the answers that they get back. A **consistency model** is a rule that says which answers are allowed. **Linearizability** is the strongest common model for a single object. It says that the replicas must act as if there were only one copy.

To state the rule, we record a **history**. Each operation in it has an **invocation** (the moment the client sends it) and a **response** (the moment the client gets the answer). Two operations are **concurrent** if their intervals overlap. If operation a returns before operation b starts, then a **precedes** b in real time.

## The definition

Herlihy and Wing defined linearizability in "Linearizability: A Correctness Condition for Concurrent Objects" (ACM TOPLAS, 1990). A history is linearizable if there is a total order of its operations with two properties.

1. **Legal**: the order is a correct run of the sequential object. For a register, each read returns the value of the last write before it, or the initial value.
2. **Real time**: if a precedes b in the history, then a comes before b in the order.

An equivalent picture is the **linearization point**. Each operation takes effect at one instant between its invocation and its response. The dots in the demo are such points. If you can place one dot on each bar so that the dots, in time order, give a legal run, then the history is linearizable.

Two details matter in practice. First, an operation can be **pending**: the client sent it but never got an answer, for example after a timeout. A pending write may take effect at any time after its invocation, or never. A checker must try both.

Second, linearizability is **local**. Herlihy and Wing proved that a history is linearizable if and only if the history of each object is linearizable. So a store can check, or guarantee, each key on its own.

## Why it is the "single copy" model

With one copy and one lock, every operation does take effect at one instant. A client that gets an answer knows that every later operation, by anyone, will see its effect. Linearizability promises exactly this for a replicated object. So code that is correct against one machine stays correct against the cluster.

This is why locks, leader election, fencing tokens and unique-ID counters need linearizable storage. A lock service that lets two clients each read "lock is free" after one of them took it is useless.

## How real systems provide it

| System | Writes | Default read | Weaker option |
|---|---|---|---|
| etcd | through the Raft log | linearizable, by a ReadIndex round | serializable read: `etcdctl get --consistency=s`, or `clientv3.WithSerializable()` |
| ZooKeeper | linearizable (the paper calls it A-linearizable) | served by the local server, can be stale | call `sync` before a read to catch up with the leader |
| Consul | through the Raft log | `default`: the leader answers, with a small stale window after a leader change | `consistent` confirms leadership with a quorum; `stale` lets any server answer |

The etcd API guarantees page says that etcd gives linearizability for all operations except watch, by default. In the source, a linearizable range read waits on `linearizableReadNotify`, which sends a ReadIndex request through Raft. ZooKeeper is weaker by design. The paper (Hunt et al., USENIX ATC 2010) calls `sync` followed by a read a "slow read". The implementation does not send `sync` through the atomic broadcast, so even a slow read relies on timing assumptions.

The ReadIndex read from the Raft thesis (Ongaro 2014) looks like this:

```go
// ReadIndex: a linearizable read without writing to the log.
func (n *Node) LinearizableRead(ctx context.Context, key string) ([]byte, error) {
	// 0. A new leader must first commit an entry of its own term (Raft commits a no-op).
	//    Until then, commitIndex can miss writes that already returned.
	if err := n.waitCurrentTermCommitted(ctx); err != nil {
		return nil, err
	}
	readIndex := n.commitIndex // 1. note the commit index now
	// 2. Prove that we are still the leader: a heartbeat round that a majority acknowledges.
	//    A deposed leader cannot collect this majority, so it cannot serve a stale value.
	if err := n.confirmLeadership(ctx); err != nil {
		return nil, err
	}
	// 3. Wait until the state machine has applied everything up to readIndex.
	if err := n.waitApplied(ctx, readIndex); err != nil {
		return nil, err
	}
	return n.kv.Get(key), nil // 4. Any write that returned before step 1 is visible.
}
```

## What it costs

A linearizable read must rule out a newer write that it has not heard of. With a single leader, that means the leader must prove that it is still the leader. So it pays one round trip to a majority. In the sim, ReadIndex reads took 36.7 ms on average, against 20.2 ms for reads that the leader answered at once.

The cost grows with distance. With replicas in three regions, the round trip to a majority is a cross-region round trip, often tens of milliseconds. The Raft thesis also describes a **lease** read. The leader skips the round trip while a lease is valid, but correctness then depends on a bound on clock drift. Answering at once without a lease, as **leader only** does here, is only safe while the leader cannot change. A deposed leader that does not know it has been replaced will serve stale data.

Writes cost a round trip to a majority in any case. So linearizability mainly makes reads expensive. That is why many systems offer a weaker read as an option, and the next lessons describe what those weaker reads still promise.

## Linearizability is not serializability

The two words sound alike, but they describe different things.

| | Linearizability | Serializability |
|---|---|---|
| unit | one operation on one object | a transaction over many objects |
| real time | yes: the order must respect it | no: any serial order will do |
| typical home | registers, locks, queues, key-value stores | databases |

**Strict serializability** combines both: transactions in a serial order that respects real time. Spanner gives this with TrueTime. A database at plain SERIALIZABLE may legally order a read-only transaction before a write that committed earlier in real time.
