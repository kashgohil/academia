[Linearizability](/distributed/consistency/linearizability) costs a round trip to a quorum for every read. Weaker models remove parts of its promise, so that a replica can answer sooner. This lesson covers the two classic steps down. **Sequential consistency** keeps one order of all operations but drops real time. **Causal consistency** drops the single order and keeps only the order of cause and effect.

To compare models, we use **litmus histories**. A litmus history is a small history that one model allows and a stronger model forbids. The demo checks each history against four models with the same search, so you can see where each model draws its line.

## Sequential consistency

Lamport defined it in "How to Make a Multiprocessor Computer That Correctly Executes Multiprocess Programs" (IEEE Transactions on Computers, 1979). He asks that the result of a run be "the same as if the operations of all the processors were executed in some sequential order". In that order, the operations of each processor must appear "in the order specified by its program".

Compare this with the definition of linearizability. Both ask for one legal total order of all operations. Sequential consistency only asks that the order keeps each **program order**: the order of the operations of one process. It does not ask the order to respect real time between processes. So a process can read a value that is old in real time, as long as all processes agree on one story.

Sequential consistency has a less obvious weakness: it is not **local**. In the store buffering history, the operations on x alone are sequentially consistent: put the read before the write. The operations on y alone are also sequentially consistent. But the whole history is not. So a system cannot get sequential consistency by giving it to each key separately. Linearizability does not have this problem, which is one reason why it is the usual choice.

Where you meet it:

- **Multiprocessors.** Lamport wrote about shared memory. In C++, a data-race-free program that uses only `seq_cst` atomics behaves as if it were sequentially consistent. Real hardware gives less: store buffering appears on x86.
- **ZooKeeper.** Its list of guarantees starts with sequential consistency: the updates of a client are applied in the order that it sent them. Reads are served by the local server, so a client can see the past.

## Causal consistency

Ahamad, Neiger, Burns, Kohli and Hutto defined **causal memory** (Distributed Computing, 1995). It builds on the happens-before relation of Lamport clocks. An operation a is **causally before** b in three cases.

1. a and b are in the same process, and a comes first.
2. b is a read that returns the value that write a wrote.
3. There is a c with a before c and c before b.

Operations with no causal order between them are **concurrent**. A history is causally consistent if each process sees all writes in some legal order that keeps the causal order. Different processes may see concurrent writes in different orders. That is why **Two readers disagree** and **Concurrent writes, two orders** are allowed.

What causal consistency forbids is the effect without its cause. If Bob reads Alice's question and then writes a reply, the reply depends on the question. Nobody may see the reply without the question. This is the anomaly that users notice, in comment threads, chat and access control. A classic case: remove your boss from a photo album, then upload a photo. If the upload overtakes the removal, your boss sees the photo.

## Causal+ and COPS

Lloyd, Freedman, Kaminsky and Andersen built COPS, a causal store for many data centers (SOSP 2011). They defined **causal+** consistency: causal consistency with **convergent conflict handling**. Two replicas that have seen the same writes must hold the same value, for example by last-writer-wins. Plain causal consistency allows replicas to disagree forever about concurrent writes. Causal+ does not.

COPS works like the demo. A client library tracks the writes that the client has read or written. Each write that it sends carries these as dependencies. A remote data center makes the write visible only after it has the dependencies. COPS sends only the **nearest dependencies**, because the others follow by transitivity. Its variant COPS-GT keeps more metadata, so that it can also offer read-only **get transactions** without locks.

```ts
// A remote write becomes visible only after its dependencies (as in COPS).
interface Write { key: string; version: number; value: string; deps: { key: string; version: number }[] }

function receive(dc: DataCenter, w: Write) {
  dc.waiting.push(w);
  let progress = true;
  while (progress) {
    progress = false;
    for (const x of [...dc.waiting]) {
      if (x.deps.every((d) => (dc.visibleVersion.get(d.key) ?? 0) >= d.version)) {
        dc.apply(x); // last-writer-wins on version: convergent conflict handling
        dc.waiting.splice(dc.waiting.indexOf(x), 1);
        progress = true;
      }
    }
  }
}
```

The local data center answers every read and write at once. Only the remote visibility waits. MongoDB offers a similar guarantee per client with **causally consistent sessions**, added in version 3.6. The driver sends `afterClusterTime` with each read. MongoDB documents that only reads with "majority" read concern and writes with "majority" write concern give all four session guarantees.

## The ladder

| Model | One order for all? | Real time? | Forbids, in addition to the model below |
|---|---|---|---|
| linearizable | yes | yes | stale reads, new-then-old |
| sequential | yes | no | clients that disagree on the order (store buffering, IRIW) |
| causal | no, one per process | no | an effect without its cause; time going back for one client |
| eventual | no | no | (in a finite history) only values that nobody wrote |

Each model allows everything that the model above it allows. The tests check this on random histories: a history that passes one row also passes every row below it.
