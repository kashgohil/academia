Many systems need one node to act alone: one primary for a database shard, one writer for a file, one worker for a job. A lock gives that right. But a lock in a distributed system has a problem that a mutex in one process does not have. The holder can crash, or a partition can cut it off. Then nobody can release the lock, and the system stops.

A **lease** solves this with a timeout. A lease is a lock that is valid only for a fixed time, the **time to live** (TTL). The holder must **renew** the lease before the TTL runs out. If the holder crashes, it stops renewing, and the lease expires. Then the lock service can give it to another client. Cary Gray and David Cheriton described leases for file caches in "Leases: an efficient fault-tolerant mechanism for distributed file cache consistency" (SOSP 1989).

The timeout fixes the crash case, but it adds a new one. A holder that is not dead, only slow, can still act after its lease expired. This lesson shows how that happens, and how a **fencing token** makes the damage impossible.

## Why a check cannot help

A careful client checks its lease before each write. Step 1 shows why that is not enough. There is a gap between the check and the moment the write reaches the storage. Any delay in that gap can outlast the lease:

- A stop-the-world **garbage-collection pause** in a JVM, Go or .NET process.
- A **virtual machine** that the hypervisor stops, for example during a live migration. See [virtual machines and hypervisors](/os/isolation/virtual-machines-and-hypervisors).
- A page fault that must read from a slow disk, or memory that the kernel has [swapped out](/os/memory/swapping-and-the-oom-killer).
- A `SIGSTOP`, a debugger, or a busy CPU that does not run the thread.
- A packet that waits in a queue or is sent again by TCP.

None of these has a hard upper limit in a normal system. Martin Kleppmann's post "How to do distributed locking" (February 2016) describes this case, and notes that HBase used to have this problem. A check by the client moves the gap, but it cannot close it. The client cannot both check and act in one atomic step, because the check is local and the action is remote.

## Two clocks

The lease has two views of time. The service measures the TTL with its clock. The holder measures it with its own clock. Each must use a **monotonic clock**, which counts elapsed time and does not jump when NTP or an operator changes the time of day. See [physical clocks and drift](/distributed/time/physical-clocks-and-drift).

Even a monotonic clock has a rate error, the **drift**. Quartz clocks in servers drift by tens of parts per million (ppm), and Spanner assumes a worst case of 200 ppm. The range of 1 to 100 ppm here is a model input. The holder also starts its timer before it sends the request. So its lease can only start earlier than the service's lease, which is the safe direction.

Step 4 shows the worst case: a clock that stops. In this model, a paused VM resumes with its clock behind, and the guest corrects it only later. Then a check after the pause passes, although the lease has expired.

Assume that each clock runs at most a fraction $\rho$ too fast or too slow. In the worst case the service clock is fast and the holder clock is slow. Assume also that the last request waits for a pause of at most $P$ and a network delay of at most $\delta$. The holder must stop a margin $m$ before its local TTL $T$ ends:

$$
\frac{T - m}{1 - \rho} + P + \delta \le \frac{T}{1 + \rho}
\quad\Longrightarrow\quad
m \ge T \cdot \frac{2\rho}{1 + \rho} + (1 - \rho)(P + \delta)
$$

The margin has a real cost: the holder gives up that part of every lease. A system can pay it for drift and delay. It cannot pay it for pauses. A pause bound long enough for every GC, VM stall and swap storm is longer than any useful lease.

## Fencing tokens

So the protection must be at the resource itself. A **fencing token** is a number that the lock service increases on each grant. The client sends its token with every request to the storage. The storage remembers the highest token that it has seen, and it rejects any request with a lower token.

```go
// The storage side of fencing. It must run atomically with the write.
func (s *Store) Write(token uint64, key string, value []byte) error {
	s.mu.Lock()
	defer s.mu.Unlock()
	if token < s.maxToken {
		return ErrStaleToken // an older holder woke up: refuse it
	}
	s.maxToken = token
	s.data[key] = value
	return nil
}
```

The token turns a timing problem into an ordering problem. The storage does not need a clock, and the client does not need to know that it paused. A stale holder can still send a request, but the storage will refuse it after it has seen a newer token. Three rules make this work:

- The token must grow with each grant, even across a crash of the lock service. So the service must store it durably, which in practice means consensus.
- The storage must check the token and apply the request in one atomic step.
- Every access in the critical section must carry the token. The next lesson shows that a check on writes only can still lose updates.

Real systems call this by different names. Google's Chubby (Burrows, OSDI 2006) gives a **sequencer**: an opaque string with the lock name, the mode and a lock generation number. A server checks it against its Chubby cache, or against the most recent sequencer that it has seen.

Chubby also has a **lock-delay** for servers that do not check sequencers. After a holder fails, nobody can take the lock for a time that the client chooses, up to one minute. Kleppmann points out that ZooKeeper's `zxid` or a znode version can serve as a token. The etcd documentation says that the revision number plays the same role.

## Lease reads in Raft

A Raft leader must prove that it is still the leader before it answers a read, as [linearizability](/distributed/consistency/linearizability) explains. The safe way is a round of heartbeats to a majority for each batch of reads. Ongaro's dissertation (section 6.4.1) describes a lease instead. When a majority acknowledges a heartbeat sent at time `start`, followers will not elect anyone for about an election timeout. So the leader may answer reads alone until:

$$
\text{start} + \frac{\text{election timeout}}{\text{drift bound}}
$$

Take an election timeout of 1000 ms, the etcd default, and a drift bound of 1.1. Then the leader may serve reads for 909 ms after it sent the heartbeat. The dissertation adds two warnings. The leader must let its lease expire before it transfers leadership. And scheduling, GC pauses and VM migration can break the drift bound. So the dissertation does not recommend this method unless performance needs it.

etcd's Raft library has this as `ReadOnlyLeaseBased`. Its source comment says that it "can be affected by clock drift", and that `CheckQuorum` must be on. The default, `ReadOnlySafe`, uses the heartbeat round. A deposed leader that serves a lease read is the same bug as client A: an old holder that acts after a new one exists.

| System | Lease | What stops a stale holder |
|---|---|---|
| Chubby | session lease, KeepAlive extends it by 12 s by default | sequencer checked by the server; lock-delay up to one minute |
| ZooKeeper | session timeout, 2 to 20 times `tickTime` | `zxid` or znode version used as a token by the application |
| etcd | lease with a TTL, kept alive by a stream | revision of the lock key, checked in a transaction |
| Raft lease read | election timeout divided by the drift bound | `CheckQuorum`, and trust in the drift bound |
