A state-based replica sends its whole state, so the network can do almost anything to the messages. An **operation-based** replica (a CmRDT) sends only the update: "add 1", "insert x after character 7". The messages are small and do not grow with the state. The price moves to the network layer. Now each message carries information that exists nowhere else, so the delivery layer must not lose it, repeat it, or deliver it too early.

Shapiro, Preguiça, Baquero and Zawirski (SSS 2011) give the conditions. Ops go through **reliable causal broadcast**: every op reaches every replica exactly once, in an order consistent with happens-before. And all **concurrent** ops must commute. This lesson takes each condition away in turn, and shows what breaks.

## Why the counter and the set need different things

The two objects fail for different reasons. Increments commute with all other increments, so a counter accepts any order. A counter still needs **exactly-once** delivery, because $x + 1 + 1 \neq x + 1$. An id per op and a set of seen ids give that.

The set fails on order. An **observed-remove set** (OR-Set) tags each add with a unique id. A remove sends the tags of the element that its origin has seen. Look at the run in the demo:

- R1 runs add(a) with tag 1.1 and sends it.
- R2 receives the add, then runs remove(a) with tags [1.1]. The remove is **causally after** the add, because R2 saw the add first.
- R3 receives the remove first. Tag 1.1 is not there, so the remove does nothing. Then the add arrives, and tag 1.1 stays forever.

The add and the remove do not commute, and they do not need to. Shapiro et al. only ask that **concurrent** ops commute. Ops that are ordered by happens-before must arrive in that order, and causal delivery makes sure that they do.

## Causal broadcast with vector clocks

The standard delivery layer uses a vector clock per replica. Replica $j$ keeps a vector $D$, where $D[k]$ counts the ops from replica $k$ that $j$ has delivered. Each op carries the vector $V$ of its origin at the time it was made, so $V[\text{origin}]$ is its sequence number. Replica $j$ delivers the op only when

$$
V[\text{origin}] = D[\text{origin}] + 1 \quad\text{and}\quad V[k] \le D[k] \text{ for every } k \neq \text{origin}.
$$

The first part says that this is the next op from that origin. The second says that $j$ has delivered every op that the origin had delivered when it made this one. If either part fails, the op waits in a buffer. An op with $V[\text{origin}] \le D[\text{origin}]$ was delivered before, so it is a duplicate and the layer drops it.

```go
// deliverable reports whether op m can be applied at a replica with delivered vector d.
func deliverable(d []uint64, m Op) bool {
	if m.VC[m.Origin] != d[m.Origin]+1 {
		return false // not the next op from this origin (a gap, or a duplicate)
	}
	for k, v := range m.VC {
		if k != m.Origin && v > d[k] {
			return false // the origin had seen an op that we have not
		}
	}
	return true
}
```

The layer does not repair loss on its own. If the network loses an op, the buffer at the receiver waits forever for the gap. Real systems add retransmission, for example anti-entropy that compares delivered vectors and resends what is missing. The lesson on sequence CRDTs uses that.

## Pure op-based CRDTs and causal stability

Classic op-based CRDTs often put metadata inside the ops. An OR-Set remove carries a list of tags, for example. Baquero, Almeida and Shoker asked how small an op can be. In "Making Operation-based CRDTs Operation-based" (DAIS 2014) and "Pure Operation-Based Replicated Data Types" (2017), each op carries only its name and arguments. The delivery layer adds a timestamp, and each replica keeps a **partially ordered log** (PO-Log) of ops. The value is a function of that log.

The log would grow forever. The fix is **causal stability**. In the 2017 paper, an op is causally stable at replica $i$ when every op that $i$ delivers from now on has a larger timestamp. So no op that is concurrent with it can still arrive.

A replica can detect this when it has delivered, from every other replica, an op made after that replica delivered the stable op. Then the stable op can lose its timestamp and fold into a compact state. The middleware in the 2017 paper, **Tagged Causal Stable Broadcast**, reports which ops are stable.

Stability has a cost: it needs to hear from every replica. One replica that is down or cut off stops all stability, and the log grows until it returns. The next lesson shows the same effect on tombstones.

## State-based or op-based?

Shapiro et al. prove that the two kinds are equivalent: each can emulate the other. The choice is about engineering.

| | state-based | op-based |
|---|---|---|
| message | the whole state (or a delta) | one op, plus an id and a vector clock |
| network may | lose, reorder and duplicate | reorder only, if the layer buffers and deduplicates |
| delivery layer | gossip of any kind | reliable causal broadcast |
| merge must be | a join (commutative, associative, idempotent) | commutative for concurrent ops |
| good when | states are small, links are poor, membership changes | states are large, ops are small, links are reliable |
| recovery after a long partition | one state exchange | replay of every missed op, or a state transfer |

Delta-state CRDTs sit between the two. They send small messages, but keep the join, so the network may still duplicate and reorder them.
