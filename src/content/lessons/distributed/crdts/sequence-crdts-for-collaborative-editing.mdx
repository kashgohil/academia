Text looks like a simple list of characters. The problem is the index. A user types "!" at index 5. At the same time, another user inserts three characters at index 0. When the first op arrives at the second replica, index 5 points at a different place. Each replica applies the same two ops and gets a different text.

There are two known fixes. **Operational transformation** (OT) rewrites each incoming op against the ops that were concurrent with it, so "insert at 5" becomes "insert at 8". A **sequence CRDT** removes the index from the op. Each character gets a unique, permanent id, and an op says "insert after character X". The id never moves, so there is nothing to transform.

## RGA: ids, a left neighbour, and one skip rule

The Replicated Growable Array (RGA) of Roh, Jeon, Kim and Lee (JPDC, 2011) is the simplest sequence CRDT to explain. The paper uses a custom timestamp, the S4Vector. Later presentations use a simpler id, and so does this lesson. Each character has an id (counter, replica). The counter is a Lamport clock: a replica takes one more than the largest counter that it has seen. Ids compare by counter, then by replica.

An insert op is (id, the id of the left neighbour, character). A delete op names an id, and the character stays as a tombstone.

To apply an insert, a replica finds the left neighbour, steps right, and skips every element with a larger id. Then it inserts.

```ts
function integrate(list: Elem[], op: { id: Id; after: Id | null; ch: string }) {
  let i = op.after === null ? 0 : indexOf(list, op.after) + 1;
  while (i < list.length && greater(list[i].id, op.id)) i++; // skip newer siblings and their text
  list.splice(i, 0, { id: op.id, ch: op.ch, deleted: false });
}
```

Why does this converge?

Two inserts after the same neighbour are **siblings**. The rule puts the sibling with the larger id first. Everything typed after a sibling has a larger counter, by the Lamport rule, so the skip moves past that whole run. Every replica therefore builds the same order, whatever the order of arrival. The rule also needs causal delivery: an insert must not arrive before its left neighbour exists. The sim uses the causal broadcast layer from the lesson on operation-based CRDTs.

Tombstones are the cost. A deleted character keeps its id, because a concurrent insert may name it as its left neighbour. A long-lived document can hold more deleted characters than visible ones. They can only be dropped when every replica has seen the delete and no op that names them can still arrive.

## Position identifiers: Logoot and LSEQ

A second family gives each character a **position** from a dense ordered set. There is always room for a new position between two others. The text is the characters sorted by position. Logoot (Weiss, Urso and Molli, ICDCS 2009) uses a list of (digit, site) pairs. LSEQ (Nédelec, Molli, Mostefaoui and Desmontils, DocEng 2013) chooses digits with an adaptive strategy, to keep ids short.

These ids need no tombstones: a delete removes the character and its position. But two users who insert at the same place pick positions in the same gap, independently. Their characters then sort in an order that nobody chose.

## The interleaving anomaly

Kleppmann, Gomes, Mulligan and Beresford named this problem in "Interleaving anomalies in collaborative text editors" (PaPoC 2019). They showed that Logoot and LSEQ interleave text that two users type at the same place. For RGA they found a lesser variant. It appears when a user types with backward cursor moves, as in step 3. A merge like "Hi dcoagt!" converges, but no user would accept it.

Weidner and Kleppmann later defined **maximal non-interleaving** and gave the Fugue algorithm ("The Art of the Fugue", IEEE TPDS, 2025). Their paper proves that the FugueMax variant has this property. Plain Fugue is simpler, but it can interleave more characters when some interleaving cannot be avoided.

## How real editors do it

**Yjs.** Its README says that it implements a modified version of YATA (Nicolaescu, Jahns, Derntl and Klamma, GROUP 2016). YATA is a list CRDT in which each inserted item records its left and right neighbours at the time of the insert. Yjs cannot drop deleted items while it keeps a unique order. Instead it removes their content and keeps small tombstones. This garbage collection is on by default; `doc.gc = false` keeps old content for version history.

**Automerge.** Its documentation says that a list is an RGA sequence. Its text type implements Peritext, a CRDT for rich text that adds formatting marks such as bold to the characters.

**Google Docs** uses OT. A 2010 series on the Google Drive blog explains how Docs merges concurrent changes. The algorithm that shifts concurrent changes is operational transformation. OT dates back to Ellis and Gibbs, "Concurrency control in groupware systems" (SIGMOD 1989).

| | operational transformation | sequence CRDT |
|---|---|---|
| op names a place by | index | unique id of a neighbour, or a dense position |
| concurrent ops | transformed against each other | applied as they are; ids decide the order |
| typical topology | clients and a central server that orders ops | any: peer to peer, offline, server relay |
| metadata | small ops, plus the history to transform against | an id per character, plus tombstones (RGA) |
| hard part | correct transforms for every pair of ops | metadata size, and interleaving |

Neither approach is free. OT keeps documents small but needs the server, or very careful proofs, to stay correct. CRDTs work offline and peer to peer, and pay for it with an id on every character.
