A state-based CRDT may only move up in its order. Adding to a set moves up. Removing moves down, and a merge would undo it: the other replica still has the element, and the union brings it back. So every replicated set must answer two questions. How does a replica remember a remove? And what happens when one replica removes an element while another adds it at the same time?

## Four answers

**G-Set.** A grow-only set: add only, and the merge is the union. It is the base for the others.

**2P-Set** (two-phase set). Two G-Sets: $A$ for adds and $R$ for removes. An element is in the set if it is in $A$ and not in $R$. The set $R$ holds **tombstones**: markers that say "this was removed".

Shapiro et al. allow a remove only if the element is in the local set. The INRIA report (RR-7506, 2011) states the limit plainly: an element may be added and removed, but never added again. Remove wins every race.

**LWW-element-Set.** Each element has the time of its latest add and its latest remove. The element is in the set if the add is later. Ties need a fixed rule; the sim lets the add win. Elements can come back, but the answer to a race depends on clocks, not on what the users saw.

**OR-Set** (observed-remove set). Each add creates a unique **tag**, for example (replica, counter). The state is a set of (element, tag) pairs, plus the tags that removes have killed. A remove kills only the tags of the element that its replica has **observed**.

An add that is concurrent with the remove has a new tag, which the remove could not see. So the add survives. The report says that the 2P-Set gives precedence to remove and the OR-Set to add.

```ts
type OrSet = { adds: Map<string, string>; tombs: Set<string> }; // tag -> element; dead tags

function add(s: OrSet, e: string, tag: string) {
  s.adds.set(tag, e); // tag = `${replica}.${counter}`, unique
}
function remove(s: OrSet, e: string) {
  for (const [tag, x] of s.adds) if (x === e) s.tombs.add(tag); // only tags this replica has seen
}
function merge(a: OrSet, b: OrSet): OrSet {
  return { adds: new Map([...a.adds, ...b.adds]), tombs: new Set([...a.tombs, ...b.tombs]) };
}
const has = (s: OrSet, e: string) => [...s.adds].some(([t, x]) => x === e && !s.tombs.has(t));
```

## Add wins or remove wins?

Neither answer is right in general. The question is what users expect when their actions race.

- In a shopping cart, a lost add loses a sale, and a stale item is easy to remove again. Add wins.
- In an access-control list, a revoked permission that comes back is a security bug. Remove wins.
- In a set of feature flags, the answer depends on the flag.

Real systems document their choice. Riak KV's sets resolve a concurrent add and remove so that the add wins. In its maps, a concurrent update wins over a remove of the field. Redis Active-Active sets also behave as OR-Sets: a remove removes only the instances that it has seen, and otherwise add wins. A remove-wins set is also possible: a remove keeps a marker that beats every concurrent add. Pick it on purpose, and write the choice down.

## Tombstones and how to collect them

The classic OR-Set keeps every dead tag forever. A replica needs the tombstone to reject the tag when an old state, which still holds it, arrives by gossip. In a busy set, the tombstones soon outnumber the live elements.

You can drop a tombstone once no state that still holds its tag can arrive. That is **causal stability** again. A replica knows that a remove is stable when it has seen, from every replica, a state that includes the remove.

The rules for safe collection are strict. The sim gossips over FIFO links, as TCP gives. Without that, an old state could arrive after a tombstone is gone and bring the tag back. A replica that leaves the cluster for good must also leave the membership, or nothing ever becomes stable again.

## No tombstones: the optimized OR-Set

Bieniusa, Zawirski, Preguiça, Shapiro, Baquero, Balegas and Duarte showed how to avoid tombstones ("An Optimized Conflict-free Replicated Set", INRIA RR-8083, 2012). Each tag is a **dot**: (replica, counter), as in dotted version vectors. Each replica also keeps a version vector of the dots that it has seen. The merge then decides by itself:

- A dot that both sides hold stays.
- A dot that only one side holds stays if the other side has not seen it yet. That is a new add.
- If the other side has seen the dot but does not hold it, the other side removed it. The dot goes.

The vector replaces all tombstones, and its size is one entry per replica. The add still wins over a concurrent remove, because the remove could not have seen the new dot. Riak's set type is this design. Its source calls it `riak_dt_orswot`: "Observe Remove Set WithOut Tombstone".

## Maps of CRDTs

A map is a set of keys, where each key holds a nested CRDT: a counter, a register, a set, or another map. The keys form an OR-Set, and the values merge with their own merge. An update to a key also makes the key present, so an update that races with a remove of the key wins. This is how a JSON-like document can be one CRDT.

Removal hides a key, but what happens to its nested state? In the sim, a remove hides the key and keeps the counter inside.

Suppose R1 removes the key "milk" with count 2, while R2 adds 1 to it. After the merge, "milk" is back with 3, not 1. The old increments came back with the key. Designs that reset the nested value on remove need more metadata, such as the dots of every nested update. This choice matters as much as add wins versus remove wins.

| type | remove | re-add | race between add and remove | metadata |
|---|---|---|---|---|
| G-Set | no | not needed | not possible | none |
| 2P-Set | once | never | remove wins | one tombstone per removed element |
| LWW-element-Set | yes | yes | later clock wins | two times per element |
| OR-Set | yes | yes | add wins | one tag per add, tombstones until collected |
| optimized OR-Set | yes | yes | add wins | live dots, one vector entry per replica |
