A replicated counter looks easy. Each replica holds a number, adds to it, and sends it to the others. Then two replicas add 1 at the same time, and each sends "my value is 6". One increment is gone. Locks or a leader would fix this, but they stop working when the network is cut.

A **conflict-free replicated data type** (CRDT) fixes it with math instead. Every replica accepts every update alone, and any two replicas that have seen the same updates hold the same state.

This lesson covers the **state-based** kind. A replica sends its whole state, and the receiver merges it into its own. The trick is to choose states and a merge so that the order of messages, lost messages and duplicates cannot matter.

## Lattices: the rules that make merging safe

A **partial order** $\le$ on states says when one state "knows at least as much" as another. Two states can be **concurrent**: neither is $\le$ the other. A **join-semilattice** is a partial order in which every pair of states $a, b$ has a **least upper bound** $a \sqcup b$. It is a state above both, and below every other state above both.

Shapiro, Preguiça, Baquero and Zawirski defined a state-based CRDT (a CvRDT) with three rules (SSS 2011).

- The states form a join-semilattice.
- A merge with a remote state computes the least upper bound.
- An update only moves the state up: $s \le \mathrm{update}(s)$. This is an **inflation**.

The least upper bound has three laws for free:

$$
a \sqcup b = b \sqcup a \qquad (a \sqcup b) \sqcup c = a \sqcup (b \sqcup c) \qquad a \sqcup a = a
$$

Commutativity means that the order of delivery does not matter. Associativity means that the grouping of merges does not matter, so gossip through a third replica is fine. Idempotence means that a duplicate does no harm. Together they say that the state of a replica is the join of every update that has reached it, by any path. Two replicas that have seen the same updates hold the same join.

## The basic types

**G-Counter.** A grow-only counter keeps one entry per replica. Replica $i$ adds only to entry $i$. The value is the sum of the entries, and the merge takes the maximum of each entry. It cannot count down, because a decrement would move entry $i$ down and break the inflation rule.

**PN-Counter.** Two G-Counters: $P$ counts increments and $N$ counts decrements. The value is $\sum P - \sum N$. Both halves only grow, so the pair is a lattice.

```rust
#[derive(Clone)]
struct PnCounter { p: Vec<u64>, n: Vec<u64> }

impl PnCounter {
    fn add(&mut self, me: usize, d: i64) {
        if d >= 0 { self.p[me] += d as u64 } else { self.n[me] += (-d) as u64 }
    }
    fn merge(&mut self, o: &PnCounter) {
        for i in 0..self.p.len() {
            self.p[i] = self.p[i].max(o.p[i]);
            self.n[i] = self.n[i].max(o.n[i]);
        }
    }
    fn value(&self) -> i64 { self.p.iter().sum::<u64>() as i64 - self.n.iter().sum::<u64>() as i64 }
}
```

**Max-register.** The state is a number, and the merge is the maximum. It is the simplest useful lattice, a chain.

**LWW-register.** A **last-writer-wins** register holds a value and a timestamp, here (time, replica id). The merge keeps the larger timestamp. It is a lattice, so it converges. But it keeps one of two concurrent writes and silently drops the other.

The naive counter in the first demo is an LWW-register that holds a count. The lattice laws give convergence, not the meaning that you want. For a counter, you must design the lattice so that the join keeps every increment.

## Strong eventual consistency

Eventual consistency only promises that replicas agree after updates stop. Shapiro et al. defined **strong eventual consistency** (SEC) in the same 2011 paper. It adds **strong convergence**: correct replicas that have delivered the same updates have equivalent state. This holds at every moment, not only after a quiet period. A replica never has to roll back or ask anybody, so a CRDT stays available during any partition.

SEC asks little of the network. A state message can be lost, delayed, reordered or duplicated. Convergence needs only that each update reaches each replica by some path, eventually. Periodic gossip of full states gives that, even if most messages are lost.

## The cost: shipping whole states

The price of this freedom is size. A G-Counter has one entry per replica that ever wrote. With an 8-byte id and an 8-byte count per entry (a model input), a state with 100 entries is 1,600 bytes. Every gossip message carries all of it, even if only one entry changed. A set that holds a million elements sends a million elements.

Almeida, Shoker and Baquero proposed **delta-state CRDTs** (JPDC, 2018). A **delta-mutator** returns a small state, the delta, that holds only what an update changed. A delta is itself a state of the lattice, so a receiver joins it like any other state. A replica joins deltas into a **delta-group** and sends that. To keep causal consistency when messages are lost, the paper sends **delta-intervals** and uses acknowledgements.

The sim compares the two. Each replica makes 4 increments in the first 400 ms. Every 40 ms, each replica sends a random peer its full state, or only the entries that it has not yet sent to that peer. Links in the delta run are reliable.

| replicas | full state, bytes per message | delta, bytes per message | full state, total kB | delta, total kB |
|---|---|---|---|---|
| 3 | 48 | 29 | 4 | 1 |
| 10 | 160 | 112 | 39 | 19 |
| 100 | 1600 | 1135 | 3984 | 2618 |

Deltas also let a replica send nothing when nothing changed. That is where most of the saving comes from. The win grows with the size of the state. A counter is small. A set with many elements is large, but a delta for one add is one element.

## Real systems

Riak KV 2.0 added data types built on CRDTs: counters, sets, maps, registers and flags. Its documentation says that flags and registers must be embedded in maps. Redis Software has Active-Active databases, which use CRDTs and a strong eventual consistency model across regions. Both pick merges per type, because no single merge is right for every kind of data.
