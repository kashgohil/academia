A pipeline reads payments from a log, processes them, and adds each amount to an account in a database. The processor can crash, and the network can lose a request or its answer. After a crash, each payment must change the balance exactly once: not zero times and not twice. Vendors call this "exactly-once". The term is easy to misread, so this lesson starts with what it can and cannot mean.

## Three guarantees

- **At-most-once**: each record has its effect zero or one times. Send without retry, or move the position before doing the work. A crash can lose a record.
- **At-least-once**: each record has its effect one or more times. Do the work, then move the position, and retry until an acknowledgement comes. A crash or a lost acknowledgement can repeat a record.
- **Exactly-once**: each record has its effect exactly once, under crashes and retries.

Exactly-once **delivery** is impossible over an unreliable network. A sender that gets no acknowledgement cannot tell a lost message from a lost acknowledgement. This is the problem of the [two generals](/distributed/foundations/the-network-model-messages-delays-and-partitions). If it resends, the receiver may get two copies. If it does not resend, the receiver may get none.

What is possible is exactly-once **processing**, or exactly-once **effects**. Messages can still arrive twice, but the second copy changes nothing.

There are two ways to make a repeat harmless. One is to make the effect **idempotent**: apply it in a way that a second application leaves the result the same. The other is to make the effect and the record of progress **atomic**: one transaction holds both, so they happen together or not at all. Real systems use both.

## A pipeline with crash points

The processor below does two writes per record. With at-most-once it commits the offset, then sends the effect once. With at-least-once it applies the effect, then commits the offset. ## Kafka's idempotent producer

The same problem appears one level down, between a producer and a Kafka broker. A producer sends a batch, the broker appends it, and the acknowledgement is lost. The producer retries, and the broker appends the batch a second time. Retries can also reorder batches when several requests are in flight.

KIP-98 ("Exactly Once Delivery and Transactional Messaging", Kafka 0.11.0, June 2017) fixed this with three numbers:

- a **producer id** (PID) that the broker gives to the producer;
- a **producer epoch**, which grows each time a producer with the same transactional id starts again;
- a **sequence number** per partition, starting at 0, on every batch.

The broker keeps the last sequence number per producer and partition. A batch with the next number is appended. A batch with an old number is a duplicate. The broker does not append it, and answers with success. A batch that skips a number gets `OutOfOrderSequenceException`. The broker remembers the last 5 batches per producer, so idempotence needs `max.in.flight.requests.per.connection` ≤ 5.

```text
broker state for (PID 4000, partition 0): last seq = 1, recent = [0 -> offset 0, 1 -> offset 1]
batch seq 2   -> 2 = last + 1: append at offset 2
batch seq 0   -> 0 <= last, in recent: duplicate, answer "offset 0", append nothing
batch seq 4   -> gap after 2: OutOfOrderSequence, the producer resends in order
```

The Confluent post that announced the feature (June 2017) reports that idempotence has a negligible cost in throughput.

## Transactions across partitions

Idempotence covers one producer session and one partition. A stream job does more: it reads input, writes to several output partitions, and commits its input offsets. KIP-98 added **transactions** that make all of these atomic.

- A producer sets a `transactional.id`. `initTransactions()` registers it with a **transaction coordinator**, a broker that keeps state in the internal topic `__transaction_state`. The call raises the epoch, so an older "zombie" instance with the same id is fenced off.
- The producer calls `beginTransaction()`, sends records to any partitions, and adds its consumer offsets with `sendOffsetsToTransaction()`.
- `commitTransaction()` makes the coordinator run a two-phase commit. It writes a COMMIT **control marker** into every partition that the transaction touched. `abortTransaction()` writes ABORT markers.
- A consumer with `isolation.level=read_committed` reads only up to the **last stable offset** (LSO), the first offset of a transaction that is still open. It skips records of aborted transactions. The default is `read_uncommitted`.

```ts
// The consume-transform-produce loop (Java client names, in TS syntax).
producer.initTransactions(); // fences an older instance with the same transactional.id
for (;;) {
  const records = consumer.poll(100);
  producer.beginTransaction();
  for (const r of records) producer.send(transform(r));
  producer.sendOffsetsToTransaction(nextOffsets(records), consumer.groupMetadata());
  producer.commitTransaction(); // outputs and input offsets: all or nothing
}
```

The cost is small at moderate commit rates. In the Confluent post's test, with 1 KB messages and transactions every 100 ms, producer throughput fell only 3% compared with an in-order at-least-once producer. Kafka Streams wraps this loop behind `processing.guarantee=exactly_once_v2`, the name since Kafka 3.0.

## End to end: idempotent and transactional sinks

Transactions end at the edge of Kafka. A database, a search index or an e-mail service is outside. The [stream processing lesson](/distributed/data-systems/stream-processing) showed that exact state inside the job still sends output twice after a replay. Two designs close the gap.

An **idempotent sink** writes each effect under a key derived from the input, so a replay overwrites instead of adding. A **transactional sink** stores the effect and the input position in one transaction of the external system, as the pipeline above does:

```sql
-- Idempotent: the (partition, offset) of the source record is the key.
INSERT INTO credits (src_partition, src_offset, account, amount)
VALUES ($1, $2, $3, $4)
ON CONFLICT (src_partition, src_offset) DO NOTHING;

-- Transactional: effect and progress commit together; restart reads progress here.
BEGIN;
UPDATE accounts SET balance = balance + $amount WHERE id = $account;
UPDATE progress SET next_offset = $offset + 1 WHERE src_partition = $p AND next_offset = $offset;
COMMIT;
```

Flink generalizes the transactional sink with a **two-phase commit sink**. The `TwoPhaseCommitSinkFunction` came in Flink 1.4.0 (December 2017). A Flink blog post by Piotr Nowojski and Mike Winters (February 2018) describes its four methods:

- `beginTransaction` opens a transaction in the external system;
- `preCommit` flushes it when the checkpoint barrier arrives: this is the vote;
- `commit` runs only after the job manager reports that the whole checkpoint succeeded;
- `abort` throws the transaction away on failure.

The current `KafkaSink` with `DeliveryGuarantee.EXACTLY_ONCE` needs a `transactionalIdPrefix`. Its transaction timeout is 1 hour by default. The broker caps transactions with `transaction.max.timeout.ms`, 15 minutes by default, so one of the two settings must change. The Flink docs warn that the timeout must be much longer than the maximum checkpoint duration plus the restart time, or data can be lost. Output also becomes visible to `read_committed` readers only at each checkpoint, so the checkpoint interval adds latency.

| Guarantee | How | Fails when |
|---|---|---|
| at-most-once | commit first, no retry | any crash between the two steps, or any loss |
| at-least-once | effect first, retry until acked | crash after the effect, or a lost ack |
| exactly-once, idempotent sink | dedup by source key | the key is not stable, or the dedup table expires |
| exactly-once, transactional | effect and offset in one transaction | the sink has no transactions, or a transaction times out |
