A **batch** job reads a finished data set, computes, and stops. A **stream** job runs forever on data that never ends: clicks, payments, sensor readings. It must give answers before all the data is in. So two questions that batch never asks become central. When is a result complete enough to emit? And how does a job that runs for months survive crashes without counting anything twice?

The [log lesson](/distributed/data-systems/distributed-logs) gave the input: a partitioned, replayable log. This lesson builds the processor on top of it. The ideas come from Google's MillWheel (VLDB 2013) and the Dataflow Model (Akidau et al., VLDB 2015). Apache Flink, Kafka Streams and Apache Beam implement them.

## Event time and processing time

Every record has two times. **Event time** is when the event happened, as the device recorded it. **Processing time** is when the stream job sees it. They differ by network delay, retries, batching, and phones that were offline for an hour. Records also arrive out of order. So a question such as "how many payments per minute?" must say which minute it means.

A **window** groups records by event time:

- **tumbling**: fixed, non-overlapping intervals, for example each whole minute;
- **sliding** (Flink) or **hopping** (Kafka Streams): fixed size with a smaller step, so windows overlap and one record falls into several;
- **session**: per key, a window that grows while events come closer together than a **gap**, and closes after a quiet gap.

## Watermarks

A window for 12:00 to 12:01 cannot wait forever for stragglers. A **watermark** is the job's statement that no event older than a time $W$ is still to come. A window $[s, e)$ fires when $W \ge e$. The simplest watermark trusts a fixed bound on disorder, the **bounded out-of-orderness** delay $d$:

$$
W = \max(\text{event time seen so far}) - d
$$

Flink's `BoundedOutOfOrdernessWatermarks` computes exactly this, minus 1 ms. A job with several inputs takes the minimum of their watermarks, so one slow input holds back every window.

An event that arrives after its window fired is **late**. The job can drop it, send it to a side output (Flink's `sideOutputLateData`), or update the result if it is within an **allowed lateness**. Flink's allowed lateness is 0 by default. Kafka Streams calls this the **grace period**. Since Kafka 3.0 it has no default, so each window must state it.

The trade-off is plain. A short delay gives fast results that may be wrong. A long delay gives right results late. Allowed lateness gives both, but then a result is not final when it first appears, and downstream systems must accept updates. The Dataflow paper calls the rule for when to emit and re-emit a **trigger**.

A heuristic watermark can never be perfect for real data. But one half can be proved, and a property test pins it. When the delay is at least the largest disorder in the input, every streaming result equals the batch result.

## State and why it must survive

A window count, a join buffer or a running total is **state**. A job may hold gigabytes of it, spread over many parallel tasks. If a task crashes, the job must restore the state and continue reading the input from a matching position. "Matching" is the hard part. The restored state must contain exactly the records before that position: no more and no less.

Chandy and Lamport solved this in "Distributed Snapshots: Determining Global States of Distributed Systems" (ACM TOCS, 1985). Their algorithm records a consistent global state while the system runs. It needs FIFO channels:

- An initiator records its state and sends a **marker** on each outgoing channel, before any further message.
- A process that receives its first marker records its state and sends markers on all its outgoing channels.
- For every other incoming channel, it records the messages that arrive after its own snapshot and before that channel's marker. They are the state of that channel.

## Barriers in Flink

Carbone, Fóra, Ewen, Haridi and Tzoumas adapted this to dataflows in "Lightweight Asynchronous Snapshots for Distributed Dataflows" (2015). That paper is the basis of Flink's checkpoints. The marker is a **barrier** that flows in line with records:

1. The coordinator (the JobManager) asks every source for checkpoint $n$. Each source records its read offset and emits barrier $n$.
2. An operator with several inputs **aligns** them. When barrier $n$ comes on one input, it stops reading that input and buffers what follows. When barrier $n$ has come on every input, it records its state, forwards the barrier and reads on.
3. Each task acknowledges with a handle to its state. Checkpoint $n$ is complete when every task has done so.
4. On a failure, every task restarts from the last complete checkpoint. Sources seek back to the recorded offsets and replay.

Alignment means that the state never contains a record from after the barrier. So on an acyclic graph, no channel state needs to be stored. Only operator state and source offsets are stored.

4. Move the crash to 250 ms. Checkpoint 3 is already complete, so nothing is replayed and the sink sees no duplicates.
5. In every aligned run, look at the sink. Its duplicates are the topic of the [next lesson](/distributed/data-systems/exactly-once-semantics).

Alignment has a cost. While an operator waits for the slow input's barrier, the fast input is blocked. Under backpressure, barriers wait behind full buffers, and checkpoints become slow. Since Flink 1.11, checkpoints can be **unaligned**. The barrier overtakes buffered records, and those in-flight records are stored as part of the checkpoint, the "channel state" of Chandy and Lamport. Flink's at-least-once mode skips alignment, which gives exactly the double count of step 3.

| Mode | Blocks inputs | Stores in-flight data | State after recovery |
|---|---|---|---|
| aligned (default) | yes | no | exact |
| unaligned | no | yes | exact |
| at-least-once | no | no | may count records twice |

Large state makes snapshots expensive, so Flink with RocksDB can make **incremental** checkpoints that upload only the changed files. The [checkpoints lesson in databases](/databases/recovery/checkpoints) solves the same problem for one machine.

## Joins on streams

A join of two unbounded streams needs a bound, or its state grows forever. A **window join** matches records of both streams in the same window. An **interval join** matches a record with records of the other stream in a time range. An example is a payment within 10 minutes after its order. A **stream-table join** looks up the current value of a key in a table, often a compacted topic. In each case, the watermark tells the job when it can drop buffered records that can no longer match.
