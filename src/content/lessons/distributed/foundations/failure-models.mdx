The [network model](/distributed/foundations/the-network-model-messages-delays-and-partitions) says what can happen to messages. A **failure model** says what a faulty node may do. A protocol tolerates f faults in a model if it stays correct while up to f nodes do anything that the model allows. The models form a ladder, from mild to arbitrary.

| Model | A faulty node may | Typical cause | Nodes for f faults |
|---|---|---|---|
| crash-stop | stop forever; it never sends again | a dead machine | f + 1 with a perfect detector, 2f + 1 without |
| crash-recovery | stop, then restart with only its stable storage | a reboot, a process restart | 2f + 1, and it must persist before it acks |
| omission | drop some messages it should send or receive | a full queue, a bad NIC, a firewall rule | 2f + 1 |
| timing (performance) | answer, but outside the time bound | a GC pause, a slow disk, swapping | 2f + 1 in an asynchronous design |
| Byzantine | do anything: lie, send different values to different nodes | a bug, corrupt memory, an attacker | 3f + 1 |

Each model includes the ones above it. A node that crashes has omitted all later messages, and an omission is an infinitely late answer. A Byzantine node can imitate any of them.

## One protocol, six behaviors

The demo runs one small protocol, a majority quorum write, built for crash faults with f = 1. The client writes x = 1 to three replicas, and it reports "committed" after 2 acks. Later it reads from R1 and R2 and takes the value with the highest version. In every run the network also loses the write to R2. A majority quorum is designed to survive exactly that.

## What each model asks of the protocol

**Crash-stop** is the easiest model. A crashed node is silent, and the quorum continues without it. The demo shows the cost: after one crash, only R0 holds the value, so f = 1 is used up.

**Crash-recovery** adds memory loss. A node that restarts is a correct node again, but it knows only what it wrote to **stable storage** before the crash. So a node must make each promise durable before it sends it. Raft states this rule directly: a server persists its current term, its vote and its log entries before it answers an RPC. The cost is an fsync on the critical path, which [group commit](/databases/recovery/group-commit) makes cheaper.

**Omission** looks harmless in the demo once the client retries. The real danger is elsewhere. A node with omission faults can still send heartbeats, so a failure detector says that it is alive, while it drops real work. A protocol that waits for every live node then waits forever.

**Timing faults** matter because a timeout reports them as failures. The client in the demo said "failed", but the write took effect. In an asynchronous design, the only honest result of a timeout is "unknown". The [timeouts lesson](/distributed/foundations/timeouts-retries-and-idempotency) shows how to make a retry after "unknown" safe.

**Byzantine** faults break every assumption that a reply is honest. Lamport, Shostak and Pease (1982) showed that with oral messages, agreement is possible only if more than two-thirds of the generals are loyal. PBFT and its successors use 3f + 1 replicas. Most systems inside one company assume crash faults and add checksums against corruption, because Byzantine protocols cost more messages and more replicas.

## How many nodes, and why

The counts in the table come from two conditions on a **quorum**, a set of nodes whose answers are enough to proceed. Let n be the number of nodes and q the quorum size.

<Steps>

1. **Liveness.** A quorum must still form when f nodes are silent. So $q \le n - f$.

2. **Safety for crash faults.** Two quorums must share at least one node, so that a read meets the last write. Two sets of size q in n nodes share at least $2q - n$ nodes, so $2q - n \ge 1$.

3. Combine them: $2(n - f) - n \ge 1$, so $n \ge 2f + 1$. With $n = 2f + 1$, the quorum is $q = f + 1$, a majority.

4. **Safety for Byzantine faults.** The shared nodes may include f liars. At least one shared node must be correct, so $2q - n \ge f + 1$.

5. Combine with liveness: $2(n - f) - n \ge f + 1$, so $n \ge 3f + 1$. With $n = 3f + 1$, the quorum is $q = 2f + 1$, and two quorums share $f + 1$ nodes.

</Steps>

Where does f + 1 come from? In a synchronous system with a **perfect failure detector**, every node learns exactly which nodes crashed. A write goes to every live node, so no quorum intersection is needed, and f + 1 copies leave one after f crashes. Primary-backup systems with a reliable lease service work this way. The detector carries the cost: in an asynchronous network, it can be wrong.

## Gray failure and fail-slow

Real faults often fit no row of the table. Huang et al. named **gray failure** (HotOS 2017). Its key feature is **differential observability**: the failure detector sees a healthy node, while applications see failures. A node whose heartbeat thread runs, but whose disk queue is stuck, is the classic case.

**Fail-slow** hardware is a common cause. Gunawi et al. collected 101 reports of hardware that worked, but far too slowly, from 12 institutions (FAST 2018). A disk, a NIC or a CPU that throttles can make a whole cluster slow, because quorums and fan-out wait for the slowest member. Defenses are to measure the latency of real requests, not only heartbeats, and to remove a slow node on purpose.
