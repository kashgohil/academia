In 1994, L Peter Deutsch at Sun Microsystems wrote down seven assumptions that programmers new to distributed systems make. All seven are false. Around 1997, James Gosling added an eighth. Earlier, Bill Joy and others at Sun had already listed the first four. Each fallacy is a model that is too kind, and each one causes a known kind of outage.

## The list, with what goes wrong

1. **The network is reliable.** A request or its reply is lost, and the client retries. If the operation is not idempotent, the retry does it twice. The [retries lesson](/distributed/foundations/timeouts-retries-and-idempotency) shows a double charge.
2. **Latency is zero.** Code that makes 100 calls one after another is fine inside one data center. With a round trip of 0.5 ms (a model input), the calls take 50 ms. Move one service to another continent, with a 70 ms round trip, and the same code takes 7 seconds.
3. **Bandwidth is infinite.** A sender can have only one window of data unacknowledged. On a long, fast link, a small window leaves most of the link idle. The second demo shows this.
4. **The network is secure.** Raft and Paxos trust every message. A process that can reach the cluster port can send a forged vote or a forged log entry. Use mutual TLS between nodes, also inside the data center.
5. **Topology does not change.** A container restarts with a new IP address, but a client keeps the old address from its DNS cache. A route change turns a clean network into a partial partition.
6. **There is one administrator.** Another team changes a firewall rule or a load balancer timeout. Your nodes see this as an omission fault that nobody announced.
7. **Transport cost is zero.** Each message costs CPU for serialization, and traffic between cloud zones or regions is billed per gigabyte. A design that replicates every write to three zones pays for it on every write.
8. **The network is homogeneous.** During a rolling upgrade, old and new versions of a protocol run side by side. Links with different maximum packet sizes (MTU) can silently drop large packets while small ones get through.

The list is from the 1990s, but it describes the cloud well. The fallacies about latency, bandwidth and reliability have the most numbers behind them. The rest of this lesson works through two of them.

## Tail latency at fan-out

A search, a feed or a dashboard often sends one request to many backends and waits for all the answers. The request is then as slow as the slowest backend. Rare slowness on one server becomes common slowness for the user.

## Why the tail grows

Let $F(t)$ be the probability that one backend answers within t. If backends are independent, a request that waits for all n answers is done by t with probability $F(t)^{n}$. A request that waits for k of n is done when at least k backends are done:

$$
P(T_{k:n} \le t) = \sum_{j=k}^{n} \binom{n}{j} F(t)^{j} \left(1 - F(t)\right)^{n-j}
$$

The demo solves this for t at the 50th and 99th percentiles. The model of one backend is a **model input**: a lognormal body with a median of 10 ms, plus a rare stall. Stalls come from garbage collection, a compaction, a slow disk or a queue behind another request.

Dean and Barroso give the same number in "The Tail at Scale" (CACM, 2013). With 100 servers, each with a p99 of 1 second, 63% of user requests take more than 1 second. Their remedies follow from the formula:

- **Wait for k of n.** If the answer is still useful without a few backends, return early. Search engines do this with partial results.
- **Hedged requests.** Send a second copy of a request when the first is slower than, for example, the p95. Use the first answer and cancel the other.
- **Fix the tail at its source.** Make backends shed load early, and schedule background work so that it does not block requests.

## The bandwidth-delay product

A sender may have only a **window** of data unacknowledged. After it sends one window, it must wait for an ack, and the first ack comes back one round trip later. So the throughput is at most the window divided by the round-trip time (RTT). To fill the link, the window must be at least the **bandwidth-delay product**, the number of bytes that are in flight on a full link:

$$
\text{BDP} = \text{bandwidth} \times \text{RTT}
$$

A 10 Gbit/s link with a 100 ms RTT holds 125 MB in flight, which is 119 MiB.

1. Read the default: a 64 KiB window gives 5.24 Mbit/s, and 1 GB takes about 25 minutes.
2. Press **Window = BDP**. The pipe fills, and throughput reaches 10 Gbit/s.
3. Go back to a 64 KiB window and set the RTT to 0.5 ms. The same window now gives about 1 Gbit/s. Short links forgive small windows.
4. Set a 100 Mbit/s link with a 100 ms RTT. The BDP is now 1.25 MB, so a window of about 1.2 MiB fills the link.

The 64 KiB limit is real. The TCP header has a 16-bit window field, so without the **window scale** option (RFC 7323) a window cannot exceed 65,535 bytes. With the largest shift, 14, the window can reach about 1 GiB. Operating systems scale windows by default today, but the buffers must also be large enough: on Linux, the `net.ipv4.tcp_rmem` and `net.ipv4.tcp_wmem` limits.

The same rule applies above TCP. A replication protocol that sends one batch and waits for its ack gets at most one batch per RTT. A follower across a continent then lags behind, however fast the link is. The fix is the same: **pipelining**, which keeps several batches in flight. The raft library of etcd, for example, keeps several append messages in flight per follower, up to its `MaxInflightMsgs` setting.
