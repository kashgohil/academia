A protocol is correct only with respect to a **model**: a precise list of what the network and the nodes may do. A model that is too kind gives a protocol that breaks in production. A model that is too harsh makes some problems impossible to solve. This lesson defines the network side of the model. The [next lesson](/distributed/foundations/failure-models) defines the node side.

## What a message can suffer

Between two nodes, the network is a **link**. On a real link, a message can suffer five things:

1. **Delay.** It arrives later than usual: a queue in a switch, a retransmission, a route change.
2. **Loss.** It never arrives: a full buffer drops it, or a cable fails.
3. **Reordering.** Message 2 arrives before message 1, because the two took different paths or one was retransmitted.
4. **Duplication.** It arrives twice, because a sender or a proxy retransmitted a message that was only slow.
5. **Partition.** A group of nodes cannot reach another group for some time, while each group works inside itself.

Corruption is a sixth. Checksums in Ethernet, TCP and the application turn almost all corruption into loss, so most models leave it out.

## Three timing models

The most important property of a model is what it says about time. There are three classic choices.

| Model | Message delay | Processing speed | What a timeout tells you |
|---|---|---|---|
| synchronous | at most a known bound Δ | known bounds | silence longer than the bound means the node crashed |
| asynchronous | finite, but no bound | no bound | nothing: the node may be slow |
| partially synchronous | bounded, but the bound or its start time is unknown | the same | eventually correct, if the timeout keeps growing |

In the **asynchronous** model, a message "may be delayed without bound". For any timeout that you choose, there is a run where the message arrives after it. The message is not lost, and it does arrive in finite time. But no fixed wait is long enough. Fischer, Lynch and Paterson showed that in this model no deterministic protocol can always reach consensus if even one node may crash. The [FLP lesson](/distributed/consensus/flp-impossibility) proves it.

The **synchronous** model is too kind for real networks. A garbage-collection pause, a full queue or a route change breaks any bound that is short enough to be useful. Protocols that depend on it, such as some leases based on clocks, fail in rare and dangerous ways.

Dwork, Lynch and Stockmeyer (1988) defined the middle ground, **partial synchrony**, in two versions. In one, bounds on delay and speed exist, but nobody knows them. In the other, the bounds are known, but they hold only after an unknown time, the **global stabilization time** (GST). Before GST, the network can act asynchronously.

Paxos and Raft are built for this model. They are always **safe**: they never return a wrong result. They are **live**, which means that they make progress, only after GST.

A protocol for partial synchrony therefore must not depend on time for correctness. It uses timeouts only to decide when to try again. If a timeout fires too early, the protocol does extra work but stays correct.

## From lossy links to reliable ones

A **fair-loss link** may lose any message, but if a node sends a message again and again, a copy eventually arrives. Retransmission plus duplicate removal turns it into a reliable link. The receiver keeps the highest sequence number it delivered from each sender:

```go
// Receiver side of a reliable link over a lossy, duplicating network.
type Link struct {
	delivered map[NodeID]uint64 // highest sequence number delivered, per sender
}

func (l *Link) OnMessage(from NodeID, seq uint64, payload []byte, ack func(uint64), deliver func([]byte)) {
	ack(seq) // always ack, even a duplicate: the first ack may have been lost
	if seq <= l.delivered[from] {
		return // a copy we already delivered
	}
	if seq == l.delivered[from]+1 {
		l.delivered[from] = seq
		deliver(payload)
	}
	// seq > next: a gap. Drop it; the sender retransmits in order (go-back-N).
}
```

The sender retransmits each message until it gets an ack. TCP does this inside one connection. Across connections and across process restarts, the application must do it again, with sequence numbers that survive a crash. Kafka producers, for example, attach a producer id and a sequence number to each batch for this reason.

## Partitions are real

A **network partition** splits the nodes into groups that cannot talk to each other. It is not a rare theoretical case. Alquraan et al. studied 136 failures caused by partitions in 25 widely used systems (OSDI 2018). About 80% of them had a catastrophic effect, and data loss was the most common one, at 27%. Most failures were silent: the system gave no error.

Two details from that study matter for design. Isolating a single node was enough to trigger 88% of the failures. And 29% of the failures came from **partial partitions**, where A can reach B and B can reach C, but A cannot reach C. A simple model of "two clean halves" misses these.

## The two generals

Two armies camp on two hills, with the enemy in the valley between. They win only if both attack at the same time. They can communicate only by messengers, and the enemy can capture any messenger. Akkoyunlu, Ekanadham and Huber described the problem in 1975, and Jim Gray stated it as a problem of two generals in 1978.

## Why no number of messengers is enough

The demo checks every threshold rule. The argument behind it covers every protocol. Compare the run where all k messengers arrive with the run where messenger k is captured. Only the receiver of messenger k sees a difference. The sender has the same view in both runs, so it decides the same way.

Repeat the step down to the run where nothing arrives. Each step changes the view of exactly one general. If the two always agree, the decision never changes along the chain. In the run where nothing arrives, B never learned the plan and cannot attack. So in the run where everything arrives, nobody attacks either.

Each messenger adds one level of knowledge. **Common knowledge**, where both know, both know that both know, and so on without end, needs infinitely many messages. Real systems give up certainty instead. They make the decision durable on a quorum, and they let a participant that is unsure ask again later. [Two-phase commit](/distributed/transactions/two-phase-commit) does exactly this, and it can block while it waits.
