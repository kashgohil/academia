A timeout is the only failure detector that a client has. When it fires, the client knows only that no answer came in time. The request may be lost, the reply may be lost, or the server may still be working. The [partial failure demo](/distributed/foundations/why-distribute) showed that these cases look the same. This lesson is about what a client should do next, so that the system stays correct and stays up.

## Choosing a timeout

A timeout trades two errors. If it is too short, it fires on requests that would have succeeded: a **false timeout**. If it is too long, the client waits a long time for a server that is really dead: **slow detection**. Choose it from the measured latency distribution of the call, not from a guess.

Take the backend model from the [fallacies lesson](/distributed/foundations/the-eight-fallacies): a median of 10 ms and a stall of 1 second on 1% of calls. A 50 ms timeout fires on about 1% of calls, and all of them are real stalls. A 20 ms timeout fires on 2.0% of calls. Half of those are normal answers that were only a little slow. A retry after a false timeout doubles the work for that request.

Real systems compute the timeout from what they observe. TCP keeps a smoothed round-trip time and its variation, and sets the retransmission timeout to $\text{SRTT} + 4 \cdot \text{RTTVAR}$. RFC 6298 rounds it up to at least 1 second, but Linux uses a minimum of 200 ms (`TCP_RTO_MIN`). For an RPC, a common rule is a little above the p99 or p99.9 of the latency.

Then send a **deadline** with the request. A server can then skip a request whose caller has already given up. In gRPC, a client sets a deadline on a call, and gRPC sends it to the server. By default, gRPC sets no deadline, so set one on every call.

## Retries can make an outage worse

A retry adds load at the moment the server is least able to take it. Retries also multiply across layers. If each of 3 services in a call chain makes 3 attempts, the bottom service can see 27 attempts for one user request.

## Backoff and jitter

**Exponential backoff** waits longer after each failure, so that the total retry rate falls as failures continue. **Jitter** adds randomness, so that clients that failed together do not retry together. Marc Brooker compared the variants on the AWS Architecture Blog ("Exponential Backoff And Jitter", 2015). In **full jitter**, the wait is uniform between 0 and the exponential value:

```go
// Full jitter: sleep a random time in [0, min(cap, base * 2^attempt)).
func backoff(attempt int, base, cap time.Duration, rnd *rand.Rand) time.Duration {
	d := base << attempt // base * 2^attempt
	if d <= 0 || d > cap {
		d = cap // also guards against overflow of the shift
	}
	return time.Duration(rnd.Int63n(int64(d)))
}
```

His conclusion was that "equal jitter", which keeps half of the wait fixed, is the loser. Full jitter does less work than "decorrelated jitter", but it takes slightly more time. Plain exponential backoff without jitter does poorly, as the demo shows.

Jitter gives a bound that you can state. Retry number a waits a uniform time over a span $c_a = \min(\text{cap}, \text{base} \cdot 2^{a-1})$. So the chance that it lands in a given window of w ms is at most $\min(1, w / c_a)$, whatever happened before. For R requests, the expected number of retries in any window is at most:

$$
R \sum_{a} \min\left(1, \frac{w}{c_a}\right)
$$

With 100 requests, a base of 100 ms, a cap of 1 second and 5 retries, the bound is 19.75 retries per 10 ms window. The tests check the bound over 300 random runs. Without jitter, all 100 retries of the same number land in one window.

## Retry budgets and metastable failure

The outage scenario shows a worse problem. After the server restarts, its queue fills with retries. Each request waits longer than the client timeout, so the client abandons it, and the server then does the work for nobody. In the demo, more than 80% of the server work after the outage is wasted, and goodput stays at 0. The trigger is gone, but the system stays down. Bronson et al. call this a **metastable failure** (HotOS 2021).

Backoff alone does not fix this, because new requests keep coming. What fixes it is a limit on the share of traffic that is retries. Three real versions:

- **gRPC retry throttling** keeps a token count per server, up to `maxTokens`. A failure costs 1 token, and a success adds `tokenRatio`. Retries stop while the count is at most half of `maxTokens`. The demo uses 10 and 0.1, the example values of the gRPC design.
- **Google SRE** ("Handling Overload") gives up after 3 attempts per request, and a client retries only while retries are below 10% of its requests.
- **AWS SDKs** in standard mode make at most 3 attempts, use full jitter, and draw each retry from a token bucket called the retry quota.

A budget has a cost. In the burst scenario with the budget on, most requests fail fast instead of succeeding late. That is the trade: under overload, a fast failure is better than a slow collapse. Also keep the server queue shorter than the client timeout, so that the server never works on requests that nobody waits for.

## Idempotency: making the retry safe

A retry is safe only if doing the operation twice has the same effect as doing it once. Such an operation is **idempotent**. "Set x to 5" is idempotent. "Add 10 to the balance" and "charge the card $10" are not.

## How an idempotency key works

The client makes a unique key for each logical operation, such as a random UUID, and sends it with every attempt. The server stores the key and the result in the same transaction as the effect:

```sql
BEGIN;
INSERT INTO idempotency_keys (key, status, created_at) VALUES ($1, 'running', now()); -- fails if the key exists
INSERT INTO charges (id, account, amount) VALUES ($2, $3, 1000);
UPDATE idempotency_keys SET status = 'done', response = $4 WHERE key = $1;
COMMIT;
```

If the key already exists, the server returns the stored response and does nothing else. The search in the demo checks all 125 combinations of fates for 3 attempts. Without a key, 87 of them charge twice. With a key, none do. If keys expire too soon, 28 do.

Stripe uses this design. A client sends an `Idempotency-Key` header with a POST. Stripe compares the parameters of a repeat with the original and returns an error if they differ. Keys can be removed once they are at least 24 hours old. The IETF draft "The Idempotency-Key HTTP Header Field" suggests two status codes. A repeat gets 409 Conflict while the first request still runs, and a reused key with a different body gets 422.

Two rules follow. The key must live longer than the longest retry window, or a late retry looks new. And the key record and the effect must commit together, or a crash between them breaks the guarantee. This pattern, **at-least-once delivery plus deduplication**, is how most systems get an effect that happens exactly once.
