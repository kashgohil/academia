The simplest hash partitioning is `node = hash(key) mod N`. It spreads keys evenly, and a lookup is one division. It breaks when $N$ changes. Going from 10 to 11 nodes changes the answer for almost every key, because $h \bmod 10$ and $h \bmod 11$ agree only by chance. In the next lesson's demo, 91% of the keys move. Each moved key is data that must cross the network, or a cache entry that is lost.

**Consistent hashing** fixes this. Karger, Lehman, Leighton, Panigrahy, Levine and Lewin described it at STOC 1997, for web caches. When a node joins or leaves, only the keys of that node move. With $K$ keys and $N$ nodes, that is about $K/N$ keys.

## The ring

Take the 32-bit hash space and bend it into a circle, so that $2^{32} - 1$ is next to 0. Hash each server name to a point on the circle. Hash each key to a point too. A key belongs to the first server point that you reach when you walk clockwise from the key. A lookup is a binary search in the sorted list of server points.

Now add a server. Its point lands inside one arc. The keys between the previous point and the new point change owner, and they all go to the new server. No other key changes owner. Removing a server is the reverse: its keys go to the next server clockwise.

## Why few points give uneven load

With one point per server, the arcs are the gaps between $N$ random points on a circle. These gaps are far from equal. The expected length of the longest gap is $H(N)/N$, where $H(N) = 1 + 1/2 + \dots + 1/N$. So the busiest server owns $H(N) \approx \ln N + 0.58$ times its fair share. For 10 servers, that is 2.93 times. The demo below measures 2.83 over 60 random rings.

A second problem is how the load moves. When a server leaves, all of its keys go to one neighbour. That neighbour now has double load, while the rest of the cluster does not help.

## Virtual nodes

The fix is to give each server $v$ points instead of one. Each point is a **virtual node**. Server A puts points at `hash("A#0")`, `hash("A#1")`, and so on. A server now owns $v$ short arcs, scattered over the ring, and the sum of many random arcs is close to its mean.

<Steps>

1. There are $Nv$ points in all, so they cut the ring into $Nv$ arcs. The arc lengths are exchangeable: any set of $v$ of them has the same distribution.

2. The total of $v$ arcs out of $Nv$ follows a Beta distribution, $\text{Beta}(v, Nv - v)$. Its mean is $1/N$, the fair share.

3. The variance of $\text{Beta}(a, b)$ is $ab/((a+b)^2(a+b+1))$. Divide by the squared mean and simplify:

$$
\frac{\sigma}{\mu} = \sqrt{\frac{N-1}{Nv+1}} \approx \frac{1}{\sqrt{v}}
$$

4. So the spread of the load falls as the square root of $v$. To halve the spread, you need four times as many virtual nodes.

</Steps>

Virtual nodes also fix the second problem. A leaving server has $v$ arcs, and each arc goes to a different neighbour. So its load spreads over many servers. A new server takes a little from many servers, not a lot from one.

Virtual nodes have costs. The ring has $Nv$ points, so it needs more memory, and the binary search takes $\log_2(Nv)$ steps. With replication, the next $r$ distinct servers clockwise hold the copies, and the walk must skip points of servers that it has already picked. Repairs and streaming also work per arc, so more arcs mean more small operations.

## Weights

Servers are often not equal. A server with twice the disk should own twice the keys. On a ring, you give it twice the virtual nodes: $v_i = v \cdot w_i$. The spread formula still holds for each server, with its own count of points.

```rust
/// A consistent hash ring with weighted virtual nodes.
pub struct Ring { points: Vec<(u32, usize)> } // (position, server), sorted by position

impl Ring {
    pub fn new(servers: &[(&str, f64)], vnodes: usize) -> Ring {
        let mut points = Vec::new();
        for (i, (name, weight)) in servers.iter().enumerate() {
            let v = ((vnodes as f64) * weight).round().max(1.0) as usize;
            for j in 0..v {
                points.push((murmur3(format!("{name}#{j}").as_bytes(), 0), i));
            }
        }
        points.sort_unstable();
        Ring { points }
    }
    /// The first point at or after the key's hash, wrapping to the start.
    pub fn owner(&self, key: &[u8]) -> usize {
        let h = murmur3(key, 0);
        let i = self.points.partition_point(|&(p, _)| p < h);
        self.points[if i == self.points.len() { 0 } else { i }].1
    }
}
```

## In real systems

Amazon's Dynamo paper (DeCandia et al., SOSP 2007) used a ring with virtual nodes. It then compared three strategies. In the first, each node has $T$ random tokens. In the third, the ring is cut into $Q$ equal partitions and each of $S$ nodes takes $Q/S$ of them. The paper found that the third strategy balances load best. The [rebalancing](/distributed/partitioning/rebalancing) lesson returns to this idea of fixed partitions.

Cassandra uses a ring of 64-bit tokens with `Murmur3Partitioner`. Before version 4.0, the shipped `cassandra.yaml` set `num_tokens: 256`. In 4.0 it sets `num_tokens: 16`, together with `allocate_tokens_for_local_replication_factor: 3`. With 16 tokens, random placement would give a spread near 25%. So the allocator places new tokens where they even out the load, instead of at random.

Cassandra's documentation gives the reasons for fewer tokens. With more tokens, a node shares data with more peers, which lowers availability, and repair has more ranges to cover.

Riak also uses a ring, on 160-bit SHA-1 hashes. But it cuts the ring into a fixed number of equal partitions, 64 by default (`ring_size`), and assigns whole partitions to nodes.
