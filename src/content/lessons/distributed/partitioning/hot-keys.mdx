Partitioning spreads keys over nodes. It cannot spread one key. If one key gets a large share of all requests, the partition that holds it runs at its limit while the others idle. This is the **hot key** problem, also called the **celebrity problem**. Examples are one account with millions of followers, or one chat channel during a live event.

Adding nodes does not help. The hot key still lives on one partition, so the busiest partition stays as busy as before. The cluster has spare capacity, but that capacity cannot reach the hot key.

## Zipf workloads

Real popularity is very uneven. A common model is the **Zipf distribution**: the key of rank $r$ gets a share proportional to $1/r^{\theta}$. With $K$ keys, the share of rank $r$ is:

$$
p_r = \frac{r^{-\theta}}{H(K, \theta)}, \qquad H(K, \theta) = \sum_{i=1}^{K} i^{-\theta}
$$

With $\theta = 0$ every key is equally popular. As $\theta$ grows, the head of the list takes more of the traffic. The YCSB benchmark uses $\theta = 0.99$ by default, with a generator from Gray et al. (SIGMOD 1994). For 10,000 keys and $\theta = 0.99$, the hottest key gets 9.8% of all requests, and the top 10 keys get 28.9%.

## Finding hot keys

To fix a hot key, you must first know which key is hot, and you must know it fast. Counting every key exactly needs memory for every key. Two small summaries do the job with fixed memory.

A **count-min sketch** (Cormode and Muthukrishnan, 2005) is a table of $d$ rows with $w$ counters each. Each row has its own hash function. To add a key, increment one counter in each row. To estimate a key, read its $d$ counters and take the smallest.

<Steps>

1. Every counter of a key holds that key's count plus the counts of other keys that collide with it. So each counter is at least the true count, and so is the smallest. The sketch never undercounts.

2. In one row, the expected excess is at most $N/w$, where $N$ is the total count. By Markov's inequality, the excess passes $eN/w$ with probability at most $1/e$.

3. The $d$ rows use independent hashes. The minimum is too high only if all $d$ rows are too high, with probability at most $e^{-d}$.

4. So with $w = \lceil e/\varepsilon \rceil$ and $d = \lceil \ln(1/\delta) \rceil$, the estimate exceeds the true count by at most $\varepsilon N$ with probability $1 - \delta$.

</Steps>

For $\varepsilon = 0.1\%$ and $\delta = 1\%$, this gives $w = 2{,}719$ and $d = 5$: about 54 KB of 4-byte counters, whatever the number of keys. To find the top keys, keep a small list of candidates beside the sketch. After each add, a key joins the list if its estimate beats the smallest entry.

**Space-Saving** (Metwally, Agrawal and El Abbadi, ICDT 2005) finds the top $k$ directly, with $k$ counters. A new key, when all counters are taken, replaces the key with the smallest count and inherits that count plus one. A counter never falls below the true count of its key, and it records how much it may be over.

In production, each node or proxy keeps such a summary over a short window, such as 10 seconds. It reports keys whose share passes a threshold. The system can then act on those keys only.

**Split the key.** Add a suffix, so that `post:42` becomes `post:42#0` to `post:42#7`. A write goes to a random sub-key, and the sub-keys land on different shards. A read must read all of them and merge.

DynamoDB's documentation describes this as write sharding. Its example adds a random number from 1 to 200 to a date key, and a read of one day must query all 200 suffixes. Use it for keys that are hot for writes, such as counters and append-only logs. Some systems split only keys that the detector reports, and keep a small table of which keys are split.

**Cache.** Put the hot keys in a cache in front of the shards: in the application, in a proxy, or in a cache tier. A read that hits the cache never reaches the shard. The cost is staleness: the cache must expire entries or be told when a key changes. A cache tier has its own hot keys, too. Facebook's memcache paper (NSDI 2013) replicates some keys inside a pool when one server cannot handle their request rate.

**Coalesce requests.** When many reads of one key arrive at the same time, send one read to the shard and give its answer to all of them. Let reads arrive at rate $\lambda$, and let a read be in flight for $T$. Each backend read covers itself and the $\lambda T$ reads that arrive while it waits. So the shard sees:

$$
\lambda_{\text{shard}} = \frac{\lambda}{1 + \lambda T}
$$

A hot key gains the most, because $\lambda T$ is large for it. Discord's data services, written in Rust, sit between the API and ScyllaDB and coalesce requests. They route requests by channel ID with consistent hashing, so that the requests for one channel meet in one service instance. Facebook's memcache uses **leases** for a related problem, the thundering herd. After a miss, a server gives a lease token for a key at most once every 10 seconds. Only the client with the token fetches the value from the database.

```go
// Coalesce concurrent reads of the same key: one backend read, many waiters.
type call struct { wg sync.WaitGroup; val []byte; err error }

type Group struct { mu sync.Mutex; m map[string]*call }

func (g *Group) Do(key string, fetch func() ([]byte, error)) ([]byte, error) {
	g.mu.Lock()
	if c, ok := g.m[key]; ok { // a read is in flight: wait for its answer
		g.mu.Unlock()
		c.wg.Wait()
		return c.val, c.err
	}
	c := &call{}
	c.wg.Add(1)
	g.m[key] = c
	g.mu.Unlock()

	c.val, c.err = fetch() // the only read that reaches the shard
	c.wg.Done()

	g.mu.Lock()
	delete(g.m, key)
	g.mu.Unlock()
	return c.val, c.err
}
```

**Replicate the hot shard.** Give the hot partition more read replicas, and spread the reads over them. Writes do not get cheaper: every write must reach every replica. With follower reads, the reads may also be stale, as the [replication lag](/distributed/replication/replication-lag-and-read-your-writes) lesson explains.

**Let the store adapt.** DynamoDB has **adaptive capacity**. It increases the throughput of partitions that receive more traffic, within the table's capacity. Each partition is designed for at most 3,000 read units and 1,000 write units per second. 

When one item stays hot, DynamoDB can "isolate frequently accessed items": it rebalances so that the hot item is alone on its partition. That partition can then serve the full per-partition limit for that one item, but no more. A single item that needs more than one partition's limit still needs a fix in the application.

| Mitigation | Helps | Costs |
|---|---|---|
| split the key | write-hot keys | every read fans out to all sub-keys |
| cache | read-hot keys | staleness, invalidation, the cache's own hot spots |
| coalesce | read bursts on one key | a short wait; all waiters share one answer or one error |
| replicate the shard | read-hot partitions | every write goes to all replicas; follower reads may be stale |
| adaptive capacity | uneven partitions | cannot exceed one partition's limit for one item |
