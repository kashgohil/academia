A partitioned table answers one question fast: "give me the row with this key". The partition key leads straight to one partition. Real applications ask other questions too, such as "all red cars" or "all orders of customer 42". A **secondary index** answers them. On one machine, a secondary index is a second B-tree, as the [secondary and covering indexes](/databases/indexes/secondary-and-covering-indexes) lesson shows. On a partitioned table, the index must be partitioned too, and there are two ways to do it.

## Local indexes

A **local index**, also called a **document-partitioned index**, lives inside each partition. Each partition indexes only its own rows. A write touches one partition: the row and its index entry change together, in one local transaction.

A query by the indexed column cannot know which partitions hold matches. So the router sends the query to every partition and merges the answers. This is **scatter/gather**. Its cost grows with the number of partitions, not with the number of matches.

## Global indexes

A **global index**, also called a **term-partitioned index**, is partitioned by the indexed value, not by the row key. All entries for `color = red` live in one index partition, wherever the rows live. A query asks that one partition. If the index entries hold only row keys, the query then fetches the rows from their partitions. If the entries also hold the needed columns, the index is **covering**, and one read is enough.

The cost moves to the writes. A new row changes its own partition and the index partition of its value. Changing a car from red to blue changes three places: the row, the red entry and the blue entry. They can be on three different partitions.

| | Local index | Global index |
|---|---|---|
| Write | 1 partition, local transaction | row partition + 1 or 2 index partitions |
| Query by index | all partitions (scatter/gather) | 1 index partition, + row fetches unless covering |
| Consistency | same as the row | needs a distributed transaction, or lags |
| Examples | Cassandra secondary indexes and SAI, DynamoDB LSIs, Elasticsearch shards, MongoDB | DynamoDB GSIs, CockroachDB secondary indexes |

## How fresh is a global index?

A global index entry and its row are in different partitions. To change both atomically, the database needs a distributed transaction, such as [two-phase commit](/distributed/transactions/two-phase-commit). Many systems avoid that cost. They write the row, acknowledge the client, and update the index later, from a queue or a change stream.

DynamoDB does this. Its documentation says that global secondary indexes are "updated asynchronously, using an eventually consistent model", and they support only eventually consistent reads. Its local secondary indexes, which live with the rows of one partition key, support strongly consistent reads too. A GSI also pushes back on the table: if a GSI has too little write capacity, writes to the table are throttled.

CockroachDB takes the other side. A secondary index is a separate span of keys, often in other ranges, and the index entries change in the same transaction as the row. So the index is never stale, and each write pays for a distributed commit.

This is the same failure of read-your-writes as with an asynchronous follower, and the same cures apply. The [replication lag](/distributed/replication/replication-lag-and-read-your-writes) lesson covers them.

## Scatter/gather and the tail

A local index looks cheap: each partition does a small lookup. But the query must wait for every partition, so its latency is the latency of the slowest one. Dean and Barroso made this point in "The Tail at Scale" (CACM 2013). Take a server that answers in 10 ms, but in one second at the 99th percentile. A request that needs 100 such servers takes more than one second 63% of the time.

The math is short. Let $F(t)$ be the probability that one partition answers within $t$. The query is done when all $P$ partitions have answered, so:

$$
P(\text{query} \le t) = F(t)^{P}, \qquad P(\text{some partition is slow}) = 1 - (1 - q)^{P}
$$

With $q = 1\%$ and $P = 100$, the second formula gives 63.4%. The demo models each partition as 5 ms on average, or 1,000 ms with probability $q$. Both numbers are model inputs.

<PartitioningTailDemo />

1. Keep 1% and 100 partitions. The median query takes 1,000 ms, because most queries meet at least one slow partition. One partition alone has a median of 3.5 ms.
2. Move **Partitions asked** down to 10. Now only 9.6% of the queries wait for a slow partition, and the median falls to about 14 ms.
3. Move **Slow answer chance** down to 0.1%. The median at 100 partitions drops back to tens of milliseconds, but the 99th percentile still hits the slow time.

There are several ways to fight the tail.

- **Ask fewer partitions.** Use a global index, or put the partition key in the query.
- **Send a hedged request.** If a partition does not answer within its 95th percentile, send the same request to a replica, and use the first answer.
- **Return partial results** when the query allows it, as a search engine can.

Elasticsearch runs a search as "query then fetch". First each shard finds its own top hits and returns their IDs and sort values. Then the coordinating node merges the lists and fetches only the documents of the requested page.
