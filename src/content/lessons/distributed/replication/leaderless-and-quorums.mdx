A leader is a single point that every write must pass. If it fails, writes stop until failover ends. **Leaderless replication** removes the leader: a client sends each write to several replicas at once, and any of them can accept it. Amazon described this design in "Dynamo: Amazon's Highly Available Key-value Store" (DeCandia et al., SOSP 2007). Cassandra and Riak follow it.

Each key lives on $N$ replicas. A node that handles a request for a client is the **coordinator**. For a write, it sends the new value to all $N$ replicas and waits for $W$ acknowledgements. For a read, it asks the replicas and waits for $R$ answers. Each value carries a version, here a timestamp, and the read returns the newest of the $R$ answers.

## Why W + R > N works

A write that succeeded is on at least $W$ replicas. A read hears from $R$ replicas. If $W + R > N$, the two sets cannot be disjoint: there are only $N$ replicas, so at least one replica is in both sets. That replica has the write, and the read returns the newest version that it sees. The Dynamo paper calls this "a quorum-like system", and its common configuration is $(N, R, W) = (3, 2, 2)$.

$$
|S_W \cap S_R| \ge W + R - N \ge 1
$$

The choice of $W$ and $R$ moves cost between reads and writes. $W = N$ makes reads cheap ($R = 1$), but one dead replica stops all writes. $R = N$ does the reverse. Majorities on both sides ($W = R = \lfloor N/2 \rfloor + 1$) tolerate the loss of a minority for both.

## Sloppy quorums and hinted handoff

The keys of a Dynamo ring have a **preference list**: the $N$ home replicas, followed by more nodes. In a **sloppy quorum**, the coordinator sends a write to the first $N$ healthy nodes in that list. If a home replica is down, a node further along the list takes the write in its place. The Dynamo paper says that this replica "will have a hint in its metadata that suggests which node was the intended recipient". When the home replica recovers, the stand-in sends it the write and deletes its copy. This is **hinted handoff**.

A sloppy quorum keeps writes available during failures. But the $W$ acks can come from stand-ins, and a later read can go to the recovered home replicas. Then the two sets do not overlap, and $W + R > N$ promises nothing until handoff ends. The overlap also fails the other way: when home replicas are down at the read, stand-ins that never saw the key answer it.

In the playground, set the read delay to 45 ms, above the handoff period of 40 ms (a model input). The share of fresh reads rises from 94.2% to 98.2%, but not to 100%. The rest are reads that stand-ins answered.

Cassandra also stores hints. The coordinator writes a hint for a replica that is down, and keeps hints for `max_hint_window`, 3 hours by default. But Cassandra does not count a hint toward the consistency level, except for the level `ANY`. So a `QUORUM` write in Cassandra needs real acks from a majority of the home replicas.

## Read repair

A read sees the versions of $R$ replicas. If some answers are older than others, the coordinator knows that those replicas are stale. **Read repair** writes the newest version back to them. The Dynamo paper describes this step.

Cassandra 4.0 removed the old background options `read_repair_chance` and `dclocal_read_repair_chance`. Now, when the answers of a read above `ONE` disagree, Cassandra repairs the replicas in the read before it returns. This is the table option `read_repair = 'BLOCKING'`, the default.

Read repair only fixes data that someone reads. A key that nobody reads stays stale on a replica for as long as it exists. The next lesson covers anti-entropy, which repairs everything in the background.

## Quorums are not linearizable

$W + R > N$ promises that a read after a finished write sees it. It does not promise anything for a read during a write. A register is **linearizable** when every operation seems to take effect at one moment between its start and its end. See [linearizability](/distributed/consistency/linearizability).

1. With the toggle off, A returns x = 1 at about 24 ms, and B returns x = 0 later. Both reads met their quorum. The write had not finished, so the quorum rule did not apply.
2. Turn on blocking read repair. A sees that r1 is stale and writes x = 1 to it before it returns. B then finds x = 1 on r1.

A read that writes back before it returns is the read of the ABD algorithm (Attiya, Bar-Noy and Dolev, 1995). With majority quorums and a single writer, it gives a linearizable register. Each read pays a second round trip, unless all the answers it gets already agree. With several writers, each write must first read the highest timestamp from a majority. Last-write-wins on clocks skips that step, so concurrent writes with skewed timestamps can make a later write lose.

## Tail latency

A coordinator waits for the $k$-th fastest of $N$ answers, where $k$ is $W$ or $R$. So a small $k$ hides slow replicas, and $k = N$ waits for the slowest replica every time.

<ReplicationQuorumLatencyDemo />

The model inputs: each replica answers in 0.5 to 3 ms, but with chance 5% it takes 20 to 100 ms. The network adds 0.5 to 1.5 ms each way.

1. With $N = 3$, the p99 latency is about 5 ms for $k = 1$ and $k = 2$. It jumps to about 97 ms for $k = 3$. At $k = 3$, the chance that at least one replica is slow is $1 - 0.95^{3} \approx 14.3\%$, far above 1%.
2. Select $N = 5$. The p99 is about 5 ms for $k = 3$, about 55 ms for $k = 4$, and about 98 ms for $k = 5$.
3. Set the slow chance to 0. All the lines drop to a few milliseconds. Quorums with $k < N$ are a cheap defence against slow replicas.

The Dynamo paper states its goals in the 99.9th percentile, for example "99.9% of the read and write requests execute within 300ms". Bailis et al. measured how fresh partial quorums are in practice in "Probabilistically Bounded Staleness for Practical Partial Quorums" (VLDB 2012).

```go
// Coordinator: send to all replicas, return after k answers.
func (c *Coord) read(ctx context.Context, key string, k int) (Versioned, error) {
	ch := make(chan Versioned, len(c.replicas))
	for _, r := range c.replicas {
		go func(r Replica) { if v, err := r.Get(ctx, key); err == nil { ch <- v } }(r)
	}
	var best Versioned
	for got := 0; got < k; got++ {
		select {
		case v := <-ch:
			if v.TS > best.TS { best = v }
		case <-ctx.Done():
			return Versioned{}, ctx.Err() // fewer than k answers in time
		}
	}
	return best, nil
}
```
