[Two-phase commit](/distributed/transactions/two-phase-commit) exists because a participant can say no at the last moment. A deadlock, a crash or a lock timeout can abort its part of the transaction. So the participants must agree on the outcome after they execute, while they hold their locks.

Calvin asks a different question. What if the participants could never disagree? Then there would be nothing to agree on at the end. Thomson, Diamond, Weng, Ren, Shao and Abadi built this idea into "Calvin: Fast Distributed Transactions for Partitioned Database Systems" (SIGMOD 2012). It follows Thomson and Abadi's "The Case for Determinism in Database Systems" (VLDB 2010).

## Order first, then execute

Calvin splits the work into two layers.

1. **Sequencing.** Clients send transactions to a sequencer. The sequencer collects them into batches, one batch per **epoch** of 10 ms. It replicates each batch, then sends it to every partition. The batches form one global input log.
2. **Deterministic execution.** Each partition runs the transactions in the order of the log. A transaction's result depends only on the database state and the log, never on thread timing or on which message came first.

Agreement happens before execution, on the input, with a replication protocol such as Paxos. After that, every replica of a partition runs the same transactions in the same order from the same state. So all replicas reach the same state without talking to each other.

## Deterministic locking

Calvin still uses locks, so that it can run many transactions at once. But its lock manager grants locks in the order of the log. A transaction asks for all its locks at once, before it runs. If T1 comes before T2 in the log and both want x, T1 gets x first on every replica.

Two consequences follow. There are no deadlocks, because every transaction takes its locks in one global order. And no transaction can abort for a reason that differs between replicas. A transaction can still abort for a deterministic reason, such as a failed check on the data. Every replica then makes the same decision.

## A transaction across partitions

Each partition runs the batch, but a transaction may read data on several partitions. Calvin handles this with one round of messages:

1. Every participant partition takes its locks, in log order.
2. It reads its local rows and sends the values to the other active participants.
3. When a participant has every remote read, it runs the transaction's logic and writes its own rows.
4. It releases its locks.

No participant can vote no. They all run the same logic on the same values, so they all reach the same decision. There is no prepare, no vote and no commit round.

<DistTxnCalvinVs2pcDemo />

1. With 3 partitions, a one-way latency of 1 ms and a 10 ms epoch, 2PC answers the client in 9 ms. Calvin needs 11 ms, because a request waits half an epoch on average for its batch.
2. Read the lock times. 2PC holds the locks for 8 ms: across the reads, the prepare write, the vote, the commit write and the COMMIT message. Calvin holds them for 1 ms, the exchange of reads.
3. Move the latency to 10 ms, as between regions. 2PC takes 90 ms and Calvin 65 ms. The epoch wait is now small next to the network delays.
4. Set 1 partition. Now 2PC has nothing to agree on, and it holds its locks for 4 ms. Calvin still waits for the epoch.

The lock time matters most. A contended row is unavailable while it is locked. Under 2PC a hot row is locked across network round trips and log writes. Under Calvin it is locked only while the data moves between partitions. The paper reports nearly half a million TPC-C transactions per second on a 100-node cluster, with a workload of 100% New Order transactions.

## The cost: read and write sets in advance

A deterministic lock manager must know a transaction's locks before the transaction runs. So Calvin needs each transaction's **read set** and **write set** in advance. A stored procedure such as "move 10 from account 7 to account 9" declares them easily.

A **dependent transaction** is harder. Its write set depends on what it reads: "give a raise to every employee whose manager is Ann". Calvin uses **optimistic lock location prediction** (OLLP). First it runs a cheap, unreplicated, read-only **reconnaissance query** to find the rows. Then it submits the real transaction with those rows as its declared sets.

At execution, the transaction checks that the sets are still correct. If the data changed in between, it aborts deterministically and goes back to the sequencer.

```ts
async function submitDependent(db: Calvin, managerId: string) {
  for (;;) {
    // 1. Reconnaissance: a plain snapshot read, outside the log.
    const ids = await db.snapshotQuery((s) => s.employees.filter((e) => e.manager === managerId).map((e) => e.id));
    // 2. The real transaction declares what reconnaissance found.
    const res = await db.submit({
      reads: [`idx:manager:${managerId}`, ...ids], writes: ids,
      run: (s) => {
        const now = s.index("manager", managerId);
        if (!sameSet(now, ids)) return { abort: "stale prediction" }; // the same decision on every replica
        for (const id of ids) s.update(id, (e) => ({ ...e, salary: e.salary * 1.05 }));
        return { ok: true };
      },
    });
    if (res.ok) return res;
  }
}
```

Other costs follow from the design. Every transaction waits for an epoch. Interactive transactions, where the client reads, thinks and then writes, do not fit. They must become one request with all their logic. And the sequencing layer is a component on the critical path of every write.

## Calvin in practice

Calvin's paper uses ZooKeeper to replicate the input log in its implementation. The design allows asynchronous replication or Paxos-based synchronous replication. Because execution is deterministic, a replica can rebuild its state from a checkpoint and the input log, as a [Raft](/distributed/consensus/raft-log-replication) state machine does.

Fauna, a commercial database, described its transaction protocol as "inspired by Calvin" in a 2018 company blog post. Like Calvin, it decides the serial order before it does any writes. Fauna shut down its service on 30 May 2025. The core idea remains useful. Agree on the input, make execution deterministic, and replication needs no commit protocol at all.
