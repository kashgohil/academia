**HTTP** is the request-response protocol of the web. A client sends a request: a method, a path and header fields. A server sends back a response: a status code, header fields and usually a body. HTTP/1.1 first appeared in RFC 2068 (1997) and RFC 2616 (1999). Today three RFCs from June 2022 define it. RFC 9110 gives the semantics of every HTTP version, RFC 9111 caching, and RFC 9112 the HTTP/1.1 message format.

HTTP/1.1 sends **text** over one TCP connection. Each line ends with CR LF, and an empty line ends the head. This is a GET request as a browser sends it, and the head of a response:

```text
GET /app.js HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 ... Chrome/130.0.0.0 Safari/537.36
Accept: */*
Accept-Encoding: gzip, deflate, br, zstd
Accept-Language: en-US,en;q=0.9
Referer: https://www.example.com/
Cookie: session=8f2c1a9e4b7d6c3a; theme=dark

HTTP/1.1 200 OK
Date: Sat, 07 Nov 2026 12:00:00 GMT
Server: nginx
Content-Type: image/jpeg
Content-Length: 80000
Cache-Control: max-age=86400
ETag: "5d8c72a1-80000"
```

The request is 331 bytes, and the response head is 174 bytes. A browser repeats most of these header fields on every request to the same site. HTTP/2 compresses them; HTTP/1.1 cannot.

## Connections and the page-load waterfall

HTTP/1.0 opened a new TCP connection for each request. HTTP/1.1 made **persistent connections** the default: the connection stays open for the next request unless a side sends `Connection: close`. A new connection is expensive. It costs one RTT for the TCP handshake, one more for TLS 1.3, and it starts in **slow start** with a small congestion window.

The light bars are round trips, and the solid bars are bytes. On a fast link most of the page load time is waiting. This is why HTTP/1.1 performance work was about fewer round trips: fewer requests (sprites, bundles, inlined CSS), more connections, and connections that stay open.

### Pipelining and head-of-line blocking

With **pipelining**, a client sends several requests without waiting for the responses. RFC 9112 section 9.3.2 lets the server work on them in parallel if all use safe methods. It must still send the responses in the order of the requests. One slow response therefore blocks all responses behind it. This is **head-of-line blocking** at the HTTP layer.

Pipelining failed in practice. Some servers and proxies mixed up or dropped pipelined requests. Also, when a server closes the connection, the client cannot tell which requests it processed. Firefox kept pipelining off by default and removed the code in version 54 (2017, Mozilla bug 1340655).

### Six connections per host

RFC 2616 told clients to open at most 2 connections to a server. RFC 7230 (2014) dropped the number and asked clients to be conservative. Browsers settled on 6 per host: Chromium's `g_max_sockets_per_group` is 6 for normal sockets and 255 for WebSockets. Sites then spread resources over several host names ("domain sharding") to get more connections.

More connections have costs. Each one pays its own handshakes and slow start. Six connections also start with six initial windows of 10 segments, so they push a burst into the bottleneck queue that one connection would not. They compete with each other and with other users. HTTP/2 instead puts all requests on one connection.

Two Linux settings matter for persistent connections. `net.ipv4.tcp_slow_start_after_idle` (default 1) shrinks the congestion window after the connection is idle for one RTO, so a kept-alive connection can start slowly again. Servers that keep long-lived connections often set it to 0.

## Framing: where a message ends

TCP delivers bytes, not messages. The receiver must find where each body ends, and RFC 9112 section 6.3 gives the rules in order:

1. `Transfer-Encoding: chunked`: the body is a series of chunks. Each chunk has a hex size line, the data and CR LF. A chunk of size 0 ends the body.
2. `Content-Length`: exactly that many bytes.
3. Neither: a request has no body; a response runs until the server closes the connection.

<NetAppFramingDemo />

1. With Content-Length, the parser finds both requests. The second request starts right after byte 19 of the body.
2. Select chunked and move the chunk size. The hex size lines change. A server uses chunked coding when it streams a body that it has not finished computing.
3. Select close. Only the end of the connection ends the body, so a connection that breaks early looks like a short body.
4. Select a wrong length. With 6 bytes too few, the rest of the body becomes the start of a "request" that is not valid.
5. Select CL + TE. The proxy and the server split the same bytes into different requests.

The last case is **request smuggling**. A front-end proxy that trusts Content-Length forwards one request. A back-end that follows Transfer-Encoding sees two, and the second one never passed the proxy's checks. RFC 9112 says that Transfer-Encoding overrides Content-Length, and that a message with both "ought to be handled as an error". A proxy that forwards such a message must first remove Content-Length.

## Caching

The fastest request is the one that a client does not send. RFC 9111 defines when a cache may reuse a stored response:

- **Fresh**: the response is younger than its freshness lifetime, from `Cache-Control: max-age=N`. The cache uses it with no request at all.
- **Stale**: older than that. The cache must **revalidate**: it sends a conditional request with `If-None-Match` (the stored ETag) or `If-Modified-Since`. If nothing changed, the server answers `304 Not Modified` with no body.
- `no-cache` means: store it, but revalidate before every use. `no-store` means: never store it.
- With no explicit lifetime but a `Last-Modified` field, a cache may guess one. RFC 9111 suggests 10% of the time since the last change.

5. Select "none". The heuristic gives the 3-day-old file a lifetime of more than 7 hours, and 6 visits run old code.
6. Select "versioned URL". The page names the file by a hash of its content and sends `max-age=31536000, immutable` (RFC 8246). Each deploy is a new URL, so the cache is always right: 3 downloads, no stale visits.

The versioned URL is the standard answer for static assets: cache them forever and change the name when the content changes. The HTML that names them gets a short lifetime or `no-cache`, so it is checked on each visit.
