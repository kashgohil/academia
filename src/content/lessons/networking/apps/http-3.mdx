**HTTP/3** (RFC 9114, June 2022) is HTTP over [QUIC](/networking/transport/quic). The QUIC lesson covers the transport: independent streams, packet numbers that never repeat, the 1-RTT handshake, 0-RTT and connection migration. This lesson covers what HTTP has to change to run on that transport. The answer is: more than one would expect, because HTTP/2 relied on TCP's single ordered byte stream in places that are easy to miss.

## Requests on QUIC streams

HTTP/3 keeps the semantics of RFC 9110 and the ideas of [HTTP/2](/networking/apps/http-2): binary frames, many concurrent requests, compressed header fields. It drops everything QUIC already does:

| HTTP/2 | HTTP/3 |
|---|---|
| a stream id in every 9-byte frame header | no stream id: the QUIC stream carries the frame |
| WINDOW_UPDATE, per stream and connection | QUIC flow control (MAX_STREAM_DATA, MAX_DATA) |
| RST_STREAM | QUIC's RESET_STREAM and STOP_SENDING |
| PING, the connection preface | QUIC does these |
| PRIORITY frames (deprecated) | RFC 9218 priorities: a header field and PRIORITY_UPDATE |
| HPACK | QPACK (RFC 9204) |

Each request uses one **client-initiated bidirectional stream**: ids 0, 4, 8 and so on. The client sends a HEADERS frame and optional DATA frames, then ends its side of the stream. The response comes back on the same stream. An HTTP/3 frame is a type, a length and a payload, and the type and length are QUIC **variable-length integers**. A varint uses its top two bits for its length: 1, 2, 4 or 8 bytes.

Each side also opens **unidirectional streams**, and the first byte of each says what it is. The **control stream** (type 0x00) starts with a SETTINGS frame and lives as long as the connection. The **QPACK encoder stream** (0x02) and **decoder stream** (0x03) carry header-table updates and their acknowledgments.

## Why HPACK cannot work over QUIC

HPACK has one dynamic table per direction, and every header block changes it. A block that adds the user agent at index 62 shifts all older entries up by one. The decoder must therefore process blocks in exactly the order the encoder wrote them. On HTTP/2 that order comes free from TCP.

QUIC delivers each stream on its own. If the packet with request 1 is lost, requests 2 and 3 still arrive and are handed to HTTP/3 at once. That is the whole point of QUIC streams.

### How QPACK works

QPACK moves every table change onto the **encoder stream**. That stream is ordered, like any QUIC stream, so the decoder applies inserts in order. A header block (a **field section**) only reads the table. It starts with a prefix of two numbers:

- **Required Insert Count**: how many inserts the decoder must have before it can decode this section.
- **Base**: a reference point. Entries below it are addressed relative to it, and entries added for this section are "post-base".

A decoder that gets a section too early **blocks** that stream until the encoder stream catches up. The decoder announces in `SETTINGS_QPACK_BLOCKED_STREAMS` how many streams may block at once. The default is 0, and so is the default table capacity: a peer must opt in. The decoder acknowledges sections on the decoder stream, so the encoder learns which entries are safe to use without any risk of blocking.

This is a trade between compression and head-of-line blocking, and the encoder chooses per section. It can refer to fresh entries and risk a wait, or send literals and never wait. An encoder can also start with literals and use the table once the decoder acknowledges the inserts. QPACK also has its own static table of 99 entries, built from HTTP traffic in 2018; it does not reuse HPACK's 61.

## Finding HTTP/3

A browser cannot just try QUIC on UDP port 443 for every site. Many sites do not run it, and some networks block or throttle UDP. It needs a hint, and there are two:

- **Alt-Svc** (RFC 7838): an HTTP response header, such as `Alt-Svc: h3=":443"; ma=86400`. It says that the same service is available over HTTP/3 on port 443 for the next 86,400 s. The browser learns it on its first, TCP-based, visit.
- The **HTTPS DNS record** (RFC 9460): `alpn=h3,h2` in the answer. A browser that asks for it beside the A record can use QUIC on its first visit. See the [DNS lesson](/networking/apps/dns).

<NetAppDiscoveryDemo />

1. With Alt-Svc at a 50 ms RTT, visit 1 uses HTTP/2 over TCP and TLS 1.3: the first byte arrives at 171 ms. Visit 2 uses QUIC: 121 ms, one RTT less.
2. Select the HTTPS record. Both visits use QUIC: 121 ms. The DNS answers come back together, so the record costs no extra round trip.
3. Block UDP and turn racing off. The browser waits for QUIC, gives up after 2,000 ms (a model input), then uses TCP: 2,171 ms.
4. Turn racing on. TCP starts at the same time as QUIC and wins: 171 ms, the same as plain HTTP/2.

Because of the last case, browsers do not wait for QUIC to fail. They race QUIC against a TCP connection. Chromium also marks HTTP/3 as broken for a server after a failure and retries it later with growing delays. Happy Eyeballs (RFC 8305) applies the same idea to IPv6 and IPv4. The cost of racing is a second handshake that the server must do and then throw away.

## Measured gains

The gains of HTTP/3 come from QUIC: one RTT less to set up, no head-of-line blocking between streams, better loss recovery, and migration. They are largest where networks are worst. When Chrome deployed IETF QUIC in October 2020, Google reported that Search latency fell by more than 2%. YouTube rebuffer time fell by more than 9%, and client throughput rose by more than 3% on desktop and 7% on mobile.

These are averages over very many users. The median user on a good wired network sees little difference. A user on a lossy mobile link, at the tail of the distribution, sees the most. The costs are also real. QUIC runs in user space and encrypts each packet on its own, so a server spends more CPU per byte than with kernel TCP.
