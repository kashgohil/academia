Every network shares links between many users. There are two basic ways to do it. **Circuit switching** reserves a fixed part of every link on the path before any data moves, as the old telephone network did. **Packet switching** reserves nothing: data travels in packets, and each packet takes its turn on each link.

Paul Baran at RAND (1964) and Donald Davies at the UK's National Physical Laboratory (1965) proposed packet switching independently. Davies gave the packet its name. The Internet is a packet network, so its links are cheap to share but give no guarantees. This lesson shows what that trade means in time, in queues and in lost packets.

## Reserved slices against shared packets

In circuit switching, a link is cut into fixed slices, for example by time (**TDM**, time-division multiplexing) or by frequency. A user who holds a slice gets its rate, all the time, whether it sends or not. Nobody can borrow an idle slice.

In packet switching, a user sends at the full link rate when it has data. When two users send at the same time, one packet waits in a queue. This is **statistical multiplexing**: the link is sized for the average sum of the traffic, not for the sum of every user's peak.

## Why sharing wins, and what it costs

Look at the numbers from the classic example. A 1 Mbit/s link serves users who need 100 kbit/s while they are active, and each is active 10% of the time. Circuits admit exactly 10 users, because each needs a reserved tenth. With packets, 35 users can share the link. More than 10 of them are active at the same time with probability only about 0.0004.

The number of active users $X$ out of $n$ follows a binomial distribution. The link overflows when $X$ exceeds the number of slots $k$:

$$
P(X > k) = \sum_{j=k+1}^{n} \binom{n}{j} p^{j} (1-p)^{n-j}
$$

The cost of this gain is that nothing is guaranteed. When many users are active together, packets wait in queues, and when a queue is full, packets are lost. Circuit switching gives a fixed delay and no loss, but it wastes every slice that is idle. Bursty traffic, such as web pages and file transfers, has a high peak and a low average, so packets win for it.

## Store-and-forward and pipelining

A normal router is **store-and-forward**: it receives the last bit of a packet before it sends the first bit on. It needs the whole packet to check the checksum and to read the destination. So each router adds one full **serialization time**, the time to put the packet's bits on the link: $L/R$ for $L$ bits at rate $R$.

If a message goes as one large packet over $h$ links, each link must wait for the whole message. If it goes as many small packets, the links work at the same time, like the stages of a pipeline. For $P$ packets of $L$ bits over $h$ equal links with propagation delay $d$:

<Steps>
<div>The first packet reaches the destination after $h$ serializations and $h$ propagation delays: $h \cdot L/R + h \cdot d$.</div>
<div>The packets leave the source back to back, so each next packet arrives one serialization later.</div>
<div>The last packet therefore arrives at $T = (P + h - 1)\,L/R + h\,d$.</div>
</Steps>

## The best packet size, and cut-through

With $M$ bytes of data and $H$ header bytes per packet, the time is about $(M/p + h - 1)(p + H) \cdot 8/R$ for $p$ data bytes per packet. Set the derivative to zero:

$$
p^{*} = \sqrt{\frac{M H}{h - 1}}
$$

For the demo's message, $p^{*}$ is about 548 bytes, and a search over whole packets gives 536 bytes and 15.32 ms. Real networks use a fixed MTU instead, mostly 1500. But the formula shows the trade: more hops favor smaller packets, and larger headers favor larger packets.

A **cut-through** switch starts to send a frame after it reads the destination MAC address, before the frame has fully arrived. It cuts the wait at each switch from a full serialization to a few header byte times, plus the lookup time. Low-latency data center switches use it. The cost is that the switch forwards a frame before it can check the FCS, so it passes on corrupt frames. It also falls back to store-and-forward when the output port is busy, or when the input and output links run at different rates.

## The queue inside a router

A router has three main parts. An **input port** looks up the destination in the forwarding table, by longest-prefix match. A **switching fabric** moves the packet to the output port. The **output port** sends the packet, and it has a queue for packets that arrive while the link is busy.

Queueing is the part of the delay that changes with load. When packets arrive faster than the link sends them, the queue grows. When the queue is full, a simple **drop-tail** queue discards each new packet.

## How large should a buffer be?

The demo shows the M/D/1 mean wait, $W = \rho S / (2(1-\rho))$. With 1500-byte packets on 10 Mbit/s, $S$ = 1.2 ms. At 80% load the mean wait is 2.4 ms, and at 90% it is 5.4 ms. [Queueing theory](/performance/systems/queueing-theory-and-littles-law) gives the general rule: the wait grows as $1/(1-\rho)$.

Random load is not the main reason for buffers, though. Bursts are. Several inputs often send to one output at the same time, as in the **incast** pattern of a data center. The output must then hold the burst or drop it. In the demo, 40 packets arrive almost at once at a 20-packet buffer: one goes on the wire, 20 wait, and 19 are dropped.

The classic rule of thumb sizes a buffer as the round-trip time times the link rate, $\text{RTT} \times C$. It is usually attributed to Villamizar and Song (1994). Appenzeller, Keslassy and McKeown ("Sizing Router Buffers", SIGCOMM 2004) showed that a link with $n$ long-lived TCP flows needs only about $\text{RTT} \times C / \sqrt{n}$.

Too much buffer is also a problem. A large buffer that stays full adds delay to every packet but no throughput. Gettys and Nichols called this **bufferbloat** ("Bufferbloat: Dark Buffers in the Internet", ACM Queue, 2011). On Linux each device has a queueing discipline (qdisc), and `tc qdisc show` lists it. Active queue management keeps such queues short; the [congestion control](/networking/transport/congestion-control-reno-and-cubic) lessons return to it.

## Head-of-line blocking

Some switches queue packets at the inputs instead of the outputs, because the fabric then needs to run only at the link rate. Each input then has one FIFO queue. If the packet at the head of a queue waits for a busy output, every packet behind it waits too. This is true even if their own outputs are idle. This is **head-of-line (HOL) blocking**.

<HolDemo />

1. Press **Step one slot** a few times. When two inputs want the same output, one loses. A red note marks an input that is HOL-blocked: a packet behind its head wants an output that stays idle.
2. Press **Run 500 slots**. With 4 ports, the throughput settles near 65%, far below 100%.
3. Increase **Ports** and run again. The throughput falls toward the dashed line at 58.6%.

Karol, Hluchyj and Morgan (IEEE Transactions on Communications, 1987) computed this limit. With fixed-size packets, random outputs and FIFO inputs, the throughput of each input approaches $2 - \sqrt{2} \approx 58.6\%$ as $N$ grows. The demo measures 75% for 2 ports, 65.5% for 4 and 61.8% for 8. The fix is **virtual output queues**: each input keeps one queue per output, so a blocked packet blocks only its own output. A scheduler then matches inputs to outputs in each slot. McKeown's iSLIP (IEEE/ACM Transactions on Networking, 1999) is a well-known scheduler for this.

The same pattern returns at higher layers. HTTP/1.1 requests on one connection and TCP's in-order delivery both block later data behind an earlier item. [HTTP/2](/networking/apps/http-2) and [QUIC](/networking/transport/quic) were built partly to remove it.
