A **content delivery network** (CDN) is a set of caching servers in many places, close to users. Each place is a **point of presence** (PoP), and its servers are **edge servers**. A user's request goes to a nearby edge. The edge answers from its cache if it can. Otherwise it fetches the object from the customer's own server, the **origin**, and keeps a copy.

A CDN gives three things. It cuts latency, because most round trips stay short. It cuts the load on the origin, because many users share one copy. It absorbs traffic peaks and attacks with capacity that the origin does not have.

## Where the time goes

Light in fiber needs at least 157 ms for a round trip between Sydney and New York ([Latency, bandwidth and the BDP](/networking/foundations/latency-bandwidth-and-bdp)). A new HTTPS connection costs several round trips before the first byte. TCP needs one ([TCP handshake](/networking/transport/tcp-handshake-and-teardown)). TLS 1.3 needs one more (RFC 8446), and a full TLS 1.2 handshake needs two. Then the request itself needs one.

In round trips, with $r_e$ to the edge and $r_o$ from the edge to the origin, the first byte with TLS 1.3 arrives after

| Path | Time to first byte |
|---|---|
| no CDN | $3(r_e + r_o)$ |
| edge hit | $3 r_e$ |
| miss on a warm origin connection | $3 r_e + r_o$ |
| miss on a new origin connection | $3 r_e + 3 r_o$ |

So the edge helps even for content that it cannot cache, as long as it keeps warm connections to the origin. This is why CDNs end TLS at the edge and pool their origin connections.

## The hierarchy: edge, shield, origin

A large CDN has hundreds of PoPs. If each edge fetches its misses from the origin, the origin sees one miss per object per edge. A **shield** (a tier-two or regional cache) sits between the edges and the origin. Edges send their misses to the shield, and only the shield's misses reach the origin. AWS CloudFront has regional edge caches between its PoPs and the origin. An optional Origin Shield layer sits between those regional caches and the origin.

Huang and others measured Facebook's photo stack in 2013 ("An Analysis of Facebook Photo Caching", SOSP). Browser caches served 65.5% of requests, the edge caches 20.0%, the origin cache 4.6%, and the backend storage 9.9%. The edge hit ratio was 58.0% and the origin cache's was 31.8%. A lower tier sees the requests that the tier above it missed, which are the harder ones.

## Hit ratio and cache size

Requests for web objects follow a **Zipf-like** law: the object of rank $r$ gets a share proportional to $r^{-\theta}$. Breslau and others ("Web Caching and Zipf-like Distributions", INFOCOM 1999) found $\theta$ between 0.64 and 0.83 in proxy traces. They also found that the hit ratio grows like the logarithm, or a small power, of the cache size. Each doubling of the cache adds less than the one before.

4. Move **θ** to 1.0, then to 0.6. A steeper law makes caching much easier.

**Che's approximation** (Che, Tung and Wang, IEEE JSAC, 2002) predicts LRU with one number, the **characteristic time** $T$. An object stays in the cache if it was requested within the last $T$ requests. With request probabilities $p_i$ and a cache of $C$ objects:

$$
\sum_i \left(1 - e^{-p_i T}\right) = C, \qquad \text{hit ratio} = \sum_i p_i \left(1 - e^{-p_i T}\right)
$$

The dashed gray line is this formula, and the LRU dots lie on it. LFU beats LRU here, but real popularity changes, and pure LFU keeps yesterday's objects. Real caches use mixes. Facebook's study found that S4LRU, an LRU with four segments, raised the edge hit ratio by 8.5% over FIFO. That cut the requests sent downstream by 20.8%.

### Cache keys and Vary

The **cache key** decides which requests share a copy. RFC 9111 builds it from, at a minimum, the request method and the target URI.

The `Vary` response header adds request headers to the match. A cache must not reuse a stored response without revalidation unless every header that `Vary` names matches (RFC 9111, section 4.1). `Vary: *` never matches. `Vary: Accept-Encoding` makes a few variants, which is fine. `Vary: User-Agent` can make thousands, and the demo shows what that does to the hit ratio. So it pays to **normalize** keys: sort or drop query parameters, and map a header to a few classes before the lookup.

## Freshness and the thundering herd

A response stays **fresh** for its `max-age`. A shared cache uses `s-maxage` instead, if present (RFC 9111). The `Age` header carries a copy's age from one cache to the next. So an edge's copy from a shield expires when the shield's copy does. After expiry, the cache must check the copy with the origin (a conditional request) or fetch it again.

At the moment a hot object expires, every request waits for the origin. If each waiting request sends its own fetch, the origin gets a **thundering herd**: about the request rate times the fetch time. At 200 requests per second and a 180 ms fetch, that is 36 fetches.

4. Set **stale-while-revalidate** to 30 s. Users never wait for the origin: the p99 latency falls to 10 ms, one trip to the edge.

RFC 5861 defines both extensions. With `stale-while-revalidate`, a cache may serve a stale response for that many seconds while it revalidates in the background. With `stale-if-error`, it may serve a stale response when the origin answers 500, 502, 503 or 504.

**Request collapsing** (or coalescing) is the rule that only one fetch per object runs at a time. Varnish does it automatically. NGINX has it as `proxy_cache_lock`, which is off by default and covers only objects that are not yet in the cache. For an expired copy, `proxy_cache_use_stale updating` lets one request refresh it while the others get the stale copy. CloudFront calls it request collapsing.

**Purging** removes content before it expires. A CDN can purge by URL, or by a tag that the origin attached to many objects: Fastly's `Surrogate-Key` header and Cloudflare's `Cache-Tag` header. A soft purge only marks the content stale, so `stale-while-revalidate` and `stale-if-error` still protect the origin. Fastly's blog states that a purge reaches all its PoPs in about 150 ms.

## How a request finds an edge

There are two ways to send a user to a nearby edge:

| | DNS-based mapping | Anycast |
|---|---|---|
| How | the CDN's DNS server returns the address of a chosen edge | every PoP announces the same prefix with BGP |
| Who chooses | the CDN, per DNS query | BGP, per network path |
| Sees | the resolver's address, or the client's subnet with EDNS Client Subnet (RFC 7871) | nothing about load or latency |
| Reacts | within the DNS TTL | within BGP convergence |

Akamai's mapping system works through DNS, with very short TTLs (Nygren, Sitaraman and Sun, 2010). Cloudflare announces the same IP ranges from each of its data centers. The [Anycast](/networking/infrastructure/anycast) lesson shows how BGP decides where those packets go.
