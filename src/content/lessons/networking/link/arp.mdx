A host wants to send an IP packet to 10.0.0.3, which is on its own subnet. The IP layer knows the destination address. The Ethernet layer needs a destination MAC address, and nothing in the IP address gives it. The two address spaces are independent. A NIC keeps its MAC when the host moves to another subnet, and an IP address can move to another NIC.

The **Address Resolution Protocol** (ARP) fills this gap for IPv4. David Plummer defined it in RFC 826 (1982). It is a small protocol with no security, and it still runs on every IPv4 LAN.

## Request and reply

An ARP message rides directly in an Ethernet frame with EtherType `0x0806`. For Ethernet and IPv4 it has 28 bytes.

| Field | Bits | Value for Ethernet and IPv4 |
|---|---|---|
| Hardware type | 16 | 1 (Ethernet) |
| Protocol type | 16 | `0x0800` (IPv4) |
| Hardware address length | 8 | 6 |
| Protocol address length | 8 | 4 |
| Operation | 16 | 1 = request, 2 = reply |
| Sender MAC, sender IP | 48, 32 | the asker |
| Target MAC, target IP | 48, 32 | the address to resolve; the MAC is zero in a request |

The payload is shorter than 46 bytes, so the NIC pads it, and an ARP frame has the minimum 64 bytes. The asker sends the **request** to the broadcast MAC: "who has 10.0.0.3? Tell 10.0.0.1". Every host on the LAN receives it. Only the owner of 10.0.0.3 sends a **reply**, and it sends it by unicast to the asker.

RFC 826 also tells the target to learn from the request. Before it replies, the target adds the sender's IP and MAC to its own table. The asker will almost certainly send a packet that needs an answer, so the answer then needs no ARP of its own.

## The neighbour cache

A host keeps the answers in its **ARP cache**. Linux keeps one neighbour table for ARP and another for IPv6, built on the same code, and `ip neigh` shows both. Each entry has a state. The machine comes from IPv6's Neighbor Discovery (RFC 4861), and Linux uses it for ARP too.

| State | Meaning | Leaves the state when |
|---|---|---|
| INCOMPLETE | a request is out; packets wait in a queue | a reply arrives (REACHABLE), or 3 requests got no answer (FAILED) |
| REACHABLE | recently confirmed | the reachable time passes with no new confirmation (STALE) |
| STALE | the MAC is probably right, but not confirmed | a packet is sent: the host uses the MAC and moves to DELAY |
| DELAY | waiting for an upper layer to confirm | 5 s pass: REACHABLE if confirmed, otherwise PROBE |
| PROBE | sending unicast requests, one per second | a reply (REACHABLE), or 3 probes got no answer (FAILED) |

The timers are sysctls in `net.ipv4.neigh.default`: `base_reachable_time_ms` (30000), `delay_first_probe_time` (5 s), `retrans_time_ms` (1000) and `ucast_solicit` (3). Linux draws the real reachable time at random, from half to one and a half times the base. With the default base, an entry stays REACHABLE for 15 to 45 s.

The DELAY state is the clever part. A STALE entry is still used at once, so the first packet does not wait. The host then gives the upper layer 5 s to prove that the neighbour is alive. TCP gives this proof for free: an ACK for new data shows that the path works. Linux passes it down as a confirmation: TCP calls `sk_dst_confirm`, and a UDP application can pass the `MSG_CONFIRM` flag. With confirmations, a busy neighbour never needs a probe.

<NeighCacheDemo />

1. With the defaults, the entry stays REACHABLE for 44.1 s. It goes STALE, the next packet moves it to DELAY, and after 5 s one unicast probe confirms it again.
2. Turn on **TCP confirms**. The entry stays REACHABLE for the whole run, and A sends only one ARP request.
3. Now turn on **B's cable is cut**. A keeps the entry REACHABLE and sends into a dead link until 142 s. The entry fails at 152 s, 52 s after the cut.
4. Set one packet every 60 s with no confirmations. The entry is STALE when each packet leaves, so every packet starts a probe.

Step 3 shows the cost of the cache. The bound is the longest reachable time, plus DELAY, plus the probes: 45 + 5 + 3 = 53 s with the defaults. During that time, the host sends every packet to a MAC that nobody owns. A protocol that needs faster failover cannot wait for ARP. It must announce the change.

A cache is also a table with limits. Linux does not remove entries while the table holds fewer than `gc_thresh1` (128), and it allows at most `gc_thresh3` (1024) entries that are not permanent. A large flat subnet, such as a big container network, can overflow it, and new neighbours then fail to resolve.

## Gratuitous ARP

A **gratuitous ARP** is an ARP message that nobody asked for. RFC 5227 (2008) defines two related messages. An **ARP probe** has sender IP 0.0.0.0: a host asks "does anyone use this address?" before it takes it. An **ARP announcement** has the host's own IP as both sender and target: "this IP is now at this MAC". The announcement is the classic gratuitous ARP.

The announcement makes failover fast. When a standby host takes over a virtual IP, for example with keepalived, it broadcasts an announcement with its own MAC. Every host that has an entry for that IP replaces the MAC at once. Standard VRRP keeps one virtual MAC for the IP, so its announcement mainly teaches the switches the new port of that MAC. RFC 826 already requires this: a receiver that has the sender's IP in its table updates the MAC, whoever the message was for.

Linux follows that rule. The sysctl `arp_accept` only controls whether a gratuitous ARP may create a new entry; existing entries are updated in every case. The default value, 0, creates none.

## ARP spoofing

Nothing in ARP proves who sent a message. Any host on the LAN can send a reply that says "10.0.0.1 is at my MAC". The victim must accept changes, because a new NIC or a failover is legitimate.

<ArpSpoofDemo />

1. With the defaults, the attack starts at 2 s. After one forged reply, 23 of the 32 packets go through the attacker. The victim sees no outage.
2. Turn off **forwards the traffic**. The attacker now drops the packets: a denial of service.
3. Turn on the static entry. The forged replies change nothing.
4. Turn off the static entry and turn on **dynamic ARP inspection**. The switch drops every forged reply.

This is a **man-in-the-middle** position: the attacker can read, change or drop every packet. Tools that automate it have existed for decades.

The defences work at different layers:

- **Static entries** (`ip neigh replace 10.0.0.1 lladdr MAC dev eth0 nud permanent`) cannot be poisoned. Someone must update them by hand, so they suit only a few critical hosts.
- **Dynamic ARP inspection** in a managed switch checks each ARP message on an untrusted port. It compares it with the bindings of **DHCP snooping**: the IP that the DHCP server gave to each MAC. A forged message does not match, and the switch drops it.
- **Encryption above the link** keeps the man in the middle blind. With TLS, the attacker can still drop traffic, but it cannot read or change it without a valid certificate.

## IPv6: Neighbor Discovery

IPv6 has no ARP. **Neighbor Discovery** (NDP, RFC 4861) does the same job with ICMPv6 messages. They are Router Solicitation (133), Router Advertisement (134), Neighbor Solicitation (135), Neighbor Advertisement (136) and Redirect (137). A Neighbor Solicitation (NS) is the request, and a Neighbor Advertisement (NA) is the reply.

NDP does not broadcast. An NS goes to the **solicited-node multicast address** of the target: `ff02::1:ff00:0/104` plus the low 24 bits of the target (RFC 4291). Each host joins the group for each of its addresses. Its NIC filters multicast MACs in hardware, so the NS interrupts only hosts whose addresses end in the same 24 bits.

<SolicitedNodeDemo />

1. Read the steps for each address. The last 24 bits become part of the group, and the last 32 bits of the group become the MAC.
2. Set 500 hosts. An ARP request interrupts 499 of them. The NS for the same target interrupts none but the target.

NDP adds two small protections. Every NDP message must have hop limit 255, and a receiver drops any other value. A router decrements the hop limit, so this proves that the sender is on the same link. It does not stop an attacker on the link, however. **SEND** (RFC 3971) signs NDP messages but is rarely deployed. **RA Guard** (RFC 6105) lets a switch drop Router Advertisements from ports where no router should be.
