**QUIC** is a transport protocol that runs on [UDP](/networking/transport/udp). It gives what TCP and TLS give together: reliable, ordered, encrypted delivery with congestion control. It started at Google and became an IETF standard in May 2021. The standard is RFC 9000 (transport), RFC 9001 (TLS), RFC 9002 (loss detection and congestion control) and RFC 8999 (invariants). HTTP/3 (RFC 9114, 2022) runs on it.

Langley and co-authors described Google's deployment at SIGCOMM 2017. They estimated that 7% of Internet traffic was QUIC. It cut Google Search latency by 8.0% on desktops and 3.6% on mobile, and YouTube rebuffers by 18.0% and 15.3%.

## Why a new transport

- **Head-of-line blocking.** HTTP/2 puts many requests on one TCP connection. TCP delivers one ordered byte stream, so one lost packet stops every request behind it.
- **Handshake latency.** TCP needs one round trip, and TLS then needs at least one more, before the request can go.
- **Ossification.** Many middleboxes read and rewrite TCP headers, and some drop packets with options they do not know. Changes to TCP are therefore slow to deploy.
- **The kernel.** TCP lives in the operating system. A new feature reaches users only with an OS update.

QUIC answers each point. It has independent **streams** in one connection. It merges the transport and TLS 1.3 handshakes. It encrypts almost all of each packet, so middleboxes have little to read and nothing to rewrite. And it runs in user space, so an application ships its own QUIC stack.

## Streams and head-of-line blocking

A QUIC connection carries many streams. A **stream** is an ordered byte stream of its own, with its own flow control. A stream ID is a 62-bit number. Its lowest bit says who opened the stream (0 for the client), and the next bit says if it is bidirectional (0) or unidirectional (1). HTTP/3 sends each request on its own client-opened bidirectional stream.

## Packet numbers and loss recovery

A TCP retransmission carries the same sequence number as the original. When the ACK comes, the sender cannot tell which copy arrived. Karn and Partridge (1987) therefore told senders to ignore RTT samples of retransmitted segments. TCP timestamps (RFC 7323) solve the ambiguity in another way.

QUIC separates the two jobs. A **packet number** names a transmission and never repeats within a **packet number space**. There are three spaces: Initial, Handshake and application data. A packet number is an integer from 0 to $2^{62}-1$.

Lost data goes again in a new frame of a new packet, with a new number. An ACK therefore always names exactly one transmission, and every RTT sample is exact. ACK frames list ranges of packet numbers. They also carry an **ACK Delay** field: the time that the receiver held the ACK, which the sender takes out. QUIC also forbids reneging: an acknowledged packet stays acknowledged.

A PTO does not declare anything lost and does not cut the window. It only sends one or two probes to get an ACK. The default congestion controller in RFC 9002 is similar to NewReno. Its initial window is 10 maximum-size datagrams, but at most 14,720 bytes or two datagrams, whichever is larger. Many stacks also offer CUBIC or BBR, because the controller is part of the application.

## Handshakes: 1-RTT and 0-RTT

QUIC carries the TLS 1.3 handshake in its own CRYPTO frames. The first flight sets up the connection and the keys at the same time. A client datagram that carries an Initial packet must be at least 1200 bytes long. Until the server has validated the client's address, it may send at most 3 times the bytes it received. This **anti-amplification limit** stops an attacker from using a server to flood a forged address.

**0-RTT data** uses keys from an earlier session. It is not forward secret, and an attacker can replay it (RFC 8446 section 8 and appendix E.5, RFC 9001 section 9.2). TLS gives no guarantee against a replay across connections. A server can limit it with single-use tickets or by recording ClientHellos, but a cluster of servers makes this hard. The safe rule is to accept only idempotent requests in early data. HTTP has a status code for this: 425 (Too Early) in RFC 8470 asks the client to retry after the handshake.

## Connection IDs and migration

A TCP connection is its 4-tuple: two addresses and two ports. If one changes, the connection is gone. QUIC names a connection by **connection IDs** of up to 20 bytes in version 1. Each endpoint chooses the IDs that its peer puts in packets. A phone can move from Wi-Fi to cellular, or a NAT can give the client a new port. Packets then arrive from a new address with a known connection ID.

The server then checks that the new path works. It sends a PATH_CHALLENGE frame with 8 random bytes, and the client echoes them in a PATH_RESPONSE. A new path can have a very different bandwidth and RTT. So unless only the port changed, the endpoints reset the congestion controller and the RTT estimate. To stop an observer from linking the two paths, a client uses a fresh connection ID when it moves on purpose.

<NetCcMigrationDemo />

1. At the defaults, Wi-Fi goes down at 600 ms. TCP gets no new data for 160 ms and QUIC for 110 ms. The file is complete at 1,310 ms with TCP and 1,260 ms with QUIC.
2. Raise the cellular RTT to 150 ms. The gap grows, because TCP pays 2.5 RTTs to reconnect, and QUIC pays 1.5.

The model is kind to TCP. Its application learns of the change at once and asks for the rest of the file with a range request. A real application may learn of it only after a timeout.

## Encrypted headers

<NetCcHeaderDemo />

1. Press **Next packet, same number**. The packet number on the wire changes each time, because the mask comes from a sample of the encrypted payload.
2. Change the spin bit. It changes on the wire too: it is not protected.
3. Read the bytes. Only the low 5 bits of the first byte and the packet number bytes differ between the two views.

A QUIC short header starts with one byte of flags. In order: header form (0), fixed bit (1), **spin bit**, two reserved bits, key phase, packet number length (2 bits). The destination connection ID and a packet number of 1 to 4 bytes follow.

**Header protection** (RFC 9001) takes a 16-byte sample of the encrypted payload and makes a mask from it with a separate key. The mask hides the low 5 bits of the first byte and the packet number. Everything else, including every ACK, is inside the encrypted payload. The spin bit is optional: it flips once per RTT, so an operator can measure the RTT without reading anything else.

## User space

QUIC runs in user space on top of UDP sockets. Examples are Google's QUICHE in Chromium, Cloudflare's quiche, quinn in Rust, and Microsoft's MsQuic. MsQuic also runs inside the Windows kernel as `msquic.sys`. Mainline Linux has no in-kernel QUIC as of late 2026.

A user-space stack can ship a new congestion controller or a bug fix with the application. The cost is CPU: each packet crosses the kernel as a UDP datagram, and each packet is encrypted on its own. Stacks reduce this cost by sending batches of datagrams per system call.
