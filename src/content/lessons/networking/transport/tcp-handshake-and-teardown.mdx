TCP gives an application a reliable, ordered stream of bytes in each direction. To do that, each side numbers every byte it sends. A **sequence number** names a byte, and an **acknowledgment number** says "I have every byte before this one". Before any data flows, the two sides must agree on the first sequence number in each direction. That agreement is the **handshake**. The protocol is RFC 9293 (2022), which replaced RFC 793 (1981).

## The header

The fixed TCP header is 20 bytes. **Options** can add up to 40 more, because the 4-bit **data offset** counts the header length in 32-bit words, and 15 × 4 = 60.

| Field | Bits | Meaning |
|---|---|---|
| Source and destination port | 16 + 16 | with the two IP addresses, they name the connection (the **4-tuple**) |
| Sequence number | 32 | number of the first data byte in this segment, or of the SYN |
| Acknowledgment number | 32 | next byte the sender of this segment expects |
| Data offset, reserved | 4 + 4 | header length in words |
| Flags | 8 | CWR, ECE, URG, ACK, PSH, RST, SYN, FIN |
| Window | 16 | free space in the receive buffer, see [flow control](/networking/transport/flow-control) |
| Checksum, urgent pointer | 16 + 16 | the checksum covers a pseudo-header, as in [UDP](/networking/transport/udp) |

SYN and FIN each use one sequence number, as if they were one byte of data. So the other side can acknowledge them like data. A segment with no data, no SYN and no FIN uses no sequence number.

## Three segments to open

The client picks an **initial sequence number** (ISN) and sends a SYN. The server picks its own ISN, and answers with SYN-ACK: its SYN, plus an ACK of the client's SYN. The client acknowledges the server's SYN. After three segments, both sides know both ISNs, and each side knows that the other heard it.

The SYN also carries options that can appear only there: the **maximum segment size** (MSS), the **window scale** and **SACK permitted**. It often carries **timestamps** too, which then appear in every later segment. If a side sends no MSS option, the peer must assume 536 bytes for IPv4.

The demos start both ISNs at 0 so that the numbers stay readable. Real ISNs are not 0. RFC 9293 asks for ISN = M + F(4-tuple, secret), where M is a clock that ticks about every 4 µs and F is a pseudorandom function. The clock moves ISNs forward over time, which keeps segments of an old connection out of the window of a new one. The secret makes the ISN hard to guess, so an attacker who cannot see the traffic cannot inject a segment that the receiver accepts.

Linux retries a SYN `tcp_syn_retries` = 6 times. Since Linux 6.5 it adds `tcp_syn_linear_timeouts` = 4 more tries, and the first five waits are 1 s each. So connect() fails with ETIMEDOUT after 131 s. A listener sends up to `tcp_synack_retries` = 5 SYN-ACK retransmissions. With a 1 s timeout that doubles, the last SYN-ACK leaves 31 s after the first, and the half-open entry is dropped after 63 s. Both numbers match the Linux documentation.

## The eleven states

RFC 9293 defines each connection as a state machine. The demo draws these states under the diagram.

| State | Meaning |
|---|---|
| `LISTEN` | a server socket waits for SYNs |
| `SYN_SENT` | the client sent SYN and waits for SYN-ACK |
| `SYN_RECEIVED` | a SYN arrived and our SYN-ACK is not yet acknowledged |
| `ESTABLISHED` | data flows both ways |
| `FIN_WAIT_1` | we sent FIN; it is not yet acknowledged |
| `FIN_WAIT_2` | our FIN is acknowledged; we wait for the peer's FIN |
| `CLOSE_WAIT` | the peer sent FIN; our application has not closed yet |
| `CLOSING` | both FINs crossed; ours is not yet acknowledged |
| `LAST_ACK` | we closed after the peer; we wait for the ACK of our FIN |
| `TIME_WAIT` | we closed first; we wait 2 MSL before we forget the connection |
| `CLOSED` | no connection |

Two states point at application bugs. Many sockets in `CLOSE_WAIT` mean that the application got EOF but never called close(). Many sockets in `FIN_WAIT_2` usually mean that the peer has the same bug. Linux limits an orphaned `FIN_WAIT_2` socket with `tcp_fin_timeout`, 60 s by default.

## Closing: FIN, half-close and RST

Each direction closes separately. A FIN says "I will send no more bytes". After its FIN, a side can still receive. This is **half-close**.

In C it is `shutdown(fd, SHUT_WR)`; in Go it is `CloseWrite()` on a `*net.TCPConn`. A client can send a request, close its side to mark the end, and then read the whole answer. In the demo's **Half-close** scenario, the client is in `FIN_WAIT_2` while the answer arrives.

```go
c, _ := net.Dial("tcp", "example.com:7")
c.Write(request)
c.(*net.TCPConn).CloseWrite() // send FIN: "that is the whole request"
reply, _ := io.ReadAll(c)       // still reads until the server's FIN
```

**RST** is the abrupt end. A stack sends RST for a segment that matches no connection and no listener. Examples are a segment to a closed port, or to a host that rebooted. An application can also abort.

 RST is not acknowledged and not retransmitted. The peer's next read or write fails with ECONNRESET. RFC 5961 makes a stack accept an RST only if its sequence number is exactly the next one expected. An RST elsewhere in the window gets a "challenge ACK" instead, so a blind attacker cannot easily reset a connection.

## SYN floods and SYN cookies

A listener keeps a small entry for each SYN until the handshake completes. An attacker can send SYNs from forged source addresses. The SYN-ACKs go to addresses that never answer, and each entry stays until its retries run out. In Linux, the limit for these entries is the `listen()` backlog, capped by `net.core.somaxconn` (4096 since Linux 5.4). RFC 4987 (2007) describes the attack and the defenses.

A **SYN cookie** removes the state. When the backlog is full, the server encodes what it needs into its own ISN and forgets the SYN. The demo uses the layout that D. J. Bernstein describes on his SYN cookie page.

Things to try:

1. Change the client port. The 24-bit hash changes completely; the other fields do not.
2. Set the client MSS to 1220. The table holds only 536, 1300, 1440 and 1460, so the cookie encodes 536, the largest value that is not above 1220.
3. Move **ACK arrives after** to 92 s or more. The counter has moved two steps since the SYN, so the cookie is rejected.
4. Turn on the attacker. A guessed value fails the hash check.

Cookies have a cost. Options from the SYN, such as window scale and SACK, have no place in 32 bits, so a plain cookie connection loses them. Linux puts them into the low bits of the TCP timestamp when timestamps are on. Linux uses its own layout, with a counter that ticks every 60 s and SipHash. Its default `tcp_syncookies` = 1 sends cookies only when the queue overflows; 2 sends them always.

## TIME_WAIT

The side that closes first ends in `TIME_WAIT`. It stays there for 2 × **MSL**, the maximum segment lifetime. RFC 9293 sets MSL to 2 minutes, an arbitrary value. Linux uses a fixed 60 s (`TCP_TIMEWAIT_LEN`). TIME_WAIT has two jobs.

<NetTcpTimeWaitDemo />

Things to try:

1. **The last ACK is lost**, with TIME_WAIT. The server sends its FIN again after its timeout, and the client in TIME_WAIT acknowledges it. The server closes cleanly.
2. Turn TIME_WAIT off. The client has forgotten the connection, so its stack answers the second FIN with RST. The server application gets ECONNRESET for a connection that was closing normally.
3. **An old segment arrives late**, without TIME_WAIT. The client reuses port 40000, and the new connection happens to use the same ISN. The old segment falls inside the new window, and the server takes 1460 bytes of the old connection as new data. No checksum can catch this.
4. Turn TIME_WAIT on. The port is still taken, so the second connection uses 40001. The old segment matches nothing and gets RST.

So the first job is to answer a retransmitted FIN. The second is to keep the 4-tuple unused until old segments have died out in the network. Two MSL covers a segment that lives one MSL plus its answer.

TIME_WAIT has a real cost on busy clients. Each connection to the same server address and port holds one local port for 60 s. With Linux's default `ip_local_port_range` of 32768–60999, that is about 470 new connections per second from one client address.

The fixes are connection reuse (keep-alive and pooling), more client addresses, and `tcp_tw_reuse`. That setting lets a new outgoing connection reuse a port in TIME_WAIT when TCP timestamps make it safe. Its default, 2, enables it only for loopback. The older `tcp_tw_recycle` broke clients behind NAT and was removed in Linux 4.12. RFC 1122 also lets a host accept a new SYN for a 4-tuple in TIME_WAIT. Its new ISN must be larger than the largest sequence number it used on the old connection.
