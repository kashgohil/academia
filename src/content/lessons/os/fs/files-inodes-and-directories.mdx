A **file** is a sequence of bytes that has a size and survives a reboot. The kernel gives the bytes no structure. Records, lines and pages are ideas of the program that reads them.

The object that holds a file is an **inode** (index node): a small fixed-size record. It holds the file's attributes and the map of its data blocks. An inode has a number and no name. A **directory** is a file whose contents map names to inode numbers. So a name is only a pointer, and one inode can have several names.

`stat` prints the inode:

```text
$ stat notes.txt
  File: notes.txt
  Size: 6000        Blocks: 16         IO Block: 4096   regular file
Device: 8,1         Inode: 1837234     Links: 1
Access: (0644/-rw-r--r--)  Uid: ( 1000/ kash)   Gid: ( 1000/ kash)
```

| Field | `struct stat` | Meaning |
|---|---|---|
| Inode number | `st_ino` | The index in the inode table. It is unique in one file system. |
| Type and mode | `st_mode` | File, directory or symlink, and the permission bits. |
| Link count | `st_nlink` | The number of directory entries that point here. |
| Owner | `st_uid`, `st_gid` | The user and group for permission checks. |
| Size | `st_size` | The logical length in bytes. |
| Allocated space | `st_blocks` | Space on disk, always in units of 512 bytes. |
| Times | `st_atime`, `st_mtime`, `st_ctime` | Last read, last data change, last inode change. |

The name is not in this table, because the name is not in the inode. A size of 6,000 bytes needs two 4 KiB blocks, so `st_blocks` is 16. A file with one byte still takes one block, so it shows 8.

## The layout of ext4 on disk

ext4 divides the disk into **block groups**. One group holds its own bitmaps, inodes and data, so a file's inode and data can stay close together.

| Region | Holds |
|---|---|
| Superblock | Global facts: sizes, counts, features. Backup copies live in some groups. |
| Group descriptors | The location of each group's bitmaps and inode table. |
| Block bitmap | One bit per block in this group: free or used. |
| Inode bitmap | One bit per inode in this group. |
| Inode table | The inodes themselves, 256 bytes each by default. |
| Data blocks | File contents, directories and extent tree blocks. |

The numbers follow from one rule. One 4 KiB bitmap block has 32,768 bits, so a group has 32,768 blocks, which is 128 MiB. The default of one inode per 16 KiB gives 8,192 inodes per group. These fill 512 blocks, or 2 MiB, so inode tables take 1.5625% of the disk.

`mkfs` fixes the inode count. So a disk can report `ENOSPC` with free blocks, when millions of tiny files use up all the inodes. `df -i` shows this case. On Linux, `dumpe2fs` and `debugfs` print these structures. The root directory is always inode 2 on ext4.

## Directories and link counts

A directory block holds a list of entries (`struct ext4_dir_entry_2`): inode number, record length, name length, file type and name. Large directories add a hashed index (`dir_index`), so a lookup does not scan every entry.

A file starts with one link. A new directory starts with 2: its name in the parent, and its own `.` entry. Each subdirectory adds 1 to its parent, through its `..` entry. So on ext4, `ls -ld` shows the number of subdirectories plus 2.

| | Hard link | Symbolic link |
|---|---|---|
| What it is | Another directory entry for the same inode | A new inode that stores a path |
| Link count of the target | Grows by 1 | Does not change |
| After the target's name goes | Still works | Dangles, and open gives `ENOENT` |
| Across file systems | No (`EXDEV`) | Yes |
| To a directory | No (`EPERM`) | Yes |
| Space | One directory entry | One inode. A target under 60 bytes fits in the inode. |

The kernel forbids hard links to directories because they could make a cycle. A cycle would break `..` and every tool that walks a tree. Symlinks do not have this problem, because a walker can see them and the kernel limits how many it follows.

## Why rename is atomic

`rename(from, to)` changes directory entries and touches no data. The kernel holds the locks of both parent directories, so another process finds either the old inode or the new inode at `to`. It never finds nothing. If `to` existed, its inode loses one link, as with `unlink`.

Crash atomicity is a separate promise. The [journal](/os/fs/journaling) puts both entry changes in one transaction, so a crash leaves all of it or none of it. It does not make the change durable by itself. For the full recipe with `fsync`, see [the write-durability lesson](/databases/storage/durability-fsync-torn-writes-and-checksums).

`renameat2` on Linux adds `RENAME_NOREPLACE`, which fails if the target exists, and `RENAME_EXCHANGE`, which swaps two names in one step. On macOS, `renamex_np` has the same features, with `RENAME_EXCL` and `RENAME_SWAP`.

## Unlink with an open file

The kernel frees an inode when two counts are both zero: the link count on disk, and the open references in memory. This has useful results:

- A program can open a temporary file and unlink it at once. The space returns at exit, even after a `SIGKILL`. `O_TMPFILE` on Linux skips the name altogether.
- `df` can report a full disk when `du` finds little. A deleted log that a daemon holds open is the usual cause, and `lsof +L1` lists such files.
- A crash must not leak these blocks. So ext4 keeps an **orphan list**, which starts in the superblock at `s_last_orphan`. It frees those inodes at the next mount.

## Sparse files

A write allocates blocks only for the bytes that it touches. A range that nobody wrote is a **hole**. A read of a hole returns zeros and does no I/O.

```rust
use std::fs::File;
use std::os::unix::fs::MetadataExt;

fn main() -> std::io::Result<()> {
    let f = File::create("sparse.img")?;
    f.set_len(1 << 40)?;                     // ftruncate to 1 TiB
    let m = f.metadata()?;
    println!("size {} blocks {} links {} ino {}", m.size(), m.blocks(), m.nlink(), m.ino());
    Ok(())
}
```

On ext4 this file reports a size of 1 TiB and 0 blocks, and `ls -l` and `du` disagree. `lseek` with `SEEK_DATA` and `SEEK_HOLE` finds the parts that exist, and `cp --sparse` uses this. Virtual machine images and core dumps depend on holes. Check for free space first, because a later write into a hole can fail with `ENOSPC`.

## Three tables

A file descriptor is not a file. Three tables stand between the two, and the [fork lesson](/os/processes/fork-and-exec) uses them too.

Things to try:

1. Keep **Two opens** and press **Next** four times. Two descriptions point at one inode. Both writes land at offset 0.
2. Select **dup**. Two descriptors share one description, so the writes land at 0 and 100.
3. Select **fork**. The child gets a copy of the table with the same descriptions, and the writes land at 0, 100 and 200. After the child closes its descriptor, the description stays with one reference.
4. Select **fork, then open**. Each process opens the file on its own, so the writes overwrite each other.
5. Select **Two opens, O_APPEND**. The offsets are separate, but each write first moves to the end, so the writes land at 0 and 100.

| Table | Kernel structure | Holds | Scope |
|---|---|---|---|
| File descriptor table | `files_struct`, `fdtable` | Small integers, each with a pointer and the close-on-exec flag | One process, or threads that share it through `CLONE_FILES` |
| Open file table | `struct file` | Offset (`f_pos`), status flags such as `O_APPEND`, a reference count | System wide |
| Inode table | `struct inode` | Size, link count, mode, and the page cache of the file | System wide, one per file |

This is what happens in a shell. In `cmd > out 2>&1`, the shell uses `dup2`, so both streams share one offset and their output interleaves. In `cmd > out 2> out`, the shell opens the file twice, so the streams overwrite each other.

`pread` and `pwrite` take an explicit offset and do not move the shared one, so threads can use one descriptor safely. On Linux, `/proc/self/fdinfo/3` shows the offset and flags of a descriptor.

<Callout title="On your Mac">
APFS has no fixed inode table, so it does not run out of inodes the way ext4 can. Use `stat -x file` for a Linux-like listing. `cp -c` calls `clonefile`, which makes a new inode that shares its data blocks until one side writes. So a clone is not a hard link: each clone has its own inode and its own future. Linux has the same idea in `cp --reflink` on btrfs and XFS, but not on ext4. macOS has no `/proc`, so use `lsof -p` to see the descriptors of a process.
</Callout>
