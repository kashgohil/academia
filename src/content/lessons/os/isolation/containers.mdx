The kernel has no object called a container. There is no `struct container` and no `create_container` system call. A **container** is an ordinary process that a runtime has set up with several separate features. Each feature comes from an earlier lesson, and each can be turned off on its own.

## What a runtime does

A low-level **runtime**, such as `runc`, does these steps in about this order:

1. Read `config.json` and the root file system from a **bundle**.
2. Call `clone` with the namespace flags, and write `uid_map` if a user namespace is in use.
3. Create the cgroup, set its limits, and write the PID to `cgroup.procs`.
4. Mount the root file system, plus `/proc`, `/sys`, `/dev` and any volumes. Then call `pivot_root`.
5. Mask sensitive paths, and make others read-only.
6. Set the host name, then drop capabilities.
7. Set `no_new_privs`, install the seccomp filter, and call `execve` on the program.

The filter comes near the end because the runtime needs system calls that the filter blocks. The sim in this lesson uses one order for teaching. Toggling a layer shows what it adds, whichever order a runtime uses.

### pivot_root, not chroot

`chroot` changes only what `/` means for a process. The old mount tree stays in the mount table. A process with enough privilege can leave a chroot, and this is known behavior, not a bug. So `chroot` is not a security boundary.

`pivot_root` works on the mount namespace. It makes the new root the root mount, and it moves the old root to a directory under it. The runtime then unmounts that directory. Now the host tree is not in this mount table at all, so no path can name it.

```c
mount("rootfs", "rootfs", NULL, MS_BIND | MS_REC, NULL);
chdir("rootfs");
syscall(SYS_pivot_root, ".", ".");     /* the old root now sits under the new one */
umount2(".", MNT_DETACH);              /* and now it is gone from this namespace */
```

### Who does what

| Layer | Job |
|---|---|
| `docker` CLI, `dockerd` | user interface, build, networks |
| `kubelet` | asks for pods through CRI (Container Runtime Interface) |
| `containerd` | pulls images, keeps snapshots, manages container life |
| `containerd-shim` | stays as the parent of the container, holds its stdio and exit code |
| `runc` | sets up the process as above, then exits |

The **OCI** (Open Container Initiative) writes three specs. The runtime spec defines the bundle and `config.json`. The image spec defines manifests, config and layers. The distribution spec defines how a registry serves them. Other runtimes can replace `runc` because of this. `crun` is one, and the [next lesson](/os/isolation/virtual-machines-and-hypervisors) covers gVisor and Kata, which take the same bundle.

## Images and overlayfs

An image is a list of **layers**. Each layer is a tar file of changes, named by its SHA-256 digest. So two images with the same base layer store it once. On disk, the runtime stacks the layers with **overlayfs**:

```bash
mount -t overlay overlay \
  -o lowerdir=/l/app:/l/deps:/l/base,upperdir=/c/upper,workdir=/c/work /c/merged
```

The left-most `lowerdir` is on top. Lower layers are read-only, so many containers can share them, and they can share one page cache. Each container gets its own **upper** directory for changes. `workdir` must be an empty directory on the same file system as `upperdir`, because copy-up prepares a file there and renames it into place. This makes the copy atomic.

1. Read `/app/server` and `/usr/lib/libssl.so`. The orange outline marks the serving layer: a higher layer hides an older version below it.
2. Press **Write 1 byte** on `/data/seed.db`. The readout shows 1 GiB copied for 1 byte written. Write again, and the copied count does not change.
3. Delete `/etc/passwd`. The lower file is still there, but the upper layer has a whiteout, so the merged view says `ENOENT`.
4. Write to `/etc/passwd` after you delete it. The whiteout goes away, and nothing is copied.
5. Create a new file. It has no lower copy, so no copy-up happens.

Three rules follow from this design:

- **Whiteouts.** On overlayfs, a whiteout is a character device with device number 0:0. In an image tar file, it is an entry named `.wh.<name>`. An **opaque directory** hides all lower contents with an extended attribute, `trusted.overlay.opaque`. So deleting a file in a later Dockerfile step never makes an image smaller.
- **Keep busy files on a volume.** A database file on a lower layer pays for copy-up and for overlay lookups. A bind mount or volume bypasses overlayfs.
- **Unusual behavior.** A read-only `MAP_SHARED` mapping made before a copy-up does not see later changes to the file. A rename of a directory from a lower layer can fail with `EXDEV`, unless the `redirect_dir` feature is on.

## A shared kernel, and what it implies

All containers on a machine make system calls to one kernel. That is why they start in milliseconds and use little memory. It is also the main weakness. The kernel is a large and shared attack surface, and one kernel bug can cross every namespace.

| Class of weakness | Why it crosses the boundary | Main defense |
|---|---|---|
| Kernel bug | all containers share one kernel | seccomp, patches, or a VM |
| Too much privilege | `--privileged` or `CAP_SYS_ADMIN` removes most layers by choice | drop capabilities, use a user namespace |
| Host resource exposed | a mounted Docker socket or host path gives control of the host, with no bug | do not mount them |
| Runtime bug | the runtime works with host rights during setup | patch, rootless mode |
| Sensitive kernel files | some files in `/proc` and `/sys` control the whole host | masked and read-only paths |

Some things are not namespaced at all. The kernel log, the kernel keyring in part, loaded modules, device nodes and the system clock are shared or protected only by capabilities and filters. This is why many layers exist: each one covers a gap in the others. For two tenants who do not trust each other, the usual answer is a [VM boundary](/os/isolation/virtual-machines-and-hypervisors).

## Rootless containers

A **rootless** container has no root process on the host, including its runtime. It depends on a [user namespace](/os/isolation/namespaces) and these helpers:

- **`newuidmap` and `newgidmap`** map a range from `/etc/subuid`.
- **slirp4netns or pasta** provide the network from user space, because a normal user cannot create a veth pair in the host namespace. This costs some throughput.
- **Native overlayfs in a user namespace**, since Linux 5.11, replaces the older `fuse-overlayfs`.
- **cgroup delegation** comes from systemd, for the user's subtree.

The gain is large. A way out of the container lands in the rights of an ordinary user, not root. The limits are real too: low ports, some network features, and some file ownership need extra work.

<Callout title="On your Mac">
Containers need Linux kernel features, so Docker Desktop on macOS runs a small Linux VM, and all containers share that VM's kernel. `uname -r` in a container prints a Linux version, and the image must be for arm64 Linux, or run under emulation. File sharing between macOS and the VM crosses a boundary, so a bind mount is slower than on Linux. Apple's own `container` tool runs each container in its own light VM. A Mach-O program from your Mac cannot run in a Linux container.
</Callout>
