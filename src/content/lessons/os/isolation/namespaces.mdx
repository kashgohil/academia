A **namespace** wraps one global kernel resource, so that a group of processes sees its own copy. A process in a new PID namespace sees its own PID 1. A process in a new network namespace sees its own interfaces. No new kernel runs, and no new memory protection appears. The kernel only changes the answer that it gives to the question "which one do you mean?".

Linux has eight types:

| Type | Flag | Isolates | Since |
|---|---|---|---|
| mnt | `CLONE_NEWNS` | the mount tree | 2.4.19 |
| uts | `CLONE_NEWUTS` | host name and domain name | 2.6.19 |
| ipc | `CLONE_NEWIPC` | System V IPC and POSIX queues | 2.6.19 |
| pid | `CLONE_NEWPID` | process IDs | 2.6.24 |
| net | `CLONE_NEWNET` | interfaces, routes, ports, firewall | 2.6.29 |
| user | `CLONE_NEWUSER` | UIDs, GIDs and capabilities | 3.8 |
| cgroup | `CLONE_NEWCGROUP` | the view of the cgroup tree | 4.6 |
| time | `CLONE_NEWTIME` | offsets for `CLOCK_MONOTONIC` and `CLOCK_BOOTTIME` | 5.6 |

Three system calls control them:

- **`clone`** creates a child in new namespaces. A flag asks for each type.
- **`unshare`** moves the caller to new namespaces.
- **`setns`** joins an existing namespace, through a file descriptor.

Each process has links in `/proc/<pid>/ns`. Two processes share a namespace if their links show the same inode number. In the initial PID namespace, this number is always 4026531836:

```text
$ readlink /proc/self/ns/pid
pid:[4026531836]
$ sudo unshare --pid --fork --mount-proc sh -c 'readlink /proc/self/ns/pid; echo $$'
pid:[4026532514]
1
```

The second inode number changes from run to run. A namespace lives while a process is in it, or while something holds a reference. A bind mount of one of these links keeps it alive with no process. `ip netns add` works this way. These commands run only on Linux.

## PID namespaces

PID namespaces nest, to a limit of 32 levels. A process has one PID in its own namespace and one in each ancestor namespace. The kernel stores all of them in `struct pid`, as an array of `struct upid`. A namespace can see its own processes and those of its descendants, and never those of an ancestor.

### The special role of PID 1

The first process in a PID namespace has PID 1, and it has three duties:

- **It adopts orphans.** A process whose parent exits moves to PID 1 of its namespace, which must reap it with `wait`. A server that runs as PID 1 and never calls `wait` collects zombies. This is why `docker run --init` adds a small init process.
- **It has signal protection.** A process in the namespace can send PID 1 only the signals for which it has a handler. So `SIGTERM` does nothing to a PID 1 with no handler. An ancestor namespace can still send `SIGKILL` and `SIGSTOP`.
- **Its death ends the namespace.** The kernel sends `SIGKILL` to every process inside. After that, a `fork` in the namespace fails with `ENOMEM`.

`unshare(CLONE_NEWPID)` and `setns` on a PID namespace do not move the caller, because a process cannot change its PID. They affect only its next child. That child becomes PID 1. `/proc/<pid>/ns/pid_for_children` shows the target. `unshare(CLONE_NEWTIME)` follows the same rule.

The `/proc` file system also matters here. It shows the PID namespace of the mount, not of the reader. After `unshare --pid --fork` with no new `/proc` mount, `ps` still lists the host processes. This is why the command above needs `--mount-proc`.

## User namespaces

A **user namespace** gives a process its own UID and GID numbers, and its own capability sets. The first process in a new one gets all capabilities there. These capabilities apply only to resources that this user namespace owns. A process can be "root" over its own network namespace and have no power over the real network card.

Each user namespace has a `uid_map` and a `gid_map`. Each line has three numbers: the first ID inside, the first ID outside, and the length.

```text
$ cat /proc/$PID/uid_map
         0     100000      65536
```

This line maps inside UIDs 0 to 65535 to host UIDs 100000 to 165535. So root in the container is UID 100000 on the host. A file that the container creates has that owner on disk.

The kernel has strict rules for these files. A map has at most 340 lines, and it can be written only once. Ranges must not overlap on either side.

A process with no `CAP_SETUID` in the parent namespace can map only its own effective UID, in one line of length 1. It must also write `deny` to `/proc/<pid>/setgroups` before it writes `gid_map`. The `newuidmap` helper is a setuid program. It checks `/etc/subuid` and writes larger maps for normal users.

```rust
// Rust, Linux only: become root in a new user namespace. libc crate.
let (uid, gid) = unsafe { (libc::geteuid(), libc::getegid()) };
assert_eq!(unsafe { libc::unshare(libc::CLONE_NEWUSER) }, 0);
std::fs::write("/proc/self/setgroups", "deny")?;
std::fs::write("/proc/self/uid_map", format!("0 {uid} 1"))?;
std::fs::write("/proc/self/gid_map", format!("0 {gid} 1"))?;
assert_eq!(unsafe { libc::geteuid() }, 0); // root here, still uid on the host
```

User namespaces have a cost. They let a normal user reach kernel code that once needed root, such as mount and network configuration. Bugs in that code become reachable. So some distributions limit who can create them, and `user.max_user_namespaces` sets a count limit.

## Mount namespaces and propagation

A new mount namespace starts with a copy of the mount tree. A later mount in one copy can appear in the other, or not. **Propagation type** decides this for each mount:

| Type | Events from the peer arrive | Own events go to the peer | Use |
|---|---|---|---|
| shared | yes | yes | the default on systemd machines |
| slave | yes | no | a container that follows host mounts |
| private | no | no | full separation |
| unbindable | no | no | also blocks bind mounts of it |

`/proc/self/mountinfo` shows `shared:N` and `master:N` for each mount. Systemd makes `/` shared, so a mount inside a new namespace could leak back to the host. So `unshare` and container runtimes first change `/` to private or slave. The command is `mount --make-rprivate /`.

## Network namespaces

A **network namespace** has its own interfaces, routes, firewall rules, port numbers and loopback. A new one contains only a `lo` device, and that device is down. The link to the outside is a **veth pair**: two virtual interfaces joined like a cable. A frame sent into one end comes out of the other. The ends can be in different namespaces.

```bash
sudo ip netns add red
sudo ip link add br0 type bridge
sudo ip addr add 10.200.0.1/24 dev br0
sudo ip link set br0 up
sudo ip link add veth-r type veth peer name eth0 netns red
sudo ip link set veth-r master br0 up
sudo ip netns exec red ip addr add 10.200.0.2/24 dev eth0
sudo ip netns exec red ip link set eth0 up
sudo ip netns exec red ip route add default via 10.200.0.1
```

A **bridge** is a software switch. It learns which MAC address is on which port, and it floods a frame with an unknown destination to all ports. Docker builds its default network in the same way, with a bridge that it calls `docker0`.
