The oldest isolation in UNIX is the **user**. The kernel knows a user only as a number, the **UID** (user ID). A **GID** (group ID) names a group in the same way. Names such as `alice` live in `/etc/passwd`, and only user programs read that file. Every file has one owner UID, one GID and a set of **mode bits**.

The mode has three classes of three bits: owner, group and other. Each class has read, write and execute. Most people read these as three separate grants. The kernel does not.

## The check

`generic_permission` in `fs/namei.c` does this work for most file systems. This is the shape of it, without ACLs:

```c
int mode = inode->i_mode;
if (uid_eq(current_fsuid(), inode->i_uid))
    mode >>= 6;                     /* owner: use these bits and stop */
else if (in_group_p(inode->i_gid))
    mode >>= 3;                     /* group: use these bits and stop */
/* otherwise the low three bits apply */
if ((want & ~mode & (MAY_READ | MAY_WRITE | MAY_EXEC)) == 0)
    return 0;
/* denied by the bits: only CAP_DAC_OVERRIDE or CAP_DAC_READ_SEARCH can help */
```

The kernel runs this check at each step of a path. To open `/a/b/c`, the process needs execute on `/`, `/a` and `/a/b`, and then the access it wants on `c`. [Path lookup](/os/fs/path-lookup-and-the-vfs) shows that walk.

Execute means something different on a directory:

| Bit | On a file | On a directory |
|---|---|---|
| r | read the bytes | list the names |
| w | change the bytes | create, delete and rename entries |
| x | run it | use the directory in a path (search) |

Delete is a write to the directory, not to the file. So the mode of a file does not decide who can delete it.

## Real, effective and saved IDs

A process has several UIDs, in `struct cred`:

- **Real UID**: the user who started the process. Accounting uses it, and so do signal checks.
- **Effective UID**: the identity for most permission checks. Linux copies it to a **filesystem UID** (`fsuid`), which is what the file check above reads.
- **Saved UID**: a copy that lets a program return to an earlier effective UID.

GIDs have the same three, plus a list of **supplementary groups**. The `access` call is a known trap: it checks the real UID, not the effective UID. A setuid program that calls `access` and then `open` also has a race, because the file can change between the two calls.

## Setuid

The **setuid** bit makes `execve` set the effective UID to the owner of the file. This is how `passwd` writes to `/etc/shadow` when a normal user runs it. The saved UID keeps the old effective UID, so the program can drop privilege and take it back.

1. Press **execve setuid-root file**. The real UID stays 1000, and the effective and saved UIDs become 0. The read of `/etc/shadow` now works.
2. Press **seteuid(1000)**, and the read fails. Press **seteuid(0)**, and it works again.
3. Press **setuid(1000)**. All three IDs change. Now **seteuid(0)** returns EPERM.

Setuid is dangerous because the caller controls the environment of a program that runs with the rights of the owner. The caller sets the arguments, the environment variables, the open descriptors, the working directory, the resource limits and the signal state. The dynamic linker has a defense, the `AT_SECURE` flag, which makes it limit `LD_PRELOAD` and similar variables. Each program must still handle the rest. The 2021 `pkexec` bug (CVE-2021-4034) came from the way one such program handled its arguments.

Linux has limits on this. It ignores the setuid bit on scripts. A write by an unprivileged process clears the bit. A file system mounted with `nosuid` ignores it. A process with `no_new_privs` set also ignores it, and that flag survives `execve` and cannot be cleared.

## Sticky and setgid bits

- **Sticky on a directory** (`/tmp`, mode `1777`): only the owner of the file or of the directory can delete an entry. `CAP_FOWNER` also allows it.
- **Setgid on a directory**: new files get the group of the directory, not the group of the creator. Shared project folders use this.
- **Setgid on a file**: `execve` sets the effective GID to the group of the file. This needs the group execute bit as well.

**POSIX ACLs** (access control lists) add entries for named users and groups. The order is owner, then named user, then the groups, then other. A `mask` entry limits the named entries and the groups. `getfacl` and `setfacl` manage them. A `+` at the end of the `ls -l` mode shows that a file has an ACL.

## Capabilities

Root has two jobs on classic UNIX: it owns files, and it bypasses checks. **Capabilities** split the second job into separate rights. Linux has 41 of them, numbered 0 to 40. Binding a low port needs `CAP_NET_BIND_SERVICE`. Changing the time needs `CAP_SYS_TIME`. `CAP_SYS_ADMIN` covers so many operations that it is close to root.

A process has five sets:

| Set | Meaning |
|---|---|
| Permitted | the capabilities that the process may use or make effective |
| Effective | the capabilities that the kernel checks now |
| Inheritable | the capabilities that can pass through `execve`, with help from the file |
| Bounding | a limit on what `execve` can add from a file |
| Ambient | the capabilities that pass through `execve` to a normal program |

A file can also carry capabilities, in the `security.capability` extended attribute. It has a permitted set, an inheritable set and one effective bit. `execve` combines the process and the file by these rules:

```text
P'(ambient)     = file is privileged ? 0 : P(ambient)
P'(permitted)   = (P(inheritable) & F(inheritable)) | (F(permitted) & P(bounding)) | P'(ambient)
P'(effective)   = F(effective) ? P'(permitted) : P'(ambient)
P'(inheritable) = P(inheritable)
P'(bounding)    = P(bounding)
```

A file is **privileged** if it has file capabilities or if it changes the UID or GID. Root has a special rule: a process with UID 0 acts as if the file sets were all ones. This is why root keeps its power across `execve`.

## Least privilege in practice

A web server needs port 80 and nothing else from root. Three ways give it that right:

```bash
# 1. File capability: this binary gets one capability when it runs.
sudo setcap 'cap_net_bind_service=+ep' ./server
getcap ./server

# 2. systemd: no root, no file attribute. The ambient set carries the capability.
#    [Service]
#    User=www
#    AmbientCapabilities=CAP_NET_BIND_SERVICE
#    CapabilityBoundingSet=CAP_NET_BIND_SERVICE
#    NoNewPrivileges=yes

# 3. Move the port limit (default 1024) for this network namespace.
sudo sysctl net.ipv4.ip_unprivileged_port_start=80
```

To inspect a process, run `grep Cap /proc/self/status` and decode the masks with `capsh --decode`. A program that starts as root should drop what it does not need. It should also call `setuid` to leave UID 0, which clears the permitted, effective and ambient sets. The bounding set matters most to a container runtime. Docker keeps 14 capabilities by default, and it removes the rest from the bounding set.

Capabilities have limits as well. Several of them can lead to full root, directly or not. `CAP_SYS_ADMIN`, `CAP_SYS_MODULE` and `CAP_SYS_PTRACE` are the clearest cases. So a capability list is only as strong as its most powerful entry.

<Callout title="On your Mac">
macOS has UIDs, mode bits, setuid and ACLs, but it has no Linux capability sets. Root is also limited by other layers. **System Integrity Protection** (SIP) stops even root from changing protected system locations. `csrutil status` shows its state. **TCC** (Transparency, Consent and Control) asks the user before a program can read data such as the camera, contacts or protected folders. So `sudo cat` can fail on a file in a protected folder when the terminal has no consent. `getcap` and `setcap` do not exist on macOS.
</Callout>
