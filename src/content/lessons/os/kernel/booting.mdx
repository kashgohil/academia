A kernel is a program with no one under it. It has no loader that maps its segments for free, no C runtime, no stack it can trust, and no way to print an error. This module builds a small one, piece by piece, on x86-64. The last lesson composes all the pieces into **TinyOS**, a model that you can drive.

The earlier modules showed how Linux behaves when all of this already works. This module shows how it starts to work.

## The reset vector and the firmware

After reset, one core runs. The Intel manuals call it the bootstrap processor. The other cores wait for a startup message that the kernel sends much later. `CR0` holds `0x60000010`, so paging and protection are off and the caches are off.

**Firmware** is the code in flash ROM that runs first. It trains the memory controller, finds devices, and builds tables that describe the machine. Before DRAM works, it uses the CPU cache as RAM.

Two firmware interfaces exist on PCs:

| | BIOS (legacy) | UEFI |
|---|---|---|
| CPU mode at hand-off | Real mode | Long mode on x86-64, with an identity map |
| What it loads | First 512 bytes of the disk, to `0x7C00` | A PE file, normally `\EFI\BOOT\BOOTX64.EFI`, from a FAT partition |
| How it checks the file | `0x55 0xAA` at offset 510 | File format; optional Secure Boot signature |
| Memory map | `INT 0x15`, function `0xE820` | `GetMemoryMap` |
| First display | VGA text at `0xB8000` | A framebuffer from GOP (Graphics Output Protocol) |

An **identity map** maps each virtual address to the same physical address. New machines ship with UEFI, and many no longer support the BIOS path at all. The BIOS path still matters, because QEMU's default firmware (SeaBIOS) uses it and much old teaching material assumes it.

## The bootloader and the boot protocol

A kernel could be a UEFI application itself. Most kernels use a bootloader. It reads the file system, loads the kernel ELF, and hands over a fixed machine state. The rules of this hand-off are a **boot protocol**.

**Multiboot2** is the protocol of GRUB. The kernel places a header in the first 32 KiB of its file. The header has a magic number, an architecture, a length and a checksum, and the four fields must sum to 0. A minimal header is 24 bytes, so its checksum is `0x17ADAF12`.

The kernel starts in 32-bit protected mode with `EAX = 0x36D76289` and `EBX` pointing to the boot information. Paging is off, `ESP` is undefined, and the GDT must not be used. The kernel must do the [long mode](/os/kernel/protected-mode-and-long-mode) work itself.

**Limine** is a newer protocol. The kernel places request structures in its ELF, and the loader fills in response pointers. The kernel asks for a memory map, a framebuffer and a direct map of physical memory in this way. The kernel starts in 64-bit mode, in the higher half, with a stack, a GDT and `IF` clear.

**PVH** is the direct boot of QEMU. An ELF note in the kernel names a 32-bit entry point, and `qemu-system-x86_64 -kernel` reads that note. So you need no disk image and no bootloader. The CPU starts as it does with Multiboot2: 32-bit protected mode, paging off, and `EBX` pointing to the boot information. The kernel in this module has both headers, and it boots both ways.

The **memory map** is the most important gift. It is a list of address ranges with a type: usable, reserved, ACPI, bootloader data, kernel. The [allocator lesson](/os/kernel/a-simple-allocator) builds on it. Do not assume that any RAM exists. Holes are normal, and a machine can have reserved ranges anywhere.

On UEFI, the loader must call `ExitBootServices` with the key from its latest `GetMemoryMap`. If the map has changed, the call fails and the loader must get the map again. After success, the firmware's timer and drivers are gone. Only runtime services stay.

## A freestanding kernel

**Freestanding** means no operating system below the code. In Rust, `#![no_std]` removes the standard library, and `#![no_main]` removes the normal entry point. You must supply a panic handler, because nothing else can.

The kernel for this module is in `kernels/` in this repository. It boots in QEMU, and `pnpm test:kernels` runs its self-test. Each code sample in this module is a copy of that code, and a unit test keeps the copies correct. This is the start of the shared boot file. It holds the two headers.

{/* source: kernels/boot.s#headers */}

```asm
.section .multiboot2, "a"
.align 8
.long 0xE85250D6              // Multiboot2 magic
.long 0                       // architecture: i386
.long 24                      // header length
.long 0x17ADAF12              // checksum: the four fields sum to 0
.short 0, 0                   // end tag: type 0, flags 0
.long 8                       // end tag: size 8

.section .note.pvh, "a", @note
.long 4                       // name size: "Xen" and its 0 byte
.long 4                       // data size
.long 18                      // XEN_ELFNOTE_PHYS32_ENTRY
.asciz "Xen"
.long boot32                  // the 32-bit entry point
```

The kernel needs a way to print before anything else works. COM1 is a serial port, and QEMU connects it to your terminal.

{/* source: kernels/rust/src/serial.rs#outb */}

```rust
pub unsafe fn outb(port: u16, value: u8) {
    unsafe { asm!("out dx, al", in("dx") port, in("al") value, options(nomem, nostack, preserves_flags)) };
}

pub unsafe fn inb(port: u16) -> u8 {
    let value: u8;
    unsafe { asm!("in al, dx", in("dx") port, out("al") value, options(nomem, nostack, preserves_flags)) };
    value
}

pub fn init() {
    unsafe {
        outb(COM1 + 1, 0x00); // no UART interrupts
        outb(COM1 + 3, 0x80); // DLAB on: the next two registers are the divisor
        outb(COM1, 0x01); //     divisor 1 = 115200 baud
        outb(COM1 + 1, 0x00);
        outb(COM1 + 3, 0x03); // DLAB off, 8 data bits, no parity, 1 stop bit
        outb(COM1 + 2, 0xC7); // FIFOs on
    }
}

pub fn putc(b: u8) {
    unsafe {
        while inb(COM1 + 5) & 0x20 == 0 {} // wait until the transmitter can take a byte
        outb(COM1, b);
    }
}
```

This code uses Rust edition 2024, and it ran with rustc 1.96.1, Zig 0.17.1 and QEMU 11.1.3. QEMU accepts a byte with no UART setup, but real hardware does not, so `init` sets the divisor.

The built-in target `x86_64-unknown-none` has the settings that a kernel needs. The one to understand is the **red zone**. The System V ABI lets a leaf function use 128 bytes below `rsp` without moving `rsp`. An interrupt in ring 0 pushes its frame at `rsp`, so it would destroy that data. A kernel must compile with no red zone. The target also turns off SSE in generated code, so that an interrupt does not need to save those registers.

{/* source: kernels/rust/.cargo/config.toml#cargo */}

```toml
# .cargo/config.toml. Nothing here needs a custom target file or nightly Rust.
[build]
target = "x86_64-unknown-none"

[target.x86_64-unknown-none]
rustflags = ["-C", "link-arg=-T../kernel.ld", "-C", "relocation-model=static", "-C", "code-model=kernel"]
```

Zig has the same parts. This sample ran with Zig 0.17.1. The `-mcpu` flag removes SSE, as the Rust target does. The panic declaration and the inline assembly syntax change between Zig versions, so compare them with your version.

{/* source: kernels/zig/kernel.zig#zig-start */}

```zig
// zig build-exe kernel.zig ../boot.s -target x86_64-freestanding-none \
//   -mcpu=x86_64-sse-sse2-mmx-avx+soft_float -mcmodel=kernel -mno-red-zone \
//   -fllvm -flld -O ReleaseSafe -T ../kernel.ld -fentry=boot32
pub const panic = std.debug.no_panic;

fn outb(port: u16, value: u8) void {
    asm volatile ("outb %[value], %[port]"
        : // no outputs
        : [value] "{al}" (value),
          [port] "{dx}" (port),
    );
}

fn print(text: []const u8) void {
    for (text) |c| outb(0x3F8, c);
}

// boot.s jumps here in 64-bit mode.
comptime {
    asm (
        \\    .text
        \\    .globl high_entry
        \\high_entry:
        \\    lea kernel_stack_top(%rip), %rsp
        \\    call kmain
        \\    ud2
        \\    .section .bss
        \\    .balign 16
        \\    .skip 65536
        \\kernel_stack_top:
    );
}
```

## The linker script

An ordinary program gets its layout from a default linker script. A kernel must choose its own. The script sets the address of each section, and it defines symbols that the code reads. The kernel must clear `.bss` itself when its loader does not, and it finds the range through `__bss_start` and `__bss_end`.

Things to try:

1. Read the start state. It has three PT_LOAD segments with rights `r-x`, `r--` and `rw-`. The file holds 25,600 bytes, and memory holds 46,080. The difference is mostly `.bss`.
2. Turn off **ALIGN(4K)**. One page now holds code and data, so all sections share one RWX segment. That is the warning from recent versions of ld.
3. With alignment off, move `.bss` up to second place. The file grows to 44,544 bytes.
4. Select the base `0xFFFF800000100000`. The kernel code model uses signed 32-bit addresses, which reach only the top and bottom 2 GiB. The link fails.
5. Select the non-canonical base. No linker error stops you in real life, but the first fetch raises `#GP`.
6. Move `.text` down and read the symbols. `_start` moves with it, so `ENTRY` stays correct.

The top 2 GiB exists for this reason. A higher-half kernel at `0xFFFFFFFF80000000` can use short sign-extended addresses, as Linux does. The [next lesson](/os/kernel/protected-mode-and-long-mode) maps that address.

The real `kernel.ld` has one more idea than the form that the demo prints. `AT()` gives a low load address to sections that have high link addresses, because the loader runs with paging off. The 32-bit stub links and loads at the same address, 1 MiB.

{/* source: kernels/kernel.ld#linker */}

```text
ENTRY(boot32)
KERNEL_VMA = 0xFFFFFFFF80000000;

PHDRS {
  boot   PT_LOAD FLAGS(7); /* rwx: the 32-bit stub, its GDT and its page tables */
  text   PT_LOAD FLAGS(5); /* r-x */
  rodata PT_LOAD FLAGS(4); /* r-- */
  data   PT_LOAD FLAGS(6); /* rw- */
  notes  PT_NOTE FLAGS(4);
}

SECTIONS {
  /* Linked and loaded at 1 MiB. The CPU runs this part with paging off. */
  . = 1M;
  .boot : { KEEP(*(.multiboot2)) *(.boot .boot.*) } :boot
  .note.pvh : { KEEP(*(.note.pvh)) } :boot :notes

  /* Linked in the top 2 GiB, but loaded just above the stub. AT() sets the load address. */
  . = ALIGN(4K) + KERNEL_VMA;
  _kernel_start = .;
  .text : AT(ADDR(.text) - KERNEL_VMA) { *(.text .text.*) } :text
  . = ALIGN(4K);
  .rodata : AT(ADDR(.rodata) - KERNEL_VMA) { *(.rodata .rodata.*) } :rodata
  . = ALIGN(4K);
  .data : AT(ADDR(.data) - KERNEL_VMA) { *(.data .data.*) } :data
  .bss : AT(ADDR(.bss) - KERNEL_VMA) { *(.bss .bss.*) *(COMMON) } :data
  _kernel_end = .;

  /DISCARD/ : { *(.comment) *(.eh_frame*) *(.note.GNU-stack) }
}
```

## Running it on Apple Silicon

An x86-64 kernel cannot use the Mac's hardware virtualization, because the guest CPU differs from the host CPU. QEMU's **TCG** (Tiny Code Generator) translates the guest instructions in software. It is slow, but it is enough for a small kernel, and its logs show each interrupt. Install it with `brew install qemu`. The Rust toolchain includes `rust-lld`, so you do not need a cross-compiling GCC.

{/* source: kernels/run.sh#qemu */}

```sh
exec qemu-system-x86_64 -machine q35 -accel tcg -m 64M \
  -kernel "$KERNEL" -append "$ARGS" \
  -serial stdio -display none \
  -no-reboot \
  -device isa-debug-exit,iobase=0xf4,iosize=1
```

`-serial stdio` sends COM1 to your terminal. `-no-reboot` stops at a triple fault, so you do not get a silent reboot loop. Add `-d int,cpu_reset -D qemu.log` to log each interrupt and the CPU state at a reset. That log is your first debugger. Add `-s -S` to wait for a GDB connection.

The test script also boots the kernel through GRUB, from an ISO that `i686-elf-grub-mkrescue` builds. This checks the Multiboot2 path. Install it with `brew install i686-elf-grub xorriso mtools`. Limine and UEFI firmware are the path of many modern kernels, but this kernel has not been tested on them.

arm64 differs at each step. No real mode exists. A QEMU `virt` machine or a loader starts the kernel at EL2 or EL1 with the MMU off. It passes a device tree in `x0`.

On a Mac, `qemu-system-aarch64 -accel hvf` can run such a kernel at near full speed. Apple's own boot chain for macOS is different. It loads a signed Mach-O kernel collection through iBoot, and this path is not open to a small kernel.
