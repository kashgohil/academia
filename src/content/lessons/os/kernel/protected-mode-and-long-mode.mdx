## Real mode and segments

In **real mode**, an address is a 16-bit segment and a 16-bit offset. The physical address is `segment * 16 + offset`. This form reaches 1 MiB, and a little more: `FFFF:0010` is `0x100000`. The 8086 had only 20 address lines, so that address wrapped to 0. Old programs relied on it.

So PCs gained the **A20 gate**, which can force address line 20 to 0. A boot path through the BIOS must open it.

Real mode has no protection. Any code can write anywhere and run any instruction. In return, BIOS calls work, and this is why the boot sector starts there.

## The GDT

**Protected mode** replaces the segment number with a **selector**. A selector is an index into a table in memory, the **GDT** (Global Descriptor Table), plus a requested privilege level in its low 2 bits. Each entry describes a segment: its base, limit, type and privilege.

An entry has a strange layout, because the 80386 extended the 80286 format without moving the old fields. Base and limit are each split into parts.

5. Click **P** to clear it. A load of this selector now raises `#NP`.

In 64-bit mode the CPU ignores base and limit for code and data, so segmentation is nearly gone. Three things remain. CS still decides the mode and the current ring. FS and GS keep their bases through MSRs, which is how thread-local storage works. And the TSS still needs a descriptor, which grows to 16 bytes in long mode.

Set the accessed bit in advance if the GDT is in read-only memory. The CPU writes that bit when it loads a segment. Linux uses `0x9B`, which has that bit set.

## The path to long mode

**Long mode** is the 64-bit architecture. It has two sub-modes: **64-bit mode** runs with `CS.L = 1`, and **compatibility mode** runs old 32-bit code with `CS.L = 0`. Three bits turn it on, in three different registers.

| Register | Bit | Meaning |
|---|---|---|
| `CR0` | PE, bit 0 | Protected mode |
| `CR0` | PG, bit 31 | Paging |
| `CR4` | PAE, bit 5 | Table entries of 64 bits |
| `EFER` (MSR `0xC0000080`) | LME, bit 8 | Allow long mode |
| `EFER` | LMA, bit 10 | Long mode is active. The CPU sets this bit, not software. |

**Paging is not optional in long mode.** LMA turns on at the moment that PG turns on, and the CPU checks the rules at that moment. Setting PG with LME set and PAE clear raises `#GP`. Changing LME while paging is on raises `#GP`.

The instruction right after `mov cr0` still has a low address, and now the CPU translates it. So the page tables must map the running code at its own address. This is the job of the identity map. After that, `CS` still has `L = 0`, so a far jump to a descriptor with `L = 1` finishes the work.

This Rust file holds the whole path as assembly. It starts in 32-bit mode, as Multiboot2 leaves the CPU. The linker must place this code at a low address. It compiled to an object file with rustc 1.96.1, but it was not run.

```rust
#![no_std]
use core::arch::global_asm;

// A flat GDT. These are the values that the demo encodes.
#[repr(C, align(8))]
pub struct Gdt(pub [u64; 4]);
#[unsafe(no_mangle)]
pub static BOOT_GDT: Gdt = Gdt([
    0,
    0x00CF_9A00_0000_FFFF, // 0x08: 32-bit code
    0x00CF_9200_0000_FFFF, // 0x10: data
    0x00AF_9A00_0000_FFFF, // 0x18: 64-bit code, L = 1
]);

global_asm!(r#"
    .text
    .code32
    .globl boot32
boot32:
    cli
    mov esp, offset boot_stack_top

    // Page tables are ready in .bss: PML4, PDPT and PD, with 2 MiB leaves.
    mov eax, cr4
    or  eax, 1 << 5               // CR4.PAE
    mov cr4, eax

    mov eax, offset boot_pml4
    mov cr3, eax

    mov ecx, 0xC0000080           // EFER
    rdmsr
    or  eax, 1 << 8               // EFER.LME
    wrmsr

    mov eax, cr0
    or  eax, 1 << 31              // CR0.PG: now LMA = 1, compatibility mode
    mov cr0, eax

    lgdt [gdt_ptr]
    .byte 0xEA                    // far jump: load CS with the L = 1 descriptor
    .long boot64
    .short 0x18

    .code64
boot64:
    mov ax, 0x10
    mov ds, ax
    mov es, ax
    mov ss, ax
    movabs rax, offset high_entry
    jmp rax

    .data
gdt_ptr:
    .short 4 * 8 - 1
    .long BOOT_GDT
"#);
```

Why does a far jump matter so much? The CPU keeps a hidden copy of each segment descriptor. Writing `CR0` does not reload the copy in CS. Only a far jump, or an `iret` or `ret` of the far kind, loads CS. This is why "set PE" alone leaves the CPU decoding 16-bit code.

The real-mode start of a secondary CPU in Linux lives in `arch/x86/realmode/rm/trampoline_64.S`. It follows these same steps.

## Identity map and higher half

Most kernels link at a high address and load at a low one. So the boot tables hold two mappings of one physical range, for a short time. The low mapping keeps the current instruction valid. The high mapping is the real home. After the jump to the high address, the kernel removes the low mapping, so a null pointer faults again.

Things to try:

1. Read the indices of the kernel address: PML4[511], PDPT[510], PD[0]. That is the top 2 GiB of the address space.
2. Switch **Kernel pages** to 512 of 4 KiB. One more table appears. A 2 MiB leaf saves it, and it also uses fewer TLB entries.
3. Turn on **Direct map of the first 1 GiB**. One entry in one new PDPT maps all of it. PML4[256] starts the kernel half of the address space.
4. Pick **rip before the jump** and turn off the identity map. The walk stops at the top table. A kernel that removes the map too early dies here.
5. Pick **non-canonical**. The CPU raises `#GP` with no walk at all.

These tables come from the real `PageTable` class of the [paging lesson](/os/vm/paging-and-page-tables). The tree has one shape, and only the leaf rights differ.

A **canonical** address has bits 63 to 47 all equal, with 4-level paging. So `0x00007FFFFFFFFFFF` is valid, and `0x0000800000000000` is not. This rule keeps software from hiding data in the high bits, so that later CPUs can add address bits safely. The [address spaces](/os/vm/address-spaces) lesson draws the two halves.

## What UEFI has already done

On x86-64, UEFI firmware runs in long mode, with an identity map and its own GDT. A UEFI application starts there. Limine then builds higher-half tables and enters the kernel. So a modern kernel can start in long mode and skip this whole lesson at boot.

It still has work to do. The firmware's GDT and tables live in memory that the kernel will reuse, so the kernel must load its own. It needs a GDT with user segments and a TSS anyway. And the secondary CPUs start in real mode, through a startup message, until the kernel has its own low trampoline page. Newer platforms offer ways to start cores in long mode directly, but the real-mode path remains the common one.

arm64 has none of this history. It has no segments and no GDT. A kernel sets `TCR_EL1` and `MAIR_EL1`, loads `TTBR0_EL1` for the low half and `TTBR1_EL1` for the high half, and sets `SCTLR_EL1.M`. It also needs an identity map for the instruction that turns on the MMU. That one problem is the same on every CPU.
