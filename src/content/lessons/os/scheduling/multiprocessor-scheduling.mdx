Scheduling on one CPU is a question of order. On many CPUs it is also a question of place. A thread that returns to its last CPU finds its data in that CPU's caches. This is **cache affinity**. So a good scheduler keeps threads in place, and it also keeps all CPUs busy. These two goals conflict.

The first design choice is the queue.

- **A single shared queue.** Any CPU takes the next task. This balances load by itself. But each pick takes one global lock, and a task moves between CPUs at almost every turn. Linux had this design until the O(1) scheduler in 2.6.
- **One queue per CPU.** Each CPU has its own runqueue (`struct rq` in Linux) and its own lock. A task stays on its CPU, so picks do not contend and caches stay warm. But one CPU can be idle while another has a long queue. This is **imbalance**, and it needs a **load balancer**.

## How Linux balances

Linux has no central balancer. Each CPU balances for itself, in two ways:

- **Periodic pull.** The scheduler tick raises `SCHED_SOFTIRQ` when a balance is due, and `rebalance_domains()` runs `load_balance()`. It finds the busiest group and the busiest queue in it, and it pulls tasks to the local CPU.
- **Newly idle pull.** A CPU that is about to go idle calls `newidle_balance()`. This is **work stealing**: the idle CPU pays the cost, and busy CPUs lose nothing.

Recent kernels rename these functions with a `sched_balance_` prefix. User-space runtimes use the same idea. In Go, a `P` (a logical processor) with an empty run queue steals half of the queue of another `P`. Rayon uses work-stealing deques: the owner pushes and pops at one end, and thieves take from the other end.

"Load" is not the queue length. Linux tracks a decaying average of each task's runnable time (**PELT**, per-entity load tracking), scaled by its weight. So a task that sleeps most of the time counts for little.

## What a migration costs

A migration has a direct cost: two runqueue locks and a few counters. The real cost comes later. The task must refill its caches and TLB on the new CPU, and on another NUMA node its memory is now remote.

## Scheduling domains

The cost of a move depends on the distance. Sibling threads on a core share the L1 and L2 caches. Cores on a die usually share L3. Two sockets share nothing but the interconnect. Linux models this with a tree of **scheduling domains** (`struct sched_domain`), one tree for each CPU.

| Level | CPUs in the domain | Balance |
|---|---|---|
| SMT | hardware threads of one core | very often, almost free |
| MC | cores that share a last-level cache | often |
| PKG | all cores in a socket | less often |
| NUMA | CPUs across nodes | rarely, and only for a clear imbalance |

Higher domains have longer intervals and larger thresholds. You can read the tree on Linux under `/sys/kernel/debug/sched/domains/`. Automatic NUMA balancing (`numa_balancing`) works from the other side: it moves pages toward the threads that use them.

## Choosing a CPU at wake-up

A wake-up happens far more often than a balance, so most placement happens here. `select_task_rq_fair()` makes this choice. **Wake-affine** logic (`wake_affine()`) decides between the CPU where the task last ran and the CPU of the task that wakes it. If a thread wakes a partner to read the data it just wrote, the waker's CPU has that data in cache. Then `select_idle_sibling()` looks for an idle CPU that shares a cache with the target.

This has a failure mode too. A server thread that wakes many workers can pull them all toward one CPU. The cost plot above includes this: 5% of its wake-ups go to CPU 0, and that is why the long periods lose.

## Pinning

You can overrule all of this. **Affinity** is a mask of the CPUs that a thread may use.

```c
cpu_set_t set;
CPU_ZERO(&set);
CPU_SET(3, &set);
sched_setaffinity(0, sizeof set, &set);    // this thread, CPU 3 only
```

From the shell, use `taskset -c 3 ./prog`. Linux also offers the `cpuset` cgroup and the `isolcpus` boot parameter, which keeps the balancer away from chosen CPUs. Pin for measurements and for latency-critical threads with their own NUMA memory. A pinned thread cannot escape a busy CPU, so careless pinning makes imbalance permanent.

## SMT and heterogeneous cores

**SMT** (simultaneous multithreading) shows one core as two logical CPUs. The two threads share execution units and caches, so two busy siblings do not give twice the work. The kernel prefers a fully idle core before it uses a sibling. A pair of threads that share data can gain from being siblings. A pair of unrelated hot threads usually loses.

**Heterogeneous** chips (Arm big.LITTLE, Intel P-cores and E-cores) have cores of different speed. A fair share of time is then not a fair share of work. Linux gives each CPU a **capacity** value, and it scales load by that value. **Energy Aware Scheduling** then picks the CPU that costs the least energy and still has room. A task that needs more than a small core can give is a "misfit", and the balancer moves it to a big core.

<Callout>
macOS on Apple Silicon has no `sched_setaffinity` or `taskset`, and you cannot pin a thread to a chosen core. You state the purpose of the work with a **QoS class** instead: `USER_INTERACTIVE`, `USER_INITIATED`, `DEFAULT`, `UTILITY` or `BACKGROUND`. The scheduler uses it to choose between performance and efficiency cores. Background work usually stays on efficiency cores. Use `pthread_set_qos_class_self_np()` or Grand Central Dispatch queues in code, and `taskpolicy` from the shell.
</Callout>
