A **real-time** system is correct only if it is also on time. In a **hard** real-time system, one missed deadline is a failure: a brake controller is an example. In a **soft** system, a miss only lowers quality: an audio dropout is an example. Fair schedulers aim at shares. Real-time schedulers aim at a proof that every deadline holds.

The standard model is a set of **periodic tasks**. Task $i$ releases a **job** every $T_i$ (the period). Each job needs at most $C_i$ of CPU (the worst-case execution time) before the next release. The **utilization** of the set is $U = \sum C_i / T_i$. No scheduler can succeed on one CPU if $U > 1$.

Two classic policies preempt on every release:

- **Rate monotonic** (RM) gives each task a fixed priority. The shorter the period, the higher the priority.
- **Earliest deadline first** (EDF) gives each job a priority from its deadline. The nearest deadline runs.

## Why the bounds are what they are

Liu and Layland proved two results in 1973 for implicit deadlines (each deadline equals the next release).

**EDF: $U \le 1$ is enough.** The proof is by contradiction.

Suppose that EDF misses a deadline at time $t$. Go back to the last time $t_0$ when the CPU was idle or ran a job with a later deadline. From $t_0$ to $t$, the CPU only ran jobs with deadlines at or before $t$. Those jobs need more than $t - t_0$ of CPU. But task $i$ can have at most $(t - t_0)/T_i$ such jobs, so their total need is at most $U(t - t_0)$. Then $U > 1$, which is a contradiction.

**RM: a lower bound.** Fixed priorities waste some capacity when the periods do not divide each other. The bound is sufficient for $n$ tasks, but it is not necessary:

$$
U \le n\left(2^{1/n} - 1\right)
$$

| $n$ | 1 | 2 | 3 | 4 | 5 | 10 | limit |
|---|---|---|---|---|---|---|---|
| Bound | 1.000 | 0.828 | 0.780 | 0.757 | 0.743 | 0.718 | $\ln 2$ = 0.693 |

The **exact** test is **response-time analysis** (Joseph and Pandya, 1986). The worst case is when all tasks release together. Iterate this to a fixed point, and compare the result with the deadline:

$$
R = C_i + \sum_{j \in hp(i)} \left\lceil \frac{R}{T_j} \right\rceil C_j
$$

For T2 in the default set, $R$ goes 4, 6, 8, 8. Since 8 is more than 7, T2 is late.

RM stays popular for three reasons. Priorities are fixed, so the implementation is simple. An overload hurts only the lowest priorities, and you can choose them. And the worst case is easy to analyze.

## Linux real-time classes

Linux checks its **scheduling classes** in a fixed order: `stop`, `deadline`, `rt`, `fair`, `idle`. A runnable task in an upper class always beats a task in a lower class.

| Policy | Rule |
|---|---|
| `SCHED_FIFO` | Priority 1 to 99. The task runs until it blocks, yields, or a higher priority preempts it. |
| `SCHED_RR` | The same, with a time slice among equal priorities. The default slice is 100 ms (`/proc/sys/kernel/sched_rr_timeslice_ms`). |
| `SCHED_DEADLINE` | EDF with a bandwidth budget for each task. It has no priority number, and it beats both of the above. |

```c
struct sched_param p = { .sched_priority = 50 };
sched_setscheduler(0, SCHED_FIFO, &p);     // needs CAP_SYS_NICE or RLIMIT_RTPRIO
mlockall(MCL_CURRENT | MCL_FUTURE);        // a page fault is not a real-time event
```

From the shell, use `chrt -f 50 ./prog`. These tools are Linux only. On macOS, the nearest thing is `thread_policy_set()` with `THREAD_TIME_CONSTRAINT_POLICY`, which audio threads use.

`SCHED_DEADLINE` (since Linux 3.14) takes three numbers: a runtime, a deadline and a period. The kernel does **admission control**: it refuses a task if the total bandwidth is too high. It enforces the budget with a **constant bandwidth server**, so a task that overruns is stopped until its next period and cannot harm others. That is the difference from plain EDF, and it removes most of the domino effect.

```c
struct sched_attr a = {
    .size = sizeof a, .sched_policy = SCHED_DEADLINE,
    .sched_runtime  =  2 * 1000000,    // 2 ms of CPU
    .sched_deadline =  5 * 1000000,    // within 5 ms
    .sched_period   = 10 * 1000000,    // every 10 ms
};
syscall(SYS_sched_setattr, 0, &a, 0);  // EBUSY if admission control refuses
```

**RT throttling** is the safety net. A `SCHED_FIFO` loop with a bug would otherwise lock a CPU for ever. By default, real-time tasks may use 950,000 µs of each 1,000,000 µs (`sched_rt_runtime_us` and `sched_rt_period_us`), which is 95%. Newer kernels (about 6.12) use a deadline server for normal tasks to give the same protection.

## Priority inversion

A priority alone does not give a guarantee when tasks share a lock. **Priority inversion** means that a high-priority task waits for a lower-priority task.

1. Step through with inheritance off. M runs while H is blocked. Move M's work to 20 ticks: H's blocked time grows with it, with no limit.
2. Turn on **Priority inheritance** and step again. When H blocks, L's effective priority rises to 3. M cannot preempt L.
3. Move M's work with inheritance on. H is blocked for 2 ticks at every value.

**The Mars Pathfinder case.** Pathfinder landed in July 1997, and then it started to reset itself. A high-priority task managed the information bus. A low-priority meteorological task sometimes held a mutex that the bus task needed. Medium-priority communication tasks then preempted the meteorological task. A watchdog saw that the bus task had not finished on time, and it reset the whole system.

The VxWorks mutex had priority inheritance as an option, and the option was off. Engineers reproduced the bug on Earth and changed the flag by an upload to Mars.

**Priority inheritance** makes a lock owner run at the highest priority of its waiters, until it releases the lock. The boost must also pass along a chain of locks. On Linux, use `PTHREAD_PRIO_INHERIT`. It maps to `FUTEX_LOCK_PI` and the kernel's `rt_mutex`. It is a kernel path, so it is slower than a plain [futex](/os/sync/futexes). The alternative is a **priority ceiling** (`PTHREAD_PRIO_PROTECT`): the owner runs at a fixed high priority from the moment it takes the lock.

```c
pthread_mutexattr_t a;
pthread_mutexattr_init(&a);
pthread_mutexattr_setprotocol(&a, PTHREAD_PRIO_INHERIT);   // also on macOS
pthread_mutex_init(&m, &a);
```

## PREEMPT_RT

A real-time policy helps only if the kernel itself can be preempted. A task can be late because the kernel holds a spinlock with preemption off, or runs a long interrupt handler. **PREEMPT_RT** removes most of these cases. It turns most spinlocks into sleeping `rt_mutex` locks with inheritance, and it moves most interrupt handlers into threads that have priorities. It was developed out of tree for about two decades, and it was merged in Linux 6.12 for x86, arm64 and RISC-V. The standard measurement tool is `cyclictest`.

Do not trust a table of latency numbers from another machine. Firmware, power states and drivers decide the worst case, so measure it on your hardware under load.
