A semaphore counts. Many conditions are not counts: "the queue has an item and the shutdown flag is clear", or "this balance is above the amount". A **condition variable** lets a thread sleep until some other thread says that a condition may have changed. It holds no value. The condition lives in your own data, under your own mutex.

```c
// Waiter                               // Notifier
pthread_mutex_lock(&m);                 pthread_mutex_lock(&m);
while (count == 0)                      count++;
    pthread_cond_wait(&cv, &m);         pthread_cond_signal(&cv);
count--;                                pthread_mutex_unlock(&m);
pthread_mutex_unlock(&m);
```

`pthread_cond_wait` does three things. It releases the mutex and joins the queue in one atomic step. It sleeps. When a notifier wakes it, it takes the mutex again before it returns.

**Signal** wakes one waiter. **Broadcast** wakes all waiters. If no thread waits, both do nothing. The notification is not stored. That is why the state must live in your data.

## Why a loop

**Hoare semantics** (Hoare, 1974) hand the mutex straight to the woken thread. No thread can run between the signal and the waiter, so the condition is still true, and an `if` is enough. In the demo, the search confirms it.

**Mesa semantics** (Lampson and Redell, 1980) only move the waiter to the ready state. The signal is a hint: "look again". Other threads can run first. Almost every real system uses Mesa semantics, because a handoff forces two extra context switches and makes the scheduler less free.

A second reason is **spurious wakeups**. POSIX allows `pthread_cond_wait` to return with no signal at all. This lets implementations stay simple, and it also covers signal delivery. C++ and Rust document the same rule. So always write a loop. `std::condition_variable::wait` has a form that takes a predicate and contains the loop.

```rust
let mut q = m.lock().unwrap();
while q.is_empty() {
    q = cv.wait(q).unwrap();      // releases q; takes it again before it returns
}
let item = q.pop();
```

The Linux kernel has the same pattern. `wait_event(wq, condition)` is a macro with the loop inside. It sets the task state before it checks the condition, so a wake between the check and `schedule()` is not lost.

## Signal or broadcast

Use signal when any one waiter can use the event, and all waiters wait for the same condition. Use broadcast when the event can help many waiters, or when waiters wait for different conditions on one condition variable.

The third step above shows the danger. One condition variable served two conditions: "not full" and "not empty". A signal can wake a thread of the wrong kind, and that thread goes back to sleep, and the signal is gone. The better fix is two condition variables, one for each condition. Then signal is correct again.

Broadcast is always correct, if the check is a loop. It has a cost.

1. With 64 waiters and one item at a time, `signal` causes 64 wakeups and no sleep again.
2. `broadcast` causes 2080 wakeups and 2016 sleeps again. Each item wakes all remaining waiters, and only one of them gets the item.
3. The formula for wakeups is `W(W + 1)/2`. Move the slider, and compare.
4. Read the CPU column. At a model input of 2 µs for each sleep or wake, broadcast costs 8.19 ms, and signal costs 128 µs.

This is the **thundering herd**: many threads wake for one event. The same thing occurs with sockets: many processes sleep in `accept()` or `epoll_wait()`, and one connection arrives. Linux has `WQ_FLAG_EXCLUSIVE` wait queue entries, and `EPOLLEXCLUSIVE` since 4.5, to wake only one.

## The lost wakeup

The check and the sleep must look atomic to the notifier. Suppose that a waiter unlocks, and only then joins the queue. A notifier can run in that gap. It changes the state and signals, and nobody is in the queue. Then the waiter joins and sleeps forever.

Here the mutex protects the check, and `wait` joins the queue before it releases the mutex. So a notifier that holds the mutex cannot run in the gap. This is why a notifier must change the state under the mutex. It may call `signal` after it unlocks, which can avoid a wake that blocks at once on the mutex. It must not change the state with no lock.

## A condition variable on a futex

Rust's standard library builds its Linux condition variable on one futex word. The word is a sequence number. It is short enough to read in full.

```rust
pub fn notify_one(&self) {
    self.futex.fetch_add(1, Relaxed);
    futex_wake(&self.futex);
}
pub unsafe fn wait(&self, mutex: &Mutex) {
    let seen = self.futex.load(Relaxed);  // read before the unlock
    mutex.unlock();
    futex_wait(&self.futex, seen, None);  // sleeps only if no notify has run
    mutex.lock();
}
```

The gap between the unlock and the sleep is real here. The [value check](/os/sync/futexes) closes it: a notify in the gap changes the word, so `futex_wait` returns at once.

glibc needs more. POSIX requires that a signal wakes only threads that started to wait before it. Since glibc 2.25, `pthread_cond_t` uses two groups of waiters to give this guarantee, and it is a much larger piece of code.

## Monitors

A **monitor** is a language construct: data, a mutex that the compiler adds to each method, and condition variables. Java has `synchronized`, with `wait` and `notifyAll`. Rust gets a similar safety from its types. `Mutex<T>` holds the data, so you cannot touch the data with no lock.

## Channels in Go

Go offers another style. A channel combines the buffer, the lock and the wait queues into one object. The runtime type `hchan` has a ring buffer, a mutex, and two queues of parked goroutines (`recvq` and `sendq`).

```go
items := make(chan Item, 16)
go func() { items <- produce() }()   // blocks if the buffer is full
x := <-items                         // blocks if the buffer is empty
```

A send hands the value straight to a waiting receiver if one exists. That is a Hoare-style handoff, so the receiver needs no loop. `select` waits on several channels at once, which is hard with condition variables. Go also has `sync.Cond`, but channels are usually clearer. A channel transfers ownership of a value, and a condition variable says only that some shared state changed.
