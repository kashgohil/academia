A user-space spinlock wastes the CPU when the wait is long. A kernel lock needs a [system call](/os/processes/system-calls) for each lock and unlock, even with no contention. Most locks have no contention most of the time. So we want a lock that stays in user space when it is free, and that asks the kernel for help only to sleep.

A **futex** (fast user-space mutex) does this. Linux added it in the 2.6 series. The lock state is one 32-bit word in the memory of the program, and the kernel keeps only a queue of sleeping threads. The kernel does not know what the word means. It offers two main operations.

- `FUTEX_WAIT(addr, expected)`: if the word at `addr` still equals `expected`, sleep. If not, return `EAGAIN` at once.
- `FUTEX_WAKE(addr, n)`: wake up to `n` threads that sleep on `addr`.

glibc has no wrapper function, so C code calls `syscall(SYS_futex, ...)`.

## The lost wakeup

The window is between two events: the check in user space, and the sleep in the kernel. A **lost wakeup** occurs if the wake falls in that window.

The kernel closes it in `futex_wait`. It takes the lock of the hash bucket, reads the user word, and compares it. If the value matches, it joins the wait queue before it drops the bucket lock. `FUTEX_WAKE` takes the same bucket lock.

So there are two cases. If the wake runs before the comparison, the waker's change to the word is visible. If the wake runs after it, the wake finds the thread in the queue.

The waker must change the word before it calls `FUTEX_WAKE`. That rule is on the user-space code. The tests for this lesson search every schedule: with 2 threads and 2 rounds (1050 states), and with 3 threads and 1 round (2138 states). The correct mutex never gets stuck.

## The kernel side

The kernel does not create an object for each futex. A word with no waiters costs the kernel nothing. So there is one table of **hash buckets** (`futex_queues` in `kernel/futex/`). Each bucket has a spinlock and a priority-sorted list of waiters. The table has `256 × CPUs` buckets, rounded up to a power of two. Recent kernels can also give a process its own private table.

The key of a private futex is the address space and the virtual address. A shared futex, in [shared memory](/os/ipc/shared-memory), uses the inode and the page offset, because two processes can map the same word at different addresses. The `FUTEX_PRIVATE_FLAG` tells the kernel to skip that lookup. glibc passes it for normal mutexes.

## The 3-state mutex

Now look at the obvious mutex, with 0 for free and 1 for held. Unlock has a problem: it cannot know if anyone sleeps. So it must call `FUTEX_WAKE` every time. That is one syscall for each unlock, even for a lone thread.

Ulrich Drepper's paper "Futexes Are Tricky" gives a word with three states. 0 is free. 1 is held with no waiters. 2 is held with possible waiters.

```c
void lock(atomic_int *val) {
    int c = cmpxchg(val, 0, 1);           // returns the old value
    if (c != 0) {
        do {
            if (c == 2 || cmpxchg(val, 1, 2) != 0)
                futex_wait(val, 2);       // sleep only if val is still 2
        } while ((c = cmpxchg(val, 0, 2)) != 0);
    }
}
void unlock(atomic_int *val) {
    if (atomic_fetch_sub(val, 1) != 1) {  // old value was 2
        atomic_store(val, 0);
        futex_wake(val, 1);
    }
}
```

A woken thread sets the word to 2, not to 1, because other waiters may still sleep. So the last waiter causes one wake that finds nobody. That is why the slow path in the first demo makes 3 syscalls, not 2. This is the price of a word that has no waiter count.

## More operations

- **`FUTEX_CMP_REQUEUE`** wakes some waiters and moves the rest to another futex with no wakeup. Consider a condition variable broadcast with 100 waiters. If all wake, 99 of them block at once on the mutex. Requeue moves them straight to the mutex queue.
- **Priority inheritance futexes** (`FUTEX_LOCK_PI`, `FUTEX_UNLOCK_PI`) use a defined word format: the owner's thread ID, plus a waiters bit. Because the kernel can read the owner, it can raise the owner's priority. It uses an `rt_mutex` inside. See [real-time scheduling](/os/scheduling/real-time-scheduling).
- **Robust futexes** let the kernel mark a lock when its owner dies.
- **futex2** adds new calls. `futex_waitv` (Linux 5.16) waits on several words at once, and the Proton compatibility layer uses it. Linux 6.7 added separate `futex_wake`, `futex_wait` and `futex_requeue` calls.

## Who builds on it

| Runtime | Lock | Details |
|---|---|---|
| glibc | `pthread_mutex_t` | The low-level lock has states 0, 1 and 2. The slow path, `__lll_lock_wait`, swaps 2 into the word and sleeps |
| Rust std on Linux | `std::sync::Mutex` | States 0, 1 and 2. It spins for a bounded number of checks, and then it calls `futex_wait` |
| Go | `sync.Mutex` | It parks the goroutine on a runtime semaphore, with no kernel sleep. Threads with no work sleep on a futex inside the runtime |
| Zig | `std.Thread.Futex` | One portable API with a backend for each operating system |

```rust
// The fast paths of a Rust-style futex mutex.
const UNLOCKED: u32 = 0; const LOCKED: u32 = 1; const CONTENDED: u32 = 2;

pub fn lock(&self) {
    if self.futex.compare_exchange(UNLOCKED, LOCKED, Acquire, Relaxed).is_err() {
        self.lock_contended();   // spin, then swap in CONTENDED, then futex_wait
    }
}
pub fn unlock(&self) {
    if self.futex.swap(UNLOCKED, Release) == CONTENDED {
        futex_wake(&self.futex); // only if someone may sleep
    }
}
```

<Callout title="macOS">
XNU has no futex syscall. The closest equivalents are `__ulock_wait` and `__ulock_wake`, which are private calls. libc++ uses them for `std::atomic::wait`. Since macOS 14.4, `os_sync_wait_on_address` is the public API. The idea is the same: compare a word, then sleep on its address. To count futex calls on Linux, run `strace -f -c -e futex ./prog`. That command does not exist on macOS.
</Callout>
