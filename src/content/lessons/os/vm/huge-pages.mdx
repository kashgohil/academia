A **huge page** is a page that one upper-level entry maps. On x86-64, a PD entry with the PS bit maps 2 MiB, and a PDPT entry with the PS bit maps 1 GiB. The walk ends early, with 3 reads or 2 reads instead of 4. The main gain, however, is in the TLB: one 2 MiB entry maps 512 times more memory.

## Two ways to get them

**hugetlbfs** is the explicit way. An administrator reserves a pool of huge pages, and programs map from it. The pool is set by `/proc/sys/vm/nr_hugepages`. Reserve the 1 GiB pool at boot, with `hugepagesz=1G hugepages=N` on the kernel command line. Later, 1 GiB of contiguous free memory is rare. These pages are not swapped, and a fault never needs compaction.

```c
void *p = mmap(NULL, 1UL << 30, PROT_READ | PROT_WRITE,
               MAP_PRIVATE | MAP_ANONYMOUS | MAP_HUGETLB | MAP_HUGE_2MB, -1, 0);
// MAP_FAILED if the pool does not have enough pages
```

The cost is planning. Reserved memory is unavailable for other uses, even if nobody maps it. PostgreSQL uses this way, with `huge_pages = try` by default for its shared memory, and it falls back to small pages if the pool is empty.

**Transparent Huge Pages (THP)** is the automatic way. The kernel gives a program huge pages without any change to the program. Its controls are in `/sys/kernel/mm/transparent_hugepage/`:

A region must be aligned to 2 MiB and large enough. A program that opts in usually aligns its own block:

```c
size_t huge = 2UL << 20;
char *raw = mmap(NULL, len + huge, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
char *p = (char *)(((uintptr_t)raw + huge - 1) & ~(huge - 1));
madvise(p, len, MADV_HUGEPAGE);
```

Check the result in `AnonHugePages` in `/proc/meminfo`, or per mapping in `/proc/<pid>/smaps`. `thp_fault_alloc`, `thp_fault_fallback` and `compact_stall` in `/proc/vmstat` show how it went. These files do not exist on macOS.

## Physical memory is the hard part

A 2 MiB page needs 512 contiguous frames, aligned to 2 MiB. After a machine has run for a while, free memory is plentiful, but it is scattered in small holes. This is [fragmentation](/systems/allocators/fragmentation) at the page level.

**Compaction** moves movable pages out of a block, so that the block becomes free. Each move must unmap the page, flush the TLB, copy the page, and map it again. `kcompactd` does this in the background. **Direct compaction** does it inside the fault, and the program waits. **Pinned** pages cannot move: kernel slab pages, DMA buffers and pages held by `mlock` or `get_user_pages` can all block a region.

**khugepaged** is a kernel thread that fixes the fallback later. It scans a process, finds a 2 MiB range of small pages, allocates a huge page, copies the data, and replaces the PMD. This needs a write lock on the whole address space for part of the work, and a TLB flush. `MADV_COLLAPSE` asks for the same work directly.

## Why databases often turn THP off

THP helps long-running compute with large dense heaps. Databases often have the opposite pattern:

- **Latency spikes.** Direct compaction, and khugepaged holding locks, stop a thread at unpredictable times. A database cares about its slowest requests more than its mean.
- **Memory bloat.** One touched byte makes 2 MiB resident. With 8 touched pages per region, the model uses 64 times more memory. The default `max_ptes_none` of 511 lets khugepaged do the same to a region with only one page in it. A sparse allocator can run out of memory this way.
- **Write amplification after fork.** A copy-on-write fault on a huge page can copy 2 MiB instead of 4 KiB. Redis forks for its snapshots, and its documentation asks operators to turn THP off for this reason.
- **Freed memory stays resident.** If an allocator frees part of a huge page, the kernel must first split the page before it can reclaim the rest.

Advice differs by product and version, so read the current documentation for yours. MongoDB and Oracle have long advised turning THP off. MongoDB 8.0 changed this advice, because its new allocator handles huge pages well. A good middle setting is `enabled=madvise` with `defrag=madvise`: only programs that ask get huge pages, and only they pay for compaction.

## Between 4 KiB and 2 MiB

The jump from 4 KiB to 2 MiB is large. Recent systems fill the gap.

**Folios** (Linux 5.16 and later) let the kernel treat a contiguous group of pages as one object. Much of its memory code then stops assuming one size. **Multi-size THP (mTHP)**, from Linux 6.8, uses them for anonymous memory. The THP folder gains controls such as `hugepages-64kB/enabled`. A 64 KiB block is far easier to find than a 2 MiB block, and it causes less bloat. On arm64, 16 PTEs that map 64 KiB of contiguous memory can set the **contiguous bit** and share one TLB entry.

A **larger base page** is the other route. Apple Silicon uses 16 KiB pages under macOS, and Android 15 added support for them. Each entry reaches 4 times further, and all programs gain without compaction, because every page has this size. The costs are internal waste for small mappings, and software that assumes 4 KiB. The Linux controls above do not exist on macOS, so the base page is the main lever that you have there.
