Paging divides virtual memory into fixed-size **pages** and physical memory into **frames** of the same size. On x86-64 the base size is 4 KiB. An address has two parts. The low 12 bits are the **offset** in the page, and the CPU does not translate them. The rest is the **virtual page number**. A **page table** maps each virtual page number to a frame.

The hardware reads this table itself, with a unit called the **page walker**. The kernel only writes the table. The table lives in ordinary memory, so each translation can cost several memory reads.

## Why a flat table fails

The simplest table is one array with one entry per virtual page.

<Steps>
<div>A 48-bit address space with 4 KiB pages has $2^{48-12} = 2^{36}$ virtual pages.</div>
<div>Each entry takes 8 bytes, so the array takes $2^{36} \times 8 = 2^{39}$ bytes. This is 512 GiB, for each process.</div>
<div>The array must exist in full, because the hardware finds an entry by indexing. Even a process with one page would need all of it.</div>
<div>A 32-bit system with 4-byte entries needs only $2^{20} \times 4$ bytes, which is 4 MiB. Flat tables were a real choice then. They are not now.</div>
</Steps>

Programs use a very small part of this range, with large gaps. A sparse structure fits this better.

## The radix tree

The fix is a **radix tree**. A table is one page, and it holds $4096 / 8 = 512$ entries, so one level consumes 9 bits. Four levels give $9 + 9 + 9 + 9 + 12 = 48$ bits. A table exists only if something below it is mapped. One empty entry at the top removes 512 GiB of address range, and it needs no tables below it.

| Level | Intel name | Linux name | One entry maps | Bits of the address |
|---|---|---|---|---|
| 1 | PML4 | `pgd` | 512 GiB | 47 to 39 |
| 2 | PDPT | `pud` | 1 GiB | 38 to 30 |
| 3 | PD | `pmd` | 2 MiB | 29 to 21 |
| 4 | PT | `pte` | 4 KiB | 20 to 12 |

Linux has a generic fifth level, `p4d`, which folds away on a 4-level system. **CR3** is the register that holds the physical address of the top table. A context switch to another process writes CR3, and this switches the whole address space. Each entry holds a physical frame number, not a virtual address. The walker has no translation for its own reads, so physical addresses are the only choice.

This is the walk, in Rust. The real one is hardware:

```rust
fn walk(cr3: u64, va: u64, phys: &[u64]) -> Result<u64, Fault> {
    let mut table = cr3 & ADDR_MASK;
    for level in (0..4).rev() {
        let shift = 12 + 9 * level;
        let index = (va >> shift) & 0x1ff;
        let entry = phys[((table + index * 8) / 8) as usize];   // one memory read
        if entry & P == 0 { return Err(Fault::NotPresent { level }); }
        if level == 0 || entry & PS != 0 {                      // a leaf: 4 KiB, 2 MiB or 1 GiB
            let mask = (1u64 << shift) - 1;
            return Ok((entry & ADDR_MASK & !mask) | (va & mask));
        }
        table = entry & ADDR_MASK;
    }
    unreachable!()
}
```

## Entry bits

A leaf entry holds a frame number and these bits:

| Bit | Name | Meaning |
|---|---|---|
| 0 | P (present) | The entry is valid. If it is clear, the CPU raises a page fault, and the other bits belong to the kernel. |
| 1 | RW (writable) | Writes are allowed. |
| 2 | US (user) | User mode can use the page. |
| 5 | A (accessed) | The CPU sets it on use. Page replacement reads and clears it. |
| 6 | D (dirty) | The CPU sets it on a write. The kernel must save the page before it reuses the frame. |
| 7 | PS (page size) | In a PD or PDPT entry: this entry is a leaf, not a link to a table. |
| 8 | G (global) | The translation stays in the TLB across a CR3 write. The kernel uses it for its own pages. |
| 63 | NX (no execute) | An instruction fetch from this page raises a page fault. |

Rights combine along the path. The walker takes the AND of RW and US across all levels, and the OR of NX. Linux therefore keeps the upper levels permissive and sets the real rights in the leaf.

A very sparse pattern, with 1 page per 1 GiB, costs 2 GiB of tables for 1 GiB of data, or 200%. A completely full tree costs a little more than a flat table: 513 GiB against 512 GiB. The tree wins because real programs do not fill it. It loses only in the worst case, and only by about 0.2%.

Linux reports this memory. `VmPTE` in `/proc/<pid>/status` is the cost for one process, and `PageTables` in `/proc/meminfo` is the system total. The kernel frees tables on `munmap`, in `free_pgtables`. `MADV_DONTNEED` clears the PTEs and usually keeps the tables.

A large shared memory region, mapped by many processes, has one set of tables per process. This is a real cost for databases with many connections. Huge pages reduce it, as [the last lesson](/os/vm/huge-pages) shows.

## Five levels

48 bits limit a machine to 256 TiB of virtual range. **5-level paging (LA57)** adds one more level of 9 bits, for 57 bits and 128 PiB. The CR4.LA57 bit turns it on. Each walk then has 5 reads. Linux keeps ordinary programs in the lower 47 bits, because some programs hide tags in the top bits of pointers. A program gets a higher address only if it passes a high hint to `mmap`.

## arm64 and Apple Silicon

<Callout title="Granules">
arm64 can use a page size of 4 KiB, 16 KiB or 64 KiB. This is the **granule**. A table is still one page of 8-byte entries, so a larger page gives more bits per level. A 16 KiB granule has 2,048 entries per table, which is 11 bits. Three levels then cover 47 bits, and the first block size is 32 MiB. A 64 KiB granule has 8,192 entries, and its first block is 512 MiB. arm64 also has two table roots, TTBR0 and TTBR1, for the low and high halves.
</Callout>

macOS on Apple Silicon uses 16 KiB pages. Run `getconf PAGESIZE` on your Mac: a native process sees 16384. Code that assumes 4096 can break there. Ask the system instead, with `sysconf(_SC_PAGESIZE)` in C or `std.heap.pageSize()` in Zig. An `mmap` length or a guard page that is computed from a fixed 4096 is a common bug.
