A page walk costs up to 4 memory reads. If each load needed a walk, each load would cost 5 reads. The **translation lookaside buffer (TLB)** avoids this. It is a small cache in the CPU core that maps a virtual page number to a frame number and its rights. A hit costs almost nothing. A miss starts the walker, which fills the entry.

## Why translation must be cached

The cost of one miss grows with the depth of the tree, and virtual machines make it worse. A guest has its own page tables, and each guest table address is itself a guest physical address. The hardware must translate each one through the host tables. This is **nested paging** (EPT on Intel, NPT on AMD).

<VmNestedWalkDemo />

1. Keep 4 guest levels and 4 host levels. A miss can cost 24 reads: $(4+1)(4+1)-1$.
2. Set the host levels to 0. The cost falls to 4, which is the native walk.
3. Set both to 5. A miss can now cost 35 reads.

CPUs reduce this in two ways. **Paging-structure caches** keep upper-level entries, so a walk often needs only the last level. PTEs also live in the normal data caches. A typical walk is therefore much cheaper than the worst case. It is still far more than a hit.

## Structure

A modern core has two levels, as CPU caches do. The **L1 TLBs** are small and fast, with separate parts for instructions and data. The **L2 TLB** (STLB on Intel) is larger, and it serves both. Each TLB is **set associative**: the low bits of the page number select a set, and the entry can use any way in that set.

**TLB reach** is entries times page size. It is the memory that the TLB can map without a miss. It is the most useful single number about a TLB. Compare 6 MiB with the size of your last-level cache: on a large server, data can sit in the cache while its translation misses.

In this model, translation costs 5.2 cycles per access at 1 MiB, 15.0 at 16 MiB, 46.6 at 1 GiB, and 214.7 at 64 GiB. With 2 MiB pages, it costs 6.6 cycles at 1 GiB and 26.8 at 64 GiB. The model inputs are in `TRANSLATION_MODEL`. An L2 hit costs 7 cycles, and a walk costs 15 cycles plus one read of the PTE. The model does not include misses in the paging-structure caches, so it is low for very large sets.

This is why pointer-heavy code suffers twice. Each hop can miss the data cache and also the TLB, and the walk itself can miss the cache. A sorted array and a linked list can differ by more than the cache model predicts. To measure it on Linux:

```sh
perf stat -e dTLB-loads,dTLB-load-misses,cycles ./chase
```

`perf` does not exist on macOS. The Instruments app has a CPU Counters tool for this purpose.

## Address space tags

A TLB entry is only valid for one page table. The simple solution is to flush the TLB on every context switch, and early x86 CPUs did this. A write to CR3 still flushes everything except global entries, if the tag feature is off. The cost is not the flush, but the misses after it.

A **PCID** (process-context identifier) tags each entry with an address space. The tag has 12 bits, in the low bits of CR3, so 4,096 values exist. Entries of other address spaces stay in the TLB but do not match. If bit 63 of the new CR3 value is set, the write flushes nothing.

arm64 has the same idea under the name **ASID**, with 8 or 16 bits.

Linux does not give each process a permanent PCID. Each CPU keeps a small table of the 6 most recent address spaces (`TLB_NR_DYN_ASIDS`). A switch to one of them can skip the flush. KPTI also uses PCIDs. The user tables and the kernel tables of one process have different tags, so a system call does not lose the TLB.

The **global bit** handles the other case. The kernel half is the same in all address spaces, so its entries match any tag, and they survive a CR3 write.

## Shootdowns

The TLB is a cache that the hardware does not keep coherent on x86. If the kernel changes a PTE, other cores can keep the old translation. This is dangerous. Suppose that a core keeps a stale entry after `munmap`, and the kernel gives the frame to another process. A thread with the stale entry can then read and write the memory of that process.

The kernel must therefore invalidate the entry on each core that may hold it. On x86, one core cannot do this for another, so it sends an **inter-processor interrupt (IPI)**. This is a **TLB shootdown**. The sender also waits, because the kernel must not free the frame until every core has acknowledged.

<VmShootdownDemo />

1. Press **Replay**. The sender spins while the IPIs go out. Each target stops your code, runs a handler, and acknowledges.
2. Move the core count from 2 to 128. The sender's wait grows slowly, but the time on all cores together grows with N.
3. Set the pages above 33. Linux now flushes the whole TLB on each target, and the model adds the cost of the later misses.
4. Select **Hardware broadcast**. arm64 has `TLBI` instructions that reach all cores, and no IPI is needed.

With the model inputs in `SHOOTDOWN_MODEL`, one page on 32 cores makes the caller wait 3.25 µs and costs 40.45 µs across all cores. On 128 cores, these become 8.05 µs and 160.45 µs. One thread that calls `munmap` often can therefore slow down every other thread of its process. The mechanism is the reason why allocators delay returning memory.

Linux reduces the work in several ways:

- `mm_cpumask` records which CPUs ran this address space, and only those CPUs get an IPI.
- A CPU that runs a kernel thread can be in **lazy TLB** mode. It skips the IPI and flushes when it next returns to a user address space.
- `munmap` gathers its pages in a `struct mmu_gather`, and it frees frames only after the flush.
- `flush_tlb_mm_range` flushes one page at a time up to `tlb_single_page_flush_ceiling`, which is 33 by default. Beyond this, it flushes the whole TLB.

The count of shootdowns is in `/proc/interrupts`, on the line named TLB. Recent AMD CPUs add `INVLPGB`, a broadcast invalidate, which can remove the IPI.
