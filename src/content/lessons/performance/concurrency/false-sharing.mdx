A core can write to a cache line only when it owns the line. When a different core writes to the same line, the line must move to that core. This move takes about 40 ns.

**False sharing** occurs when threads write to different variables in the same cache line. The threads share no data. But the hardware sees one line, and it moves the line on each write.

Do these steps:

1. Watch the dark bar. It is the cache line. It moves to the core that writes next.
2. Look at **line transfers**. Almost every increment causes one.
3. Turn on **Put each counter on its own cache line**. Each core now keeps its own line. The transfers stop.

## How much it costs

<FalseSharingScalingDemo />

With one cache line, more threads do not help. The throughput stays at about 43 million increments per second. With separate lines, the throughput increases with each thread. At 8 threads, separate lines are about 66 times faster.

## How to prevent it

- Put each hot field that a thread writes on its own cache line.
- Use 128 bytes, not 64, on x86. The adjacent-line prefetcher fetches lines in pairs. Rust's `crossbeam_utils::CachePadded` uses 128 for this reason.
- Use the language tools:

```rust
#[repr(align(128))]
struct Padded(AtomicU64);
```

```zig
const Padded = struct { value: std.atomic.Value(u64) align(std.atomic.cache_line) };
```

```cpp
struct alignas(std::hardware_destructive_interference_size) Padded { std::atomic<uint64_t> value; };
```

- Keep data that only one thread writes in that thread's own memory. Combine the results at the end.

## How to find it

Run `perf c2c record`, then `perf c2c report`. The report shows cache lines with many "HITM" events. A HITM is a load that found the line modified in a different core's cache. Look for lines where different threads write different offsets.
