A **micro-benchmark** measures how long a small piece of code takes. The simple method is to read the clock, run the code, and read the clock again. This method can be wrong by a factor of 1000 or more. This lesson shows each problem and its fix.

## Problem 1: the clock is too coarse

A clock reading changes only at each tick. If the code is shorter than one tick, most readings show 0.

<QuantizationDemo />

1. Set the true time to 300 ns and the clock tick to 1 µs. Most readings are 0. Some readings are 1000 ns.
2. Set **Runs per measurement** to 100. Each measurement now covers many ticks. Divide by 100 to get the time of one run.
3. Set the clock tick to 1 ns. Now one run is enough.

Apply the fixes in this order:

1. Turn on **Keep the result alive**. The work now runs, but the median is still 0. The clock is too coarse.
2. Set **Iterations per timing** to 1000. The median is now 40 ns.
3. Turn on **Discard warm-up samples**. The first samples are slow because the caches are cold. Removing them makes the mean correct.
4. Turn on **Thermal throttling**. The later samples become about 25% slower. A long benchmark can measure the temperature of the chip, not the code.
5. Look at the points at the top. Interrupts and context switches cause them. Report the median, not the mean.

## Problems and fixes

| Problem | Symptom | Fix |
|---|---|---|
| Dead-code elimination | impossibly fast, often 0 | `std::hint::black_box` (Rust), `benchmark::DoNotOptimize` (C++), `std.mem.doNotOptimizeAway` (Zig) |
| Constant folding | the same, when inputs are constants | pass the inputs through `black_box` too |
| Clock resolution | readings of 0 or of whole ticks | time many runs per measurement |
| Warm-up | the first samples are slow | run and discard warm-up iterations |
| Frequency changes | samples drift up or down | fix the CPU frequency, or interleave A and B |
| Noise | outliers on the slow side | use many samples; report the median and the spread |
| Unrealistic state | hot caches and perfect branch prediction | use realistic data sizes and inputs |

The last row is easy to forget. A loop that calls one function a million times with the same input measures the best case. Real code has cold caches and unpredictable inputs. Use micro-benchmarks to compare two versions. Then measure the full program.

## Use a benchmark tool

Criterion (Rust), Google Benchmark (C++), `testing.B` (Go) and JMH (Java) do batching, warm-up, outlier handling and result sinks for you. For Zig, use a small loop with `std.time.Timer` and `doNotOptimizeAway`, or the zBench library.
