A micro-benchmark has one job: report how long a piece of code takes. The naive version (read the clock, call the function, read the clock again) fails in several independent ways, each of which can be off by orders of magnitude. The demo times a function that truly costs **40 ns**, with every pitfall present, and lets you apply the fixes one by one.

Apply the fixes in order and watch the median:

1. **Keep the result alive** (`black_box`): the work now happens, but the median is still 0 because of clock granularity.
2. **1000 iterations per timing**: the measured interval is about 40 µs, so the clock's resolution no longer matters. The median reads 40 ns.
3. **Discard warm-up samples**: the first samples run slow (cold caches, page faults, JIT tiers, frequency ramp-up). Dropping them pulls the mean down.
4. **Thermal throttling**: turn it on and the later samples drift up 25%. A benchmark that runs long enough to heat the chip measures the thermals, not the code.
5. The scattered high points are **interrupts and context switches**. They're why you report the median, not the mean.

## The pitfalls, and what harnesses do about them

| Pitfall | Symptom | Fix |
|---|---|---|
| Dead-code elimination | impossibly fast (often ~0) | `std::hint::black_box` (Rust), `benchmark::DoNotOptimize` (C++), `std.mem.doNotOptimizeAway` (Zig), keep results in a sink (Go: assign to a package-level var) |
| Constant folding | same, when inputs are compile-time constants | feed inputs through `black_box` too |
| Timer resolution and overhead | quantized readings; clock cost dominates | time many iterations per sample; use a monotonic high-resolution clock |
| Warm-up | early samples slow | run warm-up iterations first and discard them |
| Frequency scaling | drift up or down over the run | fix the frequency (`cpupower frequency-set -g performance`), disable turbo for comparisons, or interleave A and B |
| Noise (interrupts, other processes) | outliers, right skew | many samples; report median and spread; pin to a quiet core (`taskset`, `isolcpus`) |
| Unrealistic state | hot caches and perfectly predicted branches every iteration | benchmark with realistic data sizes and orders; vary inputs |

The last row is the subtle one. A loop that calls the same function on the same input a million times measures the **best case**: everything in L1 and every branch predicted. Real code gets cold caches and unpredictable inputs. Use micro-benchmarks to compare alternatives, then confirm with a whole-program measurement.

## Use a harness

Criterion (Rust), Google Benchmark (C++), `testing.B` (Go), `std.time.Timer` with a hand-rolled loop or the `zbench` library (Zig), and JMH (Java) already handle batching, warm-up, outliers and result sinks. They exist because everyone who writes the loop by hand gets at least one of these wrong.
