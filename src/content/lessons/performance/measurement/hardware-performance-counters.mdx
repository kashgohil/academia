A timer tells you that code is slow. The CPU can tell you why. Each modern core has **performance counters**. They count events such as cycles, instructions, cache misses and branch mispredictions. They cost almost nothing. `perf stat` reads them:

```
perf stat -e cycles,instructions,branch-misses,cache-misses ./app
```

Read **IPC** (instructions per cycle) first. A modern core can complete 4 to 6 instructions per cycle. An IPC below 1 means that the core waits during most cycles.

## Where the pipeline slots go

The **top-down method** (Ahmad Yasin, Intel, 2014) looks at every pipeline slot. A 4-wide core has 4 slots in each cycle. Each slot gets one of five labels.

<PipelineSlotsDemo />

1. Select **Branch on random data**. Red blocks appear after each misprediction. Each block is about 16 cycles of wasted slots.
2. Select **Pointer chase**. Almost all slots are orange. The core waits for memory.
3. Select **Sequential sum**. Most slots are green. The core does useful work.

| Label | Meaning | Typical fix |
|---|---|---|
| Retiring | useful work | do fewer instructions: a better algorithm, SIMD |
| Bad speculation | work that the CPU discards after a wrong branch prediction | make branches predictable, use branchless code, sort the data |
| Frontend bound | the core cannot get instructions fast enough | make the hot code smaller, use PGO and LTO |
| Backend: memory | the core waits for loads | improve locality, make the data smaller |
| Backend: core | the core waits for execution units or dependency chains | break dependency chains |

Use `perf stat -M TopdownL1`, `toplev` (pmu-tools), VTune or AMD uProf.

## Practical notes

- There are only 4 to 8 counters per core. If you request more events, perf shares the counters over time and scales the results. Then it shows percentages in brackets.
- Virtual machines often hide the counters. Measure on real hardware when possible.
- `perf c2c` finds false sharing. `perf mem` measures load latency.
