A **profiler** shows where a program spends its time. There are two types:

- A **sampling profiler** stops the program at regular intervals and records the function that runs. A function that runs 20% of the time appears in about 20% of the samples. Examples are perf, Instruments, VTune, pprof and samply.
- An **instrumenting profiler** adds timing code at the start and end of each function. Examples are gprof (`-pg`) and Valgrind's callgrind.

## How sampling works

2. Look at the bars. They show the share of samples for each function. The black marks show the true share of time.
3. Set more samples per time unit. The bars get close to the marks faster.

1. Set **100 Hz**. The run gives only about 45 samples. Small functions get 0 samples, or very wrong shares.

## How accurate is sampling?

Each sample is independent. A function that takes a fraction p of the time gets a share of samples with this standard error:

$$\text{SE} = \sqrt{\frac{p(1-p)}{n}}$$

With 1000 samples, a 25% function is correct within about ±2.7 points. Collect a few thousand samples in the code that you study. Ignore functions with only a few samples.

## Limits of sampling

- **Skid**: the profiler can report an instruction that is a few instructions after the real one. Use precise events: `perf record -e cycles:pp`.
- **Inlined functions**: they have no stack frame. Build with debug information, so the profiler can show them.
- **Missing stacks**: without frame pointers, stack walks fail. Compile with `-fno-omit-frame-pointer` (Rust: `-C force-frame-pointers=yes`), or use `perf record --call-graph dwarf`.
- **Waiting time**: a CPU profiler does not see time that a thread waits for I/O or locks. Use an off-CPU profiler for that.

Instrumentation is good for exact call counts and for traces of one request (OpenTelemetry, Tracy). Do not use it to find hotspots.
