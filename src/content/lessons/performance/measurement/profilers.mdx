A profiler answers "where does the time go?". There are two ways to ask:

- **Sampling**: interrupt the program at regular intervals (or every N hardware events), record the current stack, and count. A function's share of samples estimates its share of time. `perf`, Instruments, VTune, `pprof`, py-spy and samply all work this way.
- **Instrumentation**: insert timing code at every function entry and exit and add up exact durations. Valgrind's callgrind, compiler `-pg` / gprof and tracing frameworks work this way.

Instrumentation sounds more accurate. For finding hotspots, it usually isn't.

## How accurate is sampling?

Each sample is an independent draw, so a function that truly takes fraction $p$ of the time gets a sample share with standard error

$$\text{SE} = \sqrt{\frac{p(1-p)}{n}}.$$

With $n = 1000$ samples, a 25% function is measured within about ±2.7 points (95%), and a 4% function within ±1.2. Most profilers default to around 1–4 kHz. Profile long enough to collect a few thousand samples in the code you care about, and ignore functions with a handful of samples.

## What sampling gets wrong

- **Skid**: the reported instruction is often a few instructions after the one that caused the event. Use precise events (Intel PEBS, AMD IBS: `perf record -e cycles:pp`) when you look at individual instructions.
- **Inlining**: inlined functions don't have frames. Build with debug info so the profiler can recover inline frames from DWARF.
- **Missing stacks**: frame-pointer-less builds break stack walking. Compile with `-fno-omit-frame-pointer` (or Rust `-C force-frame-pointers=yes`), or use DWARF or LBR unwinding (`perf record --call-graph dwarf|lbr`).
- **Off-CPU time**: a CPU sampler doesn't see time spent *blocked* (I/O, locks, sleep). Use off-CPU profiling (`perf sched`, eBPF `offcputime`) or wall-clock sampling for latency questions.

## Instrumentation's place

Instrumentation gives exact **call counts** and full traces, which samplers can't. Use it for "how many times is this called?", for causal traces of a single request (OpenTelemetry spans, Tracy, `tracing` in Rust), and on coarse boundaries where the overhead is negligible. Don't use per-function instrumentation for hotspot ranking.
