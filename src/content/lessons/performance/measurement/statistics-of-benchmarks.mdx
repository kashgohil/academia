Two runs of the same code take different times. The difference is often a few percent. So "my change made it 3% faster" is a statistical claim. You must show that the difference is larger than the noise.

## The noise is not symmetric

Timing noise has a long slow tail. Interrupts, page faults and context switches make some runs much slower. They never make a run faster than the code allows.

<MeanMedianDemo />

1. Set the interrupt share to 0%. The mean and the median are almost equal.
2. Set the share to 5% and the slowdown to 20×. The mean moves far to the right. The median stays near 100 ns.
3. So compare medians, not means.

1. Click **Run a new experiment** several times with 30 samples. The verdict changes, but the code and the true speedup do not change.
2. Set the speedup to **0%**. Now each "faster" verdict is a false positive. It occurs in only a few percent of experiments.
3. Set the speedup to **1%**. Even 1000 samples find it only sometimes.

## How to compare two versions

<Steps>
<div>Compare medians, not means.</div>
<div>Calculate a confidence interval with a bootstrap. Resample each set of timings many times. Calculate the ratio of the medians each time. Use the middle 95% of the ratios.</div>
<div>Choose the number of samples for the effect that you want to see. Half the effect needs about 4 times the samples.</div>
<div>Run A and B in turns (A, B, A, B), not all of A and then all of B. Then slow changes in the machine affect both versions equally.</div>
<div>Report the interval, for example "B/A = 0.97 [0.95, 0.99]".</div>
</Steps>

Tools: Criterion.rs reports a bootstrap interval. `hyperfine` does the same for full commands. Go's `benchstat` uses a Mann-Whitney U test and shows `~` when a difference is not significant.

<Callout kind="warn" title="Many benchmarks, many false results">
With 40 benchmarks and a 5% false-positive rate, you can expect about 2 false "changes". Be careful with one small win or loss in a large set of benchmarks.
</Callout>
