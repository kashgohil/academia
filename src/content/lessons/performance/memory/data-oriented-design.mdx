Object-oriented design groups data by **what it is**: an `Entity` holds its position, velocity, health, name, inventory and AI state, often behind a pointer for polymorphism. **Data-oriented design** (Mike Acton, the Bitsquid and Molly Rocket engines, Andrew Kelley's talks on Zig's compiler) groups data by **how it's used**: the loop that updates positions reads positions and velocities, so those live together, densely, and nothing else comes along.

The three layouts tell a story in two steps:

1. **Remove the pointers** (objects inline in an array): from about 98 ns to 4.75 ns. Accesses become predictable, so misses overlap.
2. **Remove the cold bytes** (hot fields in their own arrays): from 4.75 ns to about 1.2 ns. Each line now carries only data the loop uses, so the working set is 5× smaller and fits in cache.

Try **5,000** entities: everything fits in cache, and the gap shrinks to about 8×. Data-oriented layout pays most at scale.

## The method

<Steps>
<div><b>Start from the transformations</b>, not the nouns: what does each hot loop read and write, and how often?</div>
<div><b>Split hot from cold.</b> Fields touched every frame go in one place; rarely used ones (names, debug info, inventory) go elsewhere, linked by index.</div>
<div><b>Prefer arrays and indices to pointers.</b> Indices are smaller, survive reallocation, serialize trivially, and keep data contiguous. Use generational indices for safety (the pool allocator lesson).</div>
<div><b>Process in batches, by kind.</b> Instead of a virtual call per object (each a likely branch mispredict and i-cache miss), keep one array per kind and loop over each. Entity Component Systems (Bevy, EnTT, flecs) are this idea packaged.</div>
<div><b>Encode state in where data lives, not in flags.</b> Dead entities removed or moved to another array means no `if (alive)` branch in the hot loop.</div>
</Steps>

## Costs

Data-oriented code trades encapsulation for throughput. Invariants that a class would enforce are now spread across parallel arrays that must stay in sync, and adding a field means touching every system that copies entities. Apply it where profiles show memory-bound loops over many items: simulations, game engines, compilers (Zig's and Carbon's compilers use flat, index-based ASTs), databases, ML preprocessing. Keep ordinary design elsewhere.
