---
summary: Organize data by how the code uses it, not by what it represents. Objects behind pointers are the slowest layout.
---

Object-oriented design groups data by **what it is**. An `Entity` object has a position, a velocity, health, a name and an inventory. Often each object is behind a pointer.

**Data-oriented design** groups data by **how the code uses it**. The loop that moves entities reads positions and velocities. So the positions and velocities are stored together, with nothing else. Mike Acton, game engines and Andrew Kelley's Zig compiler made this approach popular.

## Hot bytes and cold bytes

<HotColdDemo />

1. Select **Objects** (128 bytes each). The update needs 24 bytes of each object. But the cache loads full 64-byte lines. Only 38% of the loaded bytes are useful.
2. Select **Hot arrays**. The positions are next to each other, and so are the velocities. All the loaded bytes are useful.

1. **Remove the pointers** (objects stored in the array): the time drops from about 98 ns to 4.75 ns. The accesses become predictable.
2. **Remove the cold bytes** (hot fields in their own arrays): the time drops to about 1.2 ns. The data is 5 times smaller and fits in the cache.
3. Select **5,000** entities. All layouts fit in the cache, and the difference is smaller.

## The method

<Steps>
<div>Start from the loops. Find what each hot loop reads and writes, and how often.</div>
<div>Split hot data from cold data. Put the fields that each frame uses in one place. Put names and debug data in another place.</div>
<div>Use arrays and indices, not pointers. Indices are smaller, and they stay valid when an array grows.</div>
<div>Process items in groups by type. One loop for each type is faster than a virtual call for each object.</div>
<div>Use the position of data to show its state. For example, keep dead entities in a different array, so the hot loop needs no `if alive` check.</div>
</Steps>

Data-oriented code is faster, but the invariants are less visible. Parallel arrays must stay in sync. Use this approach where a profile shows memory-bound loops over many items. Examples are simulations, game engines, compilers and databases. Entity Component Systems such as Bevy, EnTT and flecs package this approach.
