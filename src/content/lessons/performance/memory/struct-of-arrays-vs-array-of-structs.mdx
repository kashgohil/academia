You can store the same table of entities in two ways:

```rust
struct Particle { x: f32, y: f32, z: f32, w: f32 }
let aos: Vec<Particle>;                       // array of structs (AoS)

struct Particles { x: Vec<f32>, y: Vec<f32>, z: Vec<f32>, w: Vec<f32> }
let soa: Particles;                           // struct of arrays (SoA)
```

The cache loads full 64-byte lines. With AoS, a loop that reads one field still loads all the fields. With SoA, a loop loads only the arrays that it reads.

## See the layouts

<LayoutPictureDemo />

1. Select **AoS** and read 1 field. All 4 cache lines are loaded, but only 25% of the bytes are used.
2. Select **SoA**. Only 1 line is loaded. All its bytes are used.
3. Read all 4 fields. Now both layouts load the same lines.
4. Select **AoSoA**. Each block of 4 entities stores each field together. It is a mix of the two layouts.

## How to choose

| Layout | Good for | Problems |
|---|---|---|
| AoS | loops that use most fields; random access to whole items | wasted bandwidth when a loop reads few fields |
| SoA | loops over a few fields of many items; SIMD | random access to one item touches many lines |
| AoSoA | SIMD-sized blocks with good locality | complex indexing |
| Hot/cold split | the common case | the two parts must stay in sync |

<Callout title="A problem that SoA can have">
If each array size is a large power of two, the arrays start at addresses that use the same cache sets. Then the arrays can remove each other's lines from the cache. Allocators usually prevent this. Without that, the 16-field SoA case in this demo is slower than AoS.
</Callout>

Tools: Zig's `std.MultiArrayList(T)` stores a struct as SoA automatically. Rust has the `soa_derive` crate. ISPC and many ECS libraries use AoSoA.
