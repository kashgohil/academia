A bump allocator over a fixed buffer runs out of memory. An **arena** solves this problem. It bump-allocates inside **chunks**: large blocks that it gets from a **backing allocator**. The backing allocator can be the operating system, `malloc`, or a parent arena.

When the current chunk cannot hold a request, the arena leaves the rest of that chunk unused and opens a new chunk. A free of the arena gives back all chunks in one step. Zig's `std.heap.ArenaAllocator`, Odin's `mem.Arena` and `context.temp_allocator`, Rust's `bumpalo`, and C++'s `std::pmr::monotonic_buffer_resource` all work in this way.

## The cost model

Let $s$ be the typical allocation size, $C$ the chunk size and $h$ the header size. Then:

- **Header overhead** is $h/C$ of each chunk.
- **Unused tails** are about $s/2$ for each chunk, on average. So the wasted part of a chunk is about $(h + s/2)/C$. Make chunks large compared with typical allocations.
- **Backing calls** happen once for each chunk. Many arenas make each new chunk larger than the last, by a constant factor. Then a long-lived arena makes only $O(\log n)$ backing calls.

Things to try:

1. Keep $s$ at 64 B. With 4 KiB chunks, the measured waste is 1.4% and the estimate is 1.2%. With 256 B chunks, the waste is 22%.
2. Move $s$ to 256 B or more. The waste goes up for all small chunks. When $s$ is near $C$, the estimate is not accurate, because large requests get their own chunks.
3. Move $s$ to 8 B. Now the headers are most of the waste, and the two lines are almost the same.

Allocation is a bump in the common case. The real memory cost of an arena is its **high-water mark**: the largest amount of memory it held at one time. The arena keeps that memory until a reset.

## Design with lifetimes

The power of an arena is in the program design. You do not track each object. You connect a group of objects to an event, and one reset frees the full group.

Things to try:

1. Click **Play** with **Every frame**. The arena holds 2 chunks (2 KiB) and makes 2 backing calls in total. After 16 frames, `malloc` would need 320 calls to `free`. The arena needs 16 resets.
2. Select **Never**. The held memory goes up in each frame, to 18 KiB after 16 frames. This is a memory leak.
3. Select **Every 4 frames**. The used memory has a sawtooth shape. The arena now holds 5 KiB, not 2 KiB, because the data of 4 frames is alive at the same time.
4. Select **Every frame** and clear **Keep the chunks after a reset**. Now the arena gives its chunks back at each reset and gets new ones again. It makes 26 backing calls in 16 frames, not 2.
5. Move **Temporary objects per frame**. More objects need more chunks, but with a reset in each frame the count stops growing.

| Lifetime | Arena | Reset when |
|---|---|---|
| Frame (games, UIs) | scratch memory for each frame, often two buffers that alternate | the frame ends |
| Request (servers) | one arena for each request | the response is sent |
| Pass (compilers) | one arena for each phase: tokens, syntax tree, IR | the next phase has used the output |
| Call (any code) | scratch scope with mark and restore | the function returns |

```zig
var arena = std.heap.ArenaAllocator.init(std.heap.page_allocator);
defer arena.deinit(); // frees every chunk at once
const a = arena.allocator();
const tokens = try lex(a, source); // no individual frees anywhere
```

```odin
process :: proc(input: string) {
    defer free_all(context.temp_allocator)
    parts := strings.split(input, ",", context.temp_allocator)
    // ...
}
```

<Callout kind="warn" title="The failure mode: dangling pointers that do not crash">
After a reset, old pointers still point at valid, mapped memory. The arena now uses that memory for new data. A read through an old pointer does not crash. It returns data that belongs to a different object. Never let an arena pointer go into a structure that lives longer than the arena. Debug builds can **poison** memory on reset: they fill it with a pattern such as `0xAA`, so that these bugs are easy to see.
</Callout>
