A bump allocator owns a buffer and one integer, `top`. To allocate, round `top` up to the requested alignment, check the end, and advance it. That's the whole fast path: a few instructions, no metadata and no searching. Compilers use it for AST nodes, games for per-frame data, and it sits underneath Zig's `FixedBufferAllocator`, Odin's temp allocator and Rust's `bumpalo`.

## Alignment arithmetic

Hardware requires (or strongly prefers) that a value of size 8 sits at an address divisible by 8. Alignments are powers of two, which makes rounding up a bit trick:

<Steps>
<div>We want the smallest multiple of $a$ that is $\ge x$. Adding $a-1$ pushes $x$ past the next multiple, unless it's already on one.</div>
<div>For $a = 2^k$, "round down to a multiple of $a$" means "clear the low $k$ bits": AND with $\lnot(a-1)$.</div>
<div>Together: $\text{align\_up}(x, a) = (x + a - 1)\ \&\ \lnot(a - 1)$. For $x = 17, a = 8$: $(24)\ \&\ \lnot 7 = 24$.</div>
<div>The padding wasted is $\text{align\_up}(x, a) - x$, between $0$ and $a - 1$ bytes.</div>
</Steps>

```zig
const Bump = struct {
    buf: []u8,
    top: usize = 0,

    fn alloc(self: *Bump, n: usize, alignment: usize) ?[*]u8 {
        const start = std.mem.alignForward(usize, self.top, alignment);
        if (start + n > self.buf.len) return null;
        self.top = start + n;
        return self.buf.ptr + start;
    }
};
```

## Struct layout is the same problem

A compiler laying out a struct is a bump allocator running over its fields. Different languages handle this differently:

- **C, C++, Zig `extern struct`** keep declaration order, so field order decides padding. Sorting fields by decreasing alignment minimizes it.
- **Rust** (default `repr(Rust)`) and **Zig** (plain `struct`) may reorder fields to reduce padding. Use `#[repr(C)]` / `extern struct` when the layout must be fixed (FFI, file formats).
- **Odin** keeps declaration order by default; `#packed` removes padding, at the cost of unaligned access.

The total size is also rounded up to the struct's alignment, so that arrays of it stay aligned. `{double; char}` is 16 bytes, not 9.

## What "free" means here

A bump allocator can only reclaim memory at the top. In practice it supports:

- **LIFO frees**: freeing the most recent allocation rolls `top` back (a stack allocator).
- **Reset**: drop everything at once.
- **Mark / restore**: save `top`, do temporary work, restore it. This is a scoped stack, which is what *Begin scope / End scope* do.

Any other free just leaks until the next reset. That's not a defect: it is the design. **Bump allocation works when lifetimes are grouped**, so that many objects die at the same moment. When they aren't, use a pool or a general-purpose allocator.

| Property | Bump |
|---|---|
| alloc | O(1), ~3 instructions |
| free | O(1) at the top; otherwise a no-op |
| metadata per allocation | none |
| locality | perfect: allocations are contiguous in program order |
| fragmentation | none until you need individual frees |
