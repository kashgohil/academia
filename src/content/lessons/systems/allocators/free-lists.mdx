Some programs need blocks of any size, and they free them in any order. For this, the allocator must remember the size of each block and find free space. The classic design is the **free list**. K&R `malloc` and most textbooks use it.

Each block starts with a small **header**. The header records the size of the block and if the block is in use. To allocate, the allocator finds a free block that is large enough. It **splits** off the remainder as a new free block and returns the bytes after the header. To free, the allocator marks the block free. Then it **coalesces** the block with free neighbors: it joins them into one larger block.

Things to try:

1. Run **Fill, free all, ask for 1 KiB** with coalescing off. There are 1928 B free, but the largest free block is 248 B. Then turn coalescing on and run it again.
2. Run **Swiss cheese**. It allocates 100 B and 40 B blocks in turn, then frees the 100 B blocks. Coalescing cannot help, because live 40 B blocks are between the holes. External fragmentation goes above 50%, and a 200 B request fails.
3. Change **Placement** and click **Churn** for some time. Look where new blocks go. First fit fills the low addresses, next fit moves across the full heap, and worst fit cuts up the largest block.
4. Allocate 1 B. It uses 16 B: an 8 B header and the minimum payload of 8 B. Small objects are expensive on a general free list.

**External fragmentation** is free memory that is split into pieces that are too small to use. The fragmentation number in the demo is $1 - \text{largest free block} / \text{total free}$.

## Block anatomy

<Steps>
<div><b>Header</b>: the block size is a multiple of 8, so the low 3 bits of the size are always zero. The allocator stores the "allocated" flag in one of these bits, at no cost.</div>
<div><b>Splitting</b>: the chosen block can be larger than the request by at least the minimum block size. Then the allocator cuts off the remainder as a new free block. If not, it gives the full block, and the extra bytes become slack.</div>
<div><b>Coalescing forward</b>: the header of the next block is at `block + size`, so it is easy to check.</div>
<div><b>Coalescing backward</b> needs the size of the <i>previous</i> block. Knuth's <b>boundary tags</b> copy the size into a footer at the end of each free block. The footer of the previous block is immediately before your header.</div>
</Steps>

## Placement policies

A **placement policy** is the rule that selects which free block gets the request. The demo walks the list one block at a time. A blue block is in use, and a dashed block is free.

Things to try:

1. Keep the request at 40 B and click **Search** with **First fit**. The search stops at the second block, a 104 B free block. The table shows that first fit walks only 2 blocks.
2. Click **Reset heap**, select **Best fit** and search again. Best fit must walk all 10 blocks to find the smallest block that fits: the 80 B block.
3. Select **Worst fit**. It takes the largest block, 304 B, and splits it. Large free blocks disappear first with this policy.
4. Select **Next fit** and search some times. The **rover** label shows where the next search starts: after the last block that the policy used.
5. Click a blue block to free it. If coalescing is on, it joins its free neighbors into one larger block. Turn coalescing off and compare.

| Policy | Chooses | Typical result |
|---|---|---|
| First fit | the free block with the lowest address that fits | good; small fragments collect near the start |
| Next fit | first fit, but it starts where the last search stopped | puts allocations everywhere: more fragmentation and worse locality |
| Best fit | the smallest block that fits | very good use of memory; it needs a structure sorted by size to be fast |
| Worst fit | the largest block | breaks up large blocks; poor |

The last lesson of this module, Fragmentation, measures these policies on the same workloads.

## Make it fast

A search over a single list is O(number of blocks). Real allocators use these methods:

- **Explicit free lists** link only the free blocks. The pointers go through the payloads of the free blocks. In the demo, best fit for 40 B walks 10 blocks on the implicit list, but only 5 on an explicit list.
- **Segregated free lists** keep one list for each size range. This is almost best fit, at almost O(1) cost. dlmalloc uses small "bins" for exact sizes and trees for large sizes.
- **Deferred coalescing** keeps recently freed blocks separate, so that the program can use them again quickly. The tcache and fastbins of glibc do this, and they coalesce later.
