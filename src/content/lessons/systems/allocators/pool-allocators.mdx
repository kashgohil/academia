Sometimes all objects have the same size: particles, network packets, tree nodes or kernel inodes. Then you do not need a general allocator. A **pool allocator** cuts a buffer into equal **slots** and keeps the free slots on a linked list.

The important idea is this: a free slot holds no data. So **the free slot itself stores the "next" pointer** of the list. A list that is stored inside the items in this way is an **intrusive list**. The result is zero metadata, O(1) allocate and free, and no external fragmentation for that size.

## The intrusive free list

<Steps>
<div>Initialize: slot $i$ holds the address of slot $i+1$. The last slot holds null. The head is slot 0.</div>
<div>Allocate: `p = head; head = *p;`. That is one load and one store.</div>
<div>Free: `*p = head; head = p;`. That is one store and one assignment.</div>
<div>A free slot must hold a pointer, so the minimum slot size is 8 bytes on a 64-bit machine. The alignment of a slot is the largest power of two that divides the slot size.</div>
</Steps>

4. Click **Free one** and **Allocate** many times. The arrows jump across the pool, because the list order follows the order of the frees.
5. Move **Slots**. Every new pool starts with the list in address order.

```rust
struct Pool { buf: Vec<u8>, slot: usize, head: Option<usize> }

impl Pool {
    fn alloc(&mut self) -> Option<usize> {
        let i = self.head?;
        self.head = self.read_next(i); // next index stored in the free slot's bytes
        Some(i)
    }
    fn free(&mut self, i: usize) {
        self.write_next(i, self.head);
        self.head = Some(i);
    }
}
```

## Handles instead of pointers

A pool uses a free slot again immediately. So an old pointer silently points at a *new* object. A safer design is a **generational handle**. Most game engines and ECS libraries use it:

- Each slot keeps a **generation** counter. The counter increases at each free of the slot.
- A handle is the pair `(index, generation)`.
- Before each access, the pool checks that the generation in the handle is equal to the generation of the slot. So the pool finds an old handle and does not give access to the new object.

Handles are also smaller than pointers: two `u32` values, or one. They stay valid when the pool moves to a different address. They are also easy to write to a file or send over a network.

## Free-list corruption

A write after a free, or a double free, changes the next pointer in a free slot. Then the next allocation can return any address that the attacker selects. Attackers often use this method. The tcache of glibc uses **safe-linking** to make this more difficult. It stores `next ^ (slot_address >> 12)`, not the plain pointer.

<SafeLinkingDemo />

Things to try:

1. Select **Nothing**. The stored value looks random, but the decoded value is the real next slot.
2. Select **Target address**. The attacker writes a plain address. It decodes to a different value that is not 16-byte aligned, so glibc stops the program.
3. Look at the number under the table. Over random heap addresses, a plain forged pointer passes the alignment check only about 1 time in 16.
4. Select **Target, encoded with a leak**. If the attacker knows a heap address, the attacker can encode the target correctly, and the attack works. Safe-linking makes an attack more difficult, but it does not make it impossible.

Debug pools add **canaries**: known values next to each slot, which the pool checks for changes. Debug pools also keep freed slots out of use for some time, so that a use after free is easier to find.
