A kernel allocates the same few object types millions of times. Examples are inodes, directory entries, socket buffers and task structures. Jeff Bonwick designed the **slab allocator** for SunOS in 1994. It is the basis of the old Linux SLAB allocator and of SLUB, which Linux uses today.

The slab allocator gives each object type or size its own **cache**. A cache owns **slabs**. A slab is one or more pages, cut into objects of equal size, plus a small descriptor. The descriptor records which objects are free. An allocation takes a free object from a slab that is partly used.

When a slab becomes fully empty, the cache can give its page back to the **page allocator**. The page allocator gives out whole pages. It is usually a buddy allocator.

## Full, partial and empty slabs

A cache sorts its slabs into three lists. A **full** slab has no free object. A **partial** slab has some free objects. An **empty** slab has no live object, so the cache can give its page back.

<SlabListsDemo />

Things to try:

1. Move **Live objects in each cache** from 12 to 40. Each cache fills its partial slabs first. Then it takes new pages.
2. Move the slider down to 20. The demo frees random objects. Now all 22 slabs are partial, and no page goes back. A page goes back only when all of its objects are free.
3. Move the slider to 0. Each slab becomes empty, and each page goes back. Turn on **Keep one empty slab per cache** and do it again. Now one empty slab stays in each cache.
4. Move the slider up and down many times. Compare **allocations** with **constructor calls**. Allocations go up each time. Constructor calls go up only when a cache makes a new slab.

This last effect is **object caching**. Bonwick saw that the construction of an object often costs more than its allocation. Construction means to set up locks, lists and reference counts. The cache constructs all objects of a slab when it makes the slab. Freed objects stay in their constructed state, so the next allocation skips the setup.

## Choose the slab size

Objects seldom fill a slab exactly. The bytes that are left over at the end cannot hold an object.

<SlabFitDemo />

Things to try:

1. At **700 B**, a slab of one page holds 5 objects and leaves 596 B (14.6%). Select **4 pages**: the slab holds 23 objects, and only 1.7% is waste.
2. Set the object size to **192 B**. A page holds 21 objects with 64 B left over. That is 1.6% waste.
3. Look at **cache colors**. The leftover bytes let the cache start the objects of different slabs at different offsets, in steps of 64 B.

Linux SLUB uses a larger slab (a higher page order) when the leftover part of a small slab is too large. A larger slab needs more contiguous pages from the buddy allocator. These can be harder to get when memory is fragmented.

## What a slab allocator adds

- **Exact-fit caches.** A cache for a 192-byte structure wastes no bytes inside each object. Power-of-two rounding would give each object 256 B.
- **Partial slabs first.** The cache fills partial slabs before empty ones. So empty slabs collect, and the cache can give them back.
- **Object caching.** Freed objects keep their constructed state. A new allocation skips the expensive setup.
- **Cache coloring.** Different slabs start their objects at slightly different offsets. So the same field in objects from different slabs does not always go to the same CPU cache set (see Computer Architecture → Caches).
- **Per-CPU caches.** SLUB and magazine designs keep a small stack of free objects for each CPU. The common path then takes no lock.

On Linux, `/proc/slabinfo` and `slabtop` list each cache. They show its object size, the objects per slab and the active objects.
