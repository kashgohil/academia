A library comes in two forms. A **static library** (`libz.a`) is an archive of object files, made with `ar`. The linker copies the members that it needs into the program. A **shared library** (`libz.so`) is a finished ELF file of type `ET_DYN`. The linker only records its name in the program, and the dynamic loader maps it at run time.

The OS lesson [Loading a program](/os/processes/loading-a-program-elf-and-the-dynamic-linker) shows that run-time part. This lesson is about the decisions that the static linker makes.

## Archives and the order of the command line

An archive has an index, the **armap**, that lists the symbols that each member defines. The linker does not copy a whole archive. It extracts a member only if that member defines a symbol that is undefined at that moment.

In this example, `main.o` calls `compress`. In `libz.a`, `deflate.o` defines `compress` and needs `log_msg`. In `liblog.a`, `log.o` defines `log_msg` and needs `crc32`, which is in `libz.a` again.

Things to try:

1. Step through the default order with **GNU ld**. `deflate.o` comes in for `compress`, `log.o` comes in for `log_msg`, and then `crc32` is left undefined.
2. Move `liblog.a` before `libz.a`. Now `log_msg` is left undefined. No order of the two archives works, because each one needs the other.
3. Turn on **Repeat libz.a at the end**, or **--start-group**. Both work. The group repeats its search until a full pass extracts nothing.
4. Switch to **ld.lld** with the first order. It links, but it warns about a backward reference. Move `main.o` to the end and count the warnings: there are two.
5. In every case, `gzip.o` and `level.o` stay out. Nothing refers to them.

### The rules

The GNU ld manual is exact about this. The linker "will search an archive only once, at the location where it is specified on the command line". A symbol that an object needs later "will not cause the linker to search the archive again". Inside one search, the linker repeats until no member of that archive is needed. So members of one archive can depend on each other in any order.

`--start-group a.a b.a --end-group` searches the group "repeatedly until no new undefined references are created". The manual warns that this "has a significant performance cost". The usual alternative is to list a library twice.

ld.lld uses a different rule. It "remembers the symbol table of archives that it has previously seen". A later reference still extracts a member from an earlier archive. Most order mistakes therefore link with ld.lld, then fail with GNU ld on another machine. `--warn-backrefs` prints a warning for each reference that GNU ld would not resolve.

### Members that nothing references

A member that defines no needed symbol never enters the program, even if it has useful side effects. This breaks a common C++ pattern: a file whose only job is a static constructor that registers a plugin. Nothing calls into that file, so the linker drops it, and the plugin never registers. `--whole-archive` forces the linker to take every member of the archives that follow it, until `--no-whole-archive`. A weak reference also does not extract a member. The gABI says: "the link editor does not extract archive members to resolve undefined weak symbols".

## Position-independent code

A shared library can load at any address, and it is mapped read-only and shared between processes. So its code cannot contain absolute addresses or direct references to symbols that another module might define. The compiler has three modes:

- `-fno-pic`: code for a non-PIE executable. It may use absolute addresses and assumes that every symbol is in the program.
- `-fPIE`: code for an executable at any address. It uses `rip`-relative addresses. It assumes that symbols defined in this file stay in the program. Clang reaches an `extern` variable through the GOT. GCC on x86-64 accesses it directly by default (`-mdirect-extern-access`), and the linker may then need a copy relocation.
- `-fPIC`: code for a shared library. A module may replace any default-visibility global symbol at load time, even one from this file. So each one goes through the GOT or the PLT.

A symbol is **preemptible** if a definition in another module can replace it at load time. In an executable, only symbols from shared libraries are preemptible. In a shared library, every default-visibility global symbol is preemptible, because the executable or an `LD_PRELOAD` library may define the same name. The [dynamic loader lesson](/systems/linking/the-dynamic-loader) shows why.

### What the linker does with each reference

| The object file has | The symbol is not preemptible | The symbol is preemptible |
|---|---|---|
| `PC32` (direct data access) | direct access | executable: copy relocation; shared library: error |
| `REX_GOTPCRELX` (GOT load) | relaxed to `lea` | GOT slot with `R_X86_64_GLOB_DAT` |
| `PLT32` (call) | direct call | PLT stub with `R_X86_64_JUMP_SLOT` |

All 18 cells of the demo match real links with clang 22.1.8 and ld.lld 22.1.8. The `-fPIE` row is Clang's: GCC writes `PC32` for the `extern` variable too.

**Copy relocations.** Non-PIC code in an executable reads `counter` at a fixed address, but `counter` is in a shared library. The linker solves this with a trick.

It reserves space for `counter` in the executable's `.bss` and emits `R_X86_64_COPY`. At startup, ld.so copies the initial value from the library into that space. The library itself reaches `counter` through its GOT, and the lookup finds the executable's copy first. Everybody uses one copy, but the size of the variable is now fixed in the executable. If a new version of the library makes the variable larger, the old program breaks.

## Static or dynamic

The OS lesson compares the two at run time. From the build side, these points matter:

- **Link-time optimization** (`-flto`) can inline across object files and archives that the linker sees. It cannot see into a shared library.
- **Unused code.** A static link takes only the archive members that the program needs. A shared library brings all of its exported code, although only touched pages use memory.
- **Start-up.** A static executable has no interpreter, so ld.so does no lookups and no relocations for libraries. The [dynamic loader lesson](/systems/linking/the-dynamic-loader) counts that work.
- **Updates.** A security fix in a static library needs a new link of every program. A shared library fix needs only a new file.
- **glibc and static links.** Some glibc functions, such as name lookup through NSS, load other libraries with `dlopen` at run time. A static glibc program needs those libraries anyway. **musl** has no such dependency. So `x86_64-unknown-linux-musl` in Rust and `-target x86_64-linux-musl` in Zig give static programs by default.
- **Go** links a pure-Go program statically, with its own linker. A program that uses cgo is a dynamic executable that needs libc. Such a program uses the system linker by default (external linking), unless its only cgo packages are `net`, `os/user` and `runtime/cgo`.

## What this means for your code

- Put libraries after the objects that use them, and put a library after every library that uses it. For a cycle, use `--start-group` or list the library twice.
- If a build links with ld.lld but not with GNU ld, run ld.lld with `--warn-backrefs`. It shows each order problem.
- If a registration file disappears from a static build, the linker did not extract it. Use `--whole-archive`, or refer to a symbol in it from `main`.
- Compile code for shared libraries with `-fPIC` and code for executables with `-fPIE`. A `-fno-pic` or `-fPIE` object in a shared library fails with "recompile with -fPIC".
- Do not export variables from a shared library if you can avoid it. Copy relocations make their size part of the ABI. Export functions that return or change the value.
